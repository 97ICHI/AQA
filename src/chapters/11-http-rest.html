HTTP и REST API

Методы, коды ответов, заголовки, тело запроса и ответа, query- и path-параметры, идемпотентность, пагинация и ограничение частоты запросов — всё, что нужно, чтобы читать, составлять и проверять HTTP-запросы.

≈ 12 мин чтенияJ
Опирается на: Веб-архитектура
Основная идея

HTTP-обмен — это текстовое сообщение-запрос и сообщение-ответ. REST — набор соглашений, как через HTTP работать с ресурсами. Зная соглашения, можно заранее сказать, какой ответ правильный, — а значит, написать проверку.

Цель главы: составлять запросы к REST API и по коду, заголовкам и телу ответа определять, корректно ли повёл себя сервер.

Кратко

Запрос = метод + URL + заголовки + тело; ответ = код статуса + заголовки + тело. описывает ресурсы существительными в URL и действия — методами .

Главное

  • GET читает, POST создаёт, PUT заменяет целиком, PATCH изменяет частично, DELETE удаляет.
  • Идемпотентный метод даёт тот же эффект при повторе, но не обязательно тот же статус: GET, PUT, DELETE, HEAD, OPTIONS. POST и PATCH — в общем случае нет.
  • 2xx — успех, 3xx — перенаправление, 4xx — ошибка клиента, 5xx — ошибка сервера. 500 в ответ на неверные данные — дефект.
  • Path-параметр определяет ресурс (/orders/42), query-параметры — фильтрацию, сортировку, страницу (?status=paid&page=2).
  • Content-Type описывает формат тела запроса/ответа, Accept — какой формат клиент ожидает, Authorization — учётные данные.
  • Пагинация: offset/limit или курсор; проверяют границы, пустую страницу и стабильность порядка. Превышение лимита запросов — 429 и Retry-After.

Термины

HTTP
Протокол «запрос–ответ» без хранения состояния: метод, URL, заголовки и тело запроса; код статуса, заголовки и тело ответа.
HTTP Method
Намерение запроса: GET — получить, POST — создать, PUT — заменить, PATCH — изменить часть, DELETE — удалить, а также HEAD и OPTIONS.
Status Code
Трёхзначный код результата: 2xx — успех, 3xx — перенаправление, 4xx — ошибка клиента, 5xx — ошибка сервера.
Query Parameter
Пара «ключ=значение» после ? в URL: фильтры, сортировка, поиск, пагинация.
Path Parameter
Часть пути URL, идентифицирующая ресурс: /orders/{id}.

Важно: Не проверяйте только код 200: тело, заголовки и побочные эффекты (что изменилось в системе) не менее важны.

Анатомия HTTP-обмена#

— текстовый протокол. Запрос на создание заказа выглядит так:

HTTP
POST /api/orders?notify=true HTTP/1.1
Host: shop.example.com
Content-Type: application/json
Accept: application/json
Authorization: Bearer eyJhbGciOi…

{"productId": 7, "qty": 2}
  • Стартовая строка: метод (POST), путь с query-параметрами, версия протокола.
  • Заголовки: пары Имя: значение с метаданными.
  • Пустая строка, затем тело — данные (здесь ).

Ответ:

HTTP
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/orders/1042
X-Request-Id: 5b2c9e1a

{"id": 1042, "status": "created", "total": 9980}
  • Строка статуса: версия, и текстовое пояснение.
  • Заголовки, пустая строка, тело.

HTTP/2 и HTTP/3 передают те же смысловые части в бинарном виде, но для тестов модель «метод, URL, заголовки, тело → статус, заголовки, тело» не меняется.

Методы HTTP#

выражает намерение запроса:

Метод Назначение Тело запроса Безопасный Идемпотентный
GET Получить ресурс или список Нет Да Да
POST Создать ресурс, выполнить действие Да Нет Нет
PUT Заменить ресурс целиком Да Нет Да
PATCH Изменить часть ресурса Да Нет Не гарантируется
DELETE Удалить ресурс Обычно нет Нет Да
HEAD Как GET, но без тела (только заголовки) Нет Да Да
OPTIONS Узнать допустимые методы (используется в CORS) Нет Да Да

Безопасный метод не предполагает, что клиент просит изменить состояние ресурса (журнал запросов на сервере при этом может вестись). Идемпотентный — несколько одинаковых запросов дают тот же предполагаемый эффект, что и один; коды ответов при этом могут отличаться. Подробнее — в разделе «Распространённые заблуждения о » ниже.

400 или 422?

Разные API используют их по-разному: одни возвращают 400 на любую ошибку валидации, другие разделяют синтаксические (400) и смысловые (422) ошибки. Правильный ответ для теста — тот, что описан в спецификации API (). Неправильно в любом случае — 500 и 200 с текстом ошибки в теле.

Заголовки#

— метаданные запроса и ответа. Самые важные для тестов:

Заголовок Где Что проверять или задавать
Content-Type Запрос и ответ Формат тела: application/json; charset=utf-8
Accept Запрос Какой формат ответа клиент примет
Authorization Запрос Bearer <token>, Basic …
Cookie / Set-Cookie Запрос / ответ Сессия, атрибуты
Location Ответ Адрес созданного ресурса (201) или редиректа (3xx)
Cache-Control, ETag Ответ Политика кэширования, версия ресурса
Retry-After Ответ Через сколько повторить (429, 503)
X-Request-Id / traceparent Оба Сквозной идентификатор для поиска в логах сервера

Имена заголовков нечувствительны к регистру. в response.headers() возвращает их в нижнем регистре: headers()['content-type'].

Тело запроса и ответа#

Чаще всего тело — . Другие форматы: application/x-www-form-urlencoded (HTML-формы), multipart/form-data (загрузка файлов), text/plain, бинарные файлы.

Что проверять в теле ответа:

  • структуру — нужные поля, типы, отсутствие лишних чувствительных полей (хеш пароля!) — схемой (глава 21);
  • значения — бизнес-результат: статус, сумма, связанные id;
  • согласованность — total равен сумме позиций, id совпадает с Location;
  • формат ошибок — единая структура { code, message, details } для всех ошибок.

Query и Path параметры#

  • — часть пути, идентифицирующая ресурс: /users/17/orders/1042.
  • — пары после ?, уточняющие запрос: фильтр, сортировка, страница, поиск: /orders?status=paid&sort=-createdAt&limit=20.

Значения кодируются: пробел — %20 или +, кириллица — UTF-8 байты в процентной записи. В передавайте параметры объектом — он закодирует их сам:

TypeScripttests/orders-filter.spec.ts
import { test, expect } from '@playwright/test';

test('фильтр заказов по статусу', async ({ request }) => {
  const res = await request.get('/api/orders', {
    params: { status: 'paid', sort: '-createdAt', limit: 20, q: 'наушники' },
  });
  expect(res.status()).toBe(200);
  const body = (await res.json()) as { items: { status: string }[] };
  expect(body.items.every((o) => o.status === 'paid')).toBe(true);
});

Негативные случаи для параметров: неизвестный параметр, неверный тип (limit=abc), граничные значения (limit=0, limit=1000), инъекции в строке поиска, несуществующий id в пути (404), id чужого пользователя (403/404).

REST#

— архитектурный стиль, а не стандарт. Основные соглашения:

  • Ресурсы — существительные во множественном числе: /orders, /orders/42, /orders/42/items.
  • Действие выражается методом: DELETE /orders/42, а не POST /deleteOrder?id=42.
  • Stateless: каждый запрос содержит всё нужное (токен, параметры), сервер не хранит контекст между запросами.
  • Единообразные коды и форматы: одинаковая структура ошибок, пагинации, дат.
Задача REST-запрос Ожидаемый ответ
Список заказов GET /orders 200 + массив
Один заказ GET /orders/42 200 или 404
Создать заказ POST /orders 201 + Location
Заменить адрес доставки целиком PUT /orders/42/address 200 / 204
Изменить статус PATCH /orders/42 с {"status":"cancelled"} 200 или 409
Удалить DELETE /orders/42 204, повторно — 404 или 204

Идемпотентность#

— свойство операции давать одинаковый результат на сервере при повторах. Это важно для надёжности: клиент, не дождавшийся ответа из-за сбоя сети, может безопасно повторить идемпотентный запрос.

  • PUT /users/17 с одним и тем же телом сто раз → пользователь в одном и том же состоянии.
  • DELETE /orders/42 дважды → заказ удалён; второй ответ может быть 404, но состояние сервера то же.
  • POST /payments дважды → два платежа, если API не защищён. Поэтому платёжные API принимают заголовок Idempotency-Key: повтор с тем же ключом возвращает результат первого запроса.

Тесты идемпотентности: повторить запрос и проверить, что состояние не изменилось (количество записей, сумма, статус), а для POST с Idempotency-Key — что не создан дубликат.

Интерактив требует JavaScriptHTTP Inspector: составьте запрос (метод, путь, заголовки, тело) к учебному API магазина и посмотрите сырой HTTP-ответ, код и пояснение — в том числе для повторных и неавторизованных запросов.

Распространённые заблуждения о HTTP#

GET запрашивает представление ресурса, POST просит обработать переданное содержимое; создание ресурса — частый, но не единственный результат POST. PUT создаёт или заменяет состояние целевого ресурса согласно контракту. PATCH описывает частичное изменение.

Safe относится к запрошенной семантике: клиент не просит менять состояние. Логирование запроса не делает GET небезопасным. Idempotent означает одинаковый предполагаемый эффект повторов; статусы ответов могут различаться. POST можно сделать идемпотентным на уровне конкретного API, например с Idempotency-Key.

Нередко GET и POST сравнивают по числу TCP-пакетов и разрыву соединения. Это неверно: пакетизация и переиспользование соединения не определяются только HTTP-методом. HTTPS защищает транспорт, но не исправляет авторизацию и бизнес-логику.

— архитектурный стиль; SOAP — протокол сообщений. Stateless не запрещает хранение ресурсов в БД: запрос должен нести необходимый контекст взаимодействия. SOAP не означает обязательную stateful-сессию.

Первоисточник: RFC 9110, HTTP Semantics (нужен интернет).

Пагинация#

разбивает большие списки на страницы:

  • Offset/limit (?offset=40&limit=20 или ?page=3&size=20) — простой, позволяет перейти на любую страницу, но при вставке записей между запросами элементы могут «съехать»: дубли или пропуски.
  • Cursor (?cursor=eyJpZCI6…&limit=20, ответ содержит nextCursor) — стабилен при изменениях данных, но нельзя прыгнуть на произвольную страницу.

Что проверять: размер страницы не превышает limit; последняя страница неполная или пустая; total соответствует данным; нет дублей и пропусков при обходе всех страниц; стабильный порядок при одинаковых значениях сортировки; некорректные параметры (page=0, limit=-1, огромный limit).

Rate Limiting#

ограничивает число запросов от клиента за интервал времени — защита от перегрузки и злоупотреблений. При превышении сервер возвращает 429 Too Many Requests, часто с Retry-After и заголовками вида X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset (или RateLimit-*).

В автотестах Rate Limiting проявляется двояко:

  • как объект проверки: после N запросов — 429, после ожидания — снова 200;
  • как помеха: параллельный прогон сотен API-тестов от одного пользователя упирается в лимит и получает «случайные» 429. Решения — отдельные лимиты для тестового окружения, разные тестовые пользователи, ограничение параллелизма.

Пример: проверка создания ресурса#

TypeScripttests/create-order.spec.ts
import { test, expect } from '@playwright/test';

test('POST /api/orders создаёт заказ', async ({ request }) => {
  const res = await request.post('/api/orders', {
    data: { productId: 7, qty: 2 },
    headers: { 'Idempotency-Key': `test-${Date.now()}` },
  });

  // 1. статус и заголовки
  expect(res.status()).toBe(201);
  expect(res.headers()['content-type']).toContain('application/json');
  const location = res.headers()['location'];
  expect(location).toMatch(/^\/api\/orders\/\d+$/);

  // 2. тело
  const order = (await res.json()) as { id: number; status: string; total: number };
  expect(order).toMatchObject({ status: 'created', total: 9980 });
  expect(location).toBe(`/api/orders/${order.id}`);

  // 3. побочный эффект: заказ действительно доступен
  const check = await request.get(location);
  expect(check.status()).toBe(200);
});

Тот же запрос в : метод и URL, вкладка Body → raw → , переменные окружения для {{baseUrl}} и {{token}}, проверки во вкладке Tests (pm.response.to.have.status(201)). Коллекции Postman запускаются из CLI через Newman — так их можно встроить в CI, но для поддерживаемого набора в репозитории удобнее тесты в коде.

Типичные ошибки#

Проверять только статус

expect(res.status()).toBe(200) пройдёт, даже если в теле {"error":"something went wrong"} или пустой массив. Проверяйте тело и побочные эффекты.

Принимать 500 как «ожидаемую ошибку»

Если невалидные данные приводят к 500, сервер не обработал ошибку ввода — это дефект, даже если «ну, ошибка же».

Собирать URL конкатенацией строк

'/api/search?q=' + text сломается на пробелах, &, # и кириллице. Передавайте параметры объектом params или используйте URLSearchParams.

Забыть про идемпотентность в ретраях

Если тестовый клиент автоматически повторяет неудачный POST, при сетевом сбое можно создать дубликаты данных и получить загадочные падения.

Что важно для собеседования#

JuniorЧем PUT отличается от PATCH и POST?

Ответ

POST создаёт ресурс или выполняет действие; повтор создаст ещё один. PUT заменяет ресурс целиком переданным представлением и идемпотентен. PATCH изменяет часть полей; идемпотентность не гарантируется (например, {"op":"increment"}). В тестах PUT проверяю на «отсутствующие поля сброшены», PATCH — на «остальные поля не изменились».

JuniorНазовите группы кодов ответов и примеры. Когда 500 — дефект?

Ответ

1xx — информационные, 2xx — успех (200, 201, 204), 3xx — перенаправления (301, 302, 304), 4xx — ошибки клиента (400, 401, 403, 404, 409, 422, 429), 5xx — ошибки сервера (500, 502, 503, 504). 500 в ответ на данные клиента — всегда дефект: сервер должен валидировать ввод и возвращать 4xx с понятным сообщением.

MiddleЧто такое идемпотентность и как её протестировать?

Ответ

Повтор запроса не меняет состояние сервера после первого выполнения. GET, PUT, DELETE идемпотентны, POST — нет. Тест: выполнить запрос дважды и проверить состояние (число записей, сумму, статус). Для POST с Idempotency-Key — повтор с тем же ключом возвращает тот же результат и не создаёт дубликат, а с другим ключом — создаёт новую сущность.

MiddleКак протестировать пагинацию?

Ответ

Создаю свой изолированный набор данных, затем: размер страницы ≤ limit, корректный total, последняя страница неполная, страница за пределами — пустая (или ошибка по спецификации), при полном обходе нет дублей и пропусков, порядок стабилен при равных значениях сортировки, граничные и некорректные параметры (0, отрицательные, слишком большой limit, нечисловые). Для курсорной пагинации — невалидный и устаревший курсор.

Middle+API-тесты в CI стали получать случайные 429. Как решать?

Ответ

Это от параллельного прогона. Варианты: отдельная политика лимитов для тестового окружения или тестовых клиентов, распределение тестов между несколькими тестовыми пользователями/ключами (лимит часто по пользователю), ограничение числа воркеров для API-проекта, обработка Retry-After в тестовом клиенте только для подготовки данных (не для проверяемого запроса). Отдельно оставляю тест, который проверяет сам лимит: 429 и восстановление после окна.

Проверьте себя#

Тест
1
Какой метод идемпотентен?

PUT заменяет ресурс целиком: повтор с тем же телом оставляет ресурс в том же состоянии. POST создаёт новый ресурс при каждом вызове.

2
Сервер вернул 200 OK с телом {"success": false, "error": "invalid email"}. Что не так?

Ошибка валидации — ошибка клиента, ей соответствует 400 или 422. Клиенты и мониторинг ориентируются на код ответа.

3
Где передать номер страницы списка заказов?

Пагинация уточняет запрос к коллекции, поэтому её параметры передают в query.

Почему повторный DELETE /orders/42 может вернуть 404 и всё равно считаться идемпотентным?

Идемпотентность относится к состоянию сервера, а не к коду ответа. После первого удаления заказа нет; после второго — тоже нет. Состояние то же, поэтому операция идемпотентна, хотя ответы различаются (204, затем 404).

Как протестировать пагинацию на offset/limit, если данные постоянно меняются другими тестами?

Изолировать данные: создать свой набор записей с уникальной меткой и фильтровать по ней, чтобы чужие записи не влияли. Затем обойти все страницы и проверить отсутствие дублей и пропусков, total, размер последней страницы, порядок сортировки и поведение на граничных параметрах.
