SQL и базы данных

SELECT, WHERE, JOIN, GROUP BY, HAVING, подзапросы, NULL, ограничения, транзакции и ACID на PostgreSQL — с упором на то, что AQA делает с базой каждый день: готовит тестовые данные и проверяет результат действий.

≈ 16 мин чтенияJ–M
Основная идея

База данных — главный свидетель того, что система действительно сделала то, о чём сообщил интерфейс. SQL позволяет быстро подготовить нужное состояние и проверить побочные эффекты, которые не видны в UI и API.

Цель главы: писать запросы для поиска, подготовки и проверки тестовых данных, понимать NULL, JOIN, агрегаты и транзакции и не ломать данные других тестов.

Кратко

в автотестах решает три задачи: найти или подготовить данные, проверить результат действия и убрать за собой — безопасно и параметризованно.

Главное

  • Логический порядок SELECT: FROM/JOIN → WHERE (фильтр строк до группировки) → → HAVING (фильтр групп) → SELECT → ORDER BY → LIMIT.
  • INNER оставляет только совпадения; LEFT JOIN сохраняет все строки левой таблицы, недостающие поля — . LEFT JOIN … WHERE b.id IS NULL находит «сирот».
  • NULL — «неизвестно»: = NULL никогда не истинно, нужен IS NULL; COUNT(col) не считает NULL; NOT IN со списком, где есть NULL, не вернёт строк.
  • Ограничения (PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, CHECK) — бесплатные проверки целостности; их нарушение — ожидаемая ошибка в негативных тестах.
  • Транзакция: всё или ничего. — атомарность, согласованность, изолированность, долговечность.
  • В коде тестов — только параметризованные запросы ($1, $2), никакой конкатенации строк.

Термины

Primary Key
Столбец или набор столбцов, однозначно идентифицирующий строку таблицы: уникален и не может быть NULL.
Foreign Key
Столбец, ссылающийся на первичный ключ другой таблицы. База не даёт сослаться на несуществующую строку или удалить строку, на которую есть ссылки.
JOIN
Объединение строк нескольких таблиц по условию. INNER JOIN оставляет совпадения, LEFT JOIN — все строки левой таблицы.
NULL
Маркер неизвестного или отсутствующего значения в SQL. Сравнение с NULL даёт NULL; проверять нужно через IS NULL.
GROUP BY
Объединение строк в группы для подсчёта агрегатов (COUNT, SUM, AVG, MIN, MAX). HAVING фильтрует группы после агрегации.

Важно: Прямая запись в базу в обход приложения может создать состояние, которое приложение никогда бы не создало. Готовьте данные через API, когда это возможно, а SQL используйте для проверок и того, что через API недоступно.

Зачем AQA SQL#

Автотестировщик работает с базой данных в четырёх ситуациях:

  1. Найти тестовые данные: «пользователь с подтверждённой почтой и без заказов».
  2. Подготовить состояние: создать заказ в статусе shipped, до которого через UI идти десять шагов.
  3. Проверить побочный эффект: после оплаты в таблице payments появилась запись с правильной суммой, а остаток товара уменьшился.
  4. Убрать за собой данные, созданные тестом.

Примеры главы используют учебную базу интернет-магазина и проверены в PostgreSQL 16. Те же таблицы доступны в Playground ниже.

SQL
-- Структура учебной базы (сокращённо)
SELECT table_name, column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'orders'
ORDER BY ordinal_position;
Таблица Поля Связи
customers id, email (UNIQUE), name, city (может быть ), is_vip, registered_at —
products id, title, category, price, stock (CHECK ≥ 0) —
orders id, customer_id, status (CHECK из списка), created_at, promo_code customer_id → customers.id
order_items order_id, product_id, qty (CHECK > 0), price → orders.id, → products.id; PK (order_id, product_id)

Таблицы связаны ключами: однозначно идентифицирует строку, ссылается на строку другой таблицы.

SELECT и WHERE#

SQL
-- Товары дороже 3000 ₽ в наличии, сначала дорогие
SELECT id, title, price, stock
FROM products
WHERE price > 3000 AND stock > 0
ORDER BY price DESC
LIMIT 5;

Полезные условия:

SQL
SELECT id, email, city
FROM customers
WHERE city IN ('Москва', 'Казань')          -- одно из значений
  AND registered_at BETWEEN '2025-01-01' AND '2025-06-30'  -- диапазон включительно
  AND email LIKE '%@example.com';           -- шаблон: % — любые символы, _ — один символ

ILIKE — регистронезависимый вариант LIKE (расширение PostgreSQL). DISTINCT убирает дубликаты строк результата.

Порядок выполнения запроса

Запрос пишется в порядке SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT, а выполняется логически так: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Поэтому в WHERE нельзя использовать псевдоним из SELECT и агрегатные функции, а в ORDER BY — можно.

NULL#

означает «значение неизвестно или отсутствует». Это не ноль и не пустая строка. Любое сравнение с NULL даёт NULL (неизвестно), а WHERE оставляет только строки, где условие истинно.

SQL
-- Ошибка: не вернёт ни одной строки, даже для Веры без города
SELECT name FROM customers WHERE city = NULL;
SQL
-- Правильно
SELECT name FROM customers WHERE city IS NULL;
SQL
-- NULL «выпадает» из обоих условий: Вера не попадёт ни туда, ни туда
SELECT
  (SELECT COUNT(*) FROM customers WHERE city = 'Москва')   AS moscow,
  (SELECT COUNT(*) FROM customers WHERE city <> 'Москва')  AS not_moscow,
  (SELECT COUNT(*) FROM customers)                         AS total;
-- moscow = 2, not_moscow = 3, total = 6

Важные следствия:

  • COUNT(*) считает строки, COUNT(city) — только не-NULL значения.
  • COALESCE(city, 'не указан') подставляет значение вместо NULL.
  • Агрегаты SUM, AVG, MIN, MAX игнорируют NULL.
  • Ловушка NOT IN: если в списке или подзапросе есть NULL, x NOT IN (…) не бывает истинным, и запрос вернёт пустой результат. Безопаснее NOT EXISTS.
SQL
-- Пустой результат: в подзапросе есть NULL (у Веры нет города)
SELECT name FROM customers WHERE city NOT IN (SELECT city FROM customers WHERE is_vip = FALSE);

JOIN#

соединяет строки нескольких таблиц по условию.

SQL
-- INNER JOIN: заказы с именами клиентов (только совпадения)
SELECT o.id, c.name, o.status, o.created_at
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
ORDER BY o.id;
SQL
-- LEFT JOIN: все клиенты и число их заказов, включая клиентов без заказов
SELECT c.name, COUNT(o.id) AS orders_count
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY orders_count DESC, c.name;
SQL
-- «Сироты»: товары, которые ни разу не заказывали
SELECT p.id, p.title
FROM products AS p
LEFT JOIN order_items AS oi ON oi.product_id = p.id
WHERE oi.product_id IS NULL;
Вид Что остаётся
INNER JOIN Только пары строк, где условие выполнено
LEFT JOIN Все строки левой таблицы; поля правой — , если пары нет
RIGHT JOIN Зеркально LEFT; на практике переписывают как LEFT
FULL JOIN Все строки обеих таблиц
CROSS JOIN Все комбинации (декартово произведение)
Размножение строк

Если соединить заказ с позициями (order_items), заказ с тремя позициями даст три строки. SUM по полю заказа после такого JOIN посчитает его трижды. Агрегируйте на правильном уровне: сначала суммы по позициям, затем соединяйте.

GROUP BY и HAVING#

собирает строки в группы, а агрегатные функции (COUNT, SUM, AVG, MIN, MAX) считают по каждой группе.

SQL
-- Сумма каждого заказа по позициям
SELECT order_id, SUM(qty * price) AS total, COUNT(*) AS positions
FROM order_items
GROUP BY order_id
ORDER BY order_id;
SQL
-- Клиенты, потратившие больше 15 000 ₽ на неотменённые заказы
SELECT c.name, SUM(oi.qty * oi.price) AS spent
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
JOIN order_items AS oi ON oi.order_id = o.id
WHERE o.status <> 'cancelled'          -- фильтр строк ДО группировки
GROUP BY c.id, c.name
HAVING SUM(oi.qty * oi.price) > 15000  -- фильтр групп ПОСЛЕ агрегации
ORDER BY spent DESC;

Правило PostgreSQL: каждое поле в SELECT должно быть либо в GROUP BY, либо внутри агрегатной функции (исключение — поля таблицы, если в GROUP BY указан её первичный ключ).

Подзапросы#

— запрос внутри запроса.

SQL
-- Скалярный подзапрос: товары дороже средней цены
SELECT title, price
FROM products
WHERE price > (SELECT AVG(price) FROM products)
ORDER BY price;
SQL
-- EXISTS: клиенты, у которых есть хотя бы один оплаченный заказ
SELECT c.name
FROM customers AS c
WHERE EXISTS (
  SELECT 1 FROM orders AS o
  WHERE o.customer_id = c.id AND o.status = 'paid'
)
ORDER BY c.name;
SQL
-- NOT EXISTS: клиенты без заказов (безопасно при NULL)
SELECT c.name
FROM customers AS c
WHERE NOT EXISTS (SELECT 1 FROM orders AS o WHERE o.customer_id = c.id);

Для сложных запросов удобны CTE — именованные подзапросы WITH:

SQL
WITH order_totals AS (
  SELECT order_id, SUM(qty * price) AS total
  FROM order_items
  GROUP BY order_id
)
SELECT o.id, o.status, t.total
FROM orders AS o
JOIN order_totals AS t ON t.order_id = o.id
WHERE t.total > 10000
ORDER BY t.total DESC;
Интерактив требует JavaScriptSQL Playground: выполняйте SELECT, JOIN, GROUP BY, подзапросы, INSERT/UPDATE/DELETE и транзакции на учебной базе магазина; база восстанавливается кнопкой «Сбросить».

Изменение данных#

SQL
-- Создать тестового клиента и сразу получить его id (RETURNING — расширение PostgreSQL)
INSERT INTO customers (id, email, name, city, registered_at)
VALUES (1001, 'qa+1001@example.com', 'QA Тест', 'Москва', CURRENT_DATE)
RETURNING id, email;
SQL
-- Перевести заказ в нужный статус для теста
UPDATE orders SET status = 'shipped' WHERE id = 102 RETURNING id, status;
SQL
-- Удалить данные теста: сначала дочерние строки, потом родительские
DELETE FROM order_items WHERE order_id = 109;
DELETE FROM orders WHERE id = 109;
UPDATE или DELETE без WHERE

Изменит или удалит все строки таблицы. Перед выполнением изменения на общем стенде выполните тот же WHERE в SELECT и проверьте число строк.

Ограничения#

— правило, которое база проверяет при каждом изменении. Нарушение — ошибка, и операция не выполняется.

Ограничение Пример Что ловит
PRIMARY KEY id Дубликат идентификатора
UNIQUE customers.email Повторная регистрация с тем же email
NOT NULL customers.name Отсутствующее обязательное поле
FOREIGN KEY orders.customer_id Заказ несуществующего клиента; удаление клиента с заказами
CHECK stock >= 0 Отрицательный остаток
SQL
-- Нарушение UNIQUE: такой email уже есть
INSERT INTO customers (id, email, name, registered_at)
VALUES (2001, 'anna@example.com', 'Дубль', CURRENT_DATE);
-- ERROR: duplicate key value violates unique constraint "customers_email_key"
SQL
-- Нарушение FOREIGN KEY: у клиента 1 есть заказы
DELETE FROM customers WHERE id = 1;
-- ERROR: update or delete on table "customers" violates foreign key constraint

Для тестировщика ограничения полезны дважды: они объясняют, в каком порядке создавать и удалять данные, и подсказывают негативные сценарии API (дубликат email должен дать 409, а не 500 с текстом ошибки базы).

Транзакции и ACID#

объединяет несколько операций в одну: либо выполнены все, либо ни одна.

SQL
BEGIN;
UPDATE products SET stock = stock - 1 WHERE id = 1;
INSERT INTO orders (id, customer_id, status, created_at) VALUES (110, 2, 'created', CURRENT_DATE);
INSERT INTO order_items (order_id, product_id, qty, price) VALUES (110, 1, 1, 4990);
COMMIT;   -- зафиксировать; ROLLBACK — отменить всё
SQL
BEGIN;
DELETE FROM order_items WHERE order_id = 101;
SELECT COUNT(*) FROM order_items WHERE order_id = 101;  -- 0 внутри транзакции
ROLLBACK;
SELECT COUNT(*) FROM order_items WHERE order_id = 101;  -- снова 2

— гарантии транзакций:

  • Atomicity (атомарность) — всё или ничего.
  • Consistency (согласованность) — после транзакции соблюдены все ограничения.
  • Isolation (изолированность) — параллельные транзакции не видят незафиксированных изменений друг друга (в PostgreSQL по умолчанию уровень Read Committed).
  • Durability (долговечность) — зафиксированные данные переживут сбой.
Откат транзакции как способ изоляции тестов

В интеграционных тестах сервиса можно открыть транзакцию перед тестом и откатить после — база остаётся чистой. Но это работает, только если тест и приложение используют одно и то же соединение. Для E2E-тестов через UI или API приложение пишет в базу своими соединениями, и откат в тесте ничего не отменит — нужна явная очистка (глава «Test Isolation»).

SQL в коде автотестов#

В Node.js к PostgreSQL подключаются библиотекой pg (node-postgres). Главное правило — Injection-безопасные параметризованные запросы: значения передаются отдельно от текста запроса.

TypeScriptsrc/db/db.ts
import { Pool } from 'pg';

export const pool = new Pool({ connectionString: process.env.DB_URL, max: 4 });

export interface OrderRow { id: number; status: string; total: number }

export async function orderWithTotal(orderId: number): Promise<OrderRow | undefined> {
  const { rows } = await pool.query<OrderRow>(
    `SELECT o.id, o.status, SUM(oi.qty * oi.price)::int AS total
       FROM orders o JOIN order_items oi ON oi.order_id = o.id
      WHERE o.id = $1
      GROUP BY o.id`,
    [orderId],  // значение передаётся отдельно — инъекция невозможна
  );
  return rows[0];
}
TypeScripttests/order-db.spec.ts
import { test, expect } from '@playwright/test';
import { orderWithTotal, pool } from '../src/db/db';

test.afterAll(async () => { await pool.end(); });

test('оплата переводит заказ в статус paid', async ({ request }) => {
  const res = await request.post('/api/orders/105/pay', { data: { card: '4242424242424242' } });
  expect(res.status()).toBe(200);

  // Проверка побочного эффекта в базе, а не только ответа API
  await expect.poll(async () => (await orderWithTotal(105))?.status).toBe('paid');
});

expect.poll повторяет запрос к базе, пока значение не станет ожидаемым: если приложение обновляет статус асинхронно (через очередь), однократная проверка была бы гонкой.

Диагностика данных и оконные функции#

Сначала убедитесь, что запись относится к вашему . Проверка через БД полезна для диагностики и определённых integration-тестов, но привязывает тест к внутренней схеме. Реплика может отставать; отсутствие строки сразу после API-запроса не всегда дефект.

PostgreSQL · фрагмент
-- Предполагается таблица orders(id, customer_id, total, created_at, test_run_id).
SELECT id, customer_id, total,
       ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC, id DESC) AS rn
FROM orders
WHERE test_run_id = 'run-123';

ROW_NUMBER нумерует строки внутри каждой группы, не схлопывая их как . Второй ключ сортировки делает порядок определённым при одинаковом времени. Оконные функции этого примера не заявлены как поддерживаемые встроенным Playground.

Cleanup ограничивайте test_run_id и принадлежащими тесту IDs. DELETE удаляет строки, DROP — объект схемы. проверяется IS NULL; по неуникальным ключам может умножить строки. Транзакционный rollback не очистит записи, созданные другим соединением сервиса.

предотвращают параметризованные запросы: строка пользовательского ввода не должна становиться SQL-синтаксисом. Проверка инъекций проводится на специально выделенном тестовом приложении.

Пример: SQL для подготовки и проверки#

Задача: проверить, что отмена оплаченного заказа возвращает товар на склад.

SQL
-- 1. Найти подходящие данные: оплаченный заказ с товаром, у которого есть остаток
SELECT o.id AS order_id, oi.product_id, oi.qty, p.stock
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE o.status = 'paid'
ORDER BY o.id
LIMIT 1;
SQL
-- 2. Запомнить остаток до действия (в тесте — переменная)
SELECT stock FROM products WHERE id = 5;

Затем тест выполняет отмену через API, а после — проверяет и ответ, и базу:

SQL
-- 3. После отмены: статус и остаток (ожидание: cancelled, stock + qty)
SELECT o.status, p.stock
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE o.id = 102;

Ещё лучше не искать существующие данные, а создать свой заказ через API в начале теста: тогда тест не зависит от того, что другие тесты сделали с заказом 102.

Типичные ошибки#

= NULL вместо IS NULL

Сравнение с никогда не истинно; запрос «молча» возвращает пустой результат.

Конкатенация значений в SQL

`SELECT * FROM users WHERE email = '${email}'` — уязвимость и источник падений на кавычках в данных. Только параметры $1.

Опора на «чужие» данные стенда

Тест, который берёт «первого VIP-клиента», сломается, когда кто-то изменит данные. Создавайте свои данные или фильтруйте по меткам своего теста.

Проверка только через базу

Если тест проверяет только таблицу, он не заметит, что API вернул ошибку или UI показал неверное сообщение. База — дополнительный свидетель, а не замена проверок интерфейса и API.

Что важно для собеседования#

JuniorЧем INNER JOIN отличается от LEFT JOIN? Как найти записи без связанных строк?

Ответ

INNER оставляет только строки, у которых нашлась пара по условию. LEFT JOIN сохраняет все строки левой таблицы, а поля правой заполняет , если пары нет. Записи без связанных строк — LEFT JOIN … WHERE right.id IS NULL или NOT EXISTS (…).

JuniorЧем WHERE отличается от HAVING?

Ответ

WHERE фильтрует строки до группировки и не может использовать агрегатные функции; HAVING фильтрует группы после и работает с агрегатами. Логический порядок: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

JuniorКакие ловушки связаны с NULL?

Ответ

= NULL никогда не истинно — нужен IS NULL; NULL не попадает ни под city = 'X', ни под city <> 'X'; COUNT(col) не считает NULL; агрегаты игнорируют NULL; NOT IN со списком, содержащим NULL, возвращает пустой результат — безопаснее NOT EXISTS.

JuniorПочему запрос WHERE city <> 'Москва' не вернул пользователей без города?

Ответ

Сравнение с NULL даёт не true и не false, а NULL (неизвестно), и WHERE отбрасывает такие строки. Чтобы включить пользователей без города: WHERE city <> 'Москва' OR city IS NULL, или WHERE city IS DISTINCT FROM 'Москва'. Та же ловушка — NOT IN с подзапросом, который возвращает NULL: такой запрос вернёт ноль строк.

Пример

SELECT name FROM customers WHERE city IS DISTINCT FROM 'Москва';

MiddleЧто такое транзакция и ACID? Можно ли изолировать тесты откатом транзакции?

Ответ

Транзакция — группа операций «всё или ничего». : атомарность, согласованность (ограничения соблюдены), изолированность (параллельные транзакции не видят незафиксированное), долговечность. Откат подходит для интеграционных тестов, где тест и код используют одно соединение. В E2E приложение фиксирует изменения своими соединениями, поэтому нужна явная очистка или изолированные данные.

MiddleКак вы используете базу данных в автотестах и какие правила соблюдаете?

Ответ

Для поиска и подготовки данных, которые недоступны через API, и для проверки побочных эффектов (статус, остаток, запись платежа). Правила: только параметризованные запросы; отдельная учётная запись с минимальными правами; готовить данные предпочтительно через API, чтобы не создавать нереалистичное состояние; асинхронные изменения проверять с повтором (expect.poll); очищать созданные данные; не полагаться на чужие данные стенда.

MiddleКогда в автотесте уместно проверять результат запросом к базе, а когда это плохая идея?

Ответ

Уместно: для эффектов, которые не видны через API (запись в аудит, отложенная задача, поле, которое API не отдаёт), для проверки целостности после сложной операции и для подготовки данных, которые нельзя создать через API. Плохая идея: заменять проверку контракта API проверкой таблиц — тест привязывается к схеме БД, ломается при рефакторинге хранения и не проверяет, что увидит клиент. Доступ к БД в тестах — только чтение или изолированные данные, с параметризованными запросами.

MiddleМожно ли изолировать тесты, оборачивая каждый в транзакцию с ROLLBACK?

Ответ

Только если тест и приложение работают через одно соединение с базой — как в интеграционных тестах внутри процесса приложения. В API- и UI-тестах приложение использует свои соединения: изменения, сделанные им, не попадут в транзакцию теста, а данные, созданные тестом внутри незафиксированной транзакции, приложение не увидит. Для таких тестов — свои данные с меткой и очистка в teardown.

Тест
1
Чем отличаются WHERE и HAVING?

WHERE применяется к отдельным строкам до GROUP BY, поэтому в нём нельзя использовать агрегаты. HAVING фильтрует уже сформированные группы.

2
Как найти клиентов без заказов?

LEFT JOIN сохраняет клиентов без пары, у них поля заказа — NULL. INNER JOIN таких клиентов отбрасывает, а = NULL никогда не истинно.

3
Что вернёт COUNT(city) по таблице, где у 1 из 6 клиентов город NULL?

COUNT(столбец) не учитывает NULL; COUNT(*) считает все строки.

Почему откат транзакции в тесте не очищает данные, созданные приложением в E2E-тесте?

Приложение пишет в базу через свои соединения и сразу фиксирует транзакции. Транзакция, открытая тестом в его соединении, не охватывает чужие изменения, поэтому её откат их не отменит. Для E2E нужна явная очистка созданных сущностей или изолированные данные.

Тест готовит данные прямым INSERT в таблицу заказов. Какие риски?

Можно создать состояние, которое приложение никогда бы не создало: без связанных записей (платежа, истории статусов), без событий в очереди, без кэша — тест проверит нереалистичный сценарий. Кроме того, тест станет зависеть от схемы базы, которая меняется чаще API. Предпочтительнее готовить данные через API, а оставить для проверок и недоступных через API состояний.
