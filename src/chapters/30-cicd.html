CI/CD

Continuous Integration, Continuous Delivery и Continuous Deployment; pipeline, stages и jobs; GitLab CI и GitHub Actions; quality gates и артефакты. Где именно в конвейере выполняются автотесты и как их результат превращается в решение «можно сливать» или «можно выпускать».

≈ 9 мин чтенияM
Опирается на: Docker
Основная идея

Автотесты приносят пользу, только когда запускаются автоматически на каждое изменение и их результат блокирует слияние или релиз. CI/CD-pipeline — то место, где тесты становятся воротами качества, а не отчётом, который кто-то иногда смотрит.

Цель главы: встроить разные наборы автотестов в pipeline на нужных этапах, настроить артефакты и quality gates в GitLab CI и GitHub Actions.

Кратко

— последовательность стадий из задач; быстрые проверки идут раньше и на каждое изменение, медленные — позже и реже. Красный результат тестов должен блокировать слияние или деплой.

Главное

  • CI — частое слияние изменений с автоматической сборкой и тестами; — каждое изменение готово к релизу, релиз по кнопке; — релиз автоматически.
  • Стадии: lint/typecheck → unit → build → API/компонентные → деплой на стенд → smoke → UI/E2E-регрессия → отчёт.
  • : .gitlab-ci.yml, stages, jobs, image, rules, parallel для шардов, artifacts (с when: always) и reports: junit.
  • : workflows в .github/workflows, jobs, strategy.matrix для шардов, upload-artifact / download-artifact.
  • Quality gate — условие, при невыполнении которого pipeline не пропускает изменение: упавшие тесты, ошибки линтера, порог нестабильности, покрытие.
  • Артефакты (JUnit XML, отчёт, trace, скриншоты) сохраняются и при падении, но always-шаги и cleanup не должны скрывать код возврата тестов.

Термины

Continuous Integration
Практика частого слияния изменений в общую ветку с автоматической сборкой и тестами на каждое изменение.
Continuous Delivery
Каждое изменение, прошедшее pipeline, готово к выпуску; релиз в продакшен выполняется по решению человека.
Continuous Deployment
Каждое изменение, прошедшее pipeline, автоматически выпускается в продакшен без ручного шага.
Pipeline
Набор задач, сгруппированных в стадии или граф зависимостей, который выполняется автоматически при изменениях, по расписанию или вручную.
CI Job
Отдельный шаг pipeline (lint, тесты, сборка, деплой), выполняемый на runner, обычно в Docker-образе, с артефактами и кэшем.

Важно: Pipeline, который можно «пропустить» при красных тестах, превращает тесты в рекомендацию. Сделайте проверки обязательными (protected branches, required checks).

CI, Continuous Delivery и Continuous Deployment#

  • (CI) — разработчики часто вливают изменения в общую ветку, и каждое изменение автоматически собирается и проверяется. Цель — узнавать о проблемах через минуты после изменения.
  • — продолжение CI: каждое изменение, прошедшее , готово к выпуску — собрано, проверено, развёрнуто на стенд. Сам релиз в продакшен — решение человека (кнопка).
  • — каждое прошедшее Pipeline изменение автоматически выпускается в продакшен. Требует очень высокого доверия к автоматическим проверкам.

Чем дальше по этой цепочке, тем больше ответственность автотестов: при Continuous Deployment между коммитом и пользователями нет ручной проверки вообще.

Pipeline: стадии, задачи, артефакты#

— набор (задач), сгруппированных в стадии. Задачи одной стадии выполняются параллельно, стадии — последовательно (или по графу зависимостей needs). Задачи выполняются на (агентах), часто внутри Docker-образа.

Типичное место автотестов в Pipeline продукта:

Стадия Задачи Время Когда
verify lint, typecheck тестов и кода 1–2 мин Каждый push
unit unit-тесты с покрытием 1–5 мин Каждый push
build сборка образа приложения 3–5 мин Каждый push
integration API- и интеграционные тесты в эфемерном окружении (Compose) 5–10 мин Каждый MR
deploy:staging деплой на стенд 2–5 мин После слияния в main
smoke smoke-тесты на стенде 2–5 мин После каждого деплоя
e2e UI/E2E-регрессия, шардирование 10–20 мин После деплоя / перед релизом
report сборка и публикация отчёта 1–2 мин Всегда (when: always)
nightly полная кросс-браузерная регрессия часы По расписанию
Интерактив требует JavaScriptCI/CD Pipeline Visualizer: запустите учебный Pipeline, внедрите падение в любую задачу, включите allow_failure, ретраи, шардирование или граф needs — и посмотрите, какие задачи выполнятся, какие артефакты сохранятся и пройдёт ли Quality Gate.

GitLab CI#

настраивается файлом .gitlab-ci.yml в корне репозитория:

YAML.gitlab-ci.yml
stages: [verify, test, report]

default:
  image: mcr.microsoft.com/playwright:v1.58.2-noble
  cache:
    key: { files: [package-lock.json] }
    paths: [.npm/]
  before_script:
    - npm ci --cache .npm --prefer-offline

variables:
  BASE_URL: https://staging.shop.example.com    # не секрет; секреты — в Settings → CI/CD → Variables

lint:
  stage: verify
  script:
    - npm run typecheck
    - npm run lint
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

api-tests:
  stage: test
  script:
    - npx playwright test --project=api
  artifacts:
    when: always                     # сохранить и при падении
    paths: [playwright-report/, test-results/]
    reports:
      junit: results/junit.xml       # тесты отобразятся в MR
    expire_in: 7 days

e2e-tests:
  stage: test
  parallel: 4                        # 4 шарда
  script:
    - npx playwright test --project=ui --shard=$CI_NODE_INDEX/$CI_NODE_TOTAL
  artifacts:
    when: always
    paths: [blob-report/]
    expire_in: 7 days
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_PIPELINE_SOURCE == "schedule"

merge-report:
  stage: report
  when: always
  needs: [e2e-tests]
  script:
    - npx playwright merge-reports --reporter html ./blob-report
  artifacts:
    when: always
    paths: [playwright-report/]
    expire_in: 14 days

Ключевые элементы:

  • image — Docker-образ, в котором выполняется задача (браузеры уже внутри).
  • cache — кэш npm между запусками ускоряет установку.
  • rules — когда задача запускается: MR, main, расписание, ручной запуск.
  • parallel + $CI_NODE_INDEX/$CI_NODE_TOTAL — шардирование.
  • artifacts с when: always — отчёты сохраняются и при красном результате; reports: junit показывает упавшие тесты прямо в .
  • needs — граф зависимостей: задача стартует, как только готовы нужные ей задачи, не дожидаясь всей стадии.

GitHub Actions#

— workflows в .github/workflows/*.yml:

YAML.github/workflows/e2e.yml
name: e2e
on:
  pull_request:
  push:
    branches: [main]
  schedule:
    - cron: '0 2 * * *'          # ночная регрессия

jobs:
  test:
    runs-on: ubuntu-latest
    container:
      image: mcr.microsoft.com/playwright:v1.58.2-noble
      options: --ipc=host
    strategy:
      fail-fast: false            # не останавливать остальные шарды при падении одного
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npx playwright test --shard=${{ matrix.shard }}/4
        env:
          BASE_URL: ${{ vars.STAGING_URL }}
          ADMIN_PASSWORD: ${{ secrets.ADMIN_PASSWORD }}
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}
        with:
          name: blob-report-${{ matrix.shard }}
          path: blob-report
          retention-days: 7

  report:
    if: ${{ !cancelled() }}
    needs: [test]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - uses: actions/download-artifact@v4
        with: { path: all-blob-reports, pattern: blob-report-*, merge-multiple: true }
      - run: npx playwright merge-reports --reporter html ./all-blob-reports
      - uses: actions/upload-artifact@v4
        with: { name: html-report, path: playwright-report, retention-days: 14 }

Версии действий (@v4) периодически обновляются — сверяйтесь с их репозиториями. Секреты передаются через secrets.* и автоматически маскируются в логах.

Quality Gates#

— автоматическое условие пропуска изменения дальше:

Ворота Где Условие
Слияние MR Protected + required Все обязательные задачи зелёные, есть одобрение ревью
Качество кода тестов verify Ноль ошибок tsc и ESLint
Регрессия test Ноль упавших тестов (не «95% прошло»)
Нестабильность test / report Доля flaky ниже порога, иначе предупреждение или красный статус (failOnFlakyTests)
Покрытие unit Не ниже порога и не ниже, чем в main (для изменённых файлов)
Деплой в прод после staging Smoke и регрессия на staging зелёные

Принцип: ворота должны быть обязательными и доверенными. Если тесты часто ложно падают, команда начнёт обходить ворота — поэтому стабильность набора (глава 30) — условие существования quality gates.

Test Artifacts в CI#

, которые стоит сохранять:

  • JUnit XML — для отображения результатов в интерфейсе GitLab/GitHub.
  • HTML-отчёт / Allure — для разбора; публикуется на GitLab Pages, в S3 или как артефакт.
  • trace, скриншоты, видео упавших тестов.
  • Логи приложения из эфемерного окружения (docker compose logs > app.log).

Срок хранения (expire_in, retention-days) — компромисс между удобством разбора и местом в хранилище.

PR-конвейер и сохранение диагностических артефактов#

Типичный конвейер проверки pull request для TypeScript-проекта: линтер, typecheck, окружение через Compose с проверкой , тесты и отчёт. Ruff — линтер для Python и относится к дополнительному Python-маршруту.

ЭтапПри успехеПри падении
Lint и typecheckПерейти к окружениюОстановить дальнейший запуск; сохранить лог
Окружение и ReadinessЗапустить тестыСохранить Compose logs и состояние
ТестыСохранить результатСохранить trace/screenshots/logs
ОтчётСохранить HTML/Allure artifactНе превращать ошибку отчётности в зелёный тестовый статус
CleanupУдалить ресурсы этого запускаСохранить первичную ошибку и сообщить ошибку cleanup

Учебный проект из главы «Первый запуск» содержит такой workflow для : ESLint, typecheck, Compose, тесты, генерация Allure, артефакты с условием always(), логи и cleanup. Аналогичный конвейер выполнялся на раннере GitHub Actions при подготовке учебника — подробности и границы проверки в разделе «О учебнике».

Bash
docker compose up --build --abort-on-container-exit --exit-code-from tests
# Далее сохраните logs и отчёты, затем выполните cleanup.
# В shell сохраните код первого запуска до остальных команд.

Для Allure добавьте совместимый и сгенерируйте allure-results при выполнении тестов. После запуска Allure CLI создаёт отдельный HTML report; публикуйте его как artifact независимо от успеха тестов. GitHub Pages — отдельная публикация с permissions и правилами доступа, а не обязательная часть PR-проверки. Публичный отчёт не должен содержать секреты.

В учебный проект включён package-lock.json. Используйте npm ci для воспроизводимой установки. При обновлении зависимостей измените и сохраните lockfile. Cache ускоряет получение зависимостей; artifacts сохраняют результаты работы. Секреты поступают из защищённой конфигурации CI, не из примеров в HTML.

Пример: от ручного запуска к воротам#

Было: автотесты запускает QA вручную перед релизом раз в две недели; падения разбираются в день релиза.

Стало:

  1. MR: lint + typecheck + API-тесты в Compose-окружении (8 минут). Обязательная проверка — без неё MR не сливается.
  2. main: деплой на staging → smoke (3 минуты) → UI-регрессия в 4 шардах (12 минут). Красный результат блокирует кнопку «в прод».
  3. Ночью: полная кросс-браузерная регрессия, Allure-отчёт с историей, уведомление в чат.
  4. Метрики: время до обратной связи на MR и доля нестабильных тестов на дашборде команды.

Регрессии стали находиться в день изменения, а релиз перестал быть «днём разбора падений».

Типичные ошибки#

Артефакты только при успехе

По умолчанию GitLab сохраняет артефакты успешных задач. Без when: always отчёт упавших тестов — самый нужный — пропадёт.

allow_failure: true для тестов «временно»

Задача становится жёлтой, на неё перестают смотреть, «временно» длится месяцами. Нестабильные тесты — в карантин с задачами, а не весь набор в необязательные.

Секреты в .gitlab-ci.yml

Файл виден всем с доступом к репозиторию. Секреты — в защищённых маскируемых переменных CI или во внешнем хранилище.

Весь набор на каждый push

Час E2E на каждый коммит — разработчики перестают ждать результат. Распределите наборы по этапам: быстрые — часто, медленные — реже.

Что важно для собеседования#

JuniorГде в CI/CD pipeline запускаются автотесты?

Ответ

На нескольких этапах: lint и проверка типов — на каждый push; unit и API/компонентные — на каждый MR (часто в эфемерном окружении); smoke — сразу после деплоя на стенд; UI/E2E-регрессия — после деплоя на staging или перед релизом; полная кросс-браузерная регрессия — по расписанию. Быстрые и стабильные — раньше и чаще, медленные — позже.

JuniorЧем отличаются CI, Continuous Delivery и Continuous Deployment?

Ответ

CI — частое слияние изменений с автоматической сборкой и тестами. — каждое прошедшее изменение готово к релизу, выпуск по кнопке. Continuous Deployment — выпуск автоматически, без ручного шага. С каждым шагом растут требования к надёжности автотестов.

MiddleКак вы настроите запуск Playwright-тестов в GitLab CI?

Ответ

Задача в образе mcr.microsoft.com/playwright той же версии, кэш npm по package-lock.json, npm ci, запуск нужного проекта; rules для MR, main и расписания; parallel: N и --shard=$CI_NODE_INDEX/$CI_NODE_TOTAL для шардов с blob-репортером и отдельной задачей merge-reports; artifacts: when: always для отчётов и trace, reports: junit для отображения в MR; секреты — в защищённых переменных.

Middle+Какие quality gates вы бы настроили и как поддерживать доверие к ним?

Ответ

Обязательный Pipeline для слияния в main (protected ), ноль ошибок типов и линтера, ноль упавших тестов в обязательных наборах, smoke и регрессия на staging перед продом, контроль нестабильности (отчёт о flaky, порог, failOnFlakyTests для критичного набора). Доверие — через стабильность: карантин нестабильных тестов с задачами и сроками, разбор каждого ложного падения, быстрые наборы на MR.

Проверьте себя#

Тест
1
Чем Continuous Delivery отличается от Continuous Deployment?

Continuous Deployment убирает ручной шаг перед продакшеном, поэтому требует максимального доверия к автотестам.

2
Что делает artifacts: when: always в GitLab CI?

Отчёты и trace особенно нужны именно при падении.

3
Как в GitLab CI разделить UI-тесты на 4 шарда?

parallel создаёт N копий задачи с переменными индекса и общего числа.

Какие наборы тестов вы бы запускали на MR, а какие — после деплоя?

На MR — быстрые и изолированные: lint и typecheck, unit, API-тесты и компонентные или ключевые UI-тесты в эфемерном окружении; они должны укладываться в 10–15 минут. После деплоя на staging — smoke (готовность стенда) и UI/E2E-регрессия с реальными интеграциями. Ночью — полная кросс-браузерная регрессия и долгие сценарии.

Почему quality gate бесполезен при нестабильном наборе тестов?

Если тесты часто краснеют без причины, команда начинает перезапускать или делать проверки необязательными, и ворота перестают защищать. Ворота работают, только когда красный результат почти всегда означает реальную проблему.
