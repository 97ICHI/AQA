Архитектура тестового проекта

Структура репозитория автотестов, конфигурация, фикстуры, клиенты API, страницы, данные, хелперы и утилиты, правила зависимостей между слоями и инструменты качества кода. Как набор тестов превращается в поддерживаемую систему.

Основная идея

Архитектура тестового проекта — это ответ на вопрос «куда положить новый код и где искать существующий». Хорошая структура делает очевидным, какой слой меняется при редизайне, изменении API или новом бизнес-правиле.

Цель главы: организовать репозиторий автотестов по слоям с однонаправленными зависимостями и единой точкой конфигурации.

Кратко

Тесты зависят от фикстур, фикстуры — от клиентов, страниц и данных, те — от конфигурации и утилит. Обратных зависимостей нет.

Главное

  • tests/ — только сценарии и ожидания, сгруппированные по видам (api, ui, e2e) и областям продукта.
  • src/ — переиспользуемый код: config, fixtures, api (клиенты), pages и components, data (фабрики), schemas, utils.
  • Конфигурация окружений читается в одном модуле с валидацией и значениями по умолчанию; тесты не обращаются к process.env напрямую.
  • Фикстуры собираются из модулей через mergeTests, тесты импортируют test из одного места.
  • Helpers знают о предметной области (создать оплаченный заказ); utilities — нет (форматирование денег, ожидание, генерация строк).
  • Качество кода тестов: strict, ESLint с eslint-plugin-playwright, Prettier, проверки в CI и ревью.

Термины

Test Framework
Код проекта вокруг инструмента: конфигурация, фикстуры, клиенты API, page objects, фабрики данных, отчётность — общий язык предметной области для тестов.
Project Structure
Раскладка репозитория автотестов по слоям: tests, fixtures, api, pages, components, data, schemas, config, utils.
Configuration Management
Получение настроек окружения (адреса, учётные данные, флаги) из одного модуля с проверкой обязательных значений и типами.
Helper / Utility
Helper — вспомогательная функция, знающая предметную область (создать оплаченный заказ); utility — общая функция без знания продукта (форматирование, генерация строк).
Linter
Инструмент (ESLint), находящий ошибки и нарушения правил без запуска: забытые await, test.only, waitForTimeout, неиспользуемый код.

Важно: Не начинайте с «фреймворка на вырост» с десятью слоями абстракций. Структура должна расти вместе с набором тестов: сначала тесты и фикстуры, затем клиенты и страницы, когда появляется дублирование.

Что такое тестовый фреймворк#

в разговоре AQA — не , а ваш код вокруг него: конфигурация окружений, фикстуры, клиенты API, objects, фабрики данных, отчётность. Playwright даёт раннер и API браузера; фреймворк проекта даёт тестам язык предметной области: paidOrder, adminApi, catalogPage.

Цели архитектуры:

  • Найти место для кода без обсуждений: новая страница → src/pages, новый эндпоинт → src/api.
  • Локализовать изменения: редизайн — pages/components, изменение API — api/schemas, бизнес-правило — tests.
  • Сделать тесты короткими: подготовка и механика вынесены, в тесте — сценарий.
  • Запускать подмножества: по виду теста, области, тегу, окружению.

Правило зависимостей#

Слои зависят только «вниз»:

Текст
tests  →  fixtures  →  api / pages / components / data / schemas  →  config / utils
  • utils ничего не знает о продукте и не импортирует остальное.
  • pages не импортируют api, а api — pages: это параллельные способы взаимодействия.
  • fixtures собирают всё вместе для тестов.
  • tests не импортируют друг друга и не содержат переиспользуемого кода.

Нарушение правила — признак проблемы: object, который создаёт пользователя через API, или утилита, импортирующая фикстуру.

Конфигурация окружений#

: тесты запускаются на локальном стенде, в CI, на staging. Значения приходят из переменных окружения; читать их нужно в одном месте с проверкой:

TypeScriptsrc/config/env.ts
type Env = 'local' | 'staging' | 'ci';

function required(name: string): string {
  const v = process.env[name];
  if (!v) throw new Error(`Не задана переменная окружения ${name} (см. .env.example)`);
  return v;
}

const env = (process.env.TEST_ENV ?? 'local') as Env;
if (!['local', 'staging', 'ci'].includes(env)) throw new Error(`Неизвестное TEST_ENV: ${env}`);

export const config = {
  env,
  baseURL: process.env.BASE_URL ?? 'http://localhost:3000',
  apiURL: process.env.API_URL ?? 'http://localhost:8080',
  admin: {
    email: process.env.ADMIN_EMAIL ?? 'admin@example.com',
    // секреты без значения по умолчанию: падение сразу с понятной ошибкой
    get password() { return required('ADMIN_PASSWORD'); },
  },
  slowMoMs: Number(process.env.SLOW_MO ?? 0),
} as const;
TypeScriptplaywright.config.ts
import { defineConfig, devices } from '@playwright/test';
import { config } from './src/config/env';

export default defineConfig({
  testDir: './tests',
  use: { baseURL: config.baseURL, trace: 'on-first-retry' },
  projects: [
    { name: 'setup', testMatch: /setup\/.*\.setup\.ts/ },
    { name: 'api', testDir: './tests/api', use: { baseURL: config.apiURL } },
    { name: 'ui', testDir: './tests/ui', dependencies: ['setup'], use: { ...devices['Desktop Chrome'] } },
  ],
});

Плюсы: опечатка в имени переменной не превращается в «тест пошёл на прод»; при отсутствии секрета ошибка понятна; значения типизированы. Как работать с секретами и окружениями — в следующей главе.

Фикстуры как точка сборки#

Фикстуры удобно делить по модулям и объединять:

TypeScriptsrc/fixtures/index.ts
import { mergeTests, test as base } from '@playwright/test';

const apiFixtures = base.extend<{ apiReady: boolean }>({
  apiReady: async ({}, use) => { await use(true); },
});
const pageFixtures = base.extend<{ pagesReady: boolean }>({
  pagesReady: async ({}, use) => { await use(true); },
});

export const test = mergeTests(apiFixtures, pageFixtures);
export { expect } from '@playwright/test';

Тесты импортируют только test и expect из src/fixtures — одна строка импорта, все фикстуры проекта доступны. (Здесь фикстуры упрощены до заглушек, чтобы показать сборку; содержательные фикстуры — в главах 16 и 20.)

Helpers и Utilities#

— частая путаница:

Helper (предметный) Utility (общая)
Знает о продукте Да Нет
Примеры createPaidOrder(api), loginViaApi(request, user) formatRub(9980), retry(fn, n), uniqueSuffix()
Где src/fixtures, src/data, рядом с клиентами src/utils
Тестируется Через тесты, которые его используют Может иметь свои unit-тесты

Свалка helpers.ts на тысячу строк — признак отсутствия архитектуры. Хелпер должен жить рядом со своей предметной областью.

Качество кода тестов#

Тестовый код проходит те же проверки, что и продуктовый:

JSONpackage.json (фрагмент)
{
  "scripts": {
    "test": "playwright test",
    "test:api": "playwright test --project=api",
    "test:ui": "playwright test --project=ui",
    "test:smoke": "playwright test --grep @smoke",
    "typecheck": "tsc --noEmit",
    "lint": "eslint .",
    "format": "prettier --write ."
  }
}
  • strict — ловит undefined и опечатки.
  • : ESLint с @typescript-eslint (no-floating-promises) и eslint-plugin-playwright (missing-playwright-await, no-wait-for-timeout, no-focused-test, no-skipped-test, prefer-web-first-assertions).
  • Prettier — единое форматирование, без споров на ревью.
  • CI — typecheck и lint выполняются до тестов.
  • Ревью — чек-лист: локаторы, независимость, очистка данных, понятные имена, отсутствие секретов.

Где живут тесты: рядом с кодом или отдельно#

В репозитории продукта Отдельный репозиторий
Синхронизация с изменениями Тесты меняются в том же MR, что и код Нужна синхронизация версий
Владение Разработчики и QA вместе Чаще команда QA
Тесты нескольких сервисов Неудобно Удобно
Запуск на каждый MR продукта Естественно Требует триггеров между пайплайнами

Частый компромисс: unit, интеграционные и API-тесты сервиса — рядом с кодом; сквозные E2E по нескольким сервисам — в отдельном репозитории.

Пример: как растёт архитектура#

  1. 10 тестов. tests/*.spec.ts, конфиг, пара фикстур. objects не нужны.
  2. 50 тестов. Дублируются локаторы корзины и вход — появляются pages/CartPage.ts, setup/auth.setup.ts, config/env.ts.
  3. 200 тестов. Отдельные проекты api/ui, клиенты API, фабрики данных, фикстуры по модулям, ESLint-правила, теги @smoke.
  4. 1000 тестов. Шардирование в CI, карантин нестабильных, отчёты Allure, CODEOWNERS для областей, документация в README.

На каждом шаге структура решает реальную проблему, а не воображаемую.

Типичные ошибки#

process.env во всех тестах

Сто мест, где читается process.env.BASE_URL, и в пяти из них опечатка. Один модуль конфигурации с проверкой.

Тест импортирует другой тест

Переиспользуемый код живёт в src. Импорт из *.spec.ts регистрирует тесты чужого файла повторно и связывает файлы.

Универсальный BaseTest/BaseHelper

Класс со всем подряд, от которого наследуются тесты. В эту роль выполняют фикстуры — модульно и лениво.

Нет README

Новый участник тратит день, чтобы запустить тесты. Опишите: установка, переменные окружения, запуск подмножеств, структура, правила.

Что важно для собеседования#

MiddleКак вы структурируете проект автотестов на Playwright?

Ответ

tests/ с разделением по видам (api, ui, e2e) и областям продукта — только сценарии; src/ со слоями: config (переменные окружения с валидацией), api (клиенты ресурсов), pages и components, data (фабрики), schemas, fixtures (сборка через mergeTests), utils. Зависимости только вниз. Плюс проекты в конфиге под виды тестов, скрипты npm, ESLint с плагином , проверка типов и README.

MiddleКак организовать запуск одних и тех же тестов на разных стендах?

Ответ

Все адреса и учётные данные — из переменных окружения, которые читаются в одном модуле конфигурации с проверкой обязательных значений и значениями по умолчанию для локального запуска. В playwright.config.ts используется baseURL из конфигурации, тесты пишут относительные пути. Стенд выбирается TEST_ENV/BASE_URL в CI; секреты приходят из хранилища CI.

Middle+Вы пришли в проект, где 800 тестов в одной папке без структуры. С чего начнёте?

Ответ

Не с переписывания всего. Сначала измерю: время, нестабильность, дублирование, самые часто ломающиеся места. Введу базу: модуль конфигурации, линтер, проверку типов в CI. Затем по частям: вынесу дублирующиеся подготовки в фикстуры, локаторы часто меняющихся страниц — в objects, разделю тесты на проекты по видам. Каждый шаг — небольшой MR с зелёным прогоном. Параллельно правила для нового кода, чтобы долг не рос.

Проверьте себя#

Тест
1
Где разместить функцию createPaidOrder(api)?

Функция знает о заказах и оплате — это предметный helper, а не общая утилита.

2
Какая зависимость нарушает правило слоёв?

Утилиты — самый нижний слой и ничего не знают о продукте.

3
Зачем читать переменные окружения в одном модуле config/env.ts?

Ошибка конфигурации обнаруживается сразу с понятным сообщением, а не случайным падением в середине прогона.

Почему структура «по видам тестов» (api/ui/e2e) удобна для CI?

Разные виды запускаются в разное время и с разными настройками: API — на каждый коммит с большим числом воркеров, UI — на MR, E2E — после деплоя на стенд. Каталог превращается в отдельный проект , и запускает нужный набор одной командой.

Что должно быть в README тестового проекта?

Требования и установка, переменные окружения (со ссылкой на .env.example), команды запуска наборов и одного теста, как открыть отчёт и trace, структура каталогов и правила (куда класть код, локаторы, теги), как добавить новый тест, к кому обращаться.
