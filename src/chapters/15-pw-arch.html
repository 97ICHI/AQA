Архитектура Playwright

Как устроен Playwright: библиотека и тестовый раннер, связь с браузерами, иерархия Browser → BrowserContext → Page, процессы-воркеры, конфигурация и запуск из командной строки.

Основная идея

Тест на Playwright — это Node.js-процесс, который по протоколу управляет настоящим браузером. Раннер запускает тесты в нескольких процессах-воркерах, и каждый тест получает свой изолированный контекст браузера — «чистый профиль» без cookies и данных предыдущего теста.

Цель главы: понимать, что происходит при запуске npx playwright test, и уметь настроить проект через playwright.config.ts.

Кратко

запускает воркеры; воркер запускает браузер; каждый тест получает новый и Page. Команды идут из Node.js в браузер по протоколу и асинхронны.

Главное

  • — библиотека управления браузерами (Chromium, Firefox, WebKit) и тестовый раннер Playwright Test.
  • Клиент на Node.js общается с драйвером Playwright, который управляет браузером: Chromium — через CDP, Firefox и WebKit — через собственные протоколы в специальных сборках.
  • Browser — процесс браузера; BrowserContext — изолированная сессия (cookies, localStorage, разрешения); — вкладка.
  • Воркер — отдельный процесс ОС; браузер переиспользуется тестами одного воркера, контекст — нет.
  • По умолчанию тесты одного файла идут последовательно в одном воркере, разные файлы — параллельно; fullyParallel распараллеливает и тесты внутри файла.
  • playwright.config.ts: testDir, timeout, retries, workers, reporter, use (baseURL, trace, screenshot), projects, webServer.

Термины

Playwright
Инструмент автоматизации браузеров Chromium, Firefox и WebKit с API для JS/TS, Python, Java и .NET.
Playwright Test
Раннер @playwright/test: параллельный запуск в воркерах, фикстуры, web-first assertions, ретраи, проекты, отчёты и trace.
BrowserContext
Изолированная сессия внутри браузера со своими cookies, хранилищем, кэшем и разрешениями. Каждый тест получает новый контекст.
Page
Вкладка браузера в контексте. Через неё выполняются навигация, действия и поиск элементов.
Worker
Отдельный процесс ОС, в котором Playwright Test выполняет тесты. Браузер переиспользуется тестами одного воркера; после падения теста воркер перезапускается.

Важно: Не создавайте браузер вручную в каждом тесте через chromium.launch() — используйте встроенные фикстуры page и context: раннер сам обеспечит изоляцию, артефакты и очистку.

Что такое Playwright#

— open-source инструмент Microsoft для автоматизации браузеров. Под этим именем живут две вещи:

  • Библиотека (playwright) — API для управления браузером из Node.js, Python, Java и .NET: открыть страницу, найти элемент, кликнуть, перехватить запрос.
  • (@playwright/test) — тестовый раннер для JavaScript/TypeScript: находит тесты, запускает их параллельно, даёт фикстуры, expect с автоожиданием, ретраи, отчёты, трассировку.

В учебнике мы используем Playwright Test — именно его выбирают для новых проектов на .

Поддерживаемые движки: Chromium (а также установленные Google Chrome и Microsoft Edge через channel), Firefox и WebKit (движок Safari). Playwright скачивает собственные сборки браузеров, совместимые с конкретной версией библиотеки, поэтому после обновления пакета выполняют npx playwright install. Начиная с версии 1.58 для Chromium-проектов используются сборки Chrome for Testing, а в headless-режиме — chrome-headless-shell.

Как Playwright управляет браузером#

Тест не «живёт» в браузере. Это обычный Node.js-процесс, который отправляет команды:

Текст
Тест (Node.js)  →  клиент Playwright  →  драйвер Playwright  →  браузер
   await click()      сериализует         CDP (Chromium) /         выполняет
                      команду             протоколы Firefox/WebKit  действие
  • Для Chromium используется (Chrome DevTools Protocol) — тот же протокол, на котором работают DevTools.
  • Для Firefox и WebKit поставляет сборки с добавленным протоколом удалённого управления.
  • Связь двусторонняя и постоянная (не HTTP-запрос на каждую команду), поэтому Playwright получает события браузера сразу: загрузку страницы, сетевые запросы, сообщения консоли, диалоги.

Сравнение с другими инструментами:

Playwright Selenium WebDriver Cypress
Где выполняется тест Отдельный процесс Отдельный процесс Внутри браузера
Связь с браузером Постоянное соединение, CDP и аналоги W3C WebDriver (), WebDriver BiDi Внутри страницы + прокси
Автоожидание Встроено в действия и expect Явные ожидания пишет тестировщик Встроено в команды

Browser, BrowserContext, Page#

Текст
Browser            — процесс браузера (дорого запускать: сотни миллисекунд)
 └─ BrowserContext — изолированная сессия: cookies, localStorage, кэш, разрешения, геолокация
     └─ Page       — вкладка
         └─ Frame  — основной фрейм и iframe
             └─ Locator — способ найти элемент

— ключ к изоляции тестов. Это как новый профиль в режиме инкогнито: создаётся за миллисекунды, ничего не знает о других контекстах. В одном браузере можно одновременно держать несколько контекстов — например, покупателя и администратора в одном тесте.

— вкладка в контексте. Через неё выполняются навигация, действия и поиск элементов.

TypeScripttests/two-users.spec.ts
import { test, expect } from '@playwright/test';

test('администратор видит заказ покупателя', async ({ browser }) => {
  // Два независимых контекста в одном браузере
  const buyerContext = await browser.newContext();
  const adminContext = await browser.newContext({ storageState: 'playwright/.auth/admin.json' });
  const buyer = await buyerContext.newPage();
  const admin = await adminContext.newPage();

  await buyer.goto('/product/7');
  await buyer.getByRole('button', { name: 'Купить в один клик' }).click();
  const orderId = await buyer.getByTestId('order-id').innerText();

  await admin.goto('/admin/orders');
  await expect(admin.getByRole('row', { name: new RegExp(orderId) })).toBeVisible();

  await buyerContext.close();
  await adminContext.close();
});

В обычном тесте контексты создавать не нужно: фикстура page уже даёт страницу в новом контексте, а после теста раннер его закроет.

Как раннер запускает тесты#

Что происходит при npx playwright test:

  1. Загрузка конфигурации playwright.config.ts.
  2. Сбор тестов: раннер импортирует файлы *.spec.ts и строит список тестов (на этом этапе код внутри test() не выполняется).
  3. Запуск воркеров. — отдельный процесс ОС. По умолчанию их число — половина логических ядер процессора; в CI его обычно задают явно.
  4. Распределение тестов. По умолчанию файлы распределяются между воркерами, а тесты одного файла выполняются в одном воркере последовательно. С fullyParallel: true параллельно идут и тесты внутри файла.
  5. В каждом воркере: браузер запускается один раз и переиспользуется; для каждого теста создаются новые context и page, после теста — закрываются.
  6. Падение теста. Воркер, в котором упал тест, завершается, и следующие тесты идут в новом воркере — так гарантируется чистое окружение.
  7. Ретраи упавших тестов, если они настроены.
  8. Отчёты: списки в консоли, HTML-отчёт, JUnit, Allure и т. д.
Интерактив требует JavaScriptСхема архитектуры Playwright: нажимайте на компоненты — раннер, воркеры, браузер, контексты, страницы, фикстуры, отчёты — чтобы увидеть, за что отвечает каждый и что живёт дольше одного теста.

Конфигурация#

описывает, где тесты, как их запускать и с какими настройками браузера.

TypeScriptplaywright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  timeout: 30_000,                 // лимит на один тест (по умолчанию 30 с)
  expect: { timeout: 5_000 },      // лимит для web-first assertions (по умолчанию 5 с)
  fullyParallel: true,
  forbidOnly: !!process.env.CI,    // в CI запрещаем случайно оставленный test.only
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 4 : undefined,
  reporter: [['list'], ['html', { open: 'never' }]],

  use: {
    baseURL: process.env.BASE_URL ?? 'http://localhost:3000',
    trace: 'on-first-retry',       // записать trace при первом повторе упавшего теста
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
    testIdAttribute: 'data-testid',
  },

  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox', use: { ...devices['Desktop Firefox'] } },
    { name: 'mobile-safari', use: { ...devices['iPhone 13'] } },
  ],

  webServer: {
    command: 'npm run start',      // поднять приложение перед тестами (локально)
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
    timeout: 120_000,
  },
});

Ключевые идеи:

  • use — опции для фикстур: baseURL позволяет писать page.goto('/cart'), а request.get('/api/...') — без полного адреса.
  • projects — один и тот же набор тестов в разных конфигурациях (браузеры, устройства, окружения, роли).
  • webServer — раннер сам запускает приложение и ждёт, пока оно ответит по url.
  • Опции можно переопределить на уровне файла или группы: test.use({ locale: 'en-US' }).

Командная строка#

Shell
npm init playwright@latest                    # создать проект с конфигом и примером
npx playwright install --with-deps            # браузеры и системные зависимости (Linux/CI)
npx playwright test                           # все тесты
npx playwright test tests/cart.spec.ts:24     # тест на конкретной строке
npx playwright test --project=chromium        # один проект
npx playwright test --grep @smoke             # по тегу или части имени
npx playwright test --grep-invert @slow       # исключить тег
npx playwright test --headed --workers=1      # с видимым браузером и без параллелизма
npx playwright test --repeat-each=10          # повторить каждый тест (поиск нестабильности)
npx playwright test --last-failed             # только упавшие в прошлом запуске
npx playwright test --shard=2/4               # вторая четверть набора (CI)
npx playwright show-report                    # открыть HTML-отчёт
npx playwright codegen https://shop.example.com # записать действия и получить код

режим (по умолчанию) — браузер без окна: быстрее и подходит для CI. --headed нужен для наблюдения и отладки.

Codegen — помощник, а не автор тестов

codegen полезен, чтобы быстро узнать локаторы и последовательность действий. Сгенерированный код — черновик: в нём нет проверок смысла, данных, структуры и переиспользования. Его переписывают по правилам следующих глав.

Минимальная структура после npm init playwright@latest:

Текст
shop-tests/

TypeScripttests/catalog.spec.ts
import { test, expect } from '@playwright/test';

test.describe('каталог', () => {
  test('поиск находит товар по названию', async ({ page }) => {
    await page.goto('/');
    await page.getByRole('searchbox', { name: 'Поиск' }).fill('наушники');
    await page.getByRole('searchbox', { name: 'Поиск' }).press('Enter');
    await expect(page).toHaveURL(/\/search\?q=/);
    await expect(page.getByRole('heading', { name: /Наушники/ }).first()).toBeVisible();
  });
});

Запуск npx playwright test --project=chromium выполнит тест в новом контексте Chromium. Если тест упадёт, при включённых ретраях повтор запишет trace — его можно открыть в отчёте.

Типичные ошибки#

Общая страница для всех тестов

Создание одной page в beforeAll и её использование во всех тестах файла связывает тесты состоянием: cookies, открытые модальные окна, данные формы. Используйте встроенную фикстуру page.

Полные URL в каждом тесте

page.goto('https://staging.shop.example.com/cart') в сотне тестов делает невозможным запуск на другом стенде. Задайте baseURL и используйте относительные пути.

Оставленный test.only

Локально удобно, но в CI запустится один тест, и будет «зелёным». Включите forbidOnly в CI.

Тестировать все браузеры на каждом коммите

Три браузера × мобильные устройства утраивают время. Частая практика: Chromium — на каждый MR, остальные проекты — ночью или перед релизом.

Что важно для собеседования#

JuniorЧто такое Browser, BrowserContext и Page в Playwright?

Ответ

Browser — процесс браузера, его дорого запускать. — изолированная сессия в браузере (cookies, localStorage, кэш, разрешения), как профиль инкогнито; создаётся за миллисекунды. — вкладка в контексте. Раннер переиспользует браузер в воркере, а каждому тесту даёт новый контекст и страницу — так тесты изолированы и быстры.

JuniorЧем Playwright отличается от Selenium?

Ответ

держит постоянное соединение с браузером (CDP для Chromium, собственные протоколы для Firefox и WebKit) и получает события браузера; в действия и expect встроено автоожидание; есть свой раннер с изоляцией контекстов, параллелизмом, trace, перехватом сети. Selenium работает по стандарту W3C WebDriver (, а также BiDi), поддерживает больше языков и браузеров, но ожидания, раннер и отчёты нужно подбирать и настраивать отдельно.

MiddleЧто происходит при запуске npx playwright test?

Ответ

Загружается конфиг, собираются тесты из файлов, запускаются воркеры (отдельные процессы). Файлы распределяются между воркерами (с fullyParallel — отдельные тесты). Воркер запускает браузер один раз; каждому тесту фикстуры создают новый контекст и страницу, после теста закрывают. Упавший тест приводит к замене воркера, при ретраях тест повторяется. В конце репортеры формируют отчёты.

MiddleДля чего нужны projects в конфиге Playwright?

Ответ

Запускать один набор тестов в разных конфигурациях: браузеры и устройства, окружения, роли пользователей, наборы (smoke/regression с разными testMatch). Через dependencies можно задать проект-setup (например, авторизация), который выполняется до остальных. Проект выбирается флагом --project.

Проверьте себя#

Тест
1
Что изолирует cookies и localStorage одного теста от другого в Playwright?

Фикстуры context и page создаются заново для каждого теста. BrowserContext — изолированная сессия; браузер при этом переиспользуется внутри воркера.

2
Что произойдёт с воркером после падения теста?

Так Playwright гарантирует, что испорченное состояние процесса не повлияет на другие тесты. Поэтому beforeAll может выполниться повторно.

3
Зачем нужна опция baseURL?

page.goto('/cart') и request.get('/api/...') дополняются baseURL; стенд меняется переменной окружения.

Почему браузер запускается один раз на воркер, а контекст — на каждый тест?

Запуск браузера дорог (сотни миллисекунд и память), а создание контекста — дёшево (миллисекунды). Контекст при этом даёт полную изоляцию cookies, хранилища и разрешений. Так достигается баланс скорости и независимости тестов.

Чем Playwright Test отличается от библиотеки Playwright?

Библиотека даёт API управления браузером. — раннер поверх неё: поиск и параллельный запуск тестов, фикстуры с автоматической изоляцией и очисткой, expect с автоожиданием, ретраи, проекты, отчёты, trace. Для автотестов на используют раннер, а не библиотеку напрямую.
