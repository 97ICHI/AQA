Mocking и Test Data

Test doubles — dummy, stub, spy, mock, fake; подмена внешних зависимостей на разных уровнях; управление тестовыми данными и data-driven тесты. Как сделать тест детерминированным и при этом не потерять связь с реальностью.

≈ 11 мин чтенияM
Опирается на: Автоматизация APIПродвинутый Playwright
Основная идея

Тест должен падать только из-за проверяемого поведения. Внешний платёжный шлюз, случайные данные, текущее время и чужие записи на стенде — источники посторонних падений. Их контролируют подменами и управляемыми данными, сознательно выбирая, что подменять, а что проверять по-настоящему.

Цель главы: различать виды test doubles, выбирать уровень подмены и выстраивать стратегию тестовых данных, при которой тесты детерминированы и независимы.

Кратко

Test double заменяет реальную зависимость: stub отдаёт заготовленный ответ, spy записывает вызовы, mock проверяет ожидаемые вызовы, fake — упрощённая рабочая реализация. Данные тест создаёт сам, уникальными, и убирает за собой.

Главное

  • Dummy — заглушка-аргумент; — фиксированный ответ; — запись вызовов; Mock — ожидания вызовов с проверкой; Fake — облегчённая реализация (in-memory база).
  • Уровни подмены: в коде (unit), в браузере (page.route), мок-сервер или виртуализация сервиса (WireMock, MSW, Prism), песочница внешнего провайдера.
  • Подменяйте то, что не является предметом проверки и не контролируется вами: платёжные шлюзы, SMS, карты, аналитика, время.
  • Стратегии данных: создание в тесте через API, сид-наборы, синтетическая генерация, обезличенные копии продакшена, снимок и восстановление базы.
  • Детерминированность: фиксированный seed генератора, контролируемое время, уникальные метки данных.
  • Data-driven: данные в массиве, или CSV, отдельный тест на каждый набор.

Термины

Stub
Test double, который возвращает заранее заданные ответы, чтобы код мог выполниться в нужном сценарии.
Mock Object
Test double, который заранее знает ожидаемые вызовы (сколько раз, с какими аргументами) и проверяет их.
Spy
Test double, который записывает вызовы зависимости для последующей проверки в тесте.
Fake
Test double с работающей, но упрощённой логикой: in-memory база, локальный SMTP, фейковый платёжный шлюз.
Data-driven Testing
Подход, при котором одна логика теста выполняется для набора входных данных и ожиданий; каждый набор — отдельный тест в отчёте.

Важно: Каждый мок — это предположение о поведении реальной системы. Тест на моках проверяет ваш код при этом предположении, но не само предположение: нужны контрактные или интеграционные проверки, которые его подтверждают.

Зачем подменять зависимости#

Сервис заказов вызывает платёжный шлюз, сервис доставки, отправку SMS и аналитику. Если тест «оплата заказа» ходит во все эти системы:

  • он падает, когда недоступна любая из них — даже если код заказов корректен;
  • он медленный (внешние вызовы — сотни миллисекунд и секунды);
  • нельзя проверить редкие ответы: «карта отклонена», «таймаут шлюза», «двойной колбэк»;
  • реальные SMS и списания — недопустимы.

— замена реальной зависимости управляемой подменой — решает эти проблемы. Общее название подмен — (по аналогии с дублёром в кино).

Виды test doubles#

Вид Что делает Пример в тестах
Dummy Передаётся, но не используется Пустой логгер, нужный конструктору
Возвращает заранее заданный ответ Курс валют всегда 90; шлюз всегда отвечает «approved»
Записывает вызовы для последующей проверки Сколько раз и с какими данными вызвана отправка письма
Заранее знает ожидаемые вызовы и проверяет их «Должен быть ровно один вызов charge(9980)»
Упрощённая, но работающая реализация In-memory база, локальный SMTP-сервер, фейковый шлюз с правилами

Stub отвечает на вопрос «что вернуть», Spy и mock — «как меня вызвали». В разговорной речи всё называют «моками» — на собеседовании полезно показать, что вы видите разницу.

TypeScriptsrc/payments.ts
export interface PaymentGateway {
  charge(amountKopecks: number, cardToken: string): Promise<{ status: 'approved' | 'declined'; id: string }>;
}

export async function payOrder(gw: PaymentGateway, total: number, card: string) {
  const res = await gw.charge(total * 100, card);
  return res.status === 'approved' ? { paid: true, paymentId: res.id } : { paid: false, paymentId: null };
}
TypeScripttests/payments.spec.ts
import { test, expect } from '@playwright/test';
import { payOrder, type PaymentGateway } from '../src/payments';

test('отказ шлюза → заказ не оплачен (stub + spy)', async () => {
  const calls: number[] = [];                                  // spy: записываем вызовы
  const declinedGateway: PaymentGateway = {                    // stub: заданный ответ
    async charge(amount) {
      calls.push(amount);
      return { status: 'declined', id: 'p-1' };
    },
  };

  const result = await payOrder(declinedGateway, 9980, 'tok_visa');

  expect(result).toEqual({ paid: false, paymentId: null });
  expect(calls).toEqual([998000]);                             // сумма передана в копейках
});

Уровень Инструменты Что проверяет тест Что не проверяет

Мок-сервер для внешнего сервиса можно поднять прямо в фикстуре воркера:

TypeScripttests/fixtures/mock-gateway.ts
import { test as base } from '@playwright/test';
import http from 'node:http';
import type { AddressInfo } from 'node:net';

type GatewayMode = 'approve' | 'decline' | 'timeout';
type MockGateway = { url: string; setMode: (m: GatewayMode) => void; calls: unknown[] };

export const test = base.extend<{}, { gateway: MockGateway }>({
  gateway: [async ({}, use) => {
    let mode: GatewayMode = 'approve';
    const calls: unknown[] = [];
    const server = http.createServer((req, res) => {
      let body = '';
      req.on('data', (c) => (body += c));
      req.on('end', () => {
        calls.push(JSON.parse(body || '{}'));
        if (mode === 'timeout') return;                     // не отвечаем — клиент упрётся в таймаут
        res.writeHead(200, { 'Content-Type': 'application/json' });
        res.end(JSON.stringify({ status: mode === 'approve' ? 'approved' : 'declined', id: `p-${calls.length}` }));
      });
    });
    await new Promise<void>((r) => server.listen(0, r));    // порт 0 — свободный случайный порт
    const { port } = server.address() as AddressInfo;
    await use({ url: `http://127.0.0.1:${port}`, setMode: (m) => (mode = m), calls });
    server.closeAllConnections();
    await new Promise<void>((r) => server.close(() => r()));
  }, { scope: 'worker' }],
});

Приложение в тестовом окружении настраивается на адрес мок-сервера (переменной окружения), а тест переключает режим и проверяет, как приложение реагирует на отказ или таймаут шлюза.

Цена моков

Чем больше подменено, тем меньше реальности в проверке. Типичная схема: большинство тестов — с подменой внешних систем (быстро и стабильно), плюс небольшой набор интеграционных тестов с песочницами реальных провайдеров и контрактные тесты, подтверждающие, что моки соответствуют реальности.

Интерактив требует JavaScriptAPI Playground с подменами: включайте сценарии внешних зависимостей (шлюз одобряет, отклоняет, не отвечает или падает; служба доставки недоступна или медленная) и смотрите, как меняется ответ учебного API и что должен проверить тест.

Test Data Management#

— как данные для тестов создаются, хранятся, изолируются и удаляются.

Стратегия Как Плюсы Минусы
Создание в тесте через API Фикстура создаёт и удаляет Изоляция, реалистичность Время на подготовку, нужен API
Сид-набор (seed) Скрипт заливает фиксированные данные при поднятии окружения Быстро, предсказуемо Тесты, меняющие сид, мешают друг другу
Синтетическая генерация Фабрики + генераторы (Faker) Разнообразие, уникальность Случайность → нужна воспроизводимость (seed)
Обезличенная копия продакшена Маскирование персональных данных Реалистичные объёмы и сочетания Юридические риски, тяжело, нестабильно
Снимок и восстановление Docker-образ базы с данными, откат после прогона Чистое состояние каждый прогон Не изолирует параллельные тесты одного прогона

Практичная комбинация: справочники и неизменяемые данные — сидом, сущности, которые тест меняет, — создаются тестом, всё уникально по метке прогона.

import { randomUUID } from 'node:crypto';

// Метка прогона: по ней можно найти и убрать «мусор» аварийно прерванных запусков
export const RUN_ID = process.env.TEST_RUN_ID ?? randomUUID().slice(0, 8);

export function uniqueEmail(prefix = 'qa'): string {
  return `${prefix}+${RUN_ID}-${randomUUID().slice(0, 8)}@example.com`;
}

// Детерминированный генератор: один seed — одна и та же последовательность
export function seededRandom(seed: number): () => number {
  let s = seed >>> 0;
  return () => {
    s = (s + 0x6d2b79f5) >>> 0;
    let t = Math.imul(s ^ (s >>> 15), s | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

Изоляция внешних зависимостей и детерминированность#

— тест с одинаковым кодом и данными всегда даёт одинаковый результат. Источники недетерминированности и способы контроля:

Источник Контроль
Текущее время и дата page.clock в браузере, конфигурируемые часы на сервере тестового окружения, данные относительно «сейчас»
Случайные значения Генератор с фиксированным seed, вывод seed в отчёт
Внешние сервисы Стабы, мок-серверы, песочницы
Чужие данные на стенде Свои данные с уникальной меткой, фильтрация по ней
Порядок элементов без явной сортировки Проверять множество, а не порядок, или задать сортировку
Часовой пояс, локаль Фиксировать timezoneId, locale в конфиге и TZ окружения

Пример: тест оплаты без реального шлюза#

Сценарий: «если шлюз не ответил за 10 секунд, заказ остаётся неоплаченным, а пользователь видит предложение повторить».

  1. Тестовое окружение приложения настроено на мок-шлюз (переменная PAYMENT_GATEWAY_URL).
  2. Фикстура gateway переключается в режим timeout.
  3. Тест оформляет заказ через API, оплачивает через UI.
  4. Проверки: сообщение «Платёж не прошёл, попробуйте ещё раз» видно; GET /api/orders/:id → status: created; мок-шлюз получил ровно один запрос с правильной суммой ().
  5. Отдельный ночной тест проходит оплату через песочницу реального провайдера — подтверждая, что интеграция действительно работает.

Типичные ошибки#

Мокать то, что проверяется

Тест сервиса заказов, где подменён сам расчёт суммы заказа, ничего не проверяет. Подменяют соседей, а не предмет проверки.

Мок, который никогда не сверяется с реальностью

Без контрактных проверок моки «застывают» в прошлой версии API. Тесты зелёные, интеграция сломана.

Случайные данные без воспроизводимости

Тест, который генерирует случайный ввод и иногда падает, невозможно отладить без seed. Фиксируйте и логируйте seed.

Общий сид, который тесты изменяют

Если тест меняет «товар из сида», другие тесты получают неожиданные данные, и результат зависит от порядка. Изменяемые сущности тест создаёт сам.

Что важно для собеседования#

JuniorЧем отличаются stub, mock, spy и fake?

Ответ

возвращает заранее заданные ответы. записывает вызовы для проверки в тесте. Mock заранее содержит ожидания вызовов и сам их проверяет. Fake — упрощённая работающая реализация (in-memory база). Dummy — заглушка, которая только передаётся. Stub обеспечивает состояние, mock и Spy — проверку взаимодействия.

MiddleЧто вы подменяете в тестах, а что нет?

Ответ

Подменяю зависимости, которые не являются предметом проверки и которые я не контролирую: внешние платёжные шлюзы, SMS, карты, аналитику, а также время и случайность. Не подменяю проверяемый компонент. Чтобы моки не расходились с реальностью — контрактные тесты, валидация моков схемой и небольшой набор интеграционных тестов с песочницами провайдеров.

MiddleКакую стратегию тестовых данных вы бы выбрали для нового проекта?

Ответ

Справочники и неизменяемые данные — сидом при подъёме окружения; изменяемые сущности — тест создаёт сам через API в фикстурах и удаляет в teardown; уникальность через метку прогона и UUID; генераторы с фиксированным seed; периодическая уборка по метке на случай прерванных прогонов. Копии продакшена — только обезличенные и по необходимости.

Middle+Как сделать тест детерминированным, если он зависит от времени и внешних сервисов?

Ответ

Время: в браузере page.clock, на сервере — конфигурируемые часы тестового окружения или данные относительно текущей даты. Внешние сервисы — мок-серверы с управляемыми режимами. Случайность — seed, записанный в отчёт. Данные — свои, с уникальной меткой. Окружение — фиксированные timezone и locale. Порядок — явная сортировка или сравнение множеств.

Middle+Где в тестовом окружении вы поставите моки, а где оставите настоящие сервисы?

Ответ

Подменяю то, что не контролирую и что делает тесты медленными, дорогими или нестабильными: внешние платёжные шлюзы, SMS, почту, сторонние API, — через мок-сервер на сетевой границе (WireMock в Compose), чтобы приложение работало без изменений кода. Собственные сервисы команды оставляю настоящими: иначе проверяем мок, а не систему. Соответствие моков реальности поддерживается контрактами или регулярными проверками против песочниц провайдеров. В UI-тестах перехват сети — для редких состояний (ошибки, пустые списки), а не для всего.

Проверьте себя#

Тест
1
Объект возвращает фиксированный курс валют и больше ничего не делает. Как он называется?

Stub даёт заранее заданный ответ. Spy дополнительно записывает вызовы, Fake — упрощённая работающая реализация.

2
Что лучше всего подходит для проверки реакции сервиса на таймаут внешнего платёжного шлюза?

Мок-сервер даёт управляемое и воспроизводимое состояние, которое у реального провайдера получить нельзя.

3
Тест с генерацией случайных данных упал один раз из ста. Что нужно было сделать заранее?

Зная seed, можно точно воспроизвести данные упавшего прогона.

Чем stub отличается от mock в строгом смысле?

только подставляет ответы, чтобы код мог выполниться; проверки делаются по результату. Mock заранее знает, какие вызовы должны произойти (сколько раз, с какими аргументами), и сам проверяет это — тест падает при неожиданном взаимодействии. Mock проверяет поведение (взаимодействие), Stub обеспечивает состояние.

Какие данные стоит залить сидом, а какие создавать в тесте?

Сидом — неизменяемые справочники и конфигурацию: категории, страны, тарифы, роли. Создавать в тесте — всё, что тест изменяет или проверяет: пользователей, заказы, корзины, платежи. Так тесты быстры и при этом не мешают друг другу.
