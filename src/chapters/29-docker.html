Docker

Образы, контейнеры, Dockerfile, Docker Compose, тома и сети — и как запускать в контейнере само приложение, его зависимости и автотесты, чтобы окружение было одинаковым у всех и в CI.

≈ 9 мин чтенияM
Опирается на: Веб-архитектураGit и Linux
Основная идея

Docker упаковывает программу вместе с окружением в образ, из которого запускаются одинаковые контейнеры где угодно. Для AQA это значит: «у меня работает» перестаёт быть отговоркой — тесты, браузеры и тестируемая система везде одних версий.

Цель главы: собрать образ для тестов, поднять тестовое окружение через Docker Compose и правильно связать контейнеры сетью и томами.

Кратко

Образ — шаблон, контейнер — запущенный экземпляр. Compose описывает многоконтейнерное окружение: сервисы, сеть, тома, порядок запуска и проверки готовности.

Главное

  • : FROM → WORKDIR → COPY зависимостей → RUN установка → COPY кода → CMD. Слои кэшируются, поэтому зависимости копируют раньше кода.
  • Для тестов — официальный образ той же версии, что пакет в проекте (mcr.microsoft.com/playwright:v1.58.2-noble; тег берите по версии из package-lock.json).
  • localhost внутри контейнера — это сам контейнер. Другие сервисы Compose доступны по имени сервиса: http://app:3000.
  • Running ≠ readiness: depends_on с condition: service_healthy и healthcheck ждут готовности приложения, а не старта процесса.
  • Chromium в контейнере: рекомендуется --ipc=host (или увеличенный shm_size) и --init.

Термины

Docker Image
Неизменяемый шаблон из слоёв файловой системы с программой, зависимостями и настройками запуска; из него создаются контейнеры.
Dockerfile
Файл с инструкциями FROM, WORKDIR, COPY, RUN, ENV, CMD, по которым собирается образ; каждая инструкция — кэшируемый слой.
Docker Compose
Инструмент описания и запуска многоконтейнерного окружения в одном YAML-файле: сервисы, сети, тома, зависимости и проверки готовности.
Docker Network
Виртуальная сеть контейнеров; в сети Compose сервисы доступны друг другу по именам сервисов.
Healthcheck
Команда, по которой Docker определяет, готов ли сервис принимать запросы; используется в depends_on с condition: service_healthy.

Важно: Контейнер «запущен» ≠ сервис «готов». Тесты, стартующие сразу после запуска базы, получат ECONNREFUSED — нужен healthcheck.

Образы и контейнеры#

— неизменяемый шаблон: файловая система с программой, библиотеками и настройками запуска. — запущенный из образа изолированный процесс со своей файловой системой, сетью и переменными окружения. Из одного образа можно запустить сколько угодно одинаковых контейнеров.

Образы хранятся в : Docker Hub, GitLab Container Registry, Microsoft Container Registry (mcr.microsoft.com). Имя образа включает тег версии: postgres:16, mcr.microsoft.com/playwright:v1.58.2-noble.

Shell
docker pull postgres:16                         # скачать образ
docker images                                   # локальные образы
docker run -d --name db -e POSTGRES_PASSWORD=pw -p 5432:5432 postgres:16   # запустить контейнер в фоне
docker ps                                       # запущенные контейнеры
docker logs -f db                               # логи контейнера
docker exec -it db psql -U postgres             # выполнить команду внутри контейнера
docker stop db && docker rm db                  # остановить и удалить

Чем контейнер отличается от виртуальной машины: контейнеры используют ядро хост-системы, поэтому стартуют за секунды и занимают мало ресурсов; виртуальная машина эмулирует целый компьютер со своей ОС.

Dockerfile#

— инструкция сборки образа. Образ для запуска тестов:

DockerfileDockerfile
# Версия образа совпадает с версией @playwright/test в package.json
FROM mcr.microsoft.com/playwright:v1.58.2-noble

WORKDIR /tests

# Сначала только файлы зависимостей: слой с npm ci кэшируется,
# пока package*.json не изменились
COPY package.json package-lock.json ./
RUN npm ci

# Затем код тестов
COPY . .

ENV CI=true
CMD ["npx", "playwright", "test"]
Текст.dockerignore
node_modules
test-results
playwright-report
allure-results
.env
playwright/.auth
.git
Shell
docker build -t shop-tests:local .
docker run --rm --ipc=host --init \
  -e BASE_URL=https://staging.shop.example.com \
  -v "$(pwd)/playwright-report:/tests/playwright-report" \
  shop-tests:local

Пояснения:

  • Порядок инструкций определяет кэширование: каждая инструкция — слой, и если файлы для слоя не изменились, Docker берёт его из кэша. Код меняется часто, зависимости — редко, поэтому COPY package*.json и npm ci идут раньше COPY . ..
  • Официальный образ уже содержит браузеры и системные библиотеки нужной версии. Версия образа должна совпадать с версией пакета, иначе Playwright не найдёт подходящие браузеры.
  • --ipc=host рекомендуется для Chromium: без него браузеру может не хватить общей памяти (/dev/shm) и он упадёт. --init корректно завершает дочерние процессы.
  • .dockerignore исключает лишнее и секреты из контекста сборки.

Тома#

Файловая система контейнера исчезает вместе с ним. связывает данные контейнера с внешним хранилищем:

Вид Пример Для чего
Bind mount -v $(pwd)/playwright-report:/tests/playwright-report Забрать отчёты и артефакты на хост; смонтировать код при разработке
Именованный том -v pgdata:/var/lib/postgresql/data Данные БД переживают пересоздание контейнера
tmpfs --tmpfs /tmp Быстрые временные данные в памяти

Для тестов главное — забрать артефакты: отчёт, trace, скриншоты, JUnit. Иначе после завершения контейнера в CI ничего не останется.

Сети#

Контейнеры общаются через . Ключевое правило:

localhost внутри контейнера — это сам контейнер

Если тесты в контейнере обращаются к http://localhost:3000, они ищут приложение в своём же контейнере и получают ECONNREFUSED. В сети сервисы доступны по имени сервиса: http://app:3000, postgres://db:5432. Порты ports: публикуются для доступа с хоста, а внутри сети сервисы общаются по внутренним портам.

Чтобы контейнер обратился к сервису на хост-машине (например, к приложению, запущенному разработчиком локально), используют имя host.docker.internal (в Linux — с параметром --add-host=host.docker.internal:host-gateway).

Docker Compose#

описывает многоконтейнерное окружение в одном YAML-файле и поднимает его одной командой:

YAMLdocker-compose.yml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: pw
      POSTGRES_DB: shop
    volumes:
      - ./db/seed.sql:/docker-entrypoint-initdb.d/seed.sql:ro   # сид при первом запуске
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d shop"]
      interval: 2s
      timeout: 3s
      retries: 20

  app:
    image: registry.example.com/shop/app:${APP_VERSION:-latest}
    environment:
      DATABASE_URL: postgres://postgres:pw@db:5432/shop        # db — имя сервиса
      PAYMENT_GATEWAY_URL: http://payments-mock:8080
    depends_on:
      db:
        condition: service_healthy                             # ждать готовности БД
      payments-mock:
        condition: service_started
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost:3000/api/health"]
      interval: 3s
      retries: 30
    ports:
      - "3000:3000"                                            # доступ с хоста для отладки

  payments-mock:
    image: wiremock/wiremock:3.9.1
    volumes:
      - ./mocks/payments:/home/wiremock

  tests:
    build: .
    environment:
      BASE_URL: http://app:3000                                # не localhost!
      CI: "true"
    depends_on:
      app:
        condition: service_healthy
    ipc: host
    init: true
    volumes:
      - ./playwright-report:/tests/playwright-report
      - ./test-results:/tests/test-results
Shell
docker compose up -d db app payments-mock        # поднять окружение
docker compose run --rm tests                    # запустить тесты; код выхода = результат
docker compose run --rm tests npx playwright test --grep @smoke
docker compose logs app                          # логи приложения при разборе падений
docker compose down -v                           # всё удалить вместе с томами

— команда, по которой Docker определяет, готов ли сервис. Без него depends_on ждёт только запуска контейнера: база ещё инициализируется, а тесты уже стучатся и падают.

Интерактив требует JavaScriptКонтейнерное окружение для тестов: переключайте настройки (BASE_URL localhost или имя сервиса, Healthcheck, общая сеть, том для отчётов, ipc=host) и смотрите, что произойдёт при запуске тестов.

Readiness и сеть контейнеров#

Running означает, что процесс запущен; — что приложение готово принять нужный запрос. должен проверять значимую готовность, а не только наличие PID. Короткий depends_on задаёт порядок старта, но не ожидает готовность; service_healthy ожидает успешную проверку зависимости.

Из контейнера тестов localhost — сам контейнер тестов. В общей Compose network приложение доступно по имени сервиса, например http://app:3000. С хоста используется опубликованный порт, например http://localhost:3000. Host networking имеет особенности платформ и конфигурации; основной маршрут здесь использует Compose network.

docker run IMAGE создаёт и запускает новый контейнер из образа. docker start запускает существующий, docker exec выполняет команду в запущенном. В docker run указывают образ, а не идентификатор контейнера.

Локальный проект можно скачать в главе «Первый запуск». Его app имеет /ready и Healthcheck; сервис tests зависит от service_healthy. После запуска сохраните logs и reports, затем остановите окружение.

Запуск тестов в контейнере: варианты#

Вариант Как Когда
Тесты в контейнере, приложение на стенде docker run … -e BASE_URL=https://staging… Единое окружение тестов в CI и локально
Всё в Compose docker compose run tests Эфемерное окружение на MR, полная изоляция
Тесты на хосте, зависимости в Compose docker compose up -d db app, затем npx playwright test Разработка и отладка тестов
CI-задача сразу в образе image: mcr.microsoft.com/playwright:… в задаче CI Самый простой вариант для CI (глава 28)

Пример: «у меня проходит, а в CI нет»#

Тест визуального сравнения проходит на macOS разработчика и падает в CI: различие шрифтов и сглаживания.

  1. Эталоны пересоздаются в контейнере той же версии, что в CI: docker run --rm --ipc=host -v "$(pwd)":/tests -w /tests mcr.microsoft.com/playwright:v1.58.2-noble npx playwright test --update-snapshots --grep @visual
  2. CI запускает тесты в том же образе.
  3. Скрипт npm run test:visual:update фиксирует команду для команды.

Теперь эталоны и проверки рендерятся в идентичном окружении.

Типичные ошибки#

BASE_URL=http://localhost:3000 в контейнере тестов

Контейнер ищет приложение у себя. Используйте имя сервиса Compose.

Разные версии образа Playwright и пакета

Образ v1.56 и пакет 1.58 — не найдёт нужные сборки браузеров. Обновляйте вместе.

Тег latest для зависимостей

Сегодняшний latest завтра станет другим образом — окружение поменяется без изменений в коде. Фиксируйте версии.

Секреты в образе

COPY .env или ENV ADMIN_PASSWORD=… в — секрет навсегда в слоях образа и в реестре. Передавайте секреты при запуске (-e, secrets CI).

Что важно для собеседования#

JuniorЧем образ отличается от контейнера?

Ответ

Образ — неизменяемый шаблон из слоёв (программа, зависимости, настройки запуска). Контейнер — запущенный из образа изолированный процесс со своей файловой системой и сетью. Из одного образа можно запустить много одинаковых контейнеров; изменения в контейнере не меняют образ.

MiddleТесты в контейнере не могут достучаться до приложения в соседнем контейнере. Что проверите?

Ответ

Что тесты обращаются к сервису по имени из Compose (http://app:3000), а не к localhost (это сам контейнер тестов); что контейнеры в одной сети; внутренний порт сервиса (публикация ports нужна только для хоста); готовность сервиса — и depends_on: condition: service_healthy; логи приложения (docker compose logs app).

MiddleКак запускать Playwright-тесты в Docker?

Ответ

Официальный образ mcr.microsoft.com/playwright той же версии, что пакет; в сначала package*.json и npm ci (кэш слоя), затем код; .dockerignore без node_modules, отчётов и секретов. Запуск с --ipc=host и --init, переменные окружения (BASE_URL) и секреты — при запуске, отчёты и trace — томом наружу. В CI можно запускать задачу сразу в этом образе.

MiddleЗачем healthcheck в Docker Compose для тестового окружения?

Ответ

depends_on без условий ждёт только запуска контейнера, а не готовности сервиса: база ещё инициализируется, приложение ещё применяет миграции, а тесты уже стартуют и получают ECONNREFUSED или 502. Healthcheck (pg_isready, /api/health) и condition: service_healthy запускают тесты только после реальной готовности.

Проверьте себя#

Тест
1
Тесты в контейнере Compose получают ECONNREFUSED на http://localhost:3000, хотя приложение запущено. Почему?

Внутри сети Compose сервисы доступны по именам. Публикация порта нужна только для доступа с хоста.

2
Зачем в Dockerfile копировать package.json отдельно перед COPY . .?

Изменение кода тестов не инвалидирует кэш слоя npm ci, и сборка идёт быстрее.

3
Что делает depends_on с condition: service_healthy?

Без условия Compose ждёт только старта контейнера, а не готовности сервиса.

Почему отчёты тестов нужно выносить из контейнера томом?

Файловая система контейнера удаляется вместе с ним (--rm, compose down). Без тома HTML-отчёт, trace и скриншоты пропадут, и в CI нечего будет сохранить как артефакты.

Когда удобнее запускать тесты на хосте, а не в контейнере?

При разработке и отладке тестов: быстрый цикл правки, видимый браузер (--headed), UI Mode, отладчик IDE. Зависимости (БД, моки, приложение) при этом удобно держать в Compose. В CI и для визуальных тестов — в контейнере, чтобы окружение совпадало.
