Git и Linux

Основные команды Git, ветки, Merge Request, rebase и merge, разрешение конфликтов, а также базовые команды Linux, без которых не обойтись при работе с CI, контейнерами и логами.

≈ 11 мин чтенияJ
Основная идея

Тестовый проект — такой же код, как продукт: изменения идут через ветки, ревью и CI. А CI-агенты и контейнеры работают на Linux, поэтому разбор падений часто начинается с терминала.

Цель главы: уверенно вести изменения в тестовом репозитории через ветку и Merge Request, разрешать конфликты и выполнять базовую диагностику в Linux.

Кратко

хранит историю как граф коммитов; ветка — подвижный указатель на коммит. Изменения в общий код попадают через с ревью и зелёным CI.

Главное

  • Три области: рабочая директория → индекс (git add) → история (git commit).
  • Ветка на задачу: git switch -c feature/…, частые небольшие коммиты, git push -u origin …, затем Merge Request.
  • Merge сохраняет историю и создаёт коммит слияния; rebase переносит ваши коммиты поверх свежего main и делает историю линейной. Не делайте rebase опубликованных общих веток.
  • Конфликт — Git не может автоматически совместить изменения одних строк; разрешается правкой файла между маркерами <<<<<<<, =======, >>>>>>>.
  • git revert безопасно отменяет опубликованный коммит новым коммитом; git reset --hard переписывает историю и удаляет несохранённые изменения.
  • Linux для AQA: логи (tail -F, grep), процессы и порты (ps, ss), права (chmod), curl для проверки API. Zombie-процесс сигналом не завершить — разбирайтесь с родителем.

Термины

Git
Распределённая система контроля версий: хранит историю изменений как граф коммитов и позволяет вести параллельную работу в ветках.
Commit
Снимок состояния проекта с автором, датой, сообщением и ссылкой на родительский коммит.
Merge Request
Предложение влить изменения ветки в основную с обсуждением, ревью и проверкой CI. В GitHub называется Pull Request.
Rebase
Перенос коммитов ветки поверх другого коммита (обычно свежего main) с созданием новых коммитов; даёт линейную историю.
Merge Conflict
Ситуация, когда обе стороны изменили одни и те же строки и Git не может совместить изменения автоматически.

Важно: Никогда не коммитьте .env, токены и пароли. Даже удалённый в следующем коммите секрет остаётся в истории и считается скомпрометированным.

Основы Git#

— распределённая система контроля версий. Каждый — снимок проекта с автором, датой, сообщением и ссылкой на родительский коммит. Коммиты образуют граф; Branch — подвижный указатель на последний коммит линии разработки; HEAD — где вы находитесь сейчас.

Файл проходит три области:

Область Как попасть Команда для просмотра
Рабочая директория Изменить файл git status, git diff
Индекс (staging area) git add <файл> git diff --staged
История git commit -m "…" git log --oneline --graph

Удалённый репозиторий (origin на GitLab или GitHub) синхронизируется командами fetch, pull, push.

Основные команды#

Shell
git clone git@gitlab.example.com:qa/shop-tests.git   # получить репозиторий
git status                                           # что изменено и что в индексе
git switch -c feature/QA-142-cart-tests              # создать ветку и перейти в неё
git add tests/cart.spec.ts                           # добавить файл в индекс
git add -p                                           # добавить изменения по частям (интерактивно)
git commit -m "test(cart): проверка пересчёта суммы при изменении количества"
git fetch origin                                     # получить изменения без слияния
git rebase origin/main                               # перенести свои коммиты на свежий main
git push -u origin feature/QA-142-cart-tests         # отправить ветку
git log --oneline --graph -15                        # компактная история
git diff main...HEAD                                 # что изменилось в ветке относительно main
git stash push -m "wip"                              # временно убрать незакоммиченные изменения
git stash pop                                        # вернуть их
git restore tests/cart.spec.ts                       # отменить изменения файла в рабочей директории
git revert 3f2a1c9                                   # отменить опубликованный коммит новым коммитом
git blame tests/cart.spec.ts                         # кто и когда менял каждую строку
Команды, переписывающие историю

git reset --hard, git rebase, git commit --amend, git push --force меняют уже существующие коммиты. Это нормально для своей ветки до ревью, но опасно для общих веток: у коллег останется старая история. Если нужно перезаписать свою опубликованную ветку, используйте git push --force-with-lease — он откажется, если в удалённой ветке появились чужие коммиты.

.gitignore для тестового проекта#

перечисляет файлы, которые не должен отслеживать. Для проекта на Playwright:

Текст.gitignore
node_modules/
test-results/
playwright-report/
blob-report/
allure-results/
allure-report/
playwright/.auth/
.env
.env.*
!.env.example
*.log

playwright/.auth/ содержит сохранённые cookies и токены авторизации — это секреты. .env.example с пустыми значениями, наоборот, коммитят: он документирует нужные переменные.

Рабочий процесс AQA: ветка и Merge Request#

Типичный путь изменения в тестовом проекте:

  1. Задача. QA-142: «Покрыть пересчёт корзины».
  2. Свежий main. git switch main && git pull.
  3. Ветка. git switch -c feature/QA-142-cart-tests.
  4. Изменения и локальная проверка. npx tsc --noEmit, npx eslint ., npx playwright test tests/cart.spec.ts --repeat-each=5 — повтор помогает поймать нестабильность до ревью.
  5. Коммиты. Небольшие, с понятными сообщениями.
  6. Синхронизация. git fetch && git rebase origin/main, разрешить конфликты, если есть.
  7. Push и . Описание: что покрыто, как запускать, ссылка на задачу.
  8. CI. прогоняет линтер, проверку типов и тесты (глава 28).
  9. Ревью. Коллега проверяет читаемость, устойчивость локаторов, независимость тестов, отсутствие секретов.
  10. Слияние в main после зелёного Pipeline и одобрения.
Интерактив требует JavaScriptGit workflow: пошагово проведите изменение тестов через ветку, коммиты, обновление от main (merge или Rebase), конфликт и Merge Request; граф коммитов обновляется на каждом шаге.

Merge и rebase#

Пока вы работали в ветке, в main появились чужие коммиты. Есть два способа совместить истории:

  • Merge (git merge origin/main) создаёт коммит слияния с двумя родителями. История честная («было параллельно»), ничего не переписывается, но граф ветвится.
  • (git rebase origin/main) пересоздаёт ваши коммиты поверх свежего main. История линейная, как будто вы начали работу только что. Хеши ваших коммитов меняются.

Практика многих команд: Rebase своей ветки перед , а в main — merge (или squash-merge, который сжимает ветку в один коммит).

Конфликты#

возникает, когда обе стороны изменили одни и те же строки, и не может выбрать за вас.

Diff
  test('итог корзины', async ({ page }) => {
<<<<<<< HEAD
    await expect(page.getByTestId('cart-total')).toHaveText('9 980 ₽');
=======
    await expect(page.getByTestId('order-total')).toHaveText('9 980 ₽');
>>>>>>> feature/QA-142-cart-tests
  });

Между <<<<<<< и ======= — версия текущей ветки (при — это уже main с применёнными коммитами), между ======= и >>>>>>> — входящие изменения. Как разрешить:

  1. Понять смысл обоих изменений. Здесь в main переименовали data-testid, а в ветке написали тест со старым именем.
  2. Отредактировать файл до правильного итогового состояния и удалить маркеры.
  3. git add <файл>, затем git rebase --continue (или git commit при merge).
  4. Запустить затронутые тесты — разрешённый конфликт легко оставляет неработающий код.

Если запутались: git rebase --abort или git merge --abort вернёт всё как было до начала.

Сообщения коммитов#

Хорошее сообщение объясняет что и зачем: test(checkout): проверка отказа оплаты при просроченной карте. Популярный формат — Conventional Commits: тип(область): описание, где тип — test, fix, feat, refactor, chore, ci. Плохие сообщения: fix, wip, tests, asdf — по ним невозможно понять историю через полгода.

Linux для автотестировщика#

CI-агенты, Docker-контейнеры и тестовые серверы почти всегда работают на Linux. Минимальный набор команд :

Shell
# Навигация и файлы
pwd                      # где я
ls -la                   # содержимое каталога, включая скрытые файлы
cd tests/ && cd ..       # перейти в каталог и обратно
cat playwright.config.ts # вывести файл
less app.log             # постраничный просмотр (q — выход, / — поиск)
head -n 50 app.log       # первые 50 строк
tail -n 100 -f app.log   # последние 100 строк и следить за новыми
mkdir -p reports/2026    # создать каталог со всеми родительскими
cp -r fixtures/ /tmp/    # копировать рекурсивно
mv old.ts new.ts         # переместить или переименовать
rm -rf test-results/     # удалить рекурсивно, без подтверждения — осторожно!

# Поиск
grep -rn "getByTestId('cart" tests/        # поиск текста в файлах с номерами строк
grep -i "error" app.log | grep -v "favicon" # фильтрация конвейером
find . -name "*.spec.ts" -newer package.json # найти файлы по имени и дате

# Конвейеры и перенаправление
npx playwright test 2>&1 | tee run.log      # вывод и на экран, и в файл
grep -c "passed" run.log                     # посчитать строки
cat results.json | jq '.stats'               # разбор JSON (если установлен jq)

# Процессы, порты, ресурсы
ps aux | grep node        # процессы node
lsof -i :3000             # кто занял порт 3000
kill 12345                # завершить процесс (kill -9 — принудительно)
df -h                     # свободное место на дисках
du -sh test-results/      # размер каталога
free -h                   # память

# Сеть и HTTP
curl -i https://staging.shop.example.com/api/health          # ответ с заголовками
curl -s -X POST -H "Content-Type: application/json" \
     -d '{"email":"qa@example.com"}' https://staging.shop.example.com/api/users

# Права и переменные окружения
chmod +x scripts/run-tests.sh    # сделать скрипт исполняемым
export BASE_URL=https://staging.shop.example.com
echo $BASE_URL
env | grep -i playwright

— основной способ передать тестам конфигурацию: адрес стенда, учётные данные, флаги. Переменная, установленная export, видна процессам, запущенным из этой оболочки, но не сохраняется после её закрытия.

Быстрая диагностика стенда из терминала

Прежде чем запускать сотню тестов на новом стенде: curl -i $BASE_URL/api/health (жив ли сервис, какой код), nslookup или dig имени (), curl -v для деталей TLS. Это занимает секунды и экономит минуты красного прогона.

Linux: права, процессы и логи на практике#

ЗадачаКоманда / механизмПояснение
Рекурсивные праваchmod -R u+rwX ./test-data-R — рекурсия; X добавляет execute каталогам и уже исполняемым файлам
Выполнение владельцуchmod u+x run.shМеняет бит; не создаёт файл и не забирает execute у других

Процесс по имениpgrep -af nodeИмя и аргументы, без собственного grep
Время жизниps -p PID -o pid,stat,etime,time,argsetime — прошедшее время; time — накопленный
Логиtail -n 100 -F app.log-F учитывает переоткрытие файла при ротации
Сервисsystemctl status appstop останавливает; disable убирает автозапуск
Журнал сервисаjournalctl -u app --since "1 hour ago"Выбор периода; -p err показывает ошибки и более высокую важность

Для каталога r позволяет читать список имён, x — проходить по пути, w вместе с x — менять записи каталога. Sticky bit дополнительно ограничивает удаление в общих каталогах. Числовые права складываются из r=4, w=2, x=1; пример rw-/r-x/--- даёт 650.

Zombie — уже завершившийся процесс с записью, чей статус ещё не забрал родитель. SIGKILL самому zombie не помогает. Диагностируйте родителя и обработку wait; не превращайте убийство родителя в обычный способ очистки. Orphan принимает init/subreaper, не обязательно именно systemd.

Сначала используйте SIGTERM для корректного завершения; SIGKILL не даёт выполнить cleanup. Высокий CPU не доказывает зависание; отсутствие CPU — не доказательство zombie. /dev содержит файлы устройств, /etc — конфигурацию, /proc — псевдофайловую систему сведений о процессах и ядре.

cat не «убивает систему» сам по себе. Для больших файлов удобнее head, tail, less. В Vim :q! выходит без сохранения, :wq сохраняет и выходит. В Linux не требуется фиксированное число дисковых разделов.

Shell: > перезаписывает stdout, >> дописывает, 2> перенаправляет stderr. После команды echo $? показывает её exit code. В скриптах пайплайн может скрывать ошибку первого процесса; Bash set -o pipefail меняет это поведение.

Пример: исправление теста после переименования#

Утром упали 12 тестов корзины: strict mode violation и element not found для getByTestId('cart-total').

Shell
git switch main && git pull
git log --oneline -10 -- src/components/Cart.tsx   # (в репозитории продукта) что меняли
grep -rln "cart-total" tests/                       # какие тесты используют старый test id
git switch -c fix/QA-150-cart-testid
# правим локатор в одном месте — page object CartPage
npx playwright test tests/cart --repeat-each=3
git commit -am "fix(cart): новый data-testid итоговой суммы order-total"
git push -u origin fix/QA-150-cart-testid

Благодаря тому, что локатор хранится в object (глава 17), правка затрагивает одну строку, а не 12 файлов.

Типичные ошибки#

Коммит секретов

.env, storageState с токенами, пароли в конфиге. Удаление в следующем коммите не помогает — секрет остаётся в истории. Его нужно отозвать и заменить.

git push --force в общую ветку

Перезаписывает историю для всех. Используйте --force-with-lease и только для своих веток.

Огромный Merge Request

200 изменённых файлов невозможно качественно проверить. Делите изменения: рефакторинг отдельно, новые тесты отдельно.

Разрешить конфликт и не запустить тесты

Синтаксически корректный файл после конфликта может логически сломать тест. Всегда прогоняйте затронутые тесты.

Что важно для собеседования#

JuniorЧем merge отличается от rebase?

Ответ

Merge объединяет истории коммитом слияния с двумя родителями и ничего не переписывает. переносит мои коммиты поверх целевой ветки, создавая новые коммиты, — история линейная, но хеши меняются. Rebase делаю для своей ветки перед MR; общие опубликованные ветки не перебазирую.

JuniorКак разрешить конфликт слияния?

Ответ

Посмотреть конфликтующие файлы (git status), понять смысл обеих версий между маркерами <<<<<<<, =======, >>>>>>>, привести файл к правильному итоговому состоянию, удалить маркеры, git add, затем git rebase --continue или git commit. Обязательно прогнать затронутые тесты. Если запутался — --abort и начать заново.

JuniorОпишите ваш процесс внесения изменений в тестовый проект.

Ответ

Обновляю main, создаю ветку под задачу, пишу тесты небольшими коммитами, локально запускаю проверку типов, линтер и новые тесты (с --repeat-each для проверки стабильности), обновляю ветку от main, пушу и создаю MR с описанием и ссылкой на задачу. После зелёного и ревью — слияние.

JuniorКакие команды Linux вы используете при разборе падений?

Ответ

tail -f и less для логов, grep -rn для поиска, конвейеры с |, ps/lsof -i :порт для процессов и занятых портов, df -h/du -sh для места на диске (частая причина падений CI), curl -i для проверки доступности API, env для переменных окружения, chmod +x для скриптов.

MiddleЧем git revert отличается от git reset?

Ответ

revert создаёт новый коммит, отменяющий изменения выбранного, — безопасно для опубликованной истории. reset перемещает указатель ветки назад: --soft оставляет изменения в индексе, --mixed — в рабочей директории, --hard удаляет их. Reset опубликованных коммитов требует force push и ломает историю коллегам.

Проверьте себя#

Тест
1
Какая команда безопасно отменяет уже опубликованный в main коммит?

revert создаёт новый коммит, отменяющий изменения, не переписывая историю, которой уже пользуются другие.

2
Чем rebase отличается от merge при обновлении своей ветки от main?

При Rebase меняются хеши ваших коммитов, поэтому его не делают с общими опубликованными ветками.

3
Как посмотреть последние строки лога приложения и следить за новыми?

tail -f выводит конец файла и продолжает показывать добавляемые строки.

Что делать, если секрет случайно попал в коммит, уже отправленный в удалённый репозиторий?

Считать секрет скомпрометированным: немедленно отозвать и заменить токен или пароль. Затем удалить файл из репозитория и добавить в .gitignore. Переписывание истории ( filter-repo) возможно, но не отменяет утечку — копии могли попасть к другим людям и в CI-кэши.

Почему перед Merge Request полезно запустить изменённые тесты с --repeat-each?

Однократное прохождение не доказывает стабильность. Повтор теста несколько раз подряд выявляет гонки и зависимость от данных до того, как нестабильный тест попадёт в main и начнёт мешать всей команде.
