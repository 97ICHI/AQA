Assertions и Synchronization

Web-first assertions, автоожидание действий, явные ожидания событий, таймауты и механизмы повторов. Главная тема для стабильности UI-тестов: как дождаться нужного состояния приложения, а не «подождать на всякий случай».

≈ 12 мин чтенияJ–M
Опирается на: LocatorsАсинхронность
Основная идея

Веб-приложение асинхронно: после клика данные приходят через десятки или тысячи миллисекунд. Стабильный тест не угадывает время, а ждёт конкретного состояния — видимости, текста, URL, ответа сервера — с разумным таймаутом.

Цель главы: писать проверки, которые сами дожидаются нужного состояния, выбирать правильный вид ожидания и понимать, как таймауты и повторы влияют на стабильность.

Кратко

Web-first assertions (await expect(locator).toHaveText(...)) повторяют проверку до таймаута; действия ждут готовности элемента. Фиксированные паузы делают тесты одновременно медленными и нестабильными.

Главное

  • Асинхронные проверки локаторов и страницы (toBeVisible, toHaveText, toHaveURL, toHaveCount…) ждут до expect.timeout (5 с по умолчанию).
  • Обычные проверки значений (toBe, toEqual, toContain) срабатывают один раз; expect(await locator.textContent()) — однократное чтение и гонка.
  • Перед действием проверяет actionability, набор проверок зависит от действия: для клика — виден, стабилен, принимает события, доступен; для fill — виден, доступен, редактируем.
  • События, которые не выражаются состоянием элемента, ждут явно (waitForResponse, waitForURL, waitForEvent); для произвольных условий — expect.poll и toPass. waitForTimeout — только для отладки, networkidle не рекомендуется.
  • Таймауты: тест — 30 с, expect — 5 с, действия и навигация — без отдельного лимита; ретраи теста — отдельный механизм поверх.
  • expect.soft продолжает тест после неудачной проверки и собирает все ошибки.

Термины

Assertion
Сравнение фактического результата с ожидаемым; при несовпадении тест падает. В Playwright — через expect.
Web-first Assertion
Проверка локатора или страницы, которая повторяет поиск и сравнение, пока условие не выполнится или не истечёт таймаут: toBeVisible, toHaveText, toHaveURL.
Actionability Checks
Условия, которые Playwright проверяет перед действием: элемент видим, стабилен, получает события, доступен и (для ввода) редактируем.
Timeout
Предел времени ожидания. В Playwright: тест — 30 с, expect — 5 с, действие и навигация — без отдельного лимита по умолчанию.
Soft Assertion
Проверка (expect.soft), которая не прерывает тест при неудаче: ошибки собираются, и тест помечается упавшим в конце.

Важно: Увеличение таймаутов и ретраев не делает тест стабильным: оно делает его медленнее и скрывает реальную гонку.

Что такое Assertion#

— проверка, которая сравнивает фактическое состояние с ожидаемым и при несовпадении выбрасывает ошибку. В проверки пишут через expect.

Важно различать два вида:

Вид Пример Как работает
Web-first (асинхронные) await expect(locator).toHaveText('Оплачен') Повторяет поиск элемента и проверку, пока условие не выполнится или не истечёт таймаут
Обычные (синхронные) expect(total).toBe(900) Проверяет значение один раз, сразу

— основа стабильных UI-тестов. Обычные проверки нужны для значений, которые уже получены и не меняются: тело ответа API, результат функции, вычисленное число.

Web-first assertions#

Проверка Что ждёт
toBeVisible() / toBeHidden() Элемент видим / скрыт или отсутствует
toHaveText(text \| RegExp \| string[]) Полное совпадение текста (с нормализацией пробелов)
toContainText(text) Текст содержит подстроку
toHaveValue(value) Значение поля ввода
toBeChecked(), toBeEnabled(), toBeDisabled(), toBeEditable(), toBeFocused() Состояние элемента
toHaveCount(n) Количество элементов, найденных локатором
toHaveAttribute(name, value), toHaveClass(), toHaveCSS() Атрибуты и стили
toHaveAccessibleName(), toHaveRole() Доступность
toHaveURL(url), toHaveTitle(title) URL и заголовок страницы
toHaveScreenshot() Визуальное сравнение со снимком
toBeOK() Ответ API в диапазоне 2xx (для APIResponse)
TypeScripttests/assertions.spec.ts
import { test, expect } from '@playwright/test';

test('оформление заказа', async ({ page }) => {
  await page.goto('/checkout');
  await page.getByRole('button', { name: 'Оплатить' }).click();

  await expect(page).toHaveURL(/\/orders\/\d+$/);
  await expect(page.getByRole('heading', { level: 1 })).toHaveText('Заказ оформлен');
  await expect(page.getByTestId('order-status')).toHaveText(/Оплачен|Ожидает подтверждения/);
  await expect(page.getByRole('listitem')).toHaveCount(2);
  await expect(page.getByRole('button', { name: 'Оплатить' })).toBeHidden();
  await expect(page.getByTestId('order-total'), 'итоговая сумма заказа').toHaveText('9 980 ₽');
});

Отрицание — через .not: await expect(locator).not.toBeVisible() тоже ждёт, пока элемент станет невидимым. Второй аргумент expect — сообщение, которое появится в отчёте при падении.

expect(text).toBe('Оплачен');
TypeScriptПроверка ждёт нужного состояния

Auto-waiting и actionability#

: перед действием сам ждёт, пока элемент будет готов. Набор проверок готовности — Actionability Checks — зависит от действия:

Действие Visible Stable Receives Events Enabled Editable
click, dblclick, check, uncheck, tap ✓ ✓ ✓ ✓
hover, dragTo ✓ ✓ ✓
fill, clear ✓ ✓ ✓
selectOption ✓ ✓
screenshot ✓ ✓
  • Visible — есть размеры, не visibility: hidden.
  • Stable — не анимируется (положение одинаково в двух соседних кадрах).
  • Receives Events — клик в эту точку попадёт в элемент, а не в перекрывающий его оверлей.
  • Enabled — не disabled.
  • Editable — можно вводить (не readonly).

Если условия не выполнены до таймаута, действие падает с подробным журналом: «element is not visible», «element is outside of the viewport», «<div class="overlay"> intercepts pointer events». Параметр force: true отключает часть проверок — используйте его осознанно: он может кликнуть по элементу, который пользователь кликнуть не может.

Что Auto-waiting не делает

Действие ждёт готовности элемента, но не завершения последствий. click() вернёт управление, когда клик выполнен, а не когда сервер ответил и страница обновилась. Последствия проверяют web-first assertions.

Explicit waiting#

нужно, когда ожидаемое состояние — не свойство элемента, а событие:

TypeScripttests/explicit-waits.spec.ts
import { test, expect } from '@playwright/test';

test('явные ожидания событий', async ({ page }) => {
  await page.goto('/reports');

  // Ответ сервера: ожидание создаётся ДО действия
  const saved = page.waitForResponse((r) => r.url().includes('/api/reports') && r.request().method() === 'POST');
  await page.getByRole('button', { name: 'Сформировать' }).click();
  expect((await saved).status()).toBe(202);

  // Скачивание файла
  const downloadPromise = page.waitForEvent('download');
  await page.getByRole('link', { name: 'Скачать CSV' }).click();
  const download = await downloadPromise;
  expect(download.suggestedFilename()).toMatch(/\.csv$/);

  // Переход на страницу
  await page.getByRole('link', { name: 'Все отчёты' }).click();
  await page.waitForURL('**/reports/all');

  // Элемент в нужном состоянии без проверки (например, перед замером)
  await page.getByTestId('chart').waitFor({ state: 'visible' });
});

Для произвольных условий есть два инструмента повторов:

TypeScripttests/poll.spec.ts
import { test, expect } from '@playwright/test';

test('асинхронная обработка заказа', async ({ request }) => {
  const res = await request.post('/api/orders', { data: { productId: 7, qty: 1 } });
  const { id } = (await res.json()) as { id: number };

  // expect.poll: повторять функцию, пока значение не станет ожидаемым
  await expect
    .poll(async () => {
      const r = await request.get(`/api/orders/${id}`);
      return ((await r.json()) as { status: string }).status;
    }, { message: 'заказ подтверждён', timeout: 15_000, intervals: [500, 1_000, 2_000] })
    .toBe('confirmed');

  // toPass: повторять блок с несколькими проверками целиком
  await expect(async () => {
    const r = await request.get(`/api/orders/${id}/invoice`);
    expect(r.status()).toBe(200);
    expect(r.headers()['content-type']).toContain('application/pdf');
  }).toPass({ timeout: 20_000 });
});
waitForTimeout и networkidle

await page.waitForTimeout(3000) — фиксированная пауза: на быстром стенде тратит время, на медленном — не дожидается. Используйте только при отладке. waitForLoadState('networkidle') ждёт отсутствия запросов 500 мс; в приложениях с аналитикой, опросом сервера и WebSocket это ненадёжно или бесконечно. Ждите конкретного состояния.

Таймауты#

— предел ожидания. В несколько уровней:

Таймаут По умолчанию Где задать Что при превышении
Тест (включая фикстуры с областью test, beforeEach/afterEach) 30 с timeout в конфиге, test.setTimeout(), test.slow() Тест падает: Test timeout of 30000ms exceeded
expect (web-first) 5 с expect.timeout, { timeout } в проверке Падает проверка
Действие (click, fill…) Нет отдельного use.actionTimeout Падает действие
Навигация (goto, waitForURL) Нет отдельного use.navigationTimeout Падает навигация
Весь прогон Нет globalTimeout Прогон прерывается
TypeScripttests/timeouts.spec.ts
import { test, expect } from '@playwright/test';

test('экспорт большого отчёта', async ({ page }) => {
  test.slow(); // утроить таймаут теста — осознанно, с причиной в названии
  await page.goto('/reports/yearly');
  await page.getByRole('button', { name: 'Экспорт' }).click();
  await expect(page.getByText('Отчёт готов')).toBeVisible({ timeout: 60_000 }); // точечно для долгой операции
});

Правило: таймаут увеличивают точечно для операции, которая заведомо долгая, а не глобально «чтобы перестало падать».

Retry Mechanisms#

В три разных механизма повторов — их часто путают:

  1. Повторы внутри — toHaveText перепроверяет элемент до таймаута expect. Это нормальная синхронизация.
  2. expect.poll / toPass — повтор произвольной функции или блока до успеха. Тоже синхронизация, но для условий вне DOM.
  3. — повтор всего упавшего теста (retries в конфиге). Это страховка, а не синхронизация. Прошедший со второй попытки тест помечается как flaky и требует разбора (глава 30).

Soft assertions#

(expect.soft) не прерывает тест при неудаче: ошибка запоминается, тест продолжается, а в конце помечается упавшим со всеми собранными ошибками.

TypeScripttests/soft.spec.ts
import { test, expect } from '@playwright/test';

test('профиль показывает все поля', async ({ page }) => {
  await page.goto('/account/profile');
  await expect.soft(page.getByLabel('Имя')).toHaveValue('Анна');
  await expect.soft(page.getByLabel('Email')).toHaveValue('anna@example.com');
  await expect.soft(page.getByLabel('Город')).toHaveValue('Москва');
  // Одна загрузка страницы — три независимые проверки в одном отчёте
});

Используйте soft-проверки для независимых проверок одного экрана. Не используйте, если следующие шаги без предыдущего результата бессмысленны.

Почему появляются Flaky Tests#

из-за синхронизации — самая частая категория:

Причина Симптом Исправление
Однократное чтение (textContent(), isVisible()) вместо web-first проверки Иногда старое значение await expect(locator).toHaveText(...)
Фиксированная пауза Падает на медленном CI Ожидание состояния или события
Ожидание ответа начато после действия Иногда таймаут ожидания Создать ожидания до действия
Клик до гидратации SPA (обработчик ещё не навешен) Клик «не сработал» Ждать признак готовности страницы; исправить приложение (кнопка disabled до готовности)
Анимация, оверлей, тост поверх кнопки intercepts pointer events Ждать исчезновения оверлея; addLocatorHandler
Забытый await Проверка после конца теста, случайные ошибки ESLint no-floating-promises

Типичные ошибки#

expect(await locator.isVisible()).toBe(true)

isVisible() проверяет состояние мгновенно, без ожидания. Используйте await expect(locator).toBeVisible().

Проверка «что-то произошло» вместо конкретного результата

toBeVisible() у контейнера результата пройдёт и тогда, когда в нём сообщение об ошибке. Проверяйте конкретный текст, значение, количество.

force: true для «непослушных» кликов

Клик сквозь оверлей проходит в тесте, хотя пользователь кликнуть не может. Это скрывает реальный дефект интерфейса.

Глобально поднять expect.timeout до 30 секунд

Каждая неудачная проверка будет ждать 30 секунд, прогон с дефектом станет очень долгим, а гонки останутся.

Что важно для собеседования#

JuniorЧем await expect(locator).toHaveText() отличается от expect(await locator.textContent()).toBe()?

Ответ

Первая — web-first: повторяет поиск элемента и сравнение до таймаута expect и дождётся обновления. Вторая читает текст один раз в текущий момент и сравнивает сразу — если страница ещё обновляется, тест получит старое значение. Это классическая причина нестабильности.

JuniorЧто такое auto-waiting в Playwright?

Ответ

Перед действием ждёт, пока элемент пройдёт проверки готовности: видим, стабилен (не анимируется), получает события (не перекрыт), доступен, а для ввода — редактируем. Web-first проверки повторяются до таймаута. Важно: действие не ждёт последствий (ответа сервера) — их проверяют assertions.

JuniorПочему waitForTimeout — плохая практика?

Ответ

Фиксированная пауза не связана с реальным состоянием: на быстром окружении тест тратит лишнее время, на медленном пауза оказывается мала — тест падает. В результате тест и медленный, и нестабильный. Нужно ждать конкретного состояния () или события (waitForResponse, waitForURL).

MiddleКакие таймауты есть в Playwright и как их правильно менять?

Ответ

Таймаут теста (30 с, включает фикстуры и хуки beforeEach/afterEach), таймаут expect (5 с), таймауты действий и навигации (по умолчанию без отдельного лимита), глобальный таймаут прогона. Меняю точечно: { timeout } у конкретной долгой проверки, test.slow() для заведомо долгого теста. Глобальное увеличение скрывает гонки и делает падения долгими.

MiddleКакие механизмы повторов есть в Playwright и чем они отличаются?

Ответ

Повторы внутри web-first проверок (синхронизация с UI), expect.poll и toPass (синхронизация с произвольными условиями: API, база, файлы) и ретраи всего теста (retries) — страховка от нестабильности, после которой тест помечается flaky. Первые два — нормальная часть теста, третий — сигнал проблемы.

Middle+Заказ обрабатывается асинхронно через очередь. Как проверить, что статус стал «confirmed»?

Ответ

expect.poll(() => getOrderStatus(id), { timeout, intervals }).toBe('confirmed') — с таймаутом, соответствующим SLA обработки, и понятным сообщением. Если нужно несколько связанных проверок — expect(async () => {...}).toPass(). Не waitForTimeout и не цикл с sleep. Если обработка регулярно не укладывается в SLA — это информация о продукте, а не повод поднять таймаут.

Проверьте себя#

Тест
1
Какая проверка дождётся, пока статус заказа сменится на «Оплачен»?

Web-first проверка повторяет поиск и сравнение до таймаута expect. Остальные варианты проверяют один раз или не проверяют вовсе.

2
Что Playwright проверяет перед click()?

Это actionability-проверки. Состояние сети и «загрузка страницы» не проверяются.

3
Тест прошёл со второй попытки благодаря retries: 2. Как его отметит Playwright?

Тест, который упал, а затем прошёл при повторе, получает статус flaky — сигнал к расследованию.

Почему waitForResponse после клика может падать, хотя запрос был?

Ожидание ловит только события после своего создания. Если ответ пришёл, пока тест выполнял await click(), ожидание, созданное позже, его не увидит и будет ждать до таймаута. Нужно создать ожидания до клика и дождаться его после.

Когда уместен expect.poll, а когда достаточно web-first проверки?

Web-first проверка — для состояния элементов страницы и самой страницы. expect.poll — для значений вне DOM: статус в API, запись в базе, файл, письмо в тестовом почтовом ящике, если они меняются асинхронно.
