Reporting и Logging

Встроенные репортеры Playwright, Allure Report, шаги и вложения, структурированные логи, скриншоты, видео и трассировки, анализ результатов прогона. Какой должна быть информация о падении, чтобы её хватало для диагноза без перезапуска.

≈ 10 мин чтенияM
Опирается на: Параллельность
Основная идея

Отчёт — интерфейс между автотестами и людьми. Хороший отчёт отвечает на три вопроса без запуска теста: что проверялось, что пошло не так и где искать причину. Если для ответа нужно перезапускать тест локально, отчёт не выполнил свою задачу.

Цель главы: настраивать репортеры и артефакты, оформлять шаги и вложения и проводить разбор результатов прогона.

Кратко

Репортеры превращают результаты в отчёты для людей (HTML, Allure) и машин (JUnit, ); шаги, вложения, скриншоты и trace делают каждое падение диагностируемым.

Главное

  • Встроенные репортеры: list, line, dot, html, json, junit, blob, github; можно указать несколько одновременно.
  • Allure: репортер allure-playwright пишет allure-results, allure generate/serve строят отчёт со шагами, вложениями, историей, категориями и метками.
  • test.step группирует действия в отчёте; testInfo.attach прикладывает данные (JSON ответа, лог, файл).
  • Артефакты падения: скриншот (only-on-failure), видео (retain-on-failure), trace (on-first-retry/retain-on-failure).
  • Структурированные логи: уровень, время, тест, шаг, идентификаторы данных и correlation id запросов — без секретов.
  • Разбор прогона: классифицировать каждое падение (дефект продукта, ошибка теста, данные, окружение), начинать с первичной ошибки, версии и данных; повтор запуска проверяет гипотезу, но не заменяет диагностику.

Термины

Allure Report
Инструмент отчётности: шаги, вложения, история и тренды прогонов, категории падений, метки feature/severity/owner.
Test Step
Именованная группа действий (test.step), которая отображается в отчёте и trace и показывает, на каком этапе произошло падение.
Test Artifacts
Файлы, сохраняемые при прогоне для диагностики и отчётности: скриншоты, видео, trace, вложения, отчёты.
Trace Viewer
Инструмент Playwright для разбора записанного прогона: действия, DOM-снимки до и после, скриншоты, сеть, консоль и исходный код.
Correlation ID
Идентификатор (X-Request-Id, traceparent), который передаётся через все сервисы и позволяет найти запрос в их логах.

Важно: Отчёт, в котором только «Expected true, received false», бесполезен. Сообщения проверок, шаги и идентификаторы данных — часть кода теста, а не украшение.

Репортеры Playwright#

получает события прогона и выводит результаты. Встроенные:

Репортер Вывод Где использовать
list Строка на каждый тест Локально, в логах CI
line / dot Компактный вывод Большие наборы
html Интерактивный отчёт с trace, скриншотами, видео Основной отчёт для людей
json Машиночитаемый файл Свои дашборды и интеграции
junit JUnit XML Отображение тестов в GitLab/Jenkins
blob Сырые данные для объединения Шардирование (глава 25)
github Аннотации в Ошибки прямо в diff PR
TypeScriptplaywright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  reporter: process.env.CI
    ? [
        ['list'],
        ['junit', { outputFile: 'results/junit.xml' }],
        ['html', { open: 'never', outputFolder: 'playwright-report' }],
        ['allure-playwright', { resultsDir: 'allure-results' }],
      ]
    : [['list'], ['html', { open: 'on-failure' }]],
  use: {
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
    trace: 'on-first-retry',
  },
  outputDir: 'test-results',   // артефакты: скриншоты, видео, trace, вложения
});

Allure Report#

— популярный инструмент отчётности, особенно когда отчёты читают не только инженеры. Возможности сверх HTML-отчёта :

  • история и тренды: как менялись результаты от прогона к прогону, «плавающие» тесты;
  • категории падений: правила по сообщению ошибки («Проблемы окружения», «Дефекты продукта»);
  • метки: epic/feature/story, , owner, ссылки на задачи и тест-кейсы;
  • группировка по функциональности, а не по файлам;
  • интеграция с Allure TestOps для хранения результатов и аналитики.

Установка и генерация:

Shell
npm i -D allure-playwright allure-commandline
npx playwright test                         # репортер пишет allure-results/
npx allure generate allure-results --clean -o allure-report
npx allure open allure-report               # или: npx allure serve allure-results

Метки и шаги в тестах (API allure-js-commons, используемый современными версиями allure-playwright):

TypeScripttests/checkout.spec.ts
import { test, expect } from '@playwright/test';
import * as allure from 'allure-js-commons';

test('оплата картой', async ({ page }) => {
  await allure.feature('Оформление заказа');
  await allure.severity('critical');
  await allure.owner('qa-checkout');
  await allure.issue('SHOP-1421');
  // ... шаги теста
});

Для истории между прогонами каталог history из предыдущего отчёта копируют в новые allure-results перед генерацией (в CI — через артефакты или хранилище).

Шаги и вложения#

(test.step) группирует действия в именованные шаги — и в HTML-отчёте, и в trace, и в Allure. (testInfo.attach) прикладывает к результату произвольные данные.

TypeScripttests/order-flow.spec.ts
import { test, expect } from '@playwright/test';

test('покупатель оформляет заказ из корзины', async ({ page, request }, testInfo) => {
  const order = await test.step('подготовить корзину через API', async () => {
    const res = await request.post('/api/cart/items', { data: { productId: 1, qty: 2 } });
    await expect(res).toBeOK();
    const body = await res.json();
    await testInfo.attach('cart.json', { body: JSON.stringify(body, null, 2), contentType: 'application/json' });
    return body as { cartId: string };
  });

  await test.step('оформить заказ в интерфейсе', async () => {
    await page.goto(`/cart/${order.cartId}`);
    await page.getByRole('button', { name: 'Оформить заказ' }).click();
  });

  await test.step('проверить подтверждение', async () => {
    await expect(page.getByRole('heading', { level: 1 }), 'заголовок страницы подтверждения').toHaveText('Заказ оформлен');
    await testInfo.attach('confirmation', { body: await page.screenshot(), contentType: 'image/png' });
  });
});

Структурированные логи#

— записи в машиночитаемом формате (обычно JSON-строки) с постоянными полями. В отличие от разрозненных console.log, их можно фильтровать по тесту, шагу и уровню, даже когда параллельно идут десятки тестов.

TypeScriptsrc/utils/logger.ts
import { test } from '@playwright/test';

type Level = 'debug' | 'info' | 'warn' | 'error';
const SECRET_KEYS = /pass|token|secret|authorization|cookie/i;

function mask(data: Record<string, unknown> = {}): Record<string, unknown> {
  return Object.fromEntries(Object.entries(data).map(([k, v]) => [k, SECRET_KEYS.test(k) ? '***' : v]));
}

export function log(level: Level, message: string, data?: Record<string, unknown>): void {
  const info = test.info();                               // текущий тест (внутри теста или фикстуры)
  const line = JSON.stringify({
    ts: new Date().toISOString(),
    level,
    test: info.titlePath.join(' › '),
    retry: info.retry,
    worker: info.parallelIndex,
    message,
    ...mask(data),
  });
  console.log(line);
}

Что логировать: идентификаторы созданных сущностей, ключевые запросы с методом, URL, статусом и (X-Request-Id, traceparent), по которому запрос находится в логах сервера. Чего не логировать: пароли, токены, персональные данные.

Артефакты: скриншоты, видео, трассировки#

— файлы, которые объясняют падение:

Артефакт Опция Плюсы Цена
Скриншот screenshot: 'only-on-failure' Мгновенно видно состояние экрана Почти бесплатно
Видео video: 'retain-on-failure' Видна последовательность событий Замедляет прогон, место
Trace trace: 'on-first-retry' или 'retain-on-failure' Действия, DOM до/после, сеть, консоль, код Место; лучший инструмент диагностики

обычно отвечает на вопрос «почему» быстрее всего: видно, на каком шаге состояние страницы разошлось с ожиданием, какой запрос вернул ошибку и что было в консоли.

Интерактив требует JavaScriptРазбор падения по trace: учебная трассировка упавшего теста — шкала действий, DOM-снимок, сеть и консоль. Найдите шаг, на котором всё пошло не так, и определите причину.

Хороший отчёт о падении#

Минимум информации, после которой не нужно перезапускать тест:

  1. Что проверялось: понятное имя теста, шаги, теги и ссылка на требование.
  2. Что ожидалось и что получено: сообщение проверки с контекстом ('итоговая сумма заказа', Expected/Received).
  3. Где: шаг и строка кода.
  4. Состояние: скриншот, DOM-снимок, trace.
  5. Сеть и логи: запросы и ответы вокруг падения, ошибки консоли браузера, для логов сервера.
  6. Данные: идентификаторы созданных сущностей, тестовый пользователь (без пароля), seed генератора.
  7. Окружение: стенд, версия приложения (Commit/build), браузер, номер попытки (retry).

Если падение — дефект продукта, из этого же набора легко собрать баг-репорт: шаги, ожидаемое и фактическое поведение, окружение и вложения.

Анализ результатов прогона#

— классификация каждого падения:

Класс Признаки Действие
Дефект продукта Воспроизводится, поведение расходится с требованием Баг-репорт, тест остаётся красным или помечается test.fail() со ссылкой
Ошибка теста Изменился UI или API по задаче, устаревший локатор или данные Исправить тест
Нестабильность Проходит при повторе, разные тесты в разных прогонах Расследовать (глава 30), карантин при необходимости
Окружение 502/503, недоступный сервис, , нехватка ресурсов Сообщить владельцам стенда, перезапуск после исправления
Данные Нет нужных данных, истёк срок, чужие изменения Изолировать данные, починить подготовку

Метрики, которые стоит смотреть по истории прогонов: доля успешных прогонов, тесты со статусом flaky, время прогона и самые медленные тесты, распределение падений по классам.

Как разобрать падение без перезапуска наугад#

  1. Определите первый неуспешный шаг и первичную ошибку. Cleanup мог добавить вторичную.
  2. Проверьте версию, окружение, , retry и .
  3. Сопоставьте trace, screenshot, request/response и серверный .
  4. Отделите дефект продукта, ошибку проверки, конфликт данных и проблему окружения.
  5. Воспроизведите минимальный сценарий и проверьте гипотезу. Исправление должно менять причину, а не только .
  6. Сохраните evidence и подтвердите, что проверка ловит контролируемый дефект.

Если ожидался 201, а получен 503, сравните и состояние зависимостей. Если ответ правильный, но UI читает старый текст, проверьте синхронизацию. Если падение зависит от соседнего теста — ищите Shared State и одинаковые IDs.

Пример: от «красного прогона» к диагнозу за 3 минуты#

Прогон ночной регрессии: 4 падения из 600.

  1. Открываем отчёт, группируем по сообщению ошибки: 3 падения с одним сообщением 503 Service Unavailable от /api/delivery/quote, 1 — toHaveText в тесте профиля.
  2. Три падения 503: в trace видно, что сервис доставки недоступен; categories в Allure относит их к «Проблемы окружения». Сообщаем в канал стенда.
  3. Падение профиля: Expected «Москва», Received «Moscow». Скриншот подтверждает английскую локализацию. В шаге attach видно, что тестовый пользователь создан с locale: 'en' — изменение в фабрике данных вчерашним MR. Ошибка теста — исправляем фабрику.

Ни один тест не пришлось перезапускать локально.

Типичные ошибки#

Только HTML-отчёт на агенте CI

Отчёт пропадает вместе с агентом. Сохраняйте отчёты и trace как артефакты задачи и публикуйте (GitLab Pages, хранилище) с разумным сроком хранения.

Видео и trace для всех тестов всегда

Прогон замедляется, хранилище переполняется. Записывайте для упавших или при повторе.

Сообщения без контекста

expect(x).toBe(true) даст «Expected true, received false». Используйте точные матчеры (toHaveText, toContain) и сообщения проверок.

Секреты во вложениях

Скриншот страницы с токеном в URL, storageState во вложении, заголовок Authorization в логе — утечки через отчёты, которые видят многие.

Что важно для собеседования#

JuniorЧто должно быть в отчёте об упавшем автотесте?

Ответ

Понятное имя и шаги теста, сообщение проверки с ожидаемым и фактическим значением и контекстом, место падения в коде, скриншот и trace, сетевые запросы и ошибки консоли вокруг падения, идентификаторы тестовых данных и , окружение (стенд, версия приложения, браузер, номер попытки).

MiddleКак вы настраиваете Allure для Playwright и что он даёт?

Ответ

Репортер allure-playwright пишет allure-results, в CI отчёт генерируется allure generate и публикуется; для истории каталог history прошлого отчёта копируется в новые результаты. Тесты размечаются метками (feature, , owner, ссылки на задачи), шаги — test.step. Даёт тренды, категории падений, группировку по функциональности и удобный отчёт для неинженеров.

MiddleКак вы разбираете результаты ночного прогона?

Ответ

Группирую падения по сообщению и шагу, классифицирую каждое: дефект продукта, ошибка теста, нестабильность, окружение, данные. По trace и логам подтверждаю причину. Дефекты — в баг-трекер со ссылкой на отчёт; ошибки тестов — исправить; нестабильные — расследование или карантин; проблемы окружения — владельцам стенда. Отслеживаю тренды: доля flaky, время прогона, повторяющиеся причины.

Middle+Ночной прогон: 40 упавших тестов из 900. Как быстро разобрать, что произошло?

Ответ

Группирую падения по сообщению об ошибке и времени: если много разных тестов упали в одну минуту с 502/503 — это окружение, смотрю логи стенда и журнал деплоев. Остальное — по области и общей причине (один изменившийся локатор ломает 15 тестов). Для групп смотрю одного представителя: trace, скриншот, сеть. Классифицирую: дефект продукта (тикет с trace), изменение продукта (обновить тесты), проблема теста или данных (исправить), окружение (передать владельцам). Результат — короткий отчёт в канал команды, а не 40 отдельных тикетов.

Проверьте себя#

Тест
1
Какой режим trace обычно выбирают для CI?

Трассировка сохраняется только для упавших или повторных тестов: максимум пользы при минимальной цене.

2
Зачем логировать correlation id запроса?

Сквозной идентификатор связывает запись теста с записями всех сервисов, через которые прошёл запрос.

3
Падение со статусом 503 от сервиса доставки в нескольких несвязанных тестах — это чаще всего…

Сервис недоступен — это проблема стенда; нужно сообщить владельцам и не тратить время на правку тестов.

Чем Allure полезен по сравнению со встроенным HTML-отчётом?

История и тренды между прогонами, категории падений, метки (feature, , owner, ссылки на задачи), группировка по функциональности, интеграция с системами управления тестированием. HTML-отчёт удобнее для технического разбора одного прогона: в нём встроен Trace Viewer.

Что вы добавите в тест, чтобы его падение было понятно человеку, не знакомому с кодом?

Название, описывающее поведение; шаги test.step на языке предметной области; сообщения проверок; вложения с идентификаторами данных и ответами API; теги и ссылку на требование. Плюс артефакты падения из конфига: скриншот и trace.
