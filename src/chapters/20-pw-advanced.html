Глава 18 · Раздел IV · UI Automation

Продвинутый Playwright

Browser Contexts, сохранённое состояние авторизации, перехват и подмена сети, проекты, скриншоты и визуальное сравнение, трассировка, ретраи и управление временем. Инструменты, которые делают UI-тесты быстрыми, изолированными и диагностируемыми.

≈ 12 мин чтенияM–M+
Опирается на: Fixtures и HooksPage Object Model
Основная идея

Самые стабильные UI-тесты контролируют всё, что не является предметом проверки: авторизацию готовят заранее, внешние сервисы подменяют, время фиксируют. Тогда тест проверяет только своё поведение и падает только из-за него.

Цель главы: управлять состоянием приложения и окружением теста средствами Playwright, не жертвуя реалистичностью и изоляцией.

Кратко

Состояние входа сохраняется один раз (storageState) и подставляется в новые контексты; сеть перехватывается page.route; проекты связывают setup и тесты; trace и скриншоты объясняют падения.

Главное

  • настраивается: viewport, locale, timezoneId, geolocation, permissions, offline, colorScheme, storageState.
  • Авторизация: setup-проект входит и сохраняет storageState в файл; тестовые проекты зависят от него через dependencies и используют use.storageState.
  • page.route(url, handler): fulfill — подменить ответ, abort — оборвать запрос, continue — пропустить с изменениями, route.fetch() — получить реальный ответ и модифицировать.
  • toHaveScreenshot сравнивает со снимком-эталоном; снимки зависят от ОС, шрифтов и браузера — генерируйте их в той же среде, что и CI (Docker).
  • Trace (on-first-retry, retain-on-failure) записывает действия, DOM-снимки, сеть и консоль — главный артефакт для разбора падений в CI.
  • page.clock управляет временем страницы: таймеры, даты, «прошло 30 минут».

Термины

BrowserContext
Изолированная сессия внутри браузера со своими cookies, хранилищем, кэшем и разрешениями. Каждый тест получает новый контекст.
Storage State
Снимок cookies и localStorage контекста в JSON-файле. Позволяет войти один раз и стартовать тесты уже авторизованными.
Network Interception
Перехват запросов страницы (page.route) с возможностью подменить ответ, оборвать запрос, изменить его или модифицировать реальный ответ.
Trace Viewer
Инструмент Playwright для разбора записанного прогона: действия, DOM-снимки до и после, скриншоты, сеть, консоль и исходный код.
Clock API
API page.clock: подмена Date и таймеров в браузере, перемотка времени для тестов, зависящих от даты и таймаутов.

Важно: Чем больше подменено, тем меньше реальности проверяет тест. Мок бэкенда в UI-тесте проверяет фронтенд, но не интеграцию — нужны и тесты без моков.

Browser Contexts на практике#

Каждый тест получает новый . Его можно настраивать — глобально в use, для файла через test.use или при ручном создании контекста:

TypeScripttests/context-options.spec.ts
import { test, expect } from '@playwright/test';

test.use({
  locale: 'ru-RU',
  timezoneId: 'Europe/Moscow',
  viewport: { width: 390, height: 844 },
  geolocation: { latitude: 55.7558, longitude: 37.6173 },
  permissions: ['geolocation'],
  colorScheme: 'dark',
});

test('ближайший пункт выдачи определяется по геолокации', async ({ page, context }) => {
  await page.goto('/pickup-points');
  await page.getByRole('button', { name: 'Найти ближайший' }).click();
  await expect(page.getByTestId('nearest-point')).toContainText('Москва');

  await context.setOffline(true);                     // проверить поведение без сети
  await page.getByRole('button', { name: 'Обновить' }).click();
  await expect(page.getByRole('alert')).toHaveText('Нет подключения к интернету');
});

Несколько контекстов в одном тесте моделируют нескольких пользователей: покупатель и администратор, два участника чата, два вкладки одного пользователя (две страницы в одном контексте делят cookies).

Authentication State#

Вход через форму в каждом тесте — медленно (секунды на тест) и делает все тесты зависимыми от страницы входа. Решение — войти один раз и сохранить : cookies и localStorage (опционально и IndexedDB).

TypeScripttests/auth.setup.ts
import { test as setup, expect } from '@playwright/test';

const customerFile = 'playwright/.auth/customer.json';

setup('вход покупателя', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill(process.env.CUSTOMER_EMAIL ?? '');
  await page.getByLabel('Пароль').fill(process.env.CUSTOMER_PASSWORD ?? '');
  await page.getByRole('button', { name: 'Войти' }).click();
  await expect(page.getByRole('link', { name: 'Профиль' })).toBeVisible();
  await page.context().storageState({ path: customerFile });
});
TypeScriptplaywright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  projects: [
    { name: 'setup', testMatch: /.*\.setup\.ts/ },
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'], storageState: 'playwright/.auth/customer.json' },
      dependencies: ['setup'],          // сначала выполнится вход
    },
  ],
});

Теперь каждый тест проекта chromium стартует уже авторизованным. Варианты:

  • Вход через API в setup вместо формы — ещё быстрее и не зависит от UI.
  • Несколько ролей — несколько файлов (admin.json, customer.json) и test.use({ storageState: … }) в нужных файлах.
  • Аккаунт на воркер — если тесты изменяют серверное состояние пользователя (корзину, настройки), один общий аккаунт приведёт к конфликтам при параллельном запуске. Тогда создают отдельного пользователя на воркер фикстурой с scope: 'worker' (см. главу 25).
  • Тест без авторизации в проекте с storageState — test.use({ storageState: { cookies: [], origins: [] } }).
Файлы состояния — секреты

playwright/.auth/*.json содержит действующие токены. Добавьте каталог в .gitignore и не прикладывайте эти файлы к отчётам.

Network Interception#

позволяет перехватить запросы страницы и решить, что с ними делать. Применения: изолировать фронтенд от нестабильного бэкенда, смоделировать ошибки и редкие состояния, ускорить тест, заблокировать стороннюю аналитику.

TypeScripttests/network.spec.ts
import { test, expect } from '@playwright/test';

test('ошибка сервера при загрузке каталога показывает сообщение', async ({ page }) => {
  await page.route('**/api/products*', (route) =>
    route.fulfill({ status: 500, contentType: 'application/json', body: JSON.stringify({ code: 'INTERNAL' }) }),
  );
  await page.goto('/catalog');
  await expect(page.getByRole('alert')).toHaveText('Не удалось загрузить каталог. Попробуйте позже');
});

test('пустой каталог', async ({ page }) => {
  await page.route('**/api/products*', (route) => route.fulfill({ json: { items: [], total: 0 } }));
  await page.goto('/catalog');
  await expect(page.getByText('Товары не найдены')).toBeVisible();
});

test('изменить реальный ответ: товар закончился', async ({ page }) => {
  await page.route('**/api/products/1', async (route) => {
    const response = await route.fetch();                 // настоящий запрос к серверу
    const product = await response.json();
    await route.fulfill({ response, json: { ...product, stock: 0 } });
  });
  await page.goto('/product/1');
  await expect(page.getByRole('button', { name: 'В корзину' })).toBeDisabled();
});

test('заблокировать стороннюю аналитику и картинки', async ({ page }) => {
  await page.route(/(google-analytics|mc\.yandex)\./, (route) => route.abort());
  await page.route('**/*.{png,jpg,webp}', (route) => route.abort());
  await page.goto('/');
  await expect(page.getByRole('heading', { level: 1 })).toBeVisible();
});

test('проверить, что фронтенд отправил правильный запрос', async ({ page }) => {
  await page.goto('/cart');
  const request = page.waitForRequest((r) => r.url().endsWith('/api/cart/promo') && r.method() === 'POST');
  await page.getByLabel('Промокод').fill('SALE10');
  await page.getByRole('button', { name: 'Применить' }).click();
  expect((await request).postDataJSON()).toEqual({ code: 'SALE10' });
});
Метод route Что делает
route.fulfill({ status, json, body, headers }) Ответить подменённым ответом, запрос до сервера не дойдёт
route.abort(errorCode?) Оборвать запрос (сетевая ошибка)
route.continue({ headers, postData, url }) Отправить запрос дальше, при необходимости изменив его
route.fetch() + route.fulfill({ response, json }) Получить реальный ответ и изменить его
route.fallback() Передать запрос следующему обработчику

page.route действует на страницу, context.route — на все страницы контекста. Для записи и воспроизведения целых сценариев есть : page.routeFromHAR('product.har', { update: false }).

Интерактив требует JavaScriptПерехват сети: выберите стратегию для запроса каталога (пропустить, подменить 200, 500, пустой ответ, задержка, обрыв) и посмотрите, что увидит пользователь и что проверяет такой тест.

Mocking в UI-тестах: когда уместно#

сетевых ответов в UI-тестах — мощный и опасный инструмент.

Уместно Неуместно
Редкие состояния: ошибки 500, таймауты, пустые списки Единственный способ проверить основной сценарий
Внешние сервисы: платёжный шлюз, карты, аналитика Подмена собственного бэкенда во всех тестах подряд
Детерминированные данные для визуальных тестов Мок, который никогда не сверяется с реальным API
Компонентные и фронтенд-тесты E2E-тесты (по определению проходят через реальные слои)

Главный риск — рассинхронизация мока и реального API: бэкенд переименовал поле, а моки отдают старую структуру, и UI-тесты зелёные, пока продакшен сломан. Защита — контрактные тесты и проверка схемы моков (глава 21), плюс набор тестов без моков.

Projects#

— именованная конфигурация, в которой запускается набор тестов:

TypeScriptprojects.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  projects: [
    { name: 'setup', testMatch: /.*\.setup\.ts/, teardown: 'cleanup' },
    { name: 'cleanup', testMatch: /.*\.teardown\.ts/ },
    { name: 'api', testDir: './tests/api', use: { baseURL: process.env.API_URL } },
    { name: 'desktop-chrome', testDir: './tests/ui', dependencies: ['setup'], use: { ...devices['Desktop Chrome'] } },
    { name: 'mobile-webkit', testDir: './tests/ui', dependencies: ['setup'], use: { ...devices['iPhone 13'] }, grep: /@mobile/ },
  ],
});
  • dependencies — проекты, которые выполняются раньше (setup).
  • teardown — проект, который выполнится после всех зависимых (очистка).
  • grep / testMatch / testDir — какие тесты входят в проект.
  • Каждый проект может иметь свои use, таймауты, ретраи.

Screenshots и визуальное тестирование#

TypeScripttests/visual.spec.ts
import { test, expect } from '@playwright/test';

test('карточка товара выглядит как эталон', async ({ page }) => {
  await page.goto('/product/1');
  await page.screenshot({ path: 'test-results/product-full.png', fullPage: true }); // просто сохранить

  await expect(page.getByTestId('product-card')).toHaveScreenshot('product-card.png', {
    mask: [page.getByTestId('delivery-date')],   // скрыть изменчивые данные
    maxDiffPixelRatio: 0.01,                      // допуск на сглаживание
    animations: 'disabled',
  });
});

с toHaveScreenshot: при первом запуске создаётся эталон (--update-snapshots), дальше каждый прогон сравнивает пиксели. Снимки зависят от ОС, шрифтов, версии браузера и даже GPU, поэтому имя файла содержит платформу, а эталоны генерируют в той же среде, что и CI — обычно в официальном Docker-образе . Изменчивое содержимое (даты, реклама, анимации) маскируют или фиксируют.

Traces#

открывает записанную трассировку: шкалу действий, DOM-снимки до и после каждого шага, скриншоты, сетевые запросы, консоль, исходный код и ошибки.

Режим trace Когда записывается
'off' Никогда
'on' Всегда (дорого по времени и месту)
'retain-on-failure' Пишется всегда, сохраняется только для упавших
'on-first-retry' Только при первом повторе упавшего теста (рекомендуется для CI)
'on-all-retries' При всех повторах

Откройте trace из HTML-отчёта или командой npx playwright show-trace path/to/trace.zip.

Test Retries#

настраивается глобально (retries), для группы (test.describe.configure({ retries: 2 })) или читается в тесте через testInfo.retry:

TypeScripttests/retries.spec.ts
import { test, expect } from '@playwright/test';

test.describe.configure({ retries: 1 });

test('загрузка отчёта', async ({ page }, testInfo) => {
  if (testInfo.retry > 0) {
    // на повторе — дополнительная диагностика, а не «другое поведение теста»
    await testInfo.attach('note', { body: `повтор #${testInfo.retry}`, contentType: 'text/plain' });
  }
  await page.goto('/reports');
  await expect(page.getByRole('table')).toBeVisible();
});

Ретраи не исправляют нестабильность — они делают её видимой как статус flaky. Как с ним работать — в главе «Flaky Tests».

Управление временем#

Тесты, зависящие от текущего времени, нестабильны: «акция заканчивается сегодня», «сессия истекает через 30 минут». в управляет временем на странице:

TypeScripttests/clock.spec.ts
import { test, expect } from '@playwright/test';

test('баннер акции скрывается после окончания', async ({ page }) => {
  await page.clock.install({ time: new Date('2026-11-30T23:59:00+03:00') });
  await page.goto('/');
  await expect(page.getByTestId('promo-banner')).toBeVisible();
  await page.clock.fastForward('02:00');            // перемотать на 2 минуты
  await expect(page.getByTestId('promo-banner')).toBeHidden();
});

page.clock подменяет Date, таймеры (setTimeout, setInterval) и requestAnimationFrame в браузере. Время сервера он не меняет — для серверной логики время фиксируют на стороне бэкенда тестового окружения.

Пример: быстрый и изолированный UI-набор#

Набор из 120 UI-тестов шёл 25 минут и падал «случайно». Что сделано:

  1. Авторизация — setup-проект с входом через API и storageState для двух ролей: −6 минут.
  2. Аккаунт на воркер — фикстура scope: 'worker' создаёт пользователя для каждого воркера: исчезли конфликты корзины.
  3. Внешние сервисы — платёжный виджет и карты подменены page.route в UI-тестах; интеграция с ними покрыта отдельными API-тестами на тестовом стенде провайдера.
  4. Аналитика и чат поддержки заблокированы route.abort() — меньше сетевого шума и оверлеев.
  5. Trace on-first-retry и retries: 1 в CI — каждое нестабильное падение теперь можно разобрать.

Итог: 9 минут на 4 воркерах, нестабильность — менее 0,5%.

Типичные ошибки#

Общий аккаунт для параллельных тестов, меняющих его состояние

Тесты одновременно меняют одну корзину или профиль. Используйте аккаунты на воркер или на тест.

Мок без проверки контракта

Моки «застывают», а API развивается. Через полгода тесты проверяют фронтенд против несуществующего API.

Эталоны скриншотов с локальной машины

Снимки с macOS не совпадут с Linux в CI из-за шрифтов. Обновляйте эталоны в Docker-образе, как в CI.

trace: 'on' в CI для тысяч тестов

Трассировка всех тестов замедляет прогон и забивает хранилище артефактов. Достаточно on-first-retry или retain-on-failure.

Что важно для собеседования#

JuniorЧто содержит Playwright trace и какой режим включить в CI?

Ответ

Шкалу действий с DOM-снимками до и после каждого шага, скриншоты, сетевые запросы, консоль, ошибки и исходный код теста. В CI обычно on-first-retry (запись при повторе упавшего теста) или retain-on-failure; on для всех тестов слишком дорог по времени и месту.

MiddleКак организовать авторизацию в большом наборе UI-тестов?

Ответ

Setup-проект выполняет вход (лучше через API) и сохраняет storageState в файл; тестовые проекты зависят от него через dependencies и используют use.storageState. Для разных ролей — разные файлы. Если тесты меняют серверное состояние пользователя, нужен аккаунт на воркер или на тест. Форму входа проверяют отдельными тестами. Файлы состояния — в .gitignore.

MiddleКак в Playwright подменить ответ сервера и когда это стоит делать?

Ответ

page.route(pattern, route => route.fulfill({ status, json })) — подмена; route.abort() — сетевая ошибка; route.fetch() + fulfill({ response, json }) — изменить реальный ответ; continue — изменить запрос. Уместно для редких состояний (500, пустой список, таймаут), внешних сервисов и детерминированных визуальных тестов. Риск — расхождение моков с реальным API, поэтому нужны контрактные проверки и тесты без моков.

Middle+Какие проблемы бывают у визуальных тестов и как их решать?

Ответ

Различия рендеринга между ОС, шрифтами, браузерами и GPU; изменчивые данные (даты, реклама, аватары); анимации; разные размеры окна. Решения: эталоны генерировать и проверять в одном Docker-образе; маскировать изменчивые области (mask), фиксировать данные моками и время через page.clock; animations: 'disabled'; разумный допуск (maxDiffPixelRatio); снимать отдельные компоненты, а не целые страницы.

Проверьте себя#

Тест
1
Как ускорить тесты, каждый из которых логинится через форму?

storageState переносит cookies и localStorage в новые контексты. Каждый тест остаётся изолированным, но стартует авторизованным.

2
Какой метод route позволит взять реальный ответ сервера и изменить одно поле?

fetch выполняет настоящий запрос, а fulfill отдаёт странице изменённый ответ.

3
Почему эталонные скриншоты лучше генерировать в Docker-образе?

Разные ОС по-разному рисуют шрифты и сглаживание, поэтому снимки с локальной машины не совпадут с CI.

Чем page.route отличается от context.route?

page.route перехватывает запросы одной страницы, context.route — всех страниц контекста, включая всплывающие окна и новые вкладки. Если сценарий открывает новую вкладку, перехват нужно ставить на контекст.

Тест проверяет таймер «до конца акции». Почему page.clock не решит проблему, если время окончания акции вычисляет сервер?

page.clock меняет время только в браузере. Если сервер сравнивает дату акции со своим текущим временем, нужно управлять временем на стороне сервера (тестовый эндпоинт, конфигурация окружения) или готовить данные акции относительно текущей даты.
