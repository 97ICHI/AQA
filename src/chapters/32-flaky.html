Flaky Tests и диагностика

Что делает тест нестабильным: гонки, неправильные ожидания, зависимость от порядка, данные, окружение, сеть и внешние сервисы. Как обнаружить, воспроизвести, расследовать и исправить нестабильность, и как управлять ею на уровне команды.

≈ 10 мин чтенияM–M+
Опирается на: Assertions и ожиданияПараллельностьReporting и Logging
Основная идея

Нестабильный тест — это тест, у которого есть неучтённая переменная: время, порядок, данные, окружение. Задача расследования — найти эту переменную и взять её под контроль. Перезапуск лишь бросает кости ещё раз.

Цель главы: систематически классифицировать причины нестабильности, воспроизводить её, исправлять по причине и выстроить процесс работы с flaky-тестами в команде.

Кратко

Flaky-тест проходит и падает без изменений кода. Причина всегда конкретна: гонка, ожидание, общий ресурс, данные, окружение или внешняя зависимость — и иногда реальный дефект продукта.

Главное

  • Обнаружение: статус flaky при ретраях, --repeat-each, история прогонов, доля flaky как метрика.
  • Воспроизведение: повтор, больше воркеров, медленная машина (CPU), задержка сети через page.route, образ CI, тот же seed и данные.
  • Расследование: сравнить trace упавшей и успешной попытки — где состояния разошлись.
  • Типовые исправления: web-first assertions вместо однократных чтений, ожидание событий до действия, изоляция данных, контроль времени и внешних сервисов.
  • Карантин: нестабильный тест выносится из блокирующего набора с задачей, владельцем и сроком; не удаляется молча и не скрывается ретраями навсегда.
  • Flaky rate считают с явным знаменателем; нестабильность может быть дефектом продукта; успешные повторы не доказывают стабильность.

Термины

Flaky Test
Тест, который при одинаковом коде и окружении то проходит, то падает. Подрывает доверие к автоматизации.
Race Condition
Ситуация, когда результат зависит от того, какая из параллельных операций завершится первой. Частая причина нестабильных тестов.
Test Order Dependency
Ситуация, когда результат теста зависит от того, какие тесты выполнялись до него и что они оставили в системе.
Flaky Rate
Доля прогонов, в которых тест был нестабилен (упал и прошёл при повторе). Метрика для отдельных тестов и набора.
Repeat Each
Опция --repeat-each=N: каждый тест выполняется N раз; используется для поиска нестабильности и burn-in новых тестов.

Важно: Ретраи, force: true, большие таймауты и waitForTimeout скрывают симптом. Без поиска причины нестабильность вернётся в другом тесте или в продакшене.

Что такое Flaky Test#

— тест, который при неизменном коде продукта, коде теста и окружении иногда проходит, иногда падает. Его цена выше, чем кажется:

  • Потеря доверия. Команда привыкает перезапускать красные прогоны и пропускает реальные дефекты.
  • Время. Разбор ложных падений, перезапуски , ожидание.
  • Скрытые дефекты. Часть «нестабильных тестов» — реальные гонки в продукте, которые пользователи тоже встречают.

Математика из главы 4: при доле ложных падений p на тест вероятность зелёного прогона из N тестов — (1 − p)^N. Даже редкие флаки в большом наборе делают красным почти каждый прогон.

Основные причины#

Причина Механизм Типичный симптом

Сетевые ошибки Обрывы, , медленные ответы, лимиты ECONNRESET, ERR_NAME_NOT_RESOLVED, 429

Дефект продукта Реальная гонка в приложении: двойной клик, параллельные запросы Воспроизводится и вручную при быстрых действиях

Обнаружение#

  • Статус flaky. С retries помечает тест, прошедший со второй попытки, как flaky — это главный источник данных в CI.
  • . npx playwright test tests/cart.spec.ts --repeat-each=20 --workers=4 — быстрый способ проверить подозрительный тест или новый тест перед слиянием.
  • История. Allure, TestOps, собственный дашборд по JSON-отчётам: какие тесты бывали flaky за последние N прогонов.
  • — доля прогонов, в которых тест был flaky или упал и прошёл при перезапуске. Метрика для всего набора и для отдельных тестов.
TypeScriptplaywright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  retries: process.env.CI ? 1 : 0,
  failOnFlakyTests: !!process.env.STRICT_FLAKY,   // для критичного набора: flaky = провал
  use: { trace: 'on-first-retry' },               // trace как раз для расследования флаков
  reporter: [['list'], ['json', { outputFile: 'results/results.json' }]],
});

Воспроизведение#

Нестабильность часто проявляется только при определённых условиях. Способы их создать:

Shell
npx playwright test tests/cart.spec.ts:31 --repeat-each=30                  # повтор одного теста
npx playwright test tests/cart --repeat-each=10 --workers=8 --fully-parallel # параллельное давление
npx playwright test --project=chromium --grep @cart --retries=0             # без маскировки ретраями
TypeScripttests/repro-slow-network.spec.ts
import { test, expect } from '@playwright/test';

test('корзина при медленном ответе API', async ({ page }) => {
  // Искусственная задержка ответа делает гонку воспроизводимой
  await page.route('**/api/cart/**', async (route) => {
    await new Promise((r) => setTimeout(r, 1500));
    await route.continue();
  });
  await page.goto('/cart');
  await page.getByRole('button', { name: 'Увеличить количество' }).click();
  await expect(page.getByTestId('cart-total')).toHaveText('9 980 ₽');
});

Ещё способы: замедление CPU через CDP-сессию в Chromium (Emulation.setCPUThrottlingRate), запуск в Docker-образе CI с теми же лимитами ресурсов, тот же seed и те же данные, запуск в обратном порядке или по одному.

Расследование#

  1. Собрать артефакты упавших попыток: trace, скриншоты, логи, .
  2. Сравнить trace упавшей и успешной попытки: на каком шаге состояние страницы или ответы сети разошлись.
  3. Сформулировать гипотезу («проверка выполняется до ответа /api/cart»).
  4. Подтвердить: сделать условие воспроизводимым (задержка ответа, параллельный запуск, другой порядок) — тест должен падать стабильно.
  5. Исправить причину, а не симптом.
  6. Проверить: --repeat-each с теми же условиями, что воспроизводили падение.
Интерактив требует JavaScriptFlaky Test Debugger: учебные расследования — код теста, история запусков, лог и фрагмент trace. Выберите наиболее вероятную причину нестабильности и получите техническое объяснение и исправление.

Карантин и процесс#

— временная изоляция нестабильного теста от блокирующих наборов, чтобы он не мешал команде, но и не потерялся:

TypeScripttests/quarantine-example.spec.ts
import { test, expect } from '@playwright/test';

test('экспорт отчёта в Excel', { tag: ['@quarantine'], annotation: { type: 'issue', description: 'QA-512: гонка при генерации файла' } }, async ({ page }) => {
  await page.goto('/reports');
  const download = page.waitForEvent('download');
  await page.getByRole('button', { name: 'Экспорт в Excel' }).click();
  expect((await download).suggestedFilename()).toMatch(/\.xlsx$/);
});
Shell
npx playwright test --grep-invert @quarantine   # блокирующий набор без карантина
npx playwright test --grep @quarantine          # отдельная неблокирующая задача: следить за состоянием

Правила процесса:

  1. Задача и владелец для каждого теста в карантине.
  2. Срок: исправить или удалить осознанно через N дней.
  3. Тест продолжает запускаться в неблокирующей задаче — видно, исправился ли он.
  4. Лимит: если карантин растёт, это сигнал о системной проблеме (окружение, архитектура данных).
  5. Профилактика: ESLint-правила (no-wait-for-timeout, missing-playwright-await), чек-лист ревью, burn-in — новые и изменённые тесты в MR запускаются с --repeat-each.

test.fixme() и test.skip() подходят для известных временных ситуаций, но тест в них не выполняется — без задачи и срока такие тесты «умирают» навсегда.

Измеримые критерии стабильности#

Выберите знаменатель явно. Например: = число test cases, упавших сначала и прошедших при retry, / число выполненных test cases за период. Это не доля всех падений и не доля запусков CI. Дополнительно отслеживайте first-attempt failure rate и постоянные падения.

У quarantine есть владелец, задача, дата пересмотра, причина и критерий возврата. Критичный сценарий временно замените другой проверкой. Зелёный прогон после исключения проблемных тестов не доказывает улучшение продукта.

20 успешных повторов — полезный smoke на стабильность, но не доказательство отсутствия flaky. При нуле ошибок грубая верхняя 95% оценка вероятности ошибки около 3/n применима лишь для независимых сопоставимых запусков; реальные запуски часто зависимы.

Пример: расследование «плавающей» корзины#

Тест «удаление товара обновляет сумму» flaky в 4% прогонов.

  1. История: падает только в CI, только при workers ≥ 4.
  2. Trace упавшей попытки: после клика «Удалить» сумма на мгновение верная, затем меняется на большую. В сети — GET /api/cart возвращает два товара.
  3. Гипотеза: другой тест в это время добавляет товар в корзину того же пользователя.
  4. Подтверждение: тест и cart-add.spec.ts используют одного пользователя из общего storageState; при запуске двух файлов с --repeat-each=20 --workers=2 падение воспроизводится в каждом третьем повторе.
  5. Исправление: аккаунт на воркер через parallelIndex + фикстура пустой корзины перед тестом.
  6. Проверка: --repeat-each=50 --workers=8 — ноль падений.

Ретраи прятали эту проблему месяцами, а «исправление» таймаутом ничего бы не дало.

Типичные ошибки#

«Просто увеличим таймаут»

Если причина — гонка за данные или порядок, таймаут не поможет. Если причина — ожидание, нужен правильный вид ожидания, а не более длинный.

Ретраи как постоянное решение

Тест с ретраями «зелёный», но статус flaky в отчётах игнорируется. Нестабильность растёт, пока ретраи перестают спасать.

Удалить нестабильный тест молча

Если тест проверял важный риск, риск остался без проверки. Удаление — осознанное решение с заменой проверки или принятием риска.

Считать любую нестабильность проблемой теста

Гонка в приложении проявляется у пользователей так же: двойной заказ, неверная сумма при быстрых действиях. Сначала убедитесь, что приложение ведёт себя корректно.

Что важно для собеседования#

JuniorКакие причины flaky-тестов вы знаете?

Ответ

Гонки (проверка или действие до обновления приложения), неправильные ожидания (паузы, однократное чтение, ожидание ответа после действия), зависимость от порядка и общего состояния, проблемы тестовых данных, нестабильное окружение и ресурсы агента, сетевые ошибки и лимиты, внешние зависимости, время и локаль, анимации и оверлеи. И реальные гонки в продукте.

MiddleКак вы расследуете нестабильный тест?

Ответ

Собираю данные: история падений, условия (только CI, только при нескольких воркерах, время суток), trace упавшей и успешной попытки. Сравниваю, где разошлось состояние. Формулирую гипотезу и делаю её воспроизводимой: --repeat-each, больше воркеров, задержка ответа через page.route, образ CI, другой порядок. Исправляю причину, подтверждаю исправление тем же способом воспроизведения.

MiddleПочему ретраи не решают проблему flaky-тестов?

Ответ

Ретраи скрывают симптом: тест зелёный, но причина (гонка, общие данные, дефект продукта) остаётся и проявляется чаще по мере роста набора. Они удлиняют прогон и могут маскировать реальные периодические дефекты. Ретраи допустимы как страховка в CI при обязательном отслеживании статуса flaky, карантине и задачах на исправление.

Middle+Как выстроить в команде процесс работы с нестабильными тестами?

Ответ

Метрика доли flaky по набору и тестам с дашбордом; trace при первом повторе; правило: flaky-тест получает задачу и владельца в течение дня, при невозможности быстрого исправления — карантин (отдельный тег и неблокирующая задача) со сроком; лимит размера карантина; профилактика — ESLint-правила, чек-лист ревью, burn-in новых тестов с --repeat-each; разбор системных причин (окружение, данные) на ретроспективах.

Middle+Доля flaky-тестов в pipeline выросла до 8%, команда начала нажимать «перезапустить». Ваш план на две недели?

Ответ

Сначала данные: выгрузить историю результатов (JSON-отчёты или Allure) и найти, какие тесты дают основную долю нестабильности, — обычно 10–20 тестов дают большую часть падений. Сгруппировать по причинам: окружение (массовые 502 в одно время), данные, ожидания, порядок. Проблемы окружения передать владельцам стенда с доказательствами. Самые частые тесты — в карантин с тикетом и владельцем, чтобы вернуть доверие к воротам; карантин ограничен по сроку. Параллельно чинить причины по убыванию вклада, проверяя исправление через --repeat-each в условиях CI. Ввести метрику на дашборде и правило: новый тест проходит --repeat-each перед слиянием.

Частая ошибка

Увеличить retries до 3 и считать проблему решённой: нестабильность скрыта, время прогона выросло.

Пример

npx playwright test tests/cart --repeat-each=30 --workers=8 --retries=0

Проверьте себя#

Тест
1
Тест падает только при запуске всего набора и проходит, если запустить его отдельно. Наиболее вероятная причина?

Изменение результата в зависимости от состава и порядка запуска — признак зависимости от общего состояния.

2
Как сделать гонку «проверка до ответа сервера» воспроизводимой?

Искусственно замедленный ответ превращает редкую гонку в стабильное падение — его можно исправить и проверить исправление.

3
Что правильнее всего сделать с нестабильным тестом, который сейчас нельзя исправить?

Карантин убирает помеху для команды и сохраняет видимость проблемы до исправления.

Как отличить нестабильность теста от нестабильности продукта?

Изучить trace и логи: если тест проверяет раньше, чем приложение закончило корректную операцию, — проблема теста. Если приложение в итоге приходит к неверному состоянию (двойной заказ, неверная сумма, ошибка сервера) при определённом тайминге — это гонка в продукте. Проверка: воспроизвести вручную или через API теми же быстрыми действиями.

Зачем запускать новые тесты в MR с --repeat-each?

Однократное прохождение не доказывает стабильность. Повтор 10–20 раз (с несколькими воркерами) выявляет большинство гонок и зависимостей до того, как тест попадёт в основной набор и начнёт мешать команде. Это называют burn-in.
