Debugging

Breakpoints, Call Stack, Stack Trace, логирование и режимы отладки Playwright. Как читать сообщение об ошибке и за несколько минут находить место и причину сбоя.

≈ 11 мин чтенияJ–M
Опирается на: Основы TypeScriptАсинхронность
Основная идея

Отладка — это сужение области поиска: от сообщения об ошибке к строке кода, от строки к состоянию программы, от состояния к причине. Stack trace говорит где, сообщение — что, а breakpoints и trace — почему.

Цель главы: уверенно читать ошибки Node.js и Playwright, пользоваться отладчиком и инструментами Playwright, а не гадать и перезапускать.

Кратко

Сначала прочитайте ошибку целиком: тип, сообщение, ожидаемое и фактическое значение, первую строку stack trace в вашем коде. Только потом запускайте отладчик.

Главное

  • Stack trace читается сверху вниз: верхний кадр — где выброшена ошибка; ищите первый кадр в вашем файле, а не в node_modules.
  • останавливает выполнение на строке; в паузе видны переменные, call stack, можно выполнять выражения.
  • Step over — выполнить строку целиком; step into — зайти внутрь вызова; step out — выйти из текущей функции.
  • : --debug (Inspector, пошагово), --ui (UI Mode с таймлайном), page.pause(), для упавших в CI тестов.
  • Сообщение Playwright содержит локатор, ожидание, полученное значение, таймаут и call log — это половина диагноза.
  • Логи полезны, когда структурированы и привязаны к шагу (test.step), а не разбросаны console.log.

Термины

Breakpoint
Отметка на строке кода, перед выполнением которой отладчик останавливает программу, чтобы можно было изучить переменные и стек.
Call Stack
Стек функций, выполняемых в данный момент. Каждый вызов добавляет кадр, возврат — снимает. Stack trace — снимок стека в момент ошибки.
Stack Trace
Список вызовов функций в момент ошибки: верхний кадр — место выброса, ниже — кто его вызвал. Содержит файлы, строки и колонки.
Debug Mode
Запуск тестов с паузами и пошаговым выполнением. В Playwright: --debug (Inspector), --ui (UI Mode), page.pause().
Trace Viewer
Инструмент Playwright для разбора записанного прогона: действия, DOM-снимки до и после, скриншоты, сеть, консоль и исходный код.

Важно: Перезапуск упавшего теста без чтения ошибки — не отладка. Если тест прошёл со второго раза, проблема никуда не делась.

Порядок отладки#

Эффективная отладка — последовательность шагов, а не перебор гипотез:

  1. Прочитать ошибку полностью. Тип, сообщение, ожидание и факт, место в коде.
  2. Воспроизвести. Локально, тот же тест, те же данные. Если не воспроизводится — смотреть артефакты прогона (trace, скриншот, логи).
  3. Локализовать. Где состояние впервые стало неправильным? Двигаться назад от места падения.
  4. Понять причину. Дефект продукта, ошибка теста, данные или окружение?
  5. Исправить и проверить, что тест падает без исправления и проходит с ним.

Call Stack и Stack Trace#

— стек выполняемых функций: main вызвала checkout, та — applyDiscount. — снимок этого стека в момент ошибки.

TypeScripttrace-demo.ts
function applyDiscount(total: number, percent: number): number {
  if (percent > 100) throw new RangeError(`Скидка ${percent}% больше 100%`);
  return total * (1 - percent / 100);
}

function checkout(items: number[], promo: { percent: number }): number {
  const total = items.reduce((s, x) => s + x, 0);
  return applyDiscount(total, promo.percent);
}

checkout([1000, 500], { percent: 150 });

Ошибка в консоли Node.js выглядит примерно так:

Текст
RangeError: Скидка 150% больше 100%
    at applyDiscount (/project/trace-demo.ts:2:25)
    at checkout (/project/trace-demo.ts:8:10)
    at Object.<anonymous> (/project/trace-demo.ts:11:1)
    at Module._compile (node:internal/modules/cjs/loader:1554:14)

Как читать:

  • Первая строка — тип и сообщение ошибки. Это «что».
  • Верхний кадр (applyDiscount … :2:25) — где ошибка выброшена: файл, строка, колонка.
  • Ниже — кто вызвал: checkout на строке 8, затем код модуля на строке 11.
  • Кадры node:internal и node_modules обычно пропускают: нужен первый кадр в вашем коде.

Важная мысль: место выброса не всегда место причины. Здесь ошибка выброшена в applyDiscount, а неправильные данные пришли из вызова на строке 11.

Breakpoints и пошаговое выполнение#

останавливает программу перед выполнением строки. В паузе можно:

  • посмотреть значения переменных и аргументов;
  • пройти по вверх и увидеть состояние вызывающих функций;
  • вычислить выражение (items.length, promo.percent > 100);
  • выполнять код по шагам.
Команда Что делает
Continue Выполнять до следующего Breakpoint
Step over Выполнить текущую строку целиком, не заходя в вызовы
Step into Зайти внутрь функции, вызываемой на текущей строке
Step out Доработать текущую функцию и остановиться у вызвавшего кода
Conditional Breakpoint Остановиться, только если условие истинно (percent > 100)
Интерактив требует JavaScriptПошаговый отладчик: выполняйте небольшую программу по шагам, ставьте breakpoints, следите за Call Stack и переменными и посмотрите, как формируется Stack Trace.

Остановить программу можно и из кода инструкцией debugger; — она срабатывает, только когда подключён отладчик.

Logging#

— запись событий во время выполнения. В тестах логи нужны, когда отладчик подключить нельзя — например, в CI.

Хорошие логи в тестах:

  • Привязаны к шагам. test.step('Создать заказ через API', …) группирует действия, и в отчёте видно, на каком шаге произошло падение.
  • Содержат идентификаторы. id созданного пользователя, номер заказа, запроса — по ним можно найти записи в логах сервера.
  • Не содержат секретов. Пароли, токены и персональные данные маскируются.
  • Прикрепляются к отчёту, а не только печатаются в консоль: testInfo.attach().
TypeScripttests/order-logging.spec.ts
import { test, expect } from '@playwright/test';

test('заказ появляется в истории', async ({ page, request }, testInfo) => {
  const orderId = await test.step('создать заказ через API', async () => {
    const res = await request.post('/api/orders', { data: { productId: 7, qty: 1 } });
    expect(res.status(), 'создание заказа').toBe(201);
    const body = (await res.json()) as { id: number };
    await testInfo.attach('order.json', { body: JSON.stringify(body, null, 2), contentType: 'application/json' });
    return body.id;
  });

  await test.step('открыть историю заказов', async () => {
    await page.goto('/account/orders');
    await expect(page.getByRole('row', { name: new RegExp(`№ ${orderId}`) })).toBeVisible();
  });
});

Debug Mode в Playwright#

— набор инструментов для пошагового выполнения:

Shell
npx playwright test tests/cart.spec.ts:15 --debug   # Inspector: шаги, подсветка локаторов
npx playwright test --ui                            # UI Mode: таймлайн, DOM-снимки, повторный запуск
npx playwright test --headed --workers=1            # видимый браузер, без параллелизма
PWDEBUG=1 npx playwright test                       # то же, что --debug
DEBUG=pw:api npx playwright test                    # подробный лог вызовов API Playwright
npx playwright show-trace test-results/…/trace.zip  # открыть trace упавшего теста
  • Playwright Inspector (--debug) запускает браузер в видимом режиме, ставит паузу перед каждым действием и подсвечивает элемент, найденный локатором. В нём же можно подобрать локатор.
  • await page.pause() — точка останова в коде теста: выполнение остановится, откроется Inspector.
  • UI Mode (--ui) — интерактивный режим: список тестов, повторный запуск при изменении файла, таймлайн действий с DOM-снимками до и после каждого шага.
  • — главный инструмент для падений в CI: trace содержит действия, DOM-снимки, скриншоты, сетевые запросы, консоль и исходный код. Как включать запись трассировки — в главе «Reporting и Logging».

Для отладки кода теста в VS Code подходит расширение Playwright: зелёная стрелка у теста, breakpoints в .ts файлах, выбор локатора на странице.

Как читать ошибки Playwright#

Ошибка неудачной web-first проверки выглядит примерно так:

Текст
Error: expect(locator).toHaveText(expected) failed

Locator:  getByTestId('total')
Expected: "900 ₽"
Received: "1 000 ₽"
Timeout:  5000ms

Call log:
  - Expect "toHaveText" with timeout 5000ms
  - waiting for getByTestId('total')
    9 × locator resolved to <span data-testid="total">1 000 ₽</span>
      - unexpected value "1 000 ₽"

  at tests/cart.spec.ts:21:47

Здесь уже есть диагноз: элемент найден, но текст за 5 секунд так и не стал ожидаемым — скидка не применилась. Проблема не в локаторе и не в ожидании, а в поведении продукта или данных (промокод просрочен?).

Частые ошибки и что они значат:

Сообщение Вероятная причина Куда смотреть
Timeout 5000ms exceeded в expect Ожидаемое состояние не наступило Received-значение, call log, скриншот
strict mode violation … resolved to 3 elements Локатор неоднозначен Уточнить локатор (, глава 14)
waiting for getByRole(…) до таймаута действия Элемента нет или он не готов к действию DOM-снимок в trace: есть ли элемент, не перекрыт ли
Test timeout of 30000ms exceeded Тест в целом слишком долгий или завис Последнее выполненное действие в trace
Target page, context or browser has been closed Действие после завершения теста — часто забытый await Floating promises (глава 6)
net::ERR_CONNECTION_REFUSED Приложение не запущено или неверный baseURL Окружение, конфигурация

Обработка исключений при отладке#

Частая ошибка — «чинить» падение, перехватывая исключение:

TypeScriptОшибка спрятана
try {
  await expect(page.getByText('Оплачено')).toBeVisible();
} catch {
  console.log('не нашли статус, но ладно');
}

Тест больше не падает, но и ничего не проверяет. Если шаг действительно необязателен (например, баннер cookies иногда не показывается), это нужно выразить явно и без поглощения ошибок проверок:

TypeScripttests/optional-banner.spec.ts
import { test } from '@playwright/test';

test('закрыть баннер cookies, если он есть', async ({ page }) => {
  await page.goto('/');
  const banner = page.getByRole('dialog', { name: 'Cookies' });
  if (await banner.isVisible()) {               // моментальная проверка без ожидания
    await banner.getByRole('button', { name: 'Принять' }).click();
  }
});

А ещё лучше — сделать состояние детерминированным: установить согласия заранее, чтобы баннер не появлялся вовсе. Для случайно появляющихся оверлеев в есть page.addLocatorHandler().

Пример: расследование падения#

В CI упал тест «оплата заказа»:

Текст
Error: expect(locator).toBeVisible() failed
Locator: getByRole('heading', { name: 'Заказ оформлен' })
Expected: visible
Error: element(s) not found
Timeout: 5000ms
  1. Читаем ошибку. Заголовка нет совсем — не «есть, но скрыт».
  2. Открываем trace (show-trace). На DOM-снимке после клика «Оплатить» — страница оплаты с сообщением «Карта отклонена».
  3. Смотрим сеть в trace. POST /api/payments → 402, тело: {"code":"CARD_DECLINED"}.
  4. Ищем причину. Тестовая карта задаётся переменной окружения; в CI на staging она истекла в прошлом месяце.
  5. Классифицируем. Проблема тестовых данных, не продукта и не кода теста. Обновляем данные и добавляем проверку срока действия карты в подготовку теста, чтобы следующая ошибка сразу говорила «тестовая карта просрочена».

На всё — несколько минут, без перезапусков и правок «наугад».

Типичные ошибки#

Начинать с перезапуска

Если тест прошёл со второго раза, причина осталась. Сначала сохраните артефакты и прочитайте ошибку.

Читать Stack Trace снизу или останавливаться на node_modules

Нужен верхний кадр в вашем коде. Кадры библиотек полезны, только если вы подозреваете ошибку в самой библиотеке.

console.log вместо структуры

Сотни строк без привязки к тестам и шагам не помогают при параллельном запуске. Используйте test.step, вложения и отчёты.

Увеличить таймаут как «исправление»

Если элемент не появился за 5 секунд, а таймаут поднят до 60, тест станет падать на минуту дольше. Таймаут меняют, только когда понятна причина долгой операции.

Что важно для собеседования#

JuniorКак читать stack trace?

Ответ

Первая строка — тип и сообщение ошибки. Ниже — кадры стека сверху вниз: верхний — где ошибка выброшена, следующие — кто вызвал. Кадры node_modules и node:internal обычно пропускаю и ищу первый кадр в коде проекта: файл, строку и колонку. Учитываю, что место выброса и место причины могут отличаться: неверные данные часто приходят из вызывающего кода.

JuniorКакие инструменты отладки есть в Playwright?

Ответ

--debug / PWDEBUG=1 — Inspector с пошаговым выполнением и подсветкой локаторов; page.pause() — остановка в нужном месте теста; --ui — UI Mode с таймлайном и DOM-снимками; (show-trace) — разбор записанного прогона, особенно из CI; --headed, --workers=1, DEBUG=pw:api для подробных логов; отладка в VS Code через расширение Playwright.

MiddleТест стабильно проходит локально и падает в CI. Ваши действия?

Ответ

Читаю ошибку и открываю артефакты CI: trace, скриншот, логи. Сравниваю окружения: версия приложения и браузера, данные, переменные окружения, часовой пояс и локаль, разрешение экрана, ресурсы машины (медленнее → гонки проявляются чаще), параллелизм (в CI больше воркеров → конфликты данных). Пробую воспроизвести с условиями CI: тот же Docker-образ, --workers как в CI, --repeat-each. Классифицирую причину: продукт, тест, данные, окружение.

MiddleКоллега обернул нестабильную проверку в try/catch, и тест стал зелёным. Что скажете?

Ответ

Это не исправление, а отключение проверки: тест больше не может упасть по этой причине, то есть ничего не проверяет. Нужно найти причину нестабильности (гонка, данные, окружение) и устранить её. Если шаг действительно необязателен, это выражается явно (проверка isVisible() или addLocatorHandler для оверлеев), а лучше — детерминированным состоянием, при котором вариативности нет.

Проверьте себя#

Тест
1
С какой строки stack trace обычно начинают поиск?

Верхние кадры могут быть внутри библиотек; первый кадр в вашем коде показывает, какое ваше действие привело к ошибке.

2
Отладчик остановился на строке const total = calc(items);. Какая команда покажет, что происходит внутри calc?

Step into заходит внутрь вызываемой функции. Step over выполнил бы calc целиком.

3
Сообщение: Expected: "Оплачен", Received: "Ожидает оплаты", Timeout: 5000ms. Что это означает?

Наличие Received означает, что элемент найден. Проблема — в состоянии приложения или данных, а не в поиске элемента.

Тест падает только в CI. Какие артефакты нужно настроить, чтобы разобраться без локального воспроизведения?

Trace (trace: 'on-first-retry' или 'retain-on-failure'), скриншот и при необходимости видео при падении, вложения с идентификаторами созданных данных, логи шагов (test.step), версию сборки и окружения в отчёте. показывает действия, DOM-снимки, сеть и консоль на каждом шаге.

Чем page.pause() отличается от breakpoint в редакторе?

page.pause() останавливает тест и открывает Inspector: можно смотреть страницу, подбирать локаторы, выполнять действия по шагам. в редакторе останавливает Node.js-код теста и показывает переменные и Call Stack. Первый удобен для работы со страницей, второй — для логики теста и данных.
