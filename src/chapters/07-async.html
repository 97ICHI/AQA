Асинхронное программирование

Event Loop, Promise, async/await, ошибки в асинхронном коде, состояния гонки и параллельное выполнение. Почти каждая строка автотеста асинхронна, и большинство «загадочных» падений начинается здесь.

≈ 13 мин чтенияJ–M
Опирается на: Основы TypeScript
Основная идея

JavaScript выполняет код в одном потоке, а долгие операции (сеть, браузер, таймеры) завершаются позже. Promise — обещание результата, await — «подожди его здесь». Забытый await означает, что тест идёт дальше, не дождавшись действия.

Цель главы: понимать порядок выполнения асинхронного кода и писать тесты без забытых await, гонок и неправильного параллелизма.

Кратко

Каждое действие возвращает ; без await тест не ждёт его завершения, а ошибки теряются или появляются не там.

Главное

  • Один поток: call stack выполняет синхронный код до конца; после каждой задачи (macrotask: таймер, I/O) выполняются все microtasks — поэтому Promise.then срабатывает раньше setTimeout(…, 0). В Node.js цикл устроен сложнее, чем в браузере.
  • async-функция всегда возвращает Promise; await приостанавливает функцию до результата, не блокируя поток.
  • Ошибку await-вызова ловит обычный try/catch; необработанный rejected Promise — unhandledRejection.
  • Race condition — результат зависит от того, какая операция завершится раньше. В тестах: проверка до обновления данных, клик до появления обработчика, ожидание ответа, начатое после клика.
  • Promise.all выполняет независимые операции параллельно и падает при первой ошибке, но не отменяет остальные; allSettled ждёт все.
  • array.forEach(async …) не ждёт итерации — используйте for...of с await или Promise.all(array.map(...)).

Термины

Event Loop
Механизм однопоточного JavaScript: берёт задачу из очереди, выполняет её до опустошения стека, затем выполняет все микрозадачи и переходит к следующей задаче.
Call Stack
Стек функций, выполняемых в данный момент. Каждый вызов добавляет кадр, возврат — снимает. Stack trace — снимок стека в момент ошибки.
Promise
Объект, представляющий результат асинхронной операции: pending, затем fulfilled со значением или rejected с ошибкой.
Microtask
Колбэк Promise или продолжение после await. Все микрозадачи выполняются сразу после текущей задачи, раньше таймеров.
Race Condition
Ситуация, когда результат зависит от того, какая из параллельных операций завершится первой. Частая причина нестабильных тестов.

Важно: Правило ESLint @typescript-eslint/no-floating-promises находит забытые await до запуска тестов — включайте его в каждом проекте.

Почему автотест асинхронный#

Когда тест вызывает page.click(), команда уходит из процесса Node.js в браузер (по сети или через pipe), браузер выполняет её и присылает ответ. Всё это занимает миллисекунды или секунды. Если бы JavaScript ждал ответа, блокируя поток, процесс не мог бы ничего делать параллельно. Поэтому такие операции асинхронны: функция сразу возвращает — объект, который позже получит результат или ошибку.

TypeScripttests/why-async.spec.ts
import { test, expect } from '@playwright/test';

test('каждое действие нужно дождаться', async ({ page }) => {
  await page.goto('/login');                                      // ждём загрузку
  await page.getByLabel('Email').fill('qa@example.com');          // ждём ввод
  await page.getByRole('button', { name: 'Войти' }).click();      // ждём клик
  await expect(page.getByRole('heading', { name: 'Профиль' })).toBeVisible(); // ждём состояние
});

Каждый await здесь не формальность: без него тест «отправит» команду и сразу перейдёт к следующей строке.

Event Loop#

— механизм, по которому однопоточный JavaScript выполняет асинхронный код. Участники:

  • — стек выполняемых сейчас функций. Синхронный код выполняется до конца, его нельзя прервать.
  • Web APIs / API среды — таймеры, сеть, файлы. Они работают вне JavaScript-потока и по завершении ставят колбэк в очередь.
  • Очередь задач (macrotasks) — колбэки таймеров, ввода-вывода, событий.
  • Очередь микрозадач () — колбэки Promise.then/catch/finally и продолжения после await.

Алгоритм: взять одну задачу → выполнить её до опустошения стека → выполнить все микрозадачи (включая новые, добавленные по ходу) → повторить. Поэтому колбэк всегда выполняется раньше setTimeout(…, 0), поставленного в то же время.

JavaScript
console.log('1. синхронный код');
setTimeout(() => console.log('5. setTimeout — macrotask'), 0);
Promise.resolve().then(() => console.log('3. then — microtask'));
queueMicrotask(() => console.log('4. queueMicrotask — microtask'));
console.log('2. синхронный код — конец');
Текст
1. синхронный код
2. синхронный код — конец
3. then — microtask
4. queueMicrotask — microtask
5. setTimeout — macrotask

Event Loop в Node.js и в браузере

Тест выполняется в Node.js, а страница — в браузере: у них два независимых Event Loop. Схема «задача → микрозадачи → следующая задача» верна для обоих и достаточна для написания тестов. Но в Node.js цикл устроен сложнее: у него есть фазы (timers, poll, check и другие), а очередь process.nextTick обрабатывается раньше микрозадач Promise. Порядок setTimeout(fn, 0) и setImmediate(fn) в главном модуле не гарантирован, а внутри колбэка ввода-вывода setImmediate всегда срабатывает первым. Поэтому порядок в примерах выше — модель, а не закон для любой среды.

Интерактив требует JavaScriptВизуализатор Event Loop: пошагово показывает Call Stack, Web APIs, очередь микрозадач, очередь задач и консоль для нескольких фрагментов кода.

Promise#

находится в одном из трёх состояний: pending (ожидание), fulfilled (выполнен со значением) или rejected (отклонён с ошибкой). Перейдя в fulfilled или rejected, он больше не меняется.

JavaScript
const wait = (ms, value) => new Promise((resolve) => setTimeout(() => resolve(value), ms));
const fail = (ms) => new Promise((_, reject) => setTimeout(() => reject(new Error('timeout')), ms));

wait(10, 'данные')
  .then((v) => v.toUpperCase())          // результат then — новый Promise
  .then((v) => console.log('получено:', v))
  .catch((e) => console.log('ошибка:', e.message))
  .finally(() => console.log('finally: освободить ресурсы'));

fail(20).catch((e) => console.log('перехвачено:', e.message));
Текст
получено: ДАННЫЕ
finally: освободить ресурсы
перехвачено: timeout

async/await#

— синтаксис поверх , который делает асинхронный код похожим на синхронный.

  • async function всегда возвращает Promise, даже если внутри return 5.
  • await promise приостанавливает только эту функцию до результата. Поток в это время свободен: выполняет другие задачи.
  • Если Promise отклонён, await выбрасывает исключение — его ловит обычный try/catch.
JavaScript
async function getPrice() {
  await new Promise((r) => setTimeout(r, 10)); // имитация запроса
  return 1990;
}

async function main() {
  console.log('A. до вызова');
  const pending = getPrice();          // без await — это Promise
  console.log('B. тип без await:', pending instanceof Promise);
  const price = await pending;         // с await — значение
  console.log('C. цена:', price);
}

main();
console.log('D. main() уже вернула управление');
Текст
A. до вызова
B. тип без await: true
D. main() уже вернула управление
C. цена: 1990

Строка D выводится раньше C: на первом await функция main приостановилась и вернула управление вызывающему коду.

Ошибки в асинхронном коде#

TypeScripterrors-async.ts
async function fetchOrder(id: number): Promise<{ id: number; status: string }> {
  await new Promise((r) => setTimeout(r, 10));
  if (id <= 0) throw new Error(`Некорректный id: ${id}`);
  return { id, status: 'paid' };
}

async function main() {
  try {
    await fetchOrder(-1);           // ошибка «вылетит» из await
  } catch (e) {
    console.log('поймали:', (e as Error).message);
  }

  // Без await try/catch бесполезен: Promise отклонится позже, вне блока
  try {
    void fetchOrder(-2).catch((e: Error) => console.log('поймали через .catch:', e.message));
  } catch {
    console.log('сюда мы не попадём');
  }
}
void main();

— , который никто не ждёт и не обрабатывает. В тестах это главный источник странностей:

  • действие выполняется после проверки или вообще после окончания теста;
  • ошибка действия теряется или прилетает в следующий тест;
  • может сообщить, что страница или контекст уже закрыты (Target page, context or browser has been closed).
TypeScriptЗабытый await
test('добавление в корзину', async ({ page }) => {
  await page.goto('/product/7');
  page.getByRole('button', { name: 'В корзину' }).click(); // не ждём!
  expect(page.getByTestId('cart-count')).toHaveText('1');   // не ждём!
});
// Тест завершится до клика и проверки — и пройдёт, ничего не проверив.
TypeScriptКаждое действие и проверка с await
test('добавление в корзину', async ({ page }) => {
  await page.goto('/product/7');
  await page.getByRole('button', { name: 'В корзину' }).click();
  await expect(page.getByTestId('cart-count')).toHaveText('1');
});
Автоматическая защита

Включите в ESLint правила @typescript-eslint/no-floating-promises и @typescript-eslint/await-thenable, а также playwright/missing-playwright-await из eslint-plugin-playwright. Они находят забытые await до запуска тестов.

Race Conditions#

— ситуация, когда результат зависит от того, какая из параллельных операций завершится первой. В автотестах гонки — самая частая причина нестабильности.

Гонка 1: проверка раньше обновления. Тест кликает «Сохранить» и сразу читает текст статуса через textContent(). Если сервер ответил быстро, тест пройдёт; если медленно — прочитает старое значение. Решение — , которая ждёт нужного состояния (глава 15).

Гонка 2: ожидание ответа начато после действия. Если быстрый ответ придёт раньше, чем тест начал его ждать, ожидание не дождётся ничего и упадёт по таймауту.

TypeScripttests/wait-response.spec.ts
import { test, expect } from '@playwright/test';

test('корзина сохраняется на сервере', async ({ page }) => {
  await page.goto('/product/7');
  // 1. Сначала начинаем ждать ответ (Promise создан, но не ожидается)
  const cartResponse = page.waitForResponse(
    (r) => r.url().endsWith('/api/cart') && r.request().method() === 'POST',
  );
  // 2. Затем выполняем действие, которое вызовет запрос
  await page.getByRole('button', { name: 'В корзину' }).click();
  // 3. Теперь дожидаемся результата — он не мог «проскочить»
  const response = await cartResponse;
  expect(response.status()).toBe(200);
});

Гонка 3: общие данные в параллельных тестах. Два теста одновременно меняют корзину одного пользователя. Это гонка уже между процессами — подробно в главе «Параллельное выполнение».

Параллельное выполнение#

Независимые асинхронные операции можно запускать одновременно и ждать вместе:

JavaScript
const delay = (ms, v) => new Promise((r) => setTimeout(() => r(v), ms));

async function sequential() {
  const t = Date.now();
  await delay(100, 'users');
  await delay(100, 'products');
  return Date.now() - t;
}

async function parallel() {
  const t = Date.now();
  await Promise.all([delay(100, 'users'), delay(100, 'products')]);
  return Date.now() - t;
}

const s = await sequential();
const p = await parallel();
console.log('последовательно ≈ 200 мс:', s >= 195);
console.log('параллельно ≈ 100 мс:', p < 150);

const results = await Promise.allSettled([delay(10, 'ok'), Promise.reject(new Error('boom'))]);
console.log(results.map((r) => r.status).join(', '));
Текст
последовательно ≈ 200 мс: true
параллельно ≈ 100 мс: true
fulfilled, rejected
Метод Ждёт При ошибке
Promise.all Все Отклоняется сразу при первой ошибке
Promise.allSettled Все Никогда не отклоняется, возвращает статусы
Promise.race Первый завершённый Результат или ошибка первого
Promise.any Первый успешный Отклоняется, если все упали

Где это полезно в тестах: подготовка независимых данных через API (Promise.all для создания трёх товаров), параллельные запросы в API-тестах, ожидание ответа одновременно с действием.

Promise.all получает уже запущенные операции: они стартуют в момент вызова функций, а не внутри all. После первого отказа остальные операции продолжаются — all их не отменяет. Если вы создаёте несколько сущностей параллельно, учитывайте частично успешный результат и очищайте всё созданное: allSettled помогает собрать результаты, но сам ничего не удаляет.

Не распараллеливайте действия на одной странице

Promise.all([page.click(a), page.click(b)]) на одной странице даёт непредсказуемый порядок действий. Пользователь не кликает в две кнопки одновременно — тест тоже не должен. Параллелизм между тестами обеспечивает раннер с отдельными процессами-воркерами (глава 25).

Ловушка forEach#

JavaScript
const ids = [1, 2, 3];
const deleted = [];
const remove = (id) => new Promise((r) => setTimeout(() => { deleted.push(id); r(); }, 10));

ids.forEach(async (id) => { await remove(id); }); // forEach не ждёт колбэки
console.log('после forEach удалено:', deleted.length);

for (const id of ids) await remove(id);           // последовательно и с ожиданием
console.log('после for...of удалено:', deleted.length);
Текст
после forEach удалено: 0
после for...of удалено: 6

forEach запустил три удаления, не дождавшись их, поэтому сразу после него удалено 0. К концу цикла for...of завершились и старые три удаления, и три новых — всего 6. В тестах такая ошибка приводит к «очистке данных», которая на самом деле происходит уже во время следующего теста.

Пример: как асинхронность делает тест нестабильным#

Тест проверяет, что после применения промокода сумма уменьшилась:

TypeScriptНестабильная версия
test('промокод уменьшает сумму', async ({ page }) => {
  await page.goto('/cart');
  await page.getByLabel('Промокод').fill('SALE10');
  await page.getByRole('button', { name: 'Применить' }).click();
  const total = await page.getByTestId('total').textContent(); // прочитать сразу
  expect(total).toBe('900 ₽');
});

click() завершается, когда клик выполнен, а не когда сервер пересчитал сумму. textContent() читает значение один раз — до или после обновления, в зависимости от скорости сервера. Локально тест проходит, в загруженном CI — падает.

TypeScriptСтабильная версия
test('промокод уменьшает сумму', async ({ page }) => {
  await page.goto('/cart');
  await page.getByLabel('Промокод').fill('SALE10');
  await page.getByRole('button', { name: 'Применить' }).click();
  await expect(page.getByTestId('total')).toHaveText('900 ₽'); // ждёт до таймаута
});

toHaveText повторяет проверку, пока текст не станет ожидаемым или не истечёт таймаут expect (по умолчанию 5 секунд).

Типичные ошибки#

Забытый await перед действием или expect

Тест завершается раньше, чем действие выполнено, и проходит без проверки. Включите ESLint-правила для floating promises.

await в forEach

forEach игнорирует возвращаемые . Используйте for...of для последовательного выполнения или Promise.all(items.map(...)) для параллельного.

waitForTimeout вместо ожидания события

Фиксированная пауза либо слишком короткая (тест нестабилен), либо слишком длинная (тест медленный). Ждите конкретного состояния или события.

Начинать ожидание после действия

await click(); await page.waitForResponse(...) пропустит быстрый ответ. Создайте Promise ожидания до действия.

Что важно для собеседования#

JuniorОбъясните Event Loop. Что выполнится раньше: setTimeout(fn, 0) или Promise.resolve().then(fn)?

Ответ

В упрощённой модели браузера JavaScript выполняет код в одном потоке. берёт задачу (macrotask: таймер, I/O, событие), выполняет её до опустошения , затем выполняет все микрозадачи (колбэки Promise, продолжения после await) и только потом берёт следующую задачу. Поэтому then выполнится раньше setTimeout(…, 0), даже если таймер поставлен первым.

JuniorЧто произойдёт, если забыть await перед действием Playwright?

Ответ

Метод вернёт , а тест сразу перейдёт к следующей строке. Действие выполнится позже — после проверки или после завершения теста; ошибка может потеряться или появиться как «Target , context or browser has been closed». Если забыт await перед expect, тест может пройти, ничего не проверив. Защита — ESLint (no-floating-promises, eslint-plugin-playwright).

MiddleКак правильно дождаться ответа сервера, который вызывается кликом?

Ответ

Создать Promise ожидания до клика, выполнить клик, затем дождаться Promise: const resp = page.waitForResponse(pred); await button.click(); await resp;. Если начать ждать после клика, быстрый ответ может прийти раньше и ожидание завершится по таймауту — это гонка.

MiddleКогда использовать Promise.all, а когда последовательные await?

Ответ

Promise.all — для независимых операций, которые можно выполнить одновременно: создать несколько тестовых сущностей через API, отправить параллельные запросы. Последовательные await — когда операции зависят друг от друга или выполняются на одной странице (действия пользователя). Promise.all падает при первой ошибке, не отменяя остальные операции; если нужен результат каждой — allSettled.

Частая ошибка

Распараллеливать клики на одной странице через Promise.all.
MiddleПочему items.forEach(async (i) => await remove(i)) не дожидается удаления?

Ответ

forEach вызывает колбэк и игнорирует возвращаемое значение — Promise никто не ждёт. Цикл завершается сразу, удаление идёт в фоне. Нужно for (const i of items) await remove(i) (последовательно) или await Promise.all(items.map(remove)) (параллельно).

Тест
1
В каком порядке выведутся буквы: setTimeout(() => log('A'), 0); Promise.resolve().then(() => log('B')); log('C');?

Сначала весь синхронный код (C), затем микрозадачи (B), затем следующая macrotask — таймер (A).

Что вернёт async function f() { return 5 } при вызове f() без await?

async-функция всегда возвращает Promise.

3
Почему waitForResponse нужно вызвать до клика, а ждать — после?

Ожидание ловит только события, произошедшие после его создания. Создав Promise заранее, мы гарантируем, что ответ не «проскочит».

Что будет, если в тесте забыть await перед expect(locator).toBeVisible()?

Проверка запустится, но тест не будет её ждать: он перейдёт к следующей строке и может завершиться успешно до окончания проверки. Если проверка упадёт позже, ошибка может появиться в другом месте или потеряться. Тест становится ложноположительным.

Чем Promise.all опасен при подготовке данных и когда лучше allSettled?

Promise.all отклоняется при первой ошибке, а остальные операции продолжают выполняться без контроля: часть данных создана, часть нет. Для подготовки это допустимо, если очистка не зависит от результата. allSettled нужен, когда важно знать результат каждой операции — например, при очистке созданных сущностей: удалить всё, что удалось, и сообщить о неудачах.
