Автоматизация API на Playwright

APIRequestContext и фикстура request, организация клиентов API, авторизованные контексты, проверка ответов, создание и гарантированное удаление тестовых сущностей, сочетание API- и UI-шагов в одном тесте.

≈ 10 мин чтенияJ–M
Опирается на: Основы API TestingFixtures и Hooks
Основная идея

Playwright Test умеет работать с HTTP напрямую — без браузера. Тот же раннер, фикстуры, отчёты и trace, что и для UI. Клиенты API становятся общим фундаментом: на них стоят и API-тесты, и быстрая подготовка данных для UI.

Цель главы: писать типизированные API-тесты на Playwright с авторизацией, проверками и надёжной очисткой созданных данных.

Кратко

request — с baseURL и опциями из конфига; клиенты ресурсов оборачивают его в типизированные методы; фикстуры создают сущности и удаляют их в teardown.

Главное

  • request.get/post/put/patch/delete(url, { data, params, headers, form, multipart }) → APIResponse с status(), ok(), headers(), json(), text().
  • await expect(response).toBeOK() — проверка 2xx с понятной ошибкой; точный код — expect(response.status()).toBe(201).
  • request.newContext({ baseURL, extraHTTPHeaders }) создаёт отдельный контекст — например, с токеном другой роли; его нужно закрывать (dispose()).
  • Клиент ресурса: методы с типами запросов и ответов, проверка статуса внутри методов подготовки данных.
  • Созданные сущности удаляются в teardown фикстуры; для удаления многих — реестр и Promise.allSettled.
  • Config, transport, services, validation, fixtures и tests имеют разные обязанности; не валидирует во время выполнения.

Термины

APIRequestContext
HTTP-клиент Playwright (фикстура request, page.request, request.newContext): отправка запросов с baseURL, заголовками и cookies без браузера.
API Client
Класс с типизированными методами для эндпоинтов одного ресурса; скрывает пути, формат тела и разбор ответов.
API Fixture
Фикстура, которая даёт тесту авторизованный клиент или созданную через API сущность и удаляет её после теста.
Test Data Cleanup
Удаление данных, созданных тестом. Надёжнее всего — в teardown фикстуры, который выполняется и при падении.
API Testing
Проверка системы через программный интерфейс: отправка запросов и проверка статуса, заголовков, тела ответа и побочных эффектов.

Важно: Не используйте в тестах failOnStatusCode: true для проверяемых запросов: тест упадёт без информации о теле ответа. Для запросов подготовки данных — допустимо и полезно.

Фикстура request и APIRequestContext#

— HTTP-клиент . Фикстура request даёт контекст с настройками из use конфига (baseURL, extraHTTPHeaders, httpCredentials, ignoreHTTPSErrors, storageState).

TypeScripttests/products-api.spec.ts
import { test, expect } from '@playwright/test';

test('GET /api/products возвращает товары категории', async ({ request }) => {
  const res = await request.get('/api/products', { params: { category: 'audio', limit: 10 } });
  await expect(res).toBeOK();                               // 2xx, иначе ошибка с телом ответа
  const body = (await res.json()) as { items: { category: string; price: number }[]; total: number };
  expect(body.items.length).toBeGreaterThan(0);
  expect(body.items.every((p) => p.category === 'audio')).toBe(true);
  expect(body.total).toBeGreaterThanOrEqual(body.items.length);
});

test('разные способы передачи тела', async ({ request }) => {
  await request.post('/api/orders', { data: { productId: 1, qty: 1 } });          // JSON
  await request.post('/login', { form: { email: 'qa@example.com', password: 'x' } }); // x-www-form-urlencoded
  await request.post('/api/avatars', {
    multipart: { file: { name: 'a.png', mimeType: 'image/png', buffer: Buffer.from([137, 80, 78, 71]) } },
  });
});

Авторизованные контексты#

Токен получают в фикстуре и создают контекст с заголовком Authorization:

TypeScriptsrc/api/auth.ts
import { request as playwrightRequest, expect, type APIRequestContext } from '@playwright/test';

export async function apiAs(baseURL: string, email: string, password: string): Promise<APIRequestContext> {
  const anon = await playwrightRequest.newContext({ baseURL });
  const res = await anon.post('/api/auth/login', { data: { email, password } });
  expect(res.status(), `вход ${email}`).toBe(200);
  const { accessToken } = (await res.json()) as { accessToken: string };
  await anon.dispose();
  return playwrightRequest.newContext({
    baseURL,
    extraHTTPHeaders: { Authorization: `Bearer ${accessToken}` },
  });
}

Клиенты ресурсов#

собирает знание об эндпоинтах ресурса в одном месте: пути, формат тела, типы. Тесты вызывают методы, а не собирают URL вручную.

TypeScriptsrc/api/OrdersApi.ts
import { expect, type APIRequestContext, type APIResponse } from '@playwright/test';

export type OrderStatus = 'created' | 'paid' | 'shipped' | 'delivered' | 'cancelled';
export interface OrderItem { productId: number; qty: number }
export interface Order { id: number; status: OrderStatus; items: OrderItem[]; total: number }

export class OrdersApi {
  constructor(private readonly request: APIRequestContext) {}

  // «Сырые» методы возвращают APIResponse — для тестов, проверяющих статусы и ошибки
  createRaw(items: OrderItem[]): Promise<APIResponse> {
    return this.request.post('/api/orders', { data: { items } });
  }
  getRaw(id: number): Promise<APIResponse> {
    return this.request.get(`/api/orders/${id}`);
  }
  setStatusRaw(id: number, status: OrderStatus): Promise<APIResponse> {
    return this.request.patch(`/api/orders/${id}`, { data: { status } });
  }

  // Методы подготовки данных сразу проверяют успех и возвращают модель
  async create(items: OrderItem[]): Promise<Order> {
    const res = await this.createRaw(items);
    expect(res.status(), `создание заказа: ${await res.text()}`).toBe(201);
    return (await res.json()) as Order;
  }
  async delete(id: number): Promise<void> {
    const res = await this.request.delete(`/api/orders/${id}`);
    expect([204, 404], `удаление заказа ${id}`).toContain(res.status());
  }
}

Разделение «сырых» методов и методов подготовки важно: тест валидации должен получить ответ 422 и проверить его, а фикстура подготовки должна громко упасть, если не смогла создать заказ, — с телом ответа в сообщении.

import { test, expect } from '../../src/fixtures/api';

test('созданный заказ можно оплатить', async ({ ordersApi, createdOrder }) => {
  const res = await ordersApi.setStatusRaw(createdOrder.id, 'paid');

  expect(await res.json()).toMatchObject({ code: 'INVALID_TRANSITION' });
});

Когда тест создаёт несколько сущностей по ходу выполнения, удобен реестр:

TypeScriptsrc/fixtures/cleanup.ts
import { test as base, type APIRequestContext } from '@playwright/test';

type Cleanup = { track: (path: string) => void };

export const test = base.extend<Cleanup>({
  track: async ({ request }, use) => {
    const created: string[] = [];
    await use((path) => { created.push(path); });
    // удаляем в обратном порядке (сначала зависимые), не прерываясь на ошибках
    const results = await Promise.allSettled(created.reverse().map((p) => remove(request, p)));
    const failed = results.filter((r) => r.status === 'rejected');
    if (failed.length) console.warn(`Не удалось удалить ${failed.length} сущностей`);
  },
});

async function remove(request: APIRequestContext, path: string) {
  const res = await request.delete(path);
  if (![200, 204, 404].includes(res.status())) throw new Error(`DELETE ${path}: ${res.status()}`);
}

API и UI в одном тесте#

Частая и эффективная схема: подготовить через API, проверить через UI (или наоборот). page.request использует cookies контекста страницы, поэтому данные, созданные им, видит тот же пользователь в браузере:

TypeScripttests/ui/order-history.spec.ts
import { test, expect } from '@playwright/test';

test('оплаченный заказ отображается в истории', async ({ page }) => {
  await page.goto('/');                                   // контекст с авторизацией (storageState)
  const res = await page.request.post('/api/orders', { data: { items: [{ productId: 1, qty: 1 }] } });
  expect(res.status()).toBe(201);
  const { id } = (await res.json()) as { id: number };
  await page.request.patch(`/api/orders/${id}`, { data: { status: 'paid' } });

  await page.goto('/account/orders');
  const row = page.getByRole('row', { name: new RegExp(`№\\s?${id}`) });
  await expect(row).toContainText('Оплачен');
  await page.request.delete(`/api/orders/${id}`);
});

Тест проверяет отображение истории, не проходя через каталог, корзину и оплату в UI: подготовка заняла десятки миллисекунд вместо десятков секунд. (В реальном проекте удаление переносится в teardown фикстуры, как выше.)

Типичные ошибки#

Проверять статус, не показывая тело при падении

expect(res.status()).toBe(201) при падении сообщит «received 500» без причины. Добавляйте тело в сообщение (expect(res.status(), await res.text())) или используйте toBeOK(), который выводит тело.

Не закрывать созданные контексты

Контексты, созданные request.newContext(), держат соединения и память. Закрывайте их dispose() в teardown фикстуры.

Очистка, которая роняет тест

Если удаление в teardown падает из-за того, что тест уже удалил сущность, — допускайте 404 в очистке. Падение очистки не должно скрывать результат теста.

Одни и те же данные для всех воркеров

Тесты, параллельно меняющие один и тот же заказ, — гонка. Каждый тест создаёт свою сущность.

Что важно для собеседования#

JuniorКак сделать так, чтобы падение API-теста было понятным?

Ответ

Использовать await expect(res).toBeOK() (выводит тело ответа) или передавать тело в сообщение проверки: expect(res.status(), await res.text()).toBe(201). Проверять точный код, а не только «успех», и прикладывать к отчёту запрос/ответ при необходимости (без секретов).

MiddleКак вы организуете код API-тестов на Playwright?

Ответ

Слои: конфиг с baseURL и отдельным проектом api; клиенты ресурсов (OrdersApi) с типами моделей, «сырыми» методами для проверок и методами подготовки, которые проверяют успех; фабрики данных; фикстуры, которые дают авторизованные клиенты и созданные сущности с очисткой в teardown; тесты — только сценарии и ожидания. Схемы ответов — отдельно для валидации.

MiddleКак гарантировать, что тестовые данные удаляются, даже если тест упал?

Ответ

Удалять в teardown фикстуры (код после await use()), который выполняется независимо от результата теста. Для нескольких сущностей — реестр созданного и удаление в обратном порядке через Promise.allSettled, допуская 404. Дополнительно — уникальная метка данных теста и периодическая уборка стенда по этой метке на случай аварийно прерванных прогонов.

MiddleКак сочетать API и UI в одном тесте?

Ответ

Подготовка состояния через API (быстро и стабильно), проверка отображения или пользовательского действия через UI — и наоборот: действие в UI, проверка результата через API или базу. page.request делит cookies с контекстом страницы, поэтому созданные данные видит тот же пользователь. Так UI-тест проверяет только свой экран, а не всю цепочку.

Проверьте себя#

Тест
1
Где правильно удалять заказ, созданный для теста?

Teardown выполняется даже при падении теста, поэтому данные гарантированно убираются.

2
Чем page.request отличается от фикстуры request?

Поэтому данные, созданные через page.request, видит пользователь этого контекста в браузере.

3
Зачем клиенту API «сырые» методы, возвращающие APIResponse?

Тесту валидации нужен ответ 422, а фикстуре подготовки — гарантированный успех с понятной ошибкой.

Почему очистку многих сущностей лучше делать через Promise.allSettled, а не Promise.all?

Promise.all прервётся на первой ошибке, и часть сущностей останется. allSettled дождётся всех удалений, после чего можно сообщить о неудачных — максимум данных будет удалён.

Как подготовить в UI-тесте заказ в статусе «доставлен», если в интерфейсе до этого 15 шагов?

Создать заказ и перевести его по статусам через API (если есть тестовые или административные эндпоинты) — с теми же правами, что использует приложение. Тест проверяет только то, что ему нужно: отображение доставленного заказа. Если API для перехода нет — обсудить с командой тестовый эндпоинт или подготовку через с проверкой реалистичности состояния.
