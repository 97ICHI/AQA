Locators

Как Playwright находит элементы: getByRole, getByLabel, getByText, getByTestId, CSS и XPath; фильтрация и цепочки; строгий режим; списки, iframe и Shadow DOM — и почему одни локаторы переживают редизайн, а другие ломаются от смены класса.

≈ 13 мин чтенияJ
Опирается на: Архитектура Playwright
Основная идея

Локатор описывает, как найти элемент так, как его находит пользователь: по роли, подписи и тексту. Такой локатор устойчив к изменениям вёрстки и одновременно проверяет доступность интерфейса.

Цель главы: писать однозначные и устойчивые локаторы и выбирать стратегию поиска по приоритету.

Кратко

— ленивое описание поиска, которое выполняется заново при каждом действии. Предпочитайте пользовательские локаторы (роль, подпись, текст), затем test id, и только в крайнем случае CSS/XPath.

Главное

  • Приоритет: getByRole → getByLabel → getByPlaceholder → getByText → getByAltText/getByTitle → getByTestId → locator(css/xpath).
  • getByRole(role, { name }) ищет по ARIA-роли и доступному имени; имя и getByText по умолчанию сравниваются как подстрока без учёта регистра, exact: true — точное совпадение.
  • Строгий режим: действие с локатором, который нашёл несколько элементов, падает с strict mode violation.
  • Уточнение: filter({ hasText, has, hasNot, visible }), цепочки parent.getByRole(...), first(), nth(i) (последние — только когда порядок действительно важен).
  • CSS-локаторы проходят через открытый , — нет; для iframe — frameLocator() или contentFrame().
  • При локализации accessible name меняется; test ID и проверка перевода решают разные задачи.

Термины

Locator
Ленивое описание того, как найти элемент на странице. В Playwright поиск выполняется заново при каждом действии и проверке.
Accessible Name
Имя элемента для вспомогательных технологий: из aria-labelledby, aria-label, связанного label, текста или alt. По нему ищет getByRole(..., { name }).
ARIA Role
Назначение элемента для вспомогательных технологий: button, link, textbox, checkbox, heading и др. Бывает явной (атрибут role) и неявной (из тега).
Test ID
Атрибут разметки для тестов (по умолчанию data-testid). Устойчив к изменениям текста и вёрстки; ищется через getByTestId.
CSS Selector
Выражение выбора элементов по тегам, классам, id, атрибутам и структуре DOM. Проходит через открытый Shadow DOM.

Важно: Локаторы по классам вроде .btn-primary-3x9f и длинные XPath вида /html/body/div[3]/div[2]/button ломаются от любой правки вёрстки и не говорят ничего о смысле элемента.

Что такое Locator#

в — не найденный элемент, а описание того, как его найти. Поиск выполняется каждый раз, когда вы что-то делаете с локатором:

TypeScripttests/locator-lazy.spec.ts
import { test, expect } from '@playwright/test';

test('локатор ищет элемент заново при каждом действии', async ({ page }) => {
  await page.goto('/cart');
  const total = page.getByTestId('cart-total');   // поиска ещё не было
  await page.getByRole('button', { name: 'Увеличить количество' }).click();
  await expect(total).toHaveText('9 980 ₽');      // поиск сейчас, с повторами до таймаута
});

Поэтому локатор переживает перерисовку: если фреймворк заменил DOM-узел после обновления, следующий поиск найдёт новый. Старый API page.$() возвращал ElementHandle — ссылку на конкретный узел, который мог «устареть»; в новом коде его не используют.

Как пользователь находит элементы#

Пользователь не видит классов и id. Он ищет кнопку «Оформить заказ», поле «Email», ссылку «Корзина». рекомендует искать так же:

Метод Ищет по Пример
getByRole(role, { name }) ARIA-роли и доступному имени getByRole('button', { name: 'Оформить заказ' })
getByLabel(text) Подписи поля (<label>, aria-label, aria-labelledby) getByLabel('Email')
getByPlaceholder(text) Атрибуту placeholder getByPlaceholder('Введите промокод')
getByText(text) Видимому тексту getByText('Товар добавлен')
getByAltText(text) Атрибуту alt изображения getByAltText('Логотип')
getByTitle(text) Атрибуту title getByTitle('Удалить')
getByTestId(id) Атрибуту data-testid (настраивается) getByTestId('cart-total')
locator(selector) CSS или locator('.price'), locator('xpath=//td[2]')

getByRole и доступное имя#

— роль элемента для вспомогательных технологий: button, link, textbox, checkbox, radio, combobox, heading, list, listitem, row, cell, dialog, alert, navigation, tab… Многие роли неявные: <button> — button, <a href> — link, <input type="text"> — textbox, <h1>–<h6> — heading, <ul> — list.

— имя, которое озвучит скринридер. Источники в порядке приоритета: aria-labelledby, aria-label, связанный <label>, текст внутри элемента (для кнопок и ссылок), alt изображения, title.

TypeScripttests/roles.spec.ts
import { test, expect } from '@playwright/test';

test('локаторы по роли', async ({ page }) => {
  await page.goto('/checkout');
  await page.getByRole('textbox', { name: 'Email' }).fill('qa@example.com');
  await page.getByRole('checkbox', { name: 'Согласен с условиями' }).check();
  await page.getByRole('combobox', { name: 'Способ доставки' }).selectOption('Курьер');
  await page.getByRole('button', { name: 'Оплатить', exact: true }).click();
  await expect(page.getByRole('heading', { level: 1 })).toHaveText('Заказ оформлен');
  await expect(page.getByRole('alert')).toBeHidden();
});

Правила сравнения имени:

  • по умолчанию — подстрока без учёта регистра (name: 'оплат' найдёт «Оплатить» и «Оплата частями»);
  • exact: true — полное совпадение с учётом регистра (пробелы по краям обрезаются);
  • регулярное выражение — полный контроль: name: /^Оплатить$/.

Дополнительные опции: checked, disabled, expanded, pressed, selected, level (для заголовков), includeHidden.

Локатор по роли — бесплатная проверка доступности

Если getByRole('button', { name: 'Удалить' }) не находит иконку-кнопку с корзиной, значит, у неё нет доступного имени, и пользователь скринридера тоже не поймёт, что это. Это повод попросить разработчиков добавить aria-label, а не переходить на CSS-селектор.

getByText, getByLabel и другие#

TypeScripttests/text-label.spec.ts
import { test, expect } from '@playwright/test';

test('поиск по тексту и подписи', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('qa@example.com');
  await page.getByLabel('Пароль').fill('Str0ngPass!');
  await page.getByRole('button', { name: 'Войти' }).click();
  await expect(page.getByText('Добро пожаловать')).toBeVisible();           // подстрока
  await expect(page.getByText('Баланс: 0 ₽', { exact: true })).toBeVisible(); // точный текст
  await expect(page.getByText(/^Заказов: \d+$/)).toBeVisible();              // шаблон
});

Особенности getByText:

  • по умолчанию ищет подстроку без учёта регистра и нормализует пробелы (несколько пробелов и переносы считаются одним пробелом);
  • находит наименьший элемент, содержащий текст;
  • для кнопок, ссылок и заголовков лучше getByRole с name — он точнее и проверяет роль.

getByText уместен для неинтерактивного содержимого: сообщения, абзацы, ячейки.

getByTestId#

— атрибут, добавленный в разметку специально для тестов: <span data-testid="cart-total">. Атрибут по умолчанию — data-testid; другой задаётся в конфиге (use: { testIdAttribute: 'data-qa' }).

Плюсы: устойчив к изменению текста, переводов и вёрстки; однозначен. Минусы: не связан с тем, что видит пользователь, требует договорённости с разработчиками.

Когда Test ID — лучший выбор:

  • элемент без роли и стабильного текста (контейнер карточки, сумма, бейдж);
  • текст меняется (локализация, динамические значения);
  • одинаковые элементы, которые нужно различать (карточки товаров по id: data-testid="product-card-7").

CSS и XPath#

и — универсальные языки выбора элементов, которые описывают структуру DOM, а не смысл для пользователя.

TypeScripttests/css-xpath.spec.ts
import { test, expect } from '@playwright/test';

test('CSS и XPath — когда без них не обойтись', async ({ page }) => {
  await page.goto('/catalog');
  // CSS по устойчивому атрибуту — допустимо
  await expect(page.locator('[data-sku="PULSE-01"] .price')).toHaveText('4 990 ₽');
  // XPath — например, ячейка в строке таблицы, найденной по тексту другой ячейки
  await expect(page.locator('xpath=//tr[td[normalize-space()="Наушники Pulse"]]/td[3]')).toHaveText('12');
});

Селектор Устойчивость Почему

Фильтрация и цепочки#

Часто элемент однозначен только в контексте: кнопка «В корзину» есть у каждого товара.

TypeScripttests/filter.spec.ts
import { test, expect } from '@playwright/test';

test('кнопка в карточке нужного товара', async ({ page }) => {
  await page.goto('/catalog');
  const card = page.getByTestId('product-card').filter({ hasText: 'Наушники Pulse' });
  await card.getByRole('button', { name: 'В корзину' }).click();

  // Карточки в наличии: есть кнопка «В корзину», нет бейджа «Нет в наличии»
  const available = page
    .getByTestId('product-card')
    .filter({ has: page.getByRole('button', { name: 'В корзину' }) })
    .filter({ hasNot: page.getByText('Нет в наличии') });
  await expect(available).toHaveCount(5);

  // Строка таблицы по тексту, затем ячейка внутри неё
  const row = page.getByRole('row').filter({ hasText: 'Заказ №1042' });
  await expect(row.getByRole('cell').nth(2)).toHaveText('Оплачен');
});
Метод Назначение
filter({ hasText }) / filter({ hasNotText }) Содержит / не содержит текст (строка или RegExp)
filter({ has }) / filter({ hasNot }) Содержит / не содержит дочерний элемент по другому локатору
filter({ visible: true }) Только видимые элементы
locator.getBy…() Поиск внутри найденного элемента (цепочка)
first(), last(), nth(i) Элемент по позиции
or(other), and(other) Любой из двух локаторов / оба условия сразу
nth() и first() — последнее средство

Позиционные локаторы ломаются, когда меняется порядок элементов: добавили новый товар — тест кликнул не туда, и, возможно, даже не упал. Используйте их, когда порядок — часть проверяемого поведения (сортировка) или элементы действительно идентичны.

Строгий режим#

: действие (click, fill, check…) и большинство проверок требуют, чтобы локатор нашёл ровно один элемент. Иначе тест падает:

Текст
Error: locator.click: Error: strict mode violation: getByRole('button', { name: 'Удалить' }) resolved to 3 elements:
    1) <button aria-label="Удалить Наушники Pulse">…</button> aka getByRole('button', { name: 'Удалить Наушники Pulse' })
    2) <button aria-label="Удалить Мышь Click">…</button> aka getByRole('button', { name: 'Удалить Мышь Click' })
    3) …

Это защита: без неё тест молча кликнул бы по первому найденному элементу. даже подсказывает однозначные альтернативы. Исправление — уточнить локатор (exact, фильтр, поиск внутри контейнера), а не добавлять .first() автоматически.

Для списков строгий режим не мешает — используйте проверки, рассчитанные на множество элементов:

TypeScripttests/lists.spec.ts
import { test, expect } from '@playwright/test';

test('сортировка по цене', async ({ page }) => {
  await page.goto('/catalog?sort=price');
  const prices = page.getByTestId('product-price');
  await expect(prices).toHaveCount(8);
  await expect(prices).toHaveText(['390 ₽', '590 ₽', '1 290 ₽', '3 490 ₽', '4 990 ₽', '7 990 ₽', '12 990 ₽', '21 990 ₽']);
  const all = await prices.allInnerTexts(); // массив строк — для собственных вычислений
  expect(all.length).toBe(8);
});

iframe и Shadow DOM#

iframe — отдельный документ внутри страницы (платёжная форма, виджет карты, капча). Обычный локатор страницы внутрь не заглядывает:

TypeScripttests/iframe.spec.ts
import { test } from '@playwright/test';

test('оплата в iframe платёжного провайдера', async ({ page }) => {
  await page.goto('/checkout/pay');
  const payment = page.frameLocator('iframe[title="Оплата картой"]');
  await payment.getByLabel('Номер карты').fill('4242 4242 4242 4242');
  await payment.getByLabel('Срок действия').fill('12/30');
  await payment.getByRole('button', { name: 'Оплатить' }).click();
});

— инкапсулированное поддерево веб-компонента. Локаторы (getBy… и CSS) проходят через открытый Shadow DOM автоматически; — нет. Закрытый (mode: 'closed') Shadow DOM недоступен.

Локаторы при смене языка и изменении DOM#

Интерфейс на нескольких языках и изменчивая разметка — частые причины ложных падений. Нужны локаторы, устойчивые к переводу и к структуре DOM. часто переводится, поэтому getByRole с русским name не станет автоматически универсальным.

СитуацияРешениеЧто проверить
Один языкgetByRole/getByLabel с точным именемУникальность и связь label/input
Проверка разных языковИмена из словаря ожидаемых переводовПеревод, role, поведение
Одна бизнес-проверка для всех языковСогласованный data-testidСтабильность атрибута; отдельно проверка перевода
Динамический списокКонтейнер по уникальному бизнес-ключуНужная строка, а не первый элемент
iframe / FrameLocator / поддерживаемые локаторы не проходит Shadow DOM; closed root недоступен

Дополнительное задание: на любой странице с формой разберите до 14 элементов по типам (label, input, checkbox, button, link, image). Для каждого запишите XPath и пользовательский , ожидаемое число совпадений и зависимость от локализации.

Интерактив: изменение локального DOM

Исходный путь: .legacy-form > button. Семантический путь: getByRole('button', { name: 'Войти', exact: true }).

Оба пути находят одну кнопку.

Демонстрация CSS и доступного имени на локальном DOM. здесь не исполняется.

Исходный тест, записанный через codegen и «доработанный» вручную:

Тот же сценарий:

TypeScripttests/promo.spec.ts
import { test, expect } from '@playwright/test';

test('промокод SALE10 уменьшает сумму на 10%', async ({ page }) => {
  await page.goto('/cart');
  await page.getByRole('button', { name: 'Есть промокод?' }).click();
  await page.getByLabel('Промокод').fill('SALE10');
  await page.getByRole('button', { name: 'Применить' }).click();
  await expect(page.getByTestId('cart-total')).toHaveText('8 982 ₽');
});

Новый вариант читается как сценарий, переживёт смену CSS-фреймворка и перестановку блоков, а сломается только при изменении смысла: переименовали кнопку, убрали подпись поля, поменяли .

Интерактив требует JavaScriptLocator Playground: учебная страница магазина и поле для локатора — getByRole, getByText, getByLabel, getByPlaceholder, getByTestId, CSS, фильтры и цепочки. Подсвечиваются найденные элементы, показывается нарушение строгого режима и подсказки.

Типичные ошибки#

Копировать селектор из DevTools

«Copy selector» даёт путь по структуре (div:nth-child(3) > …), который ломается от любой правки. Найдите элемент так, как его ищет пользователь.

Автоматически добавлять .first() при Strict Mode violation

Ошибка сообщает, что локатор неоднозначен. .first() скрывает проблему: тест будет кликать по случайному из найденных элементов.

Локатор по тексту, который меняется

getByText('Осталось 3 шт.') сломается, когда остаток станет 2. Используйте регулярное выражение (/Осталось \d+ шт\./) или и проверяйте конкретное значение отдельно.

Поиск по тексту при локализации

Если тесты запускаются на нескольких языках, тексты становятся переменными. Решения: фиксировать locale в проекте, брать тексты из словаря переводов или использовать Test ID.

Что важно для собеседования#

JuniorКакие локаторы вы используете в первую очередь и почему?

Ответ

Пользовательские: getByRole с именем, getByLabel, getByPlaceholder, getByText — они описывают элемент так, как его видит пользователь, устойчивы к изменениям вёрстки и заодно проверяют доступность. Если роли и стабильного текста нет — getByTestId по договорённости с разработчиками. CSS/XPath — в крайнем случае и по устойчивым атрибутам, а не по классам и структуре.

JuniorЧто такое strict mode violation и как это исправлять?

Ответ

Действие или проверка с локатором, нашедшим несколько элементов, падает — не выбирает за вас. Исправление — сделать локатор однозначным: exact: true, filter({ hasText / has }), поиск внутри контейнера (card.getByRole(...)). first()/nth() уместны, только если позиция действительно важна; добавлять их «чтобы прошло» нельзя.

JuniorЧем Locator отличается от ElementHandle?

Ответ

— описание поиска, которое выполняется заново при каждом действии и повторяется в web-first проверках; переживает перерисовку DOM. ElementHandle — ссылка на конкретный узел, который может устареть после обновления страницы. В современном коде используют локаторы.

MiddleКак кликнуть «В корзину» у конкретного товара в списке из одинаковых карточек?

Ответ

Найти карточку по содержимому и искать кнопку внутри: page.getByTestId('product-card').filter({ hasText: 'Наушники Pulse' }).getByRole('button', { name: 'В корзину' }). Или с идентификатором товара. Не использовать nth() по порядку — он ломается при изменении сортировки и может кликнуть по другому товару без ошибки.

MiddleИконка-кнопка не находится по роли и имени. Что делать?

Ответ

Проверить доступное имя в DevTools (Accessibility). Если имени нет — это дефект доступности: прошу добавить aria-label, тогда и тест, и скринридер получат осмысленное имя. До исправления — Test ID. CSS по классу иконки — худший вариант: хрупко и скрывает проблему.

На странице кнопки «Оплатить» и «Оплатить частями». Что найдёт getByRole('button', { name: 'Оплатить' })?

Имя сравнивается как подстрока без учёта регистра. Для точного совпадения нужен exact: true или регулярное выражение /^Оплатить$/.

2
Что произойдёт при click() по локатору, который нашёл 3 элемента?

Действия требуют однозначного локатора. Это защищает от кликов «не туда».

3
Какой локатор устойчивее к редизайну?

Роль и имя меняются только при изменении смысла элемента; классы и структура — при любой правке вёрстки.

Кнопка-иконка удаления не находится через getByRole('button', { name: 'Удалить' }). Что делать?

Проверить в DevTools (вкладка Accessibility) доступное имя кнопки. Скорее всего его нет: внутри только SVG. Правильное решение — попросить разработчиков добавить aria-label="Удалить": это исправит и доступность, и тест. Временное — . CSS по классу иконки — худший вариант.

Почему локатор лучше сохранить в переменную, а не вызывать textContent() сразу?

Локатор ленив и повторно ищет элемент при каждом использовании, а web-first проверки (toHaveText) повторяют поиск до таймаута. textContent() читает значение один раз в текущий момент — если страница ещё обновляется, тест получит старое значение и станет нестабильным.
