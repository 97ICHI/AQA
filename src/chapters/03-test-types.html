Виды автоматизированного тестирования

Unit, Integration, API, UI, End-to-end, Regression, Smoke и Contract Testing: что проверяет каждый вид, сколько стоит и как из них собрать сбалансированный набор.

≈ 10 мин чтенияJ
Опирается на: Введение в AQA
Основная идея

Один и тот же риск можно проверить на разных уровнях. Чем ниже уровень, тем быстрее, дешевле и стабильнее проверка, но тем меньше частей системы она охватывает.

Цель главы: выбирать для каждого риска самый дешёвый уровень, который надёжно его ловит.

Кратко

Уровни тестов различаются охватом системы, скоростью, стоимостью поддержки и точностью диагностики; пирамида — эвристика, а не стандарт.

Главное

  • Unit — функция или класс изолированно, миллисекунды; Integration — несколько компонентов вместе (сервис + БД).
  • API-тест проверяет поведение через без браузера; UI-тест — через интерфейс в браузере.
  • E2E проходит сквозной пользовательский путь через все слои; это самый дорогой и хрупкий вид.
  • Regression и Smoke — это цели набора (проверить, что ничего не сломалось / что система вообще жива), а не отдельный уровень.
  • проверяет договорённость между потребителем и поставщиком API без полного окружения.
  • Пирамида: много быстрых нижних проверок, мало верхних. Конкретные пропорции зависят от архитектуры продукта.

Термины

Unit Testing
Проверка отдельной функции, метода или класса изолированно от сети, базы данных и других компонентов.
Integration Testing
Проверка совместной работы нескольких компонентов: сервиса и базы данных, двух модулей, сервиса и очереди.
API Testing
Проверка системы через программный интерфейс: отправка запросов и проверка статуса, заголовков, тела ответа и побочных эффектов.
UI Testing
Проверка через пользовательский интерфейс в браузере: действия пользователя и видимый результат.
Regression Testing
Повторная проверка уже работающей функциональности после изменений, чтобы убедиться, что ничего не сломалось.

Важно: Соотношение «70/20/10» — иллюстрация идеи, а не норма. Для фронтенд-тяжёлого продукта или микросервисов баланс может быть другим.

Уровни и цели тестов#

Виды тестов удобно разделить по двум осям:

  • Уровень (что проверяется): отдельная функция, связка компонентов, API, интерфейс в браузере, вся система целиком.
  • Цель набора (зачем запускаем): убедиться, что ничего не сломалось (Regression), что система жива после деплоя (Smoke), что сервисы совместимы (Contract).

Один и тот же тест может быть одновременно API-тестом по уровню и smoke-тестом по цели. Путаница возникает, когда эти оси смешивают: «у нас есть smoke-тесты и API-тесты» — это не два непересекающихся множества.

Unit Testing#

проверяет самую маленькую единицу кода — функцию, метод, класс — изолированно от сети, базы данных и файловой системы. Зависимости заменяются (подробнее — в главе «Mocking и Test Data»).

  • Скорость: миллисекунды; тысячи тестов выполняются за секунды.
  • Диагностика: при падении сразу ясно, какая функция сломалась.
  • Кто пишет: чаще разработчики. AQA читает unit-тесты, чтобы понимать покрытие, и не дублирует их через UI.
TypeScriptprice.ts
export function applyDiscount(price: number, percent: number): number {
  if (percent < 0 || percent > 100) throw new RangeError('percent must be 0..100');
  return Math.round(price * (100 - percent)) / 100;
}
TypeScriptprice.spec.ts
import { test, expect } from '@playwright/test';
import { applyDiscount } from './price';

test('скидка 15% от 2000 = 1700', () => {
  expect(applyDiscount(2000, 15)).toBe(1700);
});

test('процент вне диапазона — ошибка', () => {
  expect(() => applyDiscount(2000, 120)).toThrow(RangeError);
});
Playwright Test для unit-тестов

Обычно unit-тесты пишут на Vitest или Jest. Здесь использован , чтобы не вводить второй инструмент: его test и expect работают и без браузера, если не запрашивать фикстуру page.

Integration Testing#

проверяет, что несколько компонентов правильно работают вместе: сервис и настоящая база данных, сервис и очередь сообщений, два модуля одного приложения. Такие тесты ловят ошибки на стыках: неверный , несовпадение форматов, транзакции, конфигурацию.

Они медленнее unit-тестов (нужно поднять зависимости, часто в Docker), но гораздо быстрее и стабильнее E2E.

API Testing#

проверяет поведение системы через её программный интерфейс — чаще всего HTTP/REST. Тест отправляет запрос и проверяет статус, заголовки, тело ответа и побочные эффекты (например, запись в базе).

Почему API-тесты — основная рабочая лошадь AQA:

  • нет браузера и рендеринга — один тест выполняется за десятки миллисекунд;
  • бизнес-логика (скидки, статусы, права доступа) почти всегда живёт на сервере;
  • API меняется реже, чем вёрстка, поэтому тесты стабильнее.

Подробно — в разделе V. API Automation.

UI Testing#

управляет настоящим браузером: кликает, вводит текст, проверяет, что пользователь видит правильный результат. Это единственный способ убедиться, что интерфейс действительно работает: кнопка нажимается, форма отправляется, ошибка показывается.

Цена: медленнее (секунды на тест), больше причин для нестабильности (анимации, асинхронная загрузка, сеть) и выше стоимость поддержки (вёрстка меняется часто). Раздел IV. UI Automation посвящён тому, как сделать такие тесты надёжными.

End-to-end Testing#

проверяет сквозной пользовательский сценарий через все слои системы: браузер → фронтенд → бэкенд → база данных → внешние сервисы. Например: «зарегистрироваться → найти товар → оплатить → получить письмо».

E2E даёт наибольшую уверенность, что система работает как целое, и одновременно самый слабый сигнал при падении: сломаться могло что угодно на любом шаге. Поэтому E2E-тестов должно быть немного — только для критических путей.

UI-тест и E2E — не синонимы

UI-тест может работать с подменённым бэкендом ( сетевых ответов) и проверять только интерфейс. E2E по определению проходит через реальные слои. В разговоре их часто смешивают, но на собеседовании разницу стоит назвать.

Regression и Smoke#

отвечает на вопрос «не сломали ли мы то, что работало?». Регрессионный набор — это совокупность тестов всех уровней, которая запускается после изменений. Автоматизация в первую очередь окупается именно на регрессии, потому что она повторяется постоянно.

— короткий набор самых базовых проверок: приложение запускается, главная страница открывается, вход работает, ключевой API отвечает. Smoke запускают сразу после деплоя; если он красный, дальнейшее тестирование бессмысленно. Хороший smoke-набор выполняется за минуты.

Близкое понятие — sanity testing: узкая проверка конкретного исправления или изменения перед более широкой регрессией.

Contract Testing#

В системе из нескольких сервисов один сервис (consumer) вызывает API другого (provider). проверяет, что provider по-прежнему отвечает так, как ожидает consumer: нужные поля есть, типы совпадают, коды ответов те же. Проверка идёт без разворачивания всей системы, поэтому она быстрее и стабильнее E2E.

Подробно, включая разницу между проверкой схемы и контрактом, — в главе «Schema и Contract Testing».

Test Automation Pyramid#

— эвристика Майка Коэна: внизу много быстрых и дешёвых тестов, наверху — мало медленных и дорогих. Смысл не в форме фигуры, а в правиле: проверяйте риск на самом низком уровне, на котором он надёжно ловится.

Интерактив требует JavaScriptИнтерактивная пирамида: выберите уровень, чтобы увидеть, что он проверяет, сколько стоит и что ловит; ниже можно собрать набор тестов и посчитать время прогона и вероятность ложного падения.

Пирамида — не закон. Известны альтернативные модели:

  • Testing Trophy (Кент Си Доддс) — больше интеграционных тестов для фронтенд-приложений, где отдельные функции мало что гарантируют.
  • Honeycomb (для микросервисов) — акцент на интеграционные и контрактные тесты сервиса, мало unit- и мало E2E-тестов.
  • Ice-cream cone — антипаттерн: много ручных и UI-тестов, мало нижних уровней. Такой набор медленный и дорогой.
Как пользоваться пирамидой на практике

Для каждого риска спросите: «На каком самом низком уровне эта ошибка проявится?» Ошибка в формуле скидки — unit или API. Ошибка в маппинге поля между сервисами — contract или integration. Кнопка «Оплатить» не нажимается — только UI. Сценарий «оплата прошла, письмо пришло» — один E2E.

Пример: распределение проверок одной фичи#

Фича: промокод на скидку в корзине.

Риск Уровень Почему
Неверный расчёт процента, округление Unit Чистая функция, много комбинаций, миллисекунды
Промокод просрочен, исчерпан, не для этого товара API Правила живут на сервере; нужны данные в БД
Скидка не сохраняется в заказе Integration / API Связка сервиса заказов и БД
Поле ввода промокода и сообщение об ошибке UI Только интерфейс показывает реакцию пользователю
«Применил промокод → оплатил → в чеке скидка» E2E (1 тест) Проверка, что всё собрано вместе
Сервис заказов ждёт поле discount от сервиса промокодов Contract Стык двух команд

Получается 1 E2E, 2–3 UI-теста, десяток API-тестов и несколько десятков unit-тестов. Пропорции получились сами из рисков, а не из целевого процента.

Типичные ошибки#

Дублировать проверки на всех уровнях

Если 30 комбинаций скидки уже проверены unit-тестами, повторять их через UI бессмысленно: это медленно и ничего не добавляет. На UI достаточно одного-двух сценариев, подтверждающих, что результат отображается.

Называть любой браузерный тест E2E

Тест формы логина с подменённым ответом сервера — UI-тест. Если на собеседовании назвать его E2E, это покажет путаницу в понятиях.

Требовать «правильные проценты» пирамиды

Цифры 70/20/10 — иллюстрация. Цель — быстрый и надёжный сигнал. Для продукта, где почти вся логика на клиенте, разумно иметь больше компонентных и UI-тестов.

Smoke-набор на час

Smoke должен быстро ответить «система жива?». Если он идёт долго, им перестают пользоваться как воротами после деплоя.

Что важно для собеседования#

JuniorЧто такое пирамида тестирования и почему наверху мало тестов?

Ответ

Это эвристика распределения тестов по уровням: внизу много unit-тестов, выше — интеграционные и API, наверху — немного UI/E2E. Верхние тесты медленнее, чаще ломаются по причинам, не связанным с дефектами, и хуже локализуют проблему. Поэтому риск проверяют на самом низком уровне, где он надёжно ловится, а UI/E2E оставляют для ключевых пользовательских сценариев.

Частая ошибка

Называть пропорции 70/20/10 обязательным стандартом.
JuniorЧем UI-тест отличается от E2E-теста?

Ответ

UI-тест проверяет поведение интерфейса и может работать с подменённым бэкендом. E2E проходит сквозной пользовательский сценарий через все реальные слои: браузер, сервер, базу, интеграции. Любой E2E через браузер — это UI-взаимодействие, но не любой UI-тест — E2E.

JuniorЧем smoke отличается от регрессии?

Ответ

Smoke — короткий набор базовых проверок «система жива и ключевые функции работают», запускается сразу после деплоя за минуты. Регрессия — широкий набор, подтверждающий, что изменения не сломали существующую функциональность. Smoke — ворота: если он красный, регрессию запускать нет смысла.

MiddleЕсть фича «промокод в корзине». Как распределите проверки по уровням?

Ответ

Расчёт скидки и округление — unit. Правила применимости (срок, лимит, категории) — API-тесты с подготовленными данными. Сохранение скидки в заказе — интеграционный или API-тест с проверкой в БД. Поле ввода и сообщения об ошибках — пара UI-тестов. Один E2E «применил промокод → оплатил → скидка в чеке». Если промокоды — отдельный сервис, добавлю контрактный тест между ним и сервисом заказов.

Middle+Подходит ли классическая пирамида для системы из 30 микросервисов?

Ответ

Как принцип — да: проверять риск на самом низком надёжном уровне. Как форма — не всегда. Для микросервисов основная часть рисков на стыках, поэтому обычно больше интеграционных тестов сервиса с его зависимостями и контрактных тестов между сервисами, а E2E по всей системе — минимум для критических путей: их дорого поддерживать и сложно диагностировать. Эту форму называют honeycomb.

Проверьте себя#

Тест
1
Тест открывает браузер, вводит логин и пароль, а ответ сервера подменён через page.route. Какой это вид теста?

Тест работает через интерфейс в браузере, но бэкенд подменён — сквозного прохождения через все слои нет, поэтому это UI-тест, а не E2E.

2
Какая проверка лучше всего подходит для правила «скидка не больше 50% для товаров со склада Б»?

Это бизнес-правило на сервере с несколькими комбинациями данных. Дешевле и надёжнее проверить его на уровне API или unit, а не через интерфейс.

3
Что из этого — цель набора, а не уровень тестирования?

Smoke отвечает на вопрос «жива ли система» и может состоять из API- и UI-проверок. Unit, API и UI — уровни.

В наборе 20 UI-тестов, каждый с вероятностью ложного падения 1%. Какова вероятность, что весь прогон будет зелёным при отсутствии дефектов?

0,99^20 ≈ 0,818. Почти каждый пятый прогон будет красным без реальной проблемы. При 200 таких тестах — 0,99^200 ≈ 0,134: зелёный прогон станет редкостью. Поэтому стабильность отдельного теста критична, а количество верхних тестов нужно ограничивать.

Чем contract-тест полезнее E2E при проверке совместимости двух сервисов?

Contract-тест проверяет конкретную договорённость (поля, типы, коды) быстро и без поднятия всей системы, а при падении указывает, какая часть контракта нарушена и кем. E2E проверит совместимость только косвенно, медленно и с размытым диагнозом.
