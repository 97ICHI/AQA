Основы API Testing

Архитектура API-тестов, категории проверок, тестовые данные, способы авторизации, валидация ответов и обработка ошибок. Как превратить описание эндпоинта в полноценный набор проверок.

≈ 10 мин чтенияJ
Опирается на: HTTP и REST
Основная идея

API-тест проверяет поведение системы на уровне, где живут бизнес-правила: быстро, стабильно и без браузера. Хороший API-набор проверяет не только «200 и что-то вернулось», но и валидацию, права доступа, побочные эффекты и формат ошибок.

Цель главы: составлять для эндпоинта полный чек-лист проверок и понимать, из каких частей состоит API-тест.

Кратко

API-тест = подготовка данных и авторизации → запрос → проверка статуса, заголовков, тела, схемы и побочных эффектов → очистка.

Главное

  • Категории проверок: позитивные сценарии, валидация входа, авторизация и права, бизнес-правила, побочные эффекты, идемпотентность, формат ошибок, контракт (схема).
  • Ответ проверяют по слоям: статус → заголовки → структура (схема) → значения → состояние системы после запроса.
  • Авторизация: API key, Basic, Bearer-токен (), client credentials, cookies сессии.
  • Ошибки должны иметь единый формат, правильный код 4xx и не раскрывать внутренности (стек, ).
  • Данные для теста создаются самим тестом (через API), уникальны и удаляются после.
  • Для eventual consistency ждите состояние по operation ID с ограниченным polling; не повторяйте создание ресурса.

Термины

API Testing
Проверка системы через программный интерфейс: отправка запросов и проверка статуса, заголовков, тела ответа и побочных эффектов.
Endpoint
Комбинация метода и пути, по которой API выполняет операцию: POST /api/orders, GET /api/orders/{id}.
API Authentication
Способ подтвердить, кто обращается к API: API key, Basic, Bearer-токен, OAuth 2.0, cookie сессии.
API Key
Секретная строка, идентифицирующая клиента API; передаётся в заголовке (например, X-API-Key).
OAuth 2.0
Стандарт выдачи токенов доступа. В межсервисном взаимодействии — client credentials: клиент обменивает свой id и секрет на access token.

Важно: Не проверяйте эндпоинт только «по документации»: документация может отставать от реализации. Найденное расхождение — уже результат тестирования.

Почему API-тесты — основа автоматизации#

Вспомним пирамиду из главы «Виды тестирования»: стоит посередине и обычно составляет основную часть регрессионного набора AQA. Причины:

  • Скорость. Запрос и ответ — десятки миллисекунд. Тысяча проверок проходит за минуты.
  • Стабильность. Нет рендеринга, анимаций, оверлеев; контракт API меняется реже вёрстки.
  • Близость к логике. Скидки, права, статусы, расчёты — на сервере.
  • Точная диагностика. Падение указывает на конкретный и запрос.
  • Подготовка данных. Те же клиенты API используются UI-тестами для быстрой подготовки состояния.

Архитектура API-теста#

Текст
Тест
 ├─ Подготовка: авторизация, данные (фабрики, фикстуры)
 ├─ Действие: запрос через клиент API
 ├─ Проверки: статус → заголовки → схема → значения → побочные эффекты
 └─ Очистка: удаление созданных сущностей (teardown фикстуры)

В проекте это раскладывается на слои:

Слой Ответственность Пример
HTTP-клиент Базовый URL, заголовки, авторизация, логирование APIRequestContext
Клиенты ресурсов Методы по эндпоинтам с типами OrdersApi.create(order)
Модели и схемы Типы запросов/ответов и Order, orderSchema
Фабрики данных Валидные данные с уникальными полями makeOrder({ qty: 2 })
Фикстуры Авторизованный клиент, созданные сущности с очисткой adminApi, paidOrder
Тесты Сценарии и ожидания test('нельзя отменить отправленный заказ')

Категории проверок#

Для каждого эндпоинта полезно пройти по категориям:

Категория Что проверяем Пример для POST /api/orders
Позитивные сценарии Основное поведение Заказ создан: 201, Location, тело с id и статусом created
Валидация входа Обязательные поля, типы, границы, форматы Нет productId → 400/422; qty: 0 → 422; qty: "два" → 400
Аутентификация Без токена, с неверным и истёкшим 401 во всех случаях
Авторизация Права и чужие ресурсы Заказ от имени другого покупателя → 403
Бизнес-правила Правила предметной области Товара нет в наличии → 409 OUT_OF_STOCK
Побочные эффекты Изменение состояния системы Остаток уменьшился; заказ виден в GET /orders
Идемпотентность Повтор запроса Тот же Idempotency-Key → тот же заказ, не дубликат
Формат ошибок Единая структура, отсутствие утечек { code, message, details[] }, без стек-трейса
Контракт и схема Структура ответа Все поля и типы по (глава 21)
Нефункциональные (базово) Время ответа, размер, заголовки безопасности Ответ за разумное время, нет Server: … с версией
Источник ожиданий

Ожидаемое поведение берут из спецификации (OpenAPI/Swagger), требований и договорённостей команды. Если поведение не описано — это вопрос аналитику, а не повод придумать ожидание в тесте.

Тестовые данные#

Главные правила для API-тестов:

  1. Тест создаёт свои данные. Не «первый заказ в базе», а заказ, созданный в начале теста.
  2. Данные уникальны. Email с меткой времени или UUID — тесты не конфликтуют при параллельном и повторном запуске.
  3. Данные валидны по умолчанию. Фабрика возвращает корректный объект; негативный случай меняет одно поле.
  4. Данные удаляются. Очистка — в teardown фикстуры, чтобы выполнилась при падении.
  5. Нет зависимости между тестами. Тест не использует то, что создал другой тест.
TypeScripttests/data/orders.ts
import { randomUUID } from 'node:crypto';

export interface NewOrder { productId: number; qty: number; comment?: string; idempotencyKey: string }

export function makeOrder(overrides: Partial<NewOrder> = {}): NewOrder {
  return { productId: 1, qty: 1, idempotencyKey: randomUUID(), ...overrides };
}

// Негативные случаи — одно изменение относительно валидного заказа
export const invalidOrders: { name: string; body: Record<string, unknown>; status: number }[] = [
  { name: 'нет productId', body: { qty: 1 }, status: 422 },
  { name: 'qty = 0', body: { productId: 1, qty: 0 }, status: 422 },
  { name: 'qty строкой', body: { productId: 1, qty: 'два' }, status: 400 },
  { name: 'несуществующий товар', body: { productId: 999999, qty: 1 }, status: 404 },
];

Подробнее о стратегиях данных — в главах «Mocking и Test Data» и «Test Isolation».

Авторизация в API#

бывает нескольких видов:

Способ Как передаётся Где встречается
Заголовок X-API-Key: … или query-параметр Сервисные интеграции
Basic Authorization: Basic base64(login:password) Внутренние сервисы, старые API
Bearer-токен () Authorization: Bearer eyJ… Большинство современных API
(client credentials) Сначала POST /oauth/token, затем Bearer Межсервисное взаимодействие
сессии Cookie: sid=… API, которым пользуется веб-интерфейс

Для тестов важно:

  • получать токен программно в фикстуре (логин через API), а не копировать вручную;
  • учитывать срок жизни токена: для долгих прогонов — обновление или новый токен на воркер;
  • проверять матрицу доступа: нет токена, неверный, истёкший, другая роль, чужой ресурс (см. главу 9);
  • не выводить токены в логи и отчёты.

JWT не обязательно зашифрован: payload обычно читается. Сервер должен проверять подпись, срок и необходимые claims. 401 означает проблему аутентификации; 403 — отказ в доступе согласно контракту. Проверяйте доступ к чужим ресурсам, истёкший токен и недостаточную роль, а не только happy path.

Валидация ответов#

идёт по слоям — от быстрых и общих к точным:

  1. Статус — 201, а не просто «успешный».
  2. Заголовки — Content-Type, Location, кэширование, CORS, если важно.
  3. Структура — по схеме: все обязательные поля, типы, отсутствие лишних чувствительных полей.
  4. Значения — бизнес-результат: статус заказа, сумма, связи.
  5. Побочные эффекты — повторный GET, связанный ресурс, запись в базе, событие в очереди.
TypeScripttests/order-create.spec.ts
import { test, expect } from '@playwright/test';
import { makeOrder } from './data/orders';

test('создание заказа: статус, заголовки, тело, побочный эффект', async ({ request }) => {
  const order = makeOrder({ qty: 2 });
  const res = await request.post('/api/orders', { data: order, headers: { 'Idempotency-Key': order.idempotencyKey } });

  expect(res.status()).toBe(201);
  expect(res.headers()['content-type']).toMatch(/^application\/json/);

  const body = (await res.json()) as Record<string, unknown>;
  expect(body).toMatchObject({ status: 'created', items: [{ productId: 1, qty: 2 }] });
  expect(body).not.toHaveProperty('internalCost');            // не утекают внутренние поля

  const list = await request.get('/api/orders', { params: { status: 'created' } });
  const ids = ((await list.json()) as { items: { id: number }[] }).items.map((o) => o.id);
  expect(ids).toContain(body.id as number);
});

Асинхронные операции и повторные запросы#

Если POST принят с 202, бизнес-операция может ещё выполняться. Получите operation ID, проверяйте связанный status до конечного состояния с ограниченным общим . Не создавайте новый заказ на каждой итерации ожидания.

TypeScript · фрагмент
const operationId = 'id-from-create-response';
await expect.poll(async () => {
  const response = await request.get(`/operations/${operationId}`);
  expect(response.status()).toBe(200);
  return (await response.json()).status;
}, { timeout: 15_000, intervals: [100, 250, 500, 1000] }).toBe('completed');

Это фрагмент для приложения с таким контрактом, не Endpoint учебного магазина. Обработайте failed-состояние отдельно, чтобы не ждать бессмысленно до таймаута. Повтор чтения допустим; повтор записи требует проверки идемпотентности.

Обработка ошибок#

— отдельная область проверок. Хороший API:

  • возвращает правильный класс кода: ошибки клиента — 4xx, ошибки сервера — 5xx;
  • использует единый формат ошибки во всех эндпоинтах, например:
JSON
{
  "code": "VALIDATION_ERROR",
  "message": "Некорректные данные заказа",
  "details": [{ "field": "qty", "reason": "must be greater than 0" }],
  "traceId": "5b2c9e1a7f"
}
  • указывает поле и причину, чтобы клиент мог показать ошибку пользователю;
  • не раскрывает внутренности: стек-трейсы, , пути файлов, версии библиотек;
  • содержит идентификатор запроса для поиска в логах.
TypeScripttests/order-errors.spec.ts
import { test, expect } from '@playwright/test';
import { invalidOrders } from './data/orders';

for (const c of invalidOrders) {
  test(`ошибка валидации: ${c.name}`, async ({ request }) => {
    const res = await request.post('/api/orders', { data: c.body });
    expect(res.status()).toBe(c.status);
    const err = (await res.json()) as { code: string; message: string };
    expect(err.code).toMatch(/^[A-Z_]+$/);
    expect(err.message.length).toBeGreaterThan(0);
    expect(JSON.stringify(err)).not.toMatch(/at \w+ \(|SELECT |Exception/); // нет утечек
  });
}

Postman и тесты в коде#

— популярный инструмент для работы с API: коллекции запросов, окружения с переменными, pre-request скрипты, проверки во вкладке Tests, запуск коллекций из CLI через Newman.

Postman Тесты в коде (Playwright)
Исследование API, ручные проверки Отлично Неудобно
Ревью изменений, история в Экспорт , сложно читать диффы Обычный код и
Переиспользование (фабрики, фикстуры, типы) Ограниченно Полностью
Общий фреймворк с UI-тестами Нет Да: одни клиенты, данные, отчёты
Порог входа Низкий Нужен

Практичный подход: Postman — для исследования и быстрых проверок, коллекция как живая документация; регрессионный набор — в коде.

Пример: чек-лист для эндпоинта#

PATCH /api/orders/{id} — изменить статус заказа. Тело: { "status": "cancelled" }.

№ Проверка Ожидание
1 Отмена своего заказа в статусе created 200, статус cancelled, остаток товара вернулся
2 Отмена заказа в paid 200, статус cancelled, создан возврат
3 Отмена заказа в shipped 409, код INVALID_TRANSITION, статус не изменился
4 Неизвестный статус "lost" 422, поле status в details
5 Пустое тело / нет поля status 400 или 422 по спецификации
6 Несуществующий id 404
7 Чужой заказ 403 или 404, заказ не изменился
8 Без токена / истёкший токен 401
9 Повторная отмена 409 или 200 без изменений — как описано в спецификации
10 Схема ответа Соответствует

Десять пунктов, каждый — отдельный короткий тест. Пункты 3, 7 и 9 часто находят дефекты, которые UI-тесты никогда не увидят: интерфейс просто не показывает кнопку отмены для отправленного заказа.

Типичные ошибки#

Только позитивные тесты

API, которое правильно отвечает на правильные запросы, — половина работы. Валидация, права и ошибки — то, что защищает систему и данные.

Проверять всё тело через toEqual целиком

Поля createdAt, id, updatedAt меняются каждый раз — тест станет хрупким. Проверяйте значимые поля (toMatchObject), структуру — схемой.

Зависеть от данных стенда

«Заказ 1042 должен быть в статусе paid» — ровно до того дня, когда его кто-то изменит. Создавайте свои данные.

Логировать токены и пароли

Логи и отчёты CI видят многие. Маскируйте заголовок Authorization и чувствительные поля.

Что важно для собеседования#

JuniorКак вы тестируете новый эндпоинт создания сущности?

Ответ

По категориям: позитивный сценарий (201, Location, тело), валидация (обязательные поля, типы, границы, форматы — по одному изменению), аутентификация (нет токена, неверный, истёкший → 401), авторизация (чужие ресурсы, роли → 403/404), бизнес-правила (409/422 с кодом), побочные эффекты (сущность доступна через GET, связанные данные изменились), идемпотентность, формат ошибок без утечек, соответствие схеме.

JuniorЧто вы проверяете в ответе API?

Ответ

По слоям: статус (точный код), заголовки (Content-Type, Location и др.), структуру по схеме (обязательные поля, типы, нет лишних чувствительных полей), значения (бизнес-результат), побочные эффекты (повторный GET, связанные ресурсы, база). Изменчивые поля (id, даты) проверяю по формату, а не по значению.

JuniorPostman или тесты в коде — что выбрать для API-регрессии?

Ответ

— для исследования API, ручных проверок и быстрых прототипов; коллекции можно запускать через Newman в CI. Для поддерживаемого регрессионного набора предпочитаю код: ревью в , типы, фабрики данных, фикстуры с очисткой, общие клиенты с UI-тестами и единые отчёты.

MiddleКак проверить обработку ошибок в API?

Ответ

Для каждого класса ошибок (валидация, не найдено, конфликт, нет прав, нет аутентификации) — правильный код и единый формат тела: машинный код ошибки, сообщение, поле и причина для валидации, traceId. Проверяю отсутствие утечек: стек-трейса, , путей, версий. Отдельно: на некорректные данные никогда не должно быть 500.

Проверьте себя#

Тест
1
Что проверить в первую очередь, если POST /api/orders вернул 201?

Успешный код — только первый слой. Нужно проверить результат и побочный эффект.

2
Пользователь А запрашивает заказ пользователя Б по id. Какой ответ ожидаем?

Пользователь аутентифицирован, но прав на ресурс нет. 404 иногда используют, чтобы не раскрывать существование ресурса.

3
Как правильно сформировать негативные данные для проверки валидации?

Изменение одного фактора показывает, что работает конкретное правило валидации.

Почему важно проверять формат ошибок, а не только код?

Клиенты (фронтенд, мобильное приложение, интеграции) разбирают тело ошибки, чтобы показать сообщение и подсветить поле. Неединый формат ломает клиентов, а утечка стек-трейса или — уязвимость. Код 400 с неправильным телом — тоже дефект.

Чем проверка побочных эффектов отличается от проверки ответа?

Ответ сообщает, что сервер «считает» результатом. Побочный эффект показывает реальное изменение системы: заказ доступен через GET, остаток уменьшился, событие отправлено. Сервер может ответить 201 и не сохранить данные — это обнаружит только проверка побочного эффекта.
