Test Design для автоматизации

Шесть техник, которые превращают «потыкать форму» в небольшой, но сильный набор проверок: классы эквивалентности, граничные значения, таблицы решений, переходы состояний, позитивные и негативные сценарии, приоритизация по рискам.

Опирается на: Виды тестирования
Основная идея

Test Design отвечает на вопрос «какие именно данные и сценарии проверить», чтобы малым числом тестов поймать большинство ошибок. В автоматизации результат техники — это таблица параметров для одного параметризованного теста.

Цель главы: выводить из требований конкретные тестовые данные и оформлять их как data-driven автотесты.

Кратко

Техники Test Design сокращают бесконечное множество входов до небольшого набора представителей, в которых ошибки наиболее вероятны.

Главное

  • : из каждого класса, который система обрабатывает одинаково, достаточно одного представителя.
  • : ошибки чаще всего на границах. Для диапазона [min, max] проверяют min−1, min, max, max+1 (двухточечный вариант).
  • : все комбинации условий → действие; позволяет найти пропущенные правила и сократить комбинации с «неважно».
  • State Transition: проверяют допустимые переходы и, отдельно, запрет недопустимых.
  • проверяет, что система корректно отказывает: правильный код ошибки, понятное сообщение, отсутствие побочных эффектов.
  • : приоритет = вероятность × влияние. Каждая проверка связывает риск, данные и oracle, а отчёт о дефекте содержит воспроизводимые шаги и evidence.

Термины

Equivalence Partitioning
Техника Test Design: входные значения делятся на классы с одинаковым поведением системы, из каждого класса берётся один представитель.
Boundary Value Analysis
Техника Test Design: проверяются значения на границах классов эквивалентности и рядом с ними, где ошибки наиболее вероятны.
Decision Table
Таблица, где каждое правило — комбинация условий и соответствующее действие. Помогает найти пропущенные комбинации и минимальный набор тестов.
State Transition Testing
Проверка допустимых и недопустимых переходов объекта между состояниями по событиям: заказ, платёж, учётная запись.
Negative Testing
Проверка реакции системы на некорректные данные и недопустимые действия: понятная ошибка, правильный код ответа, отсутствие побочных эффектов.

Важно: Техники не заменяют знание предметной области: граница «18 лет» может зависеть от часового пояса и даты рождения в високосный год.

Зачем AQA техники Test Design#

У поля «возраст» тысячи возможных значений, у формы из пяти полей — миллиарды комбинаций. Проверить всё невозможно, а случайный выбор пропускает самые вероятные ошибки. Техники Test Design дают систематический способ выбрать немного входных данных с высокой вероятностью найти дефект.

Для автоматизации это особенно важно по двум причинам:

  1. Каждый лишний тест стоит времени прогона и поддержки. Двадцать похожих проверок «возраст 25, 26, 27…» ничего не добавляют.
  2. Результат техники естественно ложится в код — массив тестовых случаев и цикл. Такой тест называют data-driven, или параметризованным ().

Equivalence Partitioning#

делит входные значения на классы, внутри которых система ведёт себя одинаково. Если программа одинаково обрабатывает возраст 25 и 40, проверка обоих значений не добавляет информации — достаточно одного представителя класса.

Пример: регистрация разрешена с 18 до 65 лет включительно, возраст — целое число.

Класс Значения Ожидание Представитель
Меньше минимума …, 16, 17 Ошибка валидации 10
Допустимый 18…65 Регистрация 30
Больше максимума 66, 67, … Ошибка валидации 80
Не число "abc", "", null Ошибка формата "abc"

Обратите внимание на последнюю строку: классы эквивалентности бывают не только числовыми. Пустое значение, неверный тип и отсутствующее поле — отдельные классы, и в API-тестах они особенно важны.

Boundary Value Analysis#

Программисты чаще ошибаются на границах: пишут < вместо <=, путают включительные и исключительные границы, забывают про пустые строки. проверяет значения на границах классов и рядом с ними.

  • Двухточечный BVA: для каждой границы — последнее значение одного класса и первое значение соседнего. Для [18, 65]: 17, 18, 65, 66.
  • Трёхточечный BVA: граница и оба соседа. Для [18, 65]: 17, 18, 19, 64, 65, 66. Он ловит ошибку вида age == 18 вместо age >= 18.

Шаг соседнего значения зависит от типа: для целых — 1, для денег — 0,01, для длины строки — один символ.

Интерактив требует JavaScriptКонструктор граничных значений: задайте минимум, максимум и шаг, выберите двух- или трёхточечный вариант — получите классы, граничные значения и готовую таблицу случаев.

Как это выглядит в автотесте#

Тест получает массив случаев и для каждого создаёт отдельный test. Так в отчёте видно, какое именно значение не прошло.

TypeScripttests/registration-age.spec.ts
import { test, expect } from '@playwright/test';

const cases = [
  { age: 17, status: 400 },
  { age: 18, status: 201 },
  { age: 65, status: 201 },
  { age: 66, status: 400 },
];

for (const { age, status } of cases) {
  test(`возраст ${age} → HTTP ${status}`, async ({ request }) => {
    const response = await request.post('/api/users', {
      data: { email: `user-${Date.now()}-${age}@example.com`, age },
    });
    expect(response.status()).toBe(status);
  });
}

Название теста содержит входные данные и ожидание — по отчёту сразу понятно, на какой границе ошибка. Уникальный email не даёт тестам конфликтовать при повторном или параллельном запуске (подробнее — в главе «Test Isolation»).

Decision Table Testing#

Когда результат зависит от комбинации нескольких условий, удобно построить : столбцы — правила, строки — условия и действие. Полная таблица для n бинарных условий содержит 2^n правил; затем её сокращают, объединяя правила, где условие не влияет на результат (отмечается «—»).

Таблица сразу показывает две полезные вещи: пропущенные в требованиях комбинации («а что, если клиент участник программы и выбрал экспресс?») и минимальный набор тестов, покрывающий все правила.

Интерактив требует JavaScriptТаблица решений для стоимости доставки: переключайте условия и смотрите, какое правило срабатывает; ниже — полная и сокращённая таблицы.

State Transition Testing#

Многие объекты проходят через состояния: заказ, платёж, учётная запись. проверяет переходы между состояниями — и допустимые, и недопустимые.

Модель заказа:

Из \ Событие pay ship deliver cancel
created → paid ✗ ✗ → cancelled
paid ✗ → shipped ✗ → cancelled (возврат)
shipped ✗ ✗ → delivered ✗
delivered ✗ ✗ ✗ ✗
cancelled ✗ ✗ ✗ ✗

Из таблицы получаются два набора тестов:

  • Покрытие допустимых переходов: каждая стрелка хотя бы раз (created → paid → shipped → delivered, created → cancelled, paid → cancelled).
  • Недопустимые переходы: каждый ✗ — потенциальная дыра. Попытка отменить отправленный заказ должна завершиться ошибкой (например, 409 Conflict), и статус не должен измениться.

Недопустимые переходы удобнее всего проверять через API: состояние готовится запросами, а UI может просто не показывать нужную кнопку, скрывая дефект сервера.

Positive и Negative Testing#

  • Positive testing — корректные данные и ожидаемое использование: система должна выполнить действие.
  • — некорректные данные или недопустимые действия: система должна корректно отказать.

Хороший негативный тест проверяет не только «была ошибка», но и:

  1. правильный код и сообщение (400 с указанием поля, а не 500);
  2. отсутствие побочных эффектов (заказ не создан, деньги не списаны);
  3. безопасность (ответ не раскрывает стек-трейс и внутренние данные).
Где брать негативные сценарии

Из классов эквивалентности (невалидные классы), из таблицы переходов (✗), из прав доступа (чужой ресурс, нет токена, истёкший токен) и из ограничений данных (дубликат email, слишком длинная строка, неверный формат даты).

Risk-based Testing#

Времени всегда меньше, чем проверок. расставляет приоритеты: для каждой функциональности оценивают вероятность дефекта (сложность, частота изменений, история багов) и влияние (деньги, данные, число пользователей, юридические последствия). Приоритет ≈ вероятность × влияние.

Функциональность Вероятность Влияние Приоритет автоматизации
Оплата заказа Средняя Очень высокое Первый: API + 1 E2E
Расчёт скидок Высокая (часто меняется) Высокое Первый: unit + API
Смена аватара Низкая Низкое Ручная проверка
Экспорт отчёта в CSV Средняя Среднее API-тест формата

Risk-based подход определяет порядок автоматизации и глубину проверок: для оплаты — все техники выше, для аватара — одна позитивная проверка или ничего.

Пример: от требования к набору тестов#

Требование: «Пароль должен содержать от 8 до 64 символов, хотя бы одну цифру и одну букву».

  1. Классы: длина (<8, 8–64, >64), наличие цифры (есть/нет), наличие буквы (есть/нет), пустое значение.
  2. Границы длины (двухточечный BVA): 7, 8, 64, 65 символов — все с цифрой и буквой, чтобы проверялась только длина.
  3. Комбинации: валидная длина без цифры; валидная длина без буквы.
  4. Негатив: пустая строка, отсутствующее поле, null.

Итого 9 случаев вместо сотен. Каждый меняет один фактор относительно валидного эталона — так при падении понятно, какое правило нарушено.

TypeScripttests/password-rules.spec.ts
import { test, expect } from '@playwright/test';

const valid = 'abc12345';
const cases: { name: string; password: string | null; ok: boolean }[] = [
  { name: '7 символов', password: 'abc1234', ok: false },
  { name: '8 символов', password: valid, ok: true },
  { name: '64 символа', password: 'a1'.repeat(32), ok: true },
  { name: '65 символов', password: 'a1'.repeat(32) + 'b', ok: false },
  { name: 'без цифры', password: 'abcdefgh', ok: false },
  { name: 'без буквы', password: '12345678', ok: false },
  { name: 'пустой', password: '', ok: false },
  { name: 'null', password: null, ok: false },
];

for (const c of cases) {
  test(`пароль: ${c.name}`, async ({ request }) => {
    const res = await request.post('/api/auth/validate-password', { data: { password: c.password } });
    expect(res.status()).toBe(c.ok ? 200 : 422);
  });
}

От риска до отчёта о дефекте#

Соберём всё вместе на примере учебного магазина из главы «Первый запуск». Требование: количество товара — целое число от 1 до 10. Риск: покупатель оформит недопустимое количество или получит неправильную сумму. Oracle: явная спецификация, а не текущий ответ сервера.

ДанныеОжидаемое поведениеУровень
0, 11Отклонение без создания заказаAPI
1, 10Создание заказа и верная суммаAPI
1.5, строка, , нет поляОтклонение согласно контрактуAPI
2 через формуПользователь видит сумму 2000 ₽UI

описывает влияние дефекта, — очередность исправления. Ошибка оформления заказа для всех покупателей обычно критичнее опечатки, но конкретное решение зависит от бизнеса.

Отчёт: заголовок, версия и окружение, предусловия, шаги, фактический и ожидаемый результат, воспроизводимость, request/response, trace или скриншот. Удалите из evidence токены и персональные данные. При отсутствии ясного ожидаемого результата сначала уточните требование.

Типичные ошибки#

Менять несколько факторов в одном негативном случае

Пароль «1234» одновременно короткий и без букв. Если система вернёт ошибку, вы не узнаете, работает ли каждое правило по отдельности.

Проверять только «середину» диапазона

Значение 30 для диапазона 18–65 почти никогда не находит ошибку. Ошибки живут на 17/18 и 65/66.

Проверять негатив только через UI

Если фронтенд блокирует кнопку при невалидных данных, сервер может их принимать. Негативные сценарии бизнес-правил проверяйте и через API.

Один тест с циклом внутри

Цикл внутри одного test() остановится на первом упавшем случае и покажет в отчёте одну строку. Создавайте отдельный test() на каждый случай, как в примерах выше.

Что важно для собеседования#

JuniorПоле «количество» принимает целые от 1 до 99. Какие значения проверите и почему?

Ответ

По классам эквивалентности: валидный класс (например, 50), меньше минимума, больше максимума, не число, пустое значение, дробное число. По граничным значениям (двухточечный BVA): 0, 1, 99, 100; при трёхточечном добавлю 2 и 98. Ошибки чаще всего в сравнениях на границах (< вместо <=), поэтому границы обязательны, а середина диапазона почти ничего не добавляет.

JuniorКогда применять таблицу решений?

Ответ

Когда результат зависит от комбинации нескольких условий: тарифы, скидки, права доступа, стоимость доставки. Полная таблица из 2^n правил показывает пропущенные в требованиях комбинации; после сокращения правил с «неважно» остаётся минимальный набор тестов, где каждое правило проверено хотя бы раз.

JuniorЧто должен проверять хороший негативный API-тест?

Ответ

Код ответа (400/401/403/404/409/422, а не 500), понятное сообщение с указанием проблемы, отсутствие побочных эффектов (сущность не создана, состояние не изменилось) и отсутствие утечки внутренней информации (стек-трейса, ). И менять один фактор относительно валидного запроса, чтобы было понятно, какое правило проверяется.

MiddleКак оформить в Playwright 20 наборов входных данных для одной проверки?

Ответ

Массив объектов { вход, ожидание } и цикл for...of, который на каждой итерации вызывает test() с уникальным именем, включающим входные данные. Каждый случай становится отдельным тестом: он падает независимо, отображается в отчёте отдельной строкой и может выполняться параллельно. Данные можно вынести в или CSV, если их поддерживают аналитики.

Частая ошибка

Цикл внутри одного test(): остановится на первом падении и скроет остальные результаты.
MiddleУ вас две недели на автоматизацию нового продукта. С чего начнёте?

Ответ

С анализа рисков: какие функции критичны для денег, данных и ключевого пути пользователя, какие часто меняются и где больше всего исторических дефектов. Оцениваю вероятность × влияние, начинаю со smoke и критического пути (вход, оплата, создание основной сущности), бизнес-правила закрываю API-тестами, UI — минимальным числом сценариев. Сразу встраиваю тесты в CI, иначе они не дают ценности.

MiddleКак техники Test Design превращаются в код автотестов?

Ответ

Результат техники — таблица случаев: классы эквивалентности, граничные значения, правила таблицы решений, переходы состояний. В коде это data-driven тест: массив случаев с входными данными и ожидаемым результатом и цикл, который создаёт отдельный test() с понятным именем для каждой строки. Тогда добавление случая — одна строка данных, отчёт показывает, какой именно случай упал, а набор случаев можно сверить с требованиями.

Пример

for (const c of cases) test(доставка: сумма ${c.sum}, VIP ${c.member}, async ({ request }) => { … });

Проверьте себя#

Тест
1
Поле принимает целые числа от 1 до 100 включительно. Какой набор соответствует двухточечному BVA?

Двухточечный BVA берёт для каждой границы последнее значение одного класса и первое значение соседнего: 0/1 и 100/101. Вариант с 2 и 99 — трёхточечный.

2
Сколько правил в полной таблице решений для четырёх бинарных условий?

Каждое бинарное условие удваивает число комбинаций: 2^4 = 16. Затем таблицу сокращают, объединяя правила с одинаковым действием.

3
Заказ уже отправлен. Что проверяет негативный тест перехода shipped → cancel?

Недопустимый переход должен быть отклонён сервером без побочных эффектов. Серая кнопка в UI не гарантирует, что API не выполнит отмену.

Почему для диапазона денег [0,01; 10 000,00] соседние значения — 0,00 и 10 000,01, а не 0 и 10 001?

Шаг соседнего значения равен минимальной единице типа. Для денег с точностью до копеек это 0,01. Значение 10 001 лежит в том же невалидном классе, что и 10 000,01, но не проверяет точную границу: ошибка вида amount <= 10000.005 осталась бы незамеченной.

Как decision table помогает при разборе требований, а не только при написании тестов?

Полная таблица перечисляет все комбинации условий. Комбинации, для которых требования не определяют результат, сразу видны — это вопросы аналитику до начала разработки. Так Test Design находит дефекты требований раньше, чем дефекты кода.
