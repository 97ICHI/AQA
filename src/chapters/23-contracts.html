Schema и Contract Testing

JSON Schema и OpenAPI, проверка схемы ответа, контрактное тестирование и consumer-driven contracts. Чем проверка «ответ соответствует схеме» отличается от «изменение провайдера не сломает потребителей».

≈ 10 мин чтенияM–M+
Опирается на: Автоматизация API
Основная идея

Схема описывает форму данных, контракт — договорённость двух сторон. Проверка схемы ловит, что ответ не похож на описание; контрактное тестирование ловит, что изменение одного сервиса сломает другой, — до того, как они встретятся на стенде.

Цель главы: валидировать ответы API схемой, читать OpenAPI и понимать, как и зачем внедряют consumer-driven contracts.

Кратко

Schema validation проверяет структуру отдельного ответа против описания; contract testing проверяет совместимость конкретного потребителя и поставщика по реально используемым взаимодействиям.

Главное

  • : type, properties, required, additionalProperties, enum, format, minimum, items, $ref.
  • описывает весь API: пути, методы, параметры, тела запросов и ответов, коды и схемы (components/schemas).
  • Валидация схемы в тестах — Ajv: compile(schema) один раз, затем validate(body) и вывод errors в сообщение.
  • Consumer-driven contracts (): тесты потребителя фиксируют ожидания в pact-файле → брокер → провайдер проверяет их на своей стороне → can-i-deploy.
  • Обратно совместимо: добавить необязательное поле в ответ, новый эндпоинт. Ломает: удалить или переименовать поле, сменить тип, сделать поле запроса обязательным.
  • Схема в тестах должна быть связана с источником (OpenAPI), иначе она устаревает так же, как моки.

Термины

JSON Schema
Стандарт описания структуры JSON: типы, обязательные поля, допустимые значения, форматы, вложенные объекты и массивы.
Schema Validation
Проверка, что данные (обычно ответ API) соответствуют JSON Schema; в TypeScript чаще всего выполняется библиотекой Ajv.
OpenAPI
Машиночитаемое описание HTTP API: пути, методы, параметры, тела запросов, ответы по кодам и схемы данных. Ранее называлась Swagger.
Contract Testing
Проверка, что поставщик API отвечает так, как ожидает потребитель, без развёртывания всей системы.
Consumer-driven Contracts
Подход, при котором потребитель фиксирует свои ожидания от API в контракте, а поставщик проверяет, что их выполняет.

Важно: Схема с additionalProperties: true и без required пропускает почти любой ответ. Слишком мягкая схема даёт ложное чувство защищённости.

Зачем проверять структуру ответа#

В главе «Основы TypeScript» мы видели, что as Order ничего не проверяет во время выполнения. Тест может долго «работать» с ответом, в котором поле total стало строкой "9980.00" или исчезло, а упасть совсем в другом месте — или не упасть. Явная проверка структуры решает это и одновременно ловит регрессии API: случайно удалённое поле, сменившийся тип, утёкшее внутреннее поле.

JSON Schema#

— стандарт описания структуры JSON-документа. Схема — тоже :

JSON
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["id", "status", "items", "total"],
  "additionalProperties": false,
  "properties": {
    "id": { "type": "integer", "minimum": 1 },
    "status": { "enum": ["created", "paid", "shipped", "delivered", "cancelled"] },
    "total": { "type": "integer", "minimum": 0 },
    "promoCode": { "type": ["string", "null"] },
    "createdAt": { "type": "string", "format": "date-time" },
    "items": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "required": ["productId", "qty"],
        "properties": {
          "productId": { "type": "integer" },
          "qty": { "type": "integer", "minimum": 1 }
        }
      }
    }
  }
}
Ключевое слово Смысл
type Тип: object, array, string, number, integer, boolean, null (или массив типов)
properties Схемы полей объекта
required Обязательные поля (без него все поля необязательны!)
additionalProperties Разрешены ли поля, не описанные в properties
enum, const Допустимые значения
minimum, maximum, minLength, maxLength, pattern Ограничения чисел и строк
format Семантика строки: date-time, email, uuid, uri (проверяется валидатором при включении форматов)
items, minItems, uniqueItems Массивы
$ref Ссылка на другую схему (переиспользование)
oneOf, anyOf, allOf Комбинации схем

Валидация схемы в тестах#

в TypeScript-проектах чаще всего делают библиотекой Ajv:

TypeScriptsrc/schemas/validate.ts
import Ajv, { type ValidateFunction } from 'ajv';
import { expect } from '@playwright/test';

const ajv = new Ajv({ allErrors: true });            // собрать все ошибки, а не только первую
const compiled = new Map<object, ValidateFunction>();  // компиляция дорогая — кэшируем

export function expectToMatchSchema(data: unknown, schema: object, name: string): void {
  let validate = compiled.get(schema);
  if (!validate) {
    validate = ajv.compile(schema);
    compiled.set(schema, validate);
  }
  const valid = validate(data);
  const details = (validate.errors ?? [])
    .map((e) => `${e.instancePath || '(корень)'} ${e.message ?? e.keyword}`)
    .join('\n');
  expect(valid, `ответ не соответствует схеме ${name}:\n${details}`).toBe(true);
}
TypeScripttests/order-schema.spec.ts
import { test } from '@playwright/test';
import { expectToMatchSchema } from '../src/schemas/validate';

const orderSchema = {
  type: 'object',
  required: ['id', 'status', 'items', 'total'],
  additionalProperties: false,
  properties: {
    id: { type: 'integer', minimum: 1 },
    status: { enum: ['created', 'paid', 'shipped', 'delivered', 'cancelled'] },
    total: { type: 'integer', minimum: 0 },
    promoCode: { type: ['string', 'null'] },
    items: { type: 'array', minItems: 1, items: { type: 'object', required: ['productId', 'qty'] } },
  },
};

test('GET /api/orders/:id соответствует схеме', async ({ request }) => {
  const res = await request.get('/api/orders/101');
  expectToMatchSchema(await res.json(), orderSchema, 'Order');
});

Для форматов (email, date-time) в Ajv 8 подключают пакет ajv-formats. Сообщение об ошибке содержит путь к полю (/items/0/qty) и нарушенное правило — по нему сразу видно, что изменилось в API.

Схема и типы из одного источника

Чтобы не поддерживать вручную и интерфейс Order, и схему, используют генерацию: типы из (openapi-typescript) или схему и тип из одного описания (zod, TypeBox). Тогда тип и проверка не разойдутся.

Интерактив требует JavaScriptВалидатор схемы: редактируйте JSON-ответ заказа и посмотрите, какие правила схемы нарушены и почему. Поддерживается учебное подмножество JSON Schema.

OpenAPI#

(ранее Swagger) — спецификация всего API в YAML или JSON: пути, методы, параметры, тела запросов, ответы по кодам и схемы данных.

YAMLOpenAPI.yaml (фрагмент)
openapi: 3.1.0
info: { title: Shop API, version: 2.4.0 }
paths:
  /api/orders/{id}:
    get:
      parameters:
        - { name: id, in: path, required: true, schema: { type: integer } }
      responses:
        '200':
          description: Заказ
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Order' }
        '404':
          description: Не найден
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Error' }
components:
  schemas:
    Order:
      type: object
      required: [id, status, items, total]
      properties:
        id: { type: integer }
        status: { type: string, enum: [created, paid, shipped, delivered, cancelled] }
        total: { type: integer }

Что AQA делает с OpenAPI:

  • берёт из спецификации ожидаемые коды и форматы для тест-дизайна;
  • валидирует ответы по схемам из components/schemas (а не по самописным копиям);
  • генерирует типы и клиенты;
  • проверяет, что спецификация соответствует реализации (расхождение — дефект документации или кода).

Contract Testing#

Представьте: сервис «Заказы» (consumer) читает поле price из ответа сервиса «Каталог» (provider). Команда каталога переименовала price в amount. Схема каталога обновлена, все тесты каталога зелёные — с их точки зрения всё корректно. Сломается сервис заказов, причём обнаружится это на общем стенде или в продакшене.

ловит такие проблемы до интеграции. Главный подход — :

  1. Тест потребителя описывает, какие запросы он делает и какие поля ответа ему нужны. Тест выполняется против мок-сервера, а ожидания записываются в контракт (Pact-файл).
  2. Контракт публикуется в брокер ( Broker / PactFlow) с версией потребителя.
  3. Поставщик проверяет контракт: инструмент воспроизводит записанные запросы против настоящего провайдера и сравнивает ответы с ожиданиями потребителя.
  4. can-i-deploy — перед деплоем любой стороны брокер отвечает, совместима ли эта версия с версиями партнёров в целевом окружении.

Pact — самый распространённый инструмент такого подхода (библиотеки для JS, Java, Go, Python и др.).

Проверка схемы — минимум для любого API-набора. Контрактное тестирование окупается в системах из многих сервисов с разными командами и независимыми релизами.

Интерактив требует JavaScriptСовместимость изменений: выберите изменение API провайдера (добавить поле, переименовать, сменить тип, сделать параметр обязательным) и посмотрите, какие потребители сломаются и поймает ли это проверка схемы или контракт.

Обратная совместимость#

— новая версия API работает со старыми клиентами. Правила для ответов и запросов:

Изменение Совместимо?
Добавить необязательное поле в ответ Да (если клиенты не валидируют additionalProperties: false у себя)
Добавить новый эндпоинт Да
Добавить необязательный параметр запроса Да
Удалить или переименовать поле ответа Нет
Изменить тип поля (integer → string) Нет
Сделать необязательное поле запроса обязательным Нет
Добавить значение в enum ответа Опасно: старые клиенты могут не знать нового статуса
Изменить смысл поля при том же имени и типе Нет, и схема этого не заметит

Ломающие изменения выпускают через версионирование (/v2/orders) или с периодом поддержки старого поля (deprecated).

Пример: внедрение проверок в команде#

  1. Неделя 1. Все API-тесты валидируют ответы схемами из . Найдено 3 расхождения документации и кода — заведены задачи.
  2. Неделя 2. Моки UI-тестов проверяются той же схемой при загрузке: устаревший мок падает сразу, а не через месяц.
  3. Месяц 2. Для самой хрупкой пары сервисов (заказы ← каталог) внедрён : потребитель публикует контракт, провайдер проверяет его в своём CI, деплой проверяется can-i-deploy.

Через квартал переименование поля в каталоге было остановлено проверкой контракта в CI провайдера — до появления на стенде.

Типичные ошибки#

Самописная копия схемы

Схема, скопированная вручную в тесты, устаревает и начинает проверять «как было». Берите схемы из или генерируйте их.

Слишком мягкая схема

Без required и с разрешёнными лишними полями схема пропустит пустой объект {}. Обязательные поля и типы — минимум.

Считать проверку схемы контрактным тестом

Схема проверяет, что провайдер соответствует своему описанию. Сломает ли он потребителей — она не знает.

Проверять в контракте значения, а не форму

Контракт потребителя должен описывать, какие поля и типы ему нужны (matchers), а не конкретные данные стенда. Иначе любое изменение данных ломает проверку.

Что важно для собеседования#

JuniorКак вы проверяете структуру ответа API?

Ответ

(лучше взятой из или сгенерированной), валидатор Ajv с allErrors, компиляция схемы один раз, понятное сообщение с путями полей. В схеме обязательно required и типы; additionalProperties: false — где важно не пропустить лишние (например, чувствительные) поля. Значения бизнес-полей проверяю отдельными assertions.

MiddleЧем проверка схемы отличается от контрактного тестирования?

Ответ

Проверка схемы сравнивает ответ с описанием API провайдера (OpenAPI/JSON Schema): структура, типы, обязательные поля. Контрактное тестирование (CDC) проверяет, что провайдер выполняет ожидания конкретных потребителей, зафиксированные их тестами. Если провайдер «законно» изменил свою схему, переименовав поле, проверка схемы пройдёт, а контракт потребителя упадёт.

MiddleКакие изменения API ломают обратную совместимость?

Ответ

Удаление или переименование поля ответа, смена типа, изменение смысла поля, превращение необязательного поля запроса в обязательное, удаление эндпоинта или значения enum в запросе. Добавление значения enum в ответ опасно для клиентов со строгой обработкой. Совместимо: новые необязательные поля ответа и параметры, новые эндпоинты.

Middle+Опишите процесс consumer-driven contract testing с Pact.

Ответ

Потребитель пишет тесты против мок-сервера , описывая запросы и нужные поля ответа (через matchers, не конкретные значения) — получается Pact-файл. Он публикуется в брокер с версией и веткой. CI провайдера скачивает контракты потребителей и воспроизводит запросы против реального провайдера (с подготовкой состояний), результат публикуется в брокер. Перед деплоем любая сторона выполняет can-i-deploy для целевого окружения.

Middle+Компания из 12 микросервисов, релизы независимые, интеграционные баги находят на staging. Внедрять Pact или хватит проверки схем?

Ответ

Проверка схемы ловит расхождение ответа со спецификацией провайдера, но не ловит законное с точки зрения провайдера изменение, которое ломает потребителя (переименование, удаление используемого поля). При независимых релизах и многих командах это как раз основной класс проблем, поэтому CDC окупается: контракты потребителей, брокер, проверка провайдера в его и can-i-deploy перед деплоем. Начать с одной пары сервисов с самыми частыми инцидентами, показать результат, затем расширять. Схемы при этом остаются базовым уровнем для всех API.

Частая ошибка

Считать, что OpenAPI-спецификация и валидация ответов делают контрактное тестирование ненужным.

Проверьте себя#

Тест
1
Схема содержит properties, но не содержит required. Что пройдёт валидацию?

Без required все описанные поля необязательны: схема проверит типы присутствующих полей, но не их наличие.

2
Провайдер переименовал поле и обновил свою OpenAPI-схему. Что поймает проблему у потребителя?

Тесты провайдера сверяются с обновлённой схемой и проходят. Только контракт потребителя знает, что поле используется.

3
Какое изменение API обратно совместимо?

Старые клиенты просто проигнорируют новое необязательное поле.

Почему моки UI-тестов полезно валидировать той же схемой, что и ответы API?

Моки отражают ожидания фронтенда о структуре ответа. Если API изменился, а мок нет, UI-тесты проверяют фронтенд против несуществующего API. Валидация мока схемой из заставляет обновить мок сразу при изменении спецификации.

Когда внедрение Pact не окупится?

В монолите или в системе из пары сервисов одной команды с общим релизом: интеграционные и API-тесты на общем стенде дешевле. CDC окупается при многих сервисах, разных командах и независимых деплоях, когда «встретиться на стенде» дорого и поздно.
