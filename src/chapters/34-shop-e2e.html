Сквозной пример: учебный интернет-магазин

Один компактный сценарий, в котором встречаются темы всего учебника: подготовка данных через API, действия в UI через page objects, проверка в базе данных, фикстуры с очисткой, отчётность и запуск в CI.

≈ 10 мин чтенияM
Опирается на: LocatorsАвтоматизация APISQL и базы данныхCI/CD
Основная идея

Каждый слой отвечает за своё: API быстро готовит состояние, UI проверяет то, что видит пользователь, база подтверждает побочный эффект, фикстуры гарантируют изоляцию, CI превращает тест в ворота качества.

Цель главы: увидеть, как отдельные техники складываются в один поддерживаемый тест и небольшой набор вокруг него.

Кратко

Сквозной тест «покупка с промокодом» готовит пользователя и корзину через API, проходит оплату в UI, проверяет заказ через API и базу и убирает данные в teardown.

Главное

  • Подготовка через API, проверка через UI и данные — каждый слой проверяет то, что видно только ему.
  • Фикстуры: уникальный пользователь, авторизованная страница, корзина; очистка в teardown.
  • Page objects и компоненты скрывают устройство страниц, тест читается как сценарий.
  • База данных — дополнительный свидетель побочного эффекта, запрос параметризован.
  • Внешний платёжный шлюз заменён мок-сервером в тестовом окружении.
  • В CI: Compose-окружение, API-набор на MR, сквозной сценарий после деплоя, отчёт с trace.

Термины

End-to-end Testing
Проверка полного пользовательского сценария через все слои системы: интерфейс, бэкенд, базу данных и интеграции.
Fixture
Именованный ресурс, который тест запрашивает в параметрах: фикстура готовит значение, передаёт его через use() и убирает за собой после теста.
Page Object Model
Паттерн: каждая страница описывается классом с локаторами и действиями пользователя; тесты используют эти методы и не знают о вёрстке.
APIRequestContext
HTTP-клиент Playwright (фикстура request, page.request, request.newContext): отправка запросов с baseURL, заголовками и cookies без браузера.
Test Artifacts
Файлы, сохраняемые при прогоне для диагностики и отчётности: скриншоты, видео, trace, вложения, отчёты.

Важно: Сквозных тестов должно быть мало. Здесь один сценарий объединяет всё, а правила промокодов, валидация и права проверяются API-тестами.

Сценарий и границы#

Продукт — учебный магазин из глав про SQL и API. Проверяемый пользовательский путь:

Зарегистрированный покупатель с товаром в корзине применяет промокод SALE10, оплачивает заказ тестовой картой и видит подтверждение; заказ сохраняется со статусом paid и скидкой 10%.

Что этот тест проверяет: что слои интерфейса, API и данных работают вместе на ключевом пути. Что он не проверяет (это задачи других наборов):

Риск Где проверяется
Все правила промокодов: срок, лимит, категории API-тесты, data-driven (глава 3)
Валидация формы оплаты UI-тесты формы с моками
Права доступа к заказам API-матрица доступа (глава 19)
Совместимость с сервисом платежей Контрактный тест (глава 21)

Клиент API#

TypeScriptsrc/api/ShopApi.ts
import { expect, type APIRequestContext } from '@playwright/test';

export interface User { id: number; email: string; password: string }
export interface Order { id: number; status: string; total: number; discount: number }

export class ShopApi {
  constructor(private readonly request: APIRequestContext) {}

  async createUser(email: string, password: string): Promise<User> {
    const res = await this.request.post('/api/users', { data: { email, password } });
    expect(res.status(), `создание пользователя: ${await res.text()}`).toBe(201);
    const { id } = (await res.json()) as { id: number };
    return { id, email, password };
  }

  async deleteUser(id: number): Promise<void> {
    const res = await this.request.delete(`/api/users/${id}`);
    expect([204, 404]).toContain(res.status());
  }

  async addToCart(productId: number, qty: number): Promise<void> {
    const res = await this.request.post('/api/cart/items', { data: { productId, qty } });
    expect(res.ok(), `добавление в корзину: ${await res.text()}`).toBeTruthy();
  }

  async lastOrder(): Promise<Order> {
    const res = await this.request.get('/api/orders', { params: { limit: 1, sort: '-createdAt' } });
    expect(res.ok()).toBeTruthy();
    const body = (await res.json()) as { items: Order[] };
    expect(body.items.length, 'у пользователя есть заказ').toBe(1);
    return body.items[0];
  }
}

Page objects#

TypeScriptsrc/pages/CheckoutPage.ts
import { expect, type Locator, type Page } from '@playwright/test';

export class CheckoutPage {
  readonly promoInput: Locator;
  readonly applyPromo: Locator;
  readonly total: Locator;
  readonly payButton: Locator;

  constructor(private readonly page: Page) {
    this.promoInput = page.getByLabel('Промокод');
    this.applyPromo = page.getByRole('button', { name: 'Применить' });
    this.total = page.getByTestId('checkout-total');
    this.payButton = page.getByRole('button', { name: 'Оплатить' });
  }

  async open() {
    await this.page.goto('/checkout');
    await expect(this.payButton).toBeVisible();
  }

  async usePromo(code: string) {
    await this.promoInput.fill(code);
    await this.applyPromo.click();
  }

  async payWithCard(card: { number: string; expiry: string; cvc: string }) {
    const frame = this.page.frameLocator('iframe[title="Оплата картой"]');
    await frame.getByLabel('Номер карты').fill(card.number);
    await frame.getByLabel('Срок действия').fill(card.expiry);
    await frame.getByLabel('CVC').fill(card.cvc);
    await this.payButton.click();
  }
}

Запрос к базе#

TypeScriptsrc/db/orders.ts
import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DB_URL, max: 2 });

export async function orderFromDb(orderId: number) {
  const { rows } = await pool.query<{ status: string; promo_code: string | null; items_total: number }>(
    `SELECT o.status, o.promo_code, SUM(oi.qty * oi.price)::int AS items_total
       FROM orders o JOIN order_items oi ON oi.order_id = o.id
      WHERE o.id = $1
      GROUP BY o.id`,
    [orderId],
  );
  return rows[0];
}

export async function closeDb() { await pool.end(); }

Сквозной тест#

TypeScripttests/e2e/checkout-promo.spec.ts
import { test, expect } from '../../src/fixtures/shop';
import { orderFromDb, closeDb } from '../../src/db/orders';

test.afterAll(async () => { await closeDb(); });

test('покупка с промокодом SALE10: подтверждение, статус paid и скидка в заказе', { tag: ['@e2e', '@checkout'] },
  async ({ buyerApi, checkoutPage, confirmationPage }) => {
    await test.step('подготовить корзину через API', async () => {
      await buyerApi.addToCart(1, 2);                     // 2 × 4 990 ₽ = 9 980 ₽
    });

    await test.step('применить промокод в интерфейсе', async () => {
      await checkoutPage.open();
      await expect(checkoutPage.total).toHaveText('9 980 ₽');
      await checkoutPage.usePromo('SALE10');
      await expect(checkoutPage.total, 'сумма со скидкой 10%').toHaveText('8 982 ₽');
    });

    await test.step('оплатить тестовой картой', async () => {
      await checkoutPage.payWithCard({ number: '4242 4242 4242 4242', expiry: '12/30', cvc: '123' });
      await expect(confirmationPage.heading).toHaveText('Заказ оформлен');
    });

    const order = await test.step('проверить заказ через API', async () => {
      const o = await buyerApi.lastOrder();
      expect(o).toMatchObject({ status: 'paid', total: 8982, discount: 998 });
      await expect(confirmationPage.orderNumber).toHaveText(`№ ${o.id}`);
      return o;
    });

    await test.step('проверить побочный эффект в базе', async () => {
      await expect.poll(async () => (await orderFromDb(order.id))?.status).toBe('paid');
      const row = await orderFromDb(order.id);
      expect(row).toMatchObject({ promo_code: 'SALE10', items_total: 9980 });
    });
  });

Что здесь важно:

  • Каждый шаг — test.step: в отчёте видно, на каком этапе упал тест.
  • Ожидаемые значения записаны числами (9 980, 8 982, 998), а не вычислены формулой продукта.
  • API и UI работают от одного пользователя: buyerApi использует page.request контекста покупателя.
  • База проверяется с повтором (expect.poll): статус может обновиться асинхронно после колбэка платёжного шлюза.
  • Очистка — в фикстуре user; заказы удаляются каскадно вместе с тестовым пользователем (это поведение тестового окружения оговорено с бэкендом).

Окружение и CI#

Платёжный шлюз в тестовом окружении — мок-сервер из главы 22, который одобряет карту 4242…. Окружение поднимается (глава 27), а выглядит так:

YAML.gitlab-ci.yml (фрагмент)
e2e-checkout:
  stage: test
  image: mcr.microsoft.com/playwright:v1.58.2-noble
  services:
    - name: docker:27-dind
  script:
    - docker compose up -d --wait db app payments-mock    # --wait: дождаться healthcheck
    - npm ci
    - npx playwright test --grep @e2e
  after_script:
    - docker compose logs app > app.log
  artifacts:
    when: always
    paths: [playwright-report/, test-results/, app.log]
    reports: { junit: results/junit.xml }
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

На MR запускаются API-тесты промокодов и форм (минуты), сквозной сценарий — после слияния в main и перед релизом. При падении в отчёте есть шаг, trace с DOM-снимками и сетью, логи приложения и id заказа для поиска в базе.

Типичные ошибки#

Делать сквозным каждый сценарий

Сотня таких тестов — медленный и хрупкий набор. Сквозные тесты подтверждают, что система собрана правильно; правила проверяются ниже.

Проходить в UI то, что можно подготовить

Регистрация и добавление товара через интерфейс в каждом E2E-тесте добавляют минуты и точки отказа, не относящиеся к проверяемому сценарию.

Проверять только финальный экран

«Заказ оформлен» на экране при неверной сумме в базе — дефект, который такой тест пропустит.

Что важно для собеседования#

MiddleКак вы спроектируете E2E-тест покупки так, чтобы он был быстрым и стабильным?

Ответ

Пользователь и корзина — через API в фикстурах с очисткой; авторизация без формы (вход через API, cookies в контексте страницы); в UI — только проверяемый путь оформления; внешний платёжный шлюз — мок или песочница; проверки результата на всех слоях: экран, API, база (с повтором для асинхронных обновлений); шаги test.step и trace для диагностики. Правила промокодов и валидацию — в API-тесты.

MiddleЧто должен и что не должен проверять сквозной тест?

Ответ

Должен — что система собрана правильно на ключевом пользовательском пути: интерфейс, API, данные и интеграции работают вместе, результат виден пользователю и сохранён. Не должен — перебирать бизнес-правила, валидацию и права доступа: это быстрее и надёжнее делают API-, unit- и UI-тесты отдельных экранов.

Проверьте себя#

Тест
1
Почему корзина в примере готовится через API, а не через каталог в UI?

Добавление в корзину через каталог проверяется своими UI-тестами; здесь важен путь оформления с промокодом.

2
Зачем проверять заказ в базе, если API уже вернул статус paid?

API и база — разные свидетели; расхождение между ними — тоже дефект.

Какие проверки из этого сценария стоит вынести в отдельные тесты нижних уровней?

Все правила промокода (срок действия, лимит, категории, сочетание с другими скидками) — в API data-driven тесты; расчёт скидки и округление — в unit; валидацию формы карты — в UI-тесты с моком; совместимость с сервисом платежей — в контрактный тест. В сквозном остаётся один путь, подтверждающий интеграцию.
