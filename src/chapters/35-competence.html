Практика и критерии инженерной готовности

Один проект, три этапа и измеримый результат. Задачи проверяют выбор проверок, изоляцию, диагностику и инженерные компромиссы.

Кратко

Один проект и три этапа: написать проверки, организовать проект, обосновать инженерные решения.

Главное

  • Этап Junior: таблица данных, позитивный API-тест и один UI-тест; ожидаемый результат известен до запуска.
  • Этап Middle: фикстуры создания и удаления, runtime validation, клиент API, linting и typecheck, запуск на двух workers.
  • Этап Middle+: устранить гонку без sleep, определить quality gate и политику quarantine, обосновать выбор числом и знаменателем.
  • Отметки практики — самооценка: уровень подтверждают ревью решения и наблюдаемая самостоятельная работа.

Частая ошибка: считать прочитанную главу освоенным навыком: «изучено» относится только к чтению.

Один проект: три этапа#

Это самостоятельная практика на скачиваемом проекте. Встроенные кнопки фиксируют самооценку, не выдают сертификат и не запускают код.

Практических этапов отмечено: 0 из 3.

Junior: первая самостоятельная проверка

По контракту starter составьте таблицу данных 0, 1, 10, 11, 1.5, строка, и отсутствующее поле. Реализуйте позитивный API-тест и один UI-тест. Каждый тест запускается отдельно.

Критерии: Есть ожидаемый результат до запуска; проверены статус, тело и сумма; студент объясняет await, и .

Показать ориентир после своей попытки

Сначала API покрывает диапазон и тип данных, затем UI подтверждает пользовательский путь. Не вычисляйте oracle через ту же функцию сервера, которую проверяете.

Middle: поддерживаемый проект

Добавьте fixtures создания/удаления заказа, , отдельный сервисный клиент, небольшой компонент формы, linting и typecheck. Запустите тесты отдельно, вместе и на двух workers; сохраните отчёт и trace при контролируемом падении.

Критерии: Нет зависимости от порядка; данные уникальны; cleanup предусмотрен после падения; ошибка диагностируется по evidence; CI сохраняет exit code и artifacts.

Показать ориентир после своей попытки

Не превращайте каждый HTTP-метод в десяток слоёв. Компонент отвечает за форму, сервис — за API, тест — за ожидаемое поведение. Частичный setup и ошибки cleanup требуют явной обработки.

Middle+: инженерные решения

Введите ограниченную искусственную задержку ответа и устраните гонку без sleep. Добавьте Allure, определите , бюджет времени и политику quarantine. Сравните 1/2 workers и 20 повторов; обоснуйте решение, а не только цифры.

Критерии: Контролируемый дефект обнаруживается; нет ложного зелёного статуса; метрики имеют знаменатель; trade-offs объяснены; решение повторяемо на чистом окружении.

Показать ориентир после своей попытки

Ожидайте наблюдаемый результат; измеряйте first-attempt failures и время. Ускорение workers ограничено ресурсами системы, а повторные успехи не исключают редкие сбои.

Оценку Middle подтверждает ревью решения или наблюдаемая самостоятельная работа. Кнопка «Изучено» относится только к чтению.

Чек-лист ревью теста#

  • Из названия понятно проверяемое поведение и риск.
  • Oracle задан независимо от реализации.
  • Тест запускается отдельно, не использует данные соседнего.
  • Ожидания связаны с состоянием, а не фиксированной задержкой.
  • Assertions проверяют значимый результат, не только факт ответа.
  • Cleanup ограничен принадлежащими тесту данными.
  • Ошибка оставляет достаточную диагностику без секретов.
  • Сложность слоёв оправдана повторением и поддержкой.

Разбор: API верен, UI-тест нестабилен#

Условие: сервер возвращает 201 и total=2000, но тест сразу читает текст «Отправляем…». Предложите исправление и способ проверить гипотезу.

Разбор

Проверка читает DOM до обновления. Используйте await expect(page.getByRole('status')).toHaveText('Заказ создан: 2000 ₽'). Создайте responsePromise до клика, если проверяется и HTTP-ответ. Добавьте контролируемую задержку, чтобы подтвердить устойчивость. Увеличение sleep только меняет вероятность гонки.

Что предъявить на собеседовании#

Покажите репозиторий, risk matrix, несколько тестов, историю контролируемого падения и исправления, CI-артефакты и описание выбора уровней. Объясните одно ограничение проекта и план следующей доработки. Знание терминов полезно, но инженерный уровень виден по самостоятельным решениям.
