Основы TypeScript

Минимум языка, достаточный для уверенного чтения и написания автотестов: переменные, типы, операторы, условия, циклы, функции, массивы, объекты, модули, интерфейсы и обработка ошибок — каждый раз на примерах из тестирования.

≈ 14 мин чтенияJ
Основная идея

TypeScript — это JavaScript с типами. Типы проверяются до запуска и ловят целый класс ошибок в тестах: опечатки в полях, забытые аргументы, неверные данные запроса.

Цель главы: читать и писать код тестов на TypeScript без «магии»: понимать, что делает каждая строка и какую ошибку подскажет компилятор.

Кратко

добавляет к JavaScript статическую типизацию: ошибки в коде тестов находятся до запуска, а редактор подсказывает поля и методы.

Главное

  • const по умолчанию, let — только если значение меняется; var не используем.
  • Сравнение — только === и !==; ?? подставляет значение по умолчанию только для null/undefined, || — для любого «ложного» значения, включая 0 и пустую строку.
  • interface и type описывают форму объектов: тестовые данные, ответы API, параметры функций.
  • Union-типы ('admin' | 'user') и сужение типов (narrowing) делают невозможными недопустимые значения.
  • unknown безопаснее any: значение нужно проверить перед использованием.
  • запускает .ts файлы без проверки типов — проверку tsc --noEmit нужно запускать отдельно.

Термины

TypeScript
Надстройка над JavaScript со статической типизацией. Типы проверяются компилятором tsc до запуска и удаляются при преобразовании в JavaScript.
Type Annotation
Явное указание типа переменной, параметра или результата: let id: number. Там, где тип очевиден из значения, TypeScript выводит его сам.
Union Type
Тип «одно из»: string | null или 'paid' | 'shipped'. Ограничивает допустимые значения и ловит опечатки при компиляции.
Interface
Описание формы объекта в TypeScript: поля и их типы. Используется для тестовых данных, ответов API и параметров.
Type Narrowing
Проверки (typeof, instanceof, in, type guard), после которых компилятор знает более точный тип значения.

Важно: any отключает проверки типов. Один any в типе ответа API распространяется дальше и лишает тесты защиты компилятора.

Зачем AQA TypeScript#

Автотест — такая же программа, как продукт, только её задача — проверять. Ошибка в коде теста приводит либо к ложному падению, либо, что хуже, к тесту, который ничего не проверяет. снижает риск второго: компилятор заранее сообщает, что поле называется totalPrice, а не total, что функция ждёт два аргумента, а в expect передан Promise.

Код на TypeScript превращается в JavaScript и выполняется в Node.js. умеет запускать .ts файлы напрямую, но не проверяет типы — он только удаляет аннотации. Поэтому в проекте обязательно нужна отдельная проверка:

Shell
npx tsc --noEmit        # проверить типы без генерации файлов
npx playwright test     # запустить тесты

В CI проверка типов запускается до тестов, чтобы ошибка в коде теста не превращалась в долгий красный прогон.

Переменные и типы данных#

TypeScriptvariables.ts
const baseUrl = 'https://shop.example.com'; // string — тип выведен автоматически
let attempts = 0;                             // number; let — значение будет меняться
attempts += 1;

const isLoggedIn: boolean = false;            // явная аннотация типа
const tags: string[] = ['@smoke', '@cart'];   // массив строк
const timeoutMs = 5_000;                      // разделитель разрядов для читаемости
let token: string | undefined;                // может быть не задан

// const нельзя переназначить, но объект внутри можно изменить:
const user = { name: 'Анна', age: 30 };
user.age = 31;      // можно
// user = { ... };  // ошибка компиляции
console.log(baseUrl, attempts, isLoggedIn, tags, timeoutMs, token, user);

Основные типы: string, number (целые и дробные — один тип), boolean, null, undefined, массивы T[], объекты, а также bigint и symbol, которые в тестах почти не встречаются.

(: boolean) нужна не везде: выводит тип из значения. Явно аннотируют параметры функций, возвращаемые значения публичных функций и переменные, которые объявляются без значения.

any и unknown

any — «отключить проверку»: с таким значением можно делать что угодно, и компилятор промолчит. unknown — «тип неизвестен»: прежде чем использовать значение, его нужно проверить. Ответ API, разобранный из , по смыслу unknown, пока вы не проверили его форму.

Операторы#

Несколько операторов, которые постоянно встречаются в тестах и часто становятся источником ошибок:

JavaScript
console.log(0 == '');          // нестрогое сравнение с приведением типов
console.log(0 === '');         // строгое: разные типы
console.log(0 || 30);          // || заменяет любое «ложное» значение
console.log(0 ?? 30);          // ?? заменяет только null и undefined
const order = { customer: null };
console.log(order.customer?.email); // ?. — безопасный доступ к полю
console.log(`Заказ №${42} на ${1500 * 2} ₽`); // шаблонная строка
Текст
true
false
30
0
undefined
Заказ №42 на 3000 ₽

Практические выводы:

  • всегда используйте === и !==;
  • для значений по умолчанию, где допустимы 0, '' или false, используйте ??: const retries = Number(process.env.RETRIES ?? 2);
  • ?. защищает от ошибки Cannot read properties of null, но может скрыть проблему: если поле обязано быть, лучше проверить его явно.

Условия#

TypeScriptconditions.ts
type Env = 'local' | 'staging' | 'production';

function baseUrlFor(env: Env): string {
  switch (env) {
    case 'local':
      return 'http://localhost:3000';
    case 'staging':
      return 'https://staging.shop.example.com';
    case 'production':
      return 'https://shop.example.com';
  }
}

const statusCode: number = 404;
const kind = statusCode >= 500 ? 'server error' : statusCode >= 400 ? 'client error' : 'ok';
if (kind !== 'ok') {
  console.log(`Запрос завершился ошибкой: ${kind}`);
}
console.log(baseUrlFor('staging'));

Благодаря типу Env компилятор знает все возможные значения: если добавить в тип 'preview' и забыть ветку в switch, функция перестанет компилироваться (не все пути возвращают string).

Условия внутри теста — тревожный знак

if в теле теста часто означает, что тест проверяет разное поведение в зависимости от обстоятельств, то есть нестабилен по смыслу. Тест должен знать, в каком состоянии находится система, и проверять одно ожидаемое поведение. Условия уместны в хелперах и конфигурации.

Циклы и методы массивов#

JavaScript
const prices = [1200, 450, 3000, 99];

for (const p of prices) {          // значения массива
  if (p > 1000) console.log('дорогой товар:', p);
}

const expensive = prices.filter((p) => p > 1000);       // отбор
const withVat = prices.map((p) => Math.round(p * 1.2)); // преобразование
const total = prices.reduce((sum, p) => sum + p, 0);    // свёртка
const hasFree = prices.some((p) => p === 0);            // хотя бы один?
const firstCheap = prices.find((p) => p < 500);         // первый подходящий

console.log(expensive, withVat, total, hasFree, firstCheap);
Текст
дорогой товар: 1200
дорогой товар: 3000
[ 1200, 3000 ] [ 1440, 540, 3600, 119 ] 4749 false 450

for...in перебирает ключи, а не значения, и для массивов почти никогда не нужен. while встречается редко: в тестах ожидание «пока не появится» почти всегда должно делать само средство автоматизации (см. главу «Assertions и Synchronization»).

Функции#

TypeScriptfunctions.ts
// Объявление функции с типами параметров и результата
function formatPrice(amount: number, currency = '₽'): string {
  return `${amount.toLocaleString('ru-RU')} ${currency}`;
}

// Стрелочная функция; необязательный параметр помечается «?»
const makeEmail = (prefix: string, domain?: string): string =>
  `${prefix}-${Date.now()}@${domain ?? 'example.com'}`;

// Параметры-объект удобнее, когда аргументов больше двух
interface NewUser {
  email: string;
  role?: 'admin' | 'customer';
  balance?: number;
}
function buildUser({ email, role = 'customer', balance = 0 }: NewUser) {
  return { email, role, balance };
}

console.log(formatPrice(1500), makeEmail('qa'), buildUser({ email: 'a@b.c' }));

Функции — основной инструмент против дублирования в тестах: генерация данных, подготовка состояния, проверки. Хорошая функция-хелпер делает одно дело и называется по результату: createPaidOrder(), а не doStuff().

Массивы и объекты#

TypeScriptobjects.ts
const product = { id: 7, title: 'Наушники', price: 4990, tags: ['audio', 'sale'] };

// Деструктуризация: достать поля в переменные
const { title, price } = product;

// Spread: копия с изменением — исходный объект не трогаем
const discounted = { ...product, price: 3990 };

// Копия массива с добавлением элемента
const moreTags = [...product.tags, 'new'];

// Перебор пар ключ–значение
for (const [key, value] of Object.entries({ status: 'paid', total: 3990 })) {
  console.log(`${key} = ${value}`);
}
console.log(title, price, discounted.price, product.price, moreTags);

В тестовых данных spread особенно удобен: есть валидный эталон, а каждый негативный случай меняет одно поле — { ...validUser, email: '' } (вспомните главу «Test Design»).

Мутация общего объекта

Если несколько тестов используют один объект validUser и один тест делает validUser.email = '', остальные тесты получат изменённые данные. Копируйте через spread или создавайте данные функцией-фабрикой.

Типизация: type, union, generics#

TypeScripttyping.ts
// Псевдоним типа и union из литералов
type OrderStatus = 'created' | 'paid' | 'shipped' | 'delivered' | 'cancelled';

type Order = {
  id: number;
  status: OrderStatus;
  total: number;
  promoCode: string | null;
};

const order: Order = { id: 1, status: 'paid', total: 3990, promoCode: null };
// order.status = 'payed'; // ошибка компиляции: такого статуса нет

// Generic: функция работает с любым типом элементов и сохраняет его
function lastItem<T>(items: T[]): T | undefined {
  return items[items.length - 1];
}
const lastOrder = lastItem([order]); // тип: Order | undefined

// Утилитные типы
type OrderDraft = Omit<Order, 'id'>;        // без id
type OrderPatch = Partial<Pick<Order, 'status' | 'promoCode'>>;
const patch: OrderPatch = { status: 'shipped' };
console.log(lastOrder?.status, patch);
const draft: OrderDraft = { status: 'created', total: 100, promoCode: 'SALE' };
console.log(draft);

из строковых литералов — один из самых полезных приёмов в тестах: опечатка 'payed' вместо 'paid' обнаруживается при компиляции, а не после 20-минутного прогона. встречаются в API постоянно: response.json() возвращает Promise<any>, и хорошая практика — сразу указать ожидаемую форму.

Сужение типов#

— проверки, после которых компилятор знает более точный тип:

TypeScriptnarrowing.ts
function describe(value: string | number | null): string {
  if (value === null) return 'нет значения';       // дальше value: string | number
  if (typeof value === 'number') return `число ${value.toFixed(2)}`;
  return `строка длиной ${value.length}`;           // здесь value: string
}

// Пользовательская проверка формы неизвестных данных
interface ApiError { code: string; message: string }
function isApiError(x: unknown): x is ApiError {
  return typeof x === 'object' && x !== null && 'code' in x && 'message' in x;
}

const body: unknown = JSON.parse('{"code":"OUT_OF_STOCK","message":"Нет в наличии"}');
if (isApiError(body)) console.log(body.code);
console.log(describe(3), describe('abc'), describe(null));

Интерфейсы#

описывает форму объекта. В тестах интерфейсами описывают тестовые данные, ответы API и параметры objects.

TypeScripttests/types.ts
export interface Product {
  id: number;
  title: string;
  price: number;
  inStock: boolean;
}

export interface ProductListResponse {
  items: Product[];
  total: number;
  page: number;
}

// Расширение интерфейса
export interface DiscountedProduct extends Product {
  oldPrice: number;
}
TypeScripttests/catalog.spec.ts
import { test, expect } from '@playwright/test';
import type { ProductListResponse } from './types';

test('каталог возвращает товары в наличии', async ({ request }) => {
  const res = await request.get('/api/products?inStock=true');
  expect(res.ok()).toBeTruthy();
  const body = (await res.json()) as ProductListResponse;
  expect(body.items.length).toBeGreaterThan(0);
  for (const p of body.items) expect(p.inStock).toBe(true);
});
as — это обещание, а не проверка

as ProductListResponse говорит компилятору «поверь мне» и ничего не проверяет во время выполнения. Если сервер вернёт другую структуру, тест упадёт позже с непонятной ошибкой или, хуже, пройдёт. Для API-ответов форму нужно проверять — это делает валидация (глава «Schema и Contract Testing»).

interface или type? Оба описывают объекты. interface можно расширять (extends) и объявлять повторно; type умеет union, пересечения и утилитные типы. Практичное правило: интерфейсы для форм объектов, type — для union и производных типов. Главное — единообразие в проекте.

Обработка ошибок#

прерывает выполнение до ближайшего catch. В тестах это обычный механизм падения: неудачная проверка expect тоже выбрасывает исключение.

TypeScripterrors.ts
class ApiRequestError extends Error {
  constructor(public readonly status: number, message: string) {
    super(message);
    this.name = 'ApiRequestError';
  }
}

function parseTotal(raw: string): number {
  const value = Number(raw.replace(/\s|₽/g, '').replace(',', '.'));
  if (Number.isNaN(value)) throw new Error(`Не удалось разобрать сумму: "${raw}"`);
  return value;
}

try {
  parseTotal('3 990,50 ₽');
  throw new ApiRequestError(503, 'Сервис недоступен');
} catch (e: unknown) {
  // в catch значение имеет тип unknown — сначала сузить
  if (e instanceof ApiRequestError) console.log(e.status, e.message);
  else throw e;
} finally {
  console.log('finally выполняется всегда — здесь освобождают ресурсы');
}

Правила для тестового кода:

  1. Не глушите ошибки. try { ... } catch {} вокруг шага теста превращает падение в ложный успех.
  2. Добавляйте контекст. Сообщение «Не удалось разобрать сумму: "abc"» полезнее, чем NaN тремя шагами позже.
  3. Очистку делайте в finally или, лучше, в teardown фикстуры — она выполнится даже при падении теста (глава 16).

Пример: типизированный хелпер тестовых данных#

TypeScripttests/data/users.ts
export type Role = 'customer' | 'manager' | 'admin';

export interface TestUser {
  email: string;
  password: string;
  role: Role;
  balance: number;
}

let counter = 0;

export function makeUser(overrides: Partial<TestUser> = {}): TestUser {
  counter += 1;
  return {
    email: `qa+${Date.now()}-${counter}@example.com`,
    password: 'Str0ngPass!',
    role: 'customer',
    balance: 0,
    ...overrides,
  };
}
TypeScripttests/users.spec.ts
import { test, expect } from '@playwright/test';
import { makeUser } from './data/users';

test('менеджер может создать пользователя', async ({ request }) => {
  const manager = makeUser({ role: 'manager' });

Фабрика возвращает новый объект при каждом вызове (нет общей мутации), уникальный email (нет конфликтов при параллельном запуске), а Partial<TestUser> позволяет переопределить только нужные поля.

Типичные ошибки#

any в типах ответов

const body: any = await res.json() — дальше любые опечатки в полях (body.totla) пройдут компиляцию и превратятся в undefined. Описывайте форму ответа и проверяйте её схемой.

|| для значений по умолчанию

const retries = Number(process.env.RETRIES) || 2 — значение 0 превратится в 2. Для «если не задано» используйте ??.

Не запускать tsc в CI

запускает тесты без проверки типов. Ошибку типов вы увидите только в редакторе — если вообще откроете файл. Добавьте tsc --noEmit в .

Пустой catch

Заглушённое исключение в шаге подготовки данных приводит к тому, что тест падает позже по непонятной причине — или проходит, ничего не проверив.

Что важно для собеседования#

JuniorЧем == отличается от ===, а || от ???

Ответ

=== сравнивает без приведения типов, == приводит типы (0 == '' — true), поэтому в коде используют только ===. || возвращает правый операнд для любого ложного левого значения (0, '', false, null, undefined, NaN), ?? — только для null и undefined. Для значений по умолчанию, где 0 допустим, нужен ??.

JuniorЧем any отличается от unknown, и что использовать для ответа API?

Ответ

any отключает проверку типов: с ним можно делать что угодно. unknown требует сначала проверить тип. Ответ API до проверки по смыслу unknown; после валидации схемы его можно считать конкретным интерфейсом. as SomeType ничего не проверяет во время выполнения.

JuniorЧем interface отличается от type?

Ответ

Оба описывают форму объектов. interface поддерживает extends и повторное объявление (слияние). type может описывать union, пересечения, кортежи, литеральные и производные типы (Partial, Omit). На практике: интерфейсы — для объектов, type — для union и вычисляемых типов; главное — единообразие в проекте.

MiddleПочему тесты на TypeScript могут пройти, хотя в них ошибка типов?

Ответ

транспилирует без проверки типов — только удаляет аннотации. Ошибки типов ловит компилятор tsc, поэтому в проекте нужен отдельный шаг tsc --noEmit (локально и первым шагом в CI), а также ESLint с правилами для асинхронного кода.

MiddleКак вы организуете тестовые данные в TypeScript-проекте?

Ответ

Типизированные фабрики: функция makeUser(overrides: Partial<User>) возвращает новый объект с валидными значениями по умолчанию и уникальными полями (email с меткой времени или UUID), переопределяя только нужное. Так нет мутации общих объектов, данные не конфликтуют при параллельном запуске, а union-типы (Role) не дают передать недопустимое значение.

Проверьте себя#

Тест
1
Что выведет console.log(0 ?? 5, 0 || 5)?

?? заменяет только null и undefined, поэтому 0 ?? 5 даёт 0. || заменяет любое ложное значение, и 0 || 5 даёт 5.

2
Чем unknown отличается от any?

unknown заставляет сузить тип (typeof, instanceof, type guard) перед использованием. any отключает проверки полностью.

3
Что гарантирует запись const body = (await res.json()) as Product[]?

Приведение типа as не выполняет проверок. Форму ответа нужно валидировать отдельно, например JSON Schema.

Почему тестовые данные лучше создавать фабрикой, а не хранить одним общим объектом?

Общий объект может быть изменён одним тестом и повлиять на другие (зависимость от порядка выполнения). Фабрика возвращает новый объект при каждом вызове, генерирует уникальные значения для параллельных запусков и позволяет переопределять поля через Partial<T>.

Тесты проходят локально, но в CI шаг tsc --noEmit падает. Как это возможно?

транспилирует без проверки типов, поэтому тест с ошибкой типов может выполниться и даже пройти. tsc --noEmit проверяет типы во всём проекте и находит ошибку. Это нормальная и полезная ситуация: ошибку нужно исправить, а не отключать проверку.
