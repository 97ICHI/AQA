Fixtures и Hooks

beforeEach, afterEach, beforeAll, afterAll, встроенные и собственные фикстуры, setup и teardown, области test и worker. Как подготовить окружение для теста так, чтобы тесты оставались независимыми.

≈ 10 мин чтенияM
Опирается на: Assertions и ожидания
Основная идея

Фикстура — это «то, что нужно тесту, чтобы начать»: страница, авторизованный пользователь, созданный заказ. Она сама себя готовит, отдаёт тесту и выполняет teardown при обычном завершении теста, в том числе после падения assertion. Тест просто перечисляет нужные фикстуры в параметрах.

Цель главы: выносить подготовку и очистку в фикстуры, выбирать правильную область жизни и избегать общего состояния, которое делает тесты зависимыми друг от друга.

Кратко

Хуки выполняются для всех тестов блока; фикстуры — только для тестов, которые их запросили, и включают гарантированную очистку после use().

Главное

  • beforeEach/afterEach — до и после каждого теста; beforeAll/afterAll — один раз на воркер для группы тестов (и повторно после перезапуска воркера).
  • Фикстура: код до await use(value) — setup, после — teardown; teardown выполняется и при падении теста.
  • Область test — новая копия для каждого теста; worker — одна на процесс-воркер (дорогие ресурсы, общие для тестов).
  • test.extend создаёт свой test с дополнительными фикстурами; фикстуры могут зависеть друг от друга.
  • Общее изменяемое состояние в beforeAll или переменных модуля — главная причина зависимости тестов от порядка.
  • Teardown не защищает от принудительного завершения процесса; для оставшихся данных нужны run ID и TTL.

Термины

Fixture
Именованный ресурс, который тест запрашивает в параметрах: фикстура готовит значение, передаёт его через use() и убирает за собой после теста.
Hook
Функция, выполняемая до или после тестов блока: beforeEach, afterEach, beforeAll, afterAll.
Setup / Teardown
Действия до теста (создать данные, открыть страницу) и после него (удалить данные, закрыть ресурсы). Teardown должен выполняться и при падении теста.
Fixture Scope
Как долго живёт значение фикстуры: test — новое для каждого теста, worker — одно на процесс-воркер.
Test Isolation
Независимость тестов: каждый можно запустить отдельно, в любом порядке, параллельно и повторно с тем же результатом.

Важно: test.describe.serial и тесты, которые используют данные, созданные предыдущим тестом, ломают параллельный запуск, ретраи и запуск отдельного теста.

Подготовка и очистка#

Почти каждому тесту нужно предварительное состояние: открытая страница, вошедший пользователь, товар в корзине. И почти каждый тест оставляет следы: созданные записи, изменённые настройки. Есть два механизма, которые решают это в :

  • — функции beforeEach, afterEach, beforeAll, afterAll, которые выполняются для всех тестов файла или группы describe.
  • — именованные ресурсы, которые тест запрашивает в параметрах и которые сами отвечают за .

Hooks#

TypeScripttests/hooks-order.spec.ts
import { test, expect } from '@playwright/test';

test.describe('корзина', () => {
  test.beforeAll(async () => {
    console.log('beforeAll — один раз на воркер перед тестами группы');
  });

  test.beforeEach(async ({ page }) => {
    console.log('beforeEach — перед каждым тестом');
    await page.goto('/cart');
  });

  test.afterEach(async ({ page }, testInfo) => {
    console.log(`afterEach — после каждого: ${testInfo.title} → ${testInfo.status}`);
  });

  test.afterAll(async () => {
    console.log('afterAll — один раз на воркер после тестов группы');
  });

  test('пустая корзина', async ({ page }) => {
    await expect(page.getByText('Корзина пуста')).toBeVisible();
  });

  test('кнопка перехода в каталог', async ({ page }) => {
    await expect(page.getByRole('link', { name: 'В каталог' })).toBeVisible();
  });
});

Порядок для двух тестов в одном воркере: beforeAll → beforeEach → тест 1 → afterEach → beforeEach → тест 2 → afterEach → afterAll.

Две особенности, которые важно помнить:

  1. beforeAll выполняется в каждом воркере, а не один раз на весь прогон. Если тесты файла распределены по трём воркерам (с fullyParallel), он выполнится трижды.
  2. После падения теста воркер перезапускается, и для оставшихся тестов beforeAll выполнится снова. Если beforeAll создаёт «единственного» пользователя с фиксированным email, второй запуск упадёт на дубликате.

Fixtures#

Встроенные фикстуры :

Фикстура Область Что даёт
page test Новая страница в новом контексте
context test Новый
browser Браузер, общий для тестов воркера
request test APIRequestContext для HTTP-запросов (с baseURL и опциями из конфига)
browserName Worker 'chromium', 'firefox' или 'webkit'
baseURL и другие опции use test / Worker Значения конфигурации

Собственные фикстуры создаются через test.extend. Код до await use(value) — setup, после — teardown:

TypeScripttests/fixtures.ts
import { test as base, expect, type APIRequestContext } from '@playwright/test';

export interface TestUser { id: number; email: string; password: string }

async function createUser(request: APIRequestContext, prefix: string): Promise<TestUser> {
  const email = `${prefix}+${Date.now()}-${Math.random().toString(36).slice(2, 8)}@example.com`;
  const password = 'Str0ngPass!';
  const res = await request.post('/api/users', { data: { email, password } });
  expect(res.status(), 'создание тестового пользователя').toBe(201);
  const { id } = (await res.json()) as { id: number };
  return { id, email, password };
}

type Fixtures = {
  user: TestUser;
  loggedInPage: import('@playwright/test').Page;
};

export const test = base.extend<Fixtures>({
  user: async ({ request }, use) => {
    const user = await createUser(request, 'qa');   // setup
    await use(user);                                // тест выполняется здесь
    await request.delete(`/api/users/${user.id}`);  // teardown — даже если тест упал
  },

  loggedInPage: async ({ page, user }, use) => {    // фикстура зависит от другой фикстуры
    await page.goto('/login');
    await page.getByLabel('Email').fill(user.email);
    await page.getByLabel('Пароль').fill(user.password);
    await page.getByRole('button', { name: 'Войти' }).click();
    await expect(page.getByRole('link', { name: 'Профиль' })).toBeVisible();
    await use(page);
  },
});

export { expect } from '@playwright/test';
TypeScripttests/profile.spec.ts

Области жизни: test и worker#

определяет, как долго живёт значение:

  • test (по умолчанию) — создаётся для каждого теста заново. Для всего, что тест может изменить: страница, пользователь, корзина.
  • worker — создаётся один раз на процесс-воркер и разделяется его тестами. Для дорогих и неизменяемых в ходе тестов ресурсов: подключение к базе, тестовый аккаунт «только для чтения», поднятый мок-сервер.
TypeScripttests/worker-fixtures.ts
import { test as base } from '@playwright/test';
import { Pool } from 'pg';

type WorkerFixtures = { db: Pool; workerAccount: string };

export const test = base.extend<{}, WorkerFixtures>({
  db: [async ({}, use) => {
    const pool = new Pool({ connectionString: process.env.DB_URL, max: 2 });
    await use(pool);
    await pool.end();
  }, { scope: 'worker' }],

  // Отдельный аккаунт на каждый воркер: тесты разных воркеров не мешают друг другу
  workerAccount: [async ({}, use, workerInfo) => {
    await use(`qa-worker-${workerInfo.workerIndex}@example.com`);
  }, { scope: 'worker' }],
});

({ auto: true }) выполняется для каждого теста без явного запроса — например, для прикрепления логов к отчёту или проверки, что в консоли браузера не было ошибок.

Интерактив требует JavaScriptПорядок выполнения хуков и фикстур: два воркера, три теста, фикстуры test и Worker. Включите падение теста или общее состояние в beforeAll и посмотрите, как меняется порядок и где появляется зависимость тестов.

Очистка не гарантирована: падения и частичный setup#

Teardown предусмотрен и при падении , но процесс может быть принудительно убит, контейнер остановлен или сеть недоступна. Поэтому cleanup не является безусловной гарантией. Для долговечных окружений нужен , TTL тестовых данных или отдельный сборщик устаревших ресурсов.

Если setup успел создать пользователя, но не дошёл до use(), предусмотрите finally вокруг уже созданных ресурсов. Ошибка удаления должна оставлять диагностику, но не стирать первичную причину падения. не может зависеть от test Fixture; test Fixture может использовать Worker Fixture.

Retries перезапускают Worker после падения: beforeAll и Worker setup могут выполниться снова. Не используйте порядковый номер Worker как единственный глобальный идентификатор запуска.

Независимость тестов#

— каждый тест можно запустить отдельно, в любом порядке, параллельно с другими и повторно, и он даст тот же результат. Неправильно организованная подготовка — главный враг изоляции:

TypeScriptТесты зависят друг от друга
let orderId: number;                          // общее изменяемое состояние модуля

test.beforeAll(async ({ request }) => {
  const res = await request.post('/api/orders', { data: { productId: 7 } });
  orderId = (await res.json()).id;            // один заказ на все тесты
});

test('оплатить заказ', async ({ request }) => {
  await request.post(`/api/orders/${orderId}/pay`);
});

test('отменить оплаченный заказ', async ({ request }) => {
  // предполагает, что предыдущий тест уже оплатил заказ!
  const res = await request.post(`/api/orders/${orderId}/cancel`);
  expect(res.status()).toBe(200);
});

Проблемы: второй тест нельзя запустить отдельно; при fullyParallel тесты попадут в разные воркеры с разными заказами; если первый тест упадёт, второй упадёт тоже; при ретрае второго теста заказ уже отменён.

TypeScriptКаждый тест готовит своё состояние
test('отменить оплаченный заказ', async ({ request, paidOrder }) => {
  const res = await request.post(`/api/orders/${paidOrder.id}/cancel`);
  expect(res.status()).toBe(200);
});
// paidOrder — фикстура: создаёт заказ, оплачивает через API, после теста удаляет

Пример: фикстура «товар в корзине»#

TypeScripttests/cart-fixtures.ts
import { test as base, expect } from '@playwright/test';

type CartFixtures = { productInCart: { id: number; title: string } };

export const test = base.extend<CartFixtures>({
  productInCart: async ({ page }, use) => {
    // Быстрая подготовка через API вместо кликов по каталогу.
    // page.request делит cookies с контекстом страницы: корзина, созданная запросом,
    // будет той же корзиной, которую увидит браузер.
    const res = await page.request.post('/api/cart/items', { data: { productId: 1, qty: 1 } });
    expect(res.ok(), 'добавление товара в корзину').toBeTruthy();
    await use({ id: 1, title: 'Наушники Pulse' });
    await page.request.delete('/api/cart/items');
  },
});

export { expect };
TypeScripttests/cart.spec.ts
import { test, expect } from './cart-fixtures';

test('изменение количества пересчитывает сумму', async ({ page, productInCart }) => {
  await page.goto('/cart');
  const row = page.getByRole('row', { name: new RegExp(productInCart.title) });
  await row.getByRole('button', { name: 'Увеличить количество' }).click();
  await expect(row.getByTestId('line-total')).toHaveText('9 980 ₽');
});

Тест описывает только проверяемое поведение; подготовка быстрая (API), очистка предусмотрена в teardown, а другие тесты корзины переиспользуют фикстуру одной строкой в параметрах.

Типичные ошибки#

Данные в beforeAll с фиксированными значениями

beforeAll выполняется в каждом воркере и повторно после падения. Фиксированный email приведёт к конфликту при втором выполнении.

Очистка в конце тела теста

Если тест упадёт раньше, строки очистки не выполнятся. Очистка — в teardown фикстуры или afterEach.

Фикстура области Worker, которую тесты изменяют

Один тест положил товар в «общую» корзину Worker-фикстуры — следующий тест видит чужой товар. Изменяемое состояние — только область test.

Огромный beforeEach «на всякий случай»

Вход, создание заказа, открытие трёх страниц для каждого теста, даже если половине это не нужно. Лишняя работа замедляет прогон; фикстуры создаются только по запросу.

Что важно для собеседования#

JuniorЧем фикстуры отличаются от хуков beforeEach/afterEach?

Ответ

Хуки выполняются для всех тестов блока; фикстуры — только для тестов, которые их запросили. Фикстура объединяет setup и teardown в одной функции (код до и после use), teardown выполняется даже при падении, фикстуры переиспользуются через импорт test, типизированы и могут зависеть друг от друга.

MiddleСколько раз выполняется beforeAll и чем это опасно?

Ответ

Один раз на воркер для группы тестов — то есть при параллельном запуске несколько раз, и ещё раз после перезапуска воркера из-за упавшего теста. Опасно, если beforeAll создаёт данные с фиксированными значениями (дубликаты) или общее изменяемое состояние, на которое полагаются тесты (зависимость от порядка).

MiddleКогда использовать фикстуру с областью worker?

Ответ

Для дорогих в создании и неизменяемых тестами ресурсов: пул подключений к базе, запущенный мок-сервер, аккаунт только для чтения, отдельный аккаунт на воркер (через workerInfo.workerIndex). Всё, что тесты изменяют, — только область test, иначе тесты одного воркера начнут влиять друг на друга.

Middle+В проекте тесты используют данные, созданные предыдущими тестами (describe.serial). Как будете исправлять?

Ответ

Выделю состояние, которое каждый тест ожидает на входе, и сделаю для него фикстуры с быстрой подготовкой через API (например, paidOrder, shippedOrder) и очисткой в teardown. Каждый тест будет создавать своё состояние. Это позволит запускать тесты по одному, параллельно и с ретраями. Сквозной сценарий, если он нужен, оставлю одним E2E-тестом с шагами test.step, а не цепочкой зависимых тестов.

Проверьте себя#

Тест
1
Где выполнится код после await use(user) в фикстуре, если тест упал?

Teardown фикстуры выполняется независимо от результата теста, поэтому очистку размещают именно там.

2
Тесты одного файла с fullyParallel: true распределились по трём воркерам. Сколько раз выполнится beforeAll этого файла?

beforeAll выполняется на воркер. Плюс повторно после перезапуска воркера из-за упавшего теста.

3
Какую область выбрать для пула подключений к базе данных?

Пул — дорогой ресурс, который тесты не изменяют. Область Worker создаёт его один раз на процесс.

Чем фикстура лучше beforeEach для создания тестового пользователя?

Фикстура создаёт пользователя только для тестов, которые её запросили, держит setup и teardown в одной функции (очистка предусмотрена в teardown), переиспользуется через импорт test в любом файле, типизирована и может зависеть от других фикстур. beforeEach выполняется для всех тестов блока и требует отдельного afterEach для очистки.

Как проверить, что тесты действительно независимы?

Запустить их в разном порядке и составе: по одному (npx playwright test file.spec.ts:LINE), в обратном порядке, с --repeat-each, с fullyParallel и несколькими воркерами. Тест, который падает в одном из режимов и проходит в другом, зависит от состояния других тестов.
