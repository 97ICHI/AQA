Page Object Model

Page Object Model и Page Components: как отделить «что проверяет тест» от «как устроена страница», чтобы изменение интерфейса правилось в одном месте. И когда POM превращается в лишнюю сложность.

≈ 9 мин чтенияM
Опирается на: Fixtures и HooksОрганизация кода
Основная идея

Page Object — класс, который знает, как устроена страница или её часть, и предоставляет тестам действия пользователя. Тест говорит «войти как Анна», а не «заполнить #email и нажать .btn-submit». Изменилась вёрстка — меняется один класс, а не десятки тестов.

Цель главы: проектировать слой страниц и компонентов с понятной ответственностью, подключать его через фикстуры и не создавать абстракций сверх необходимого.

Кратко

POM отделяет структуру страницы (локаторы, шаги взаимодействия) от сценариев и ожиданий тестов. Компоненты переиспользуются между страницами.

Главное

  • Object хранит локаторы и методы-действия пользователя (login, addToCart), а не технические операции (clickButton3).
  • Проверки бизнес-результата остаются в тесте; в Page Object допустимы проверки «страница открылась» и локаторы для проверок.
  • — повторяющаяся часть интерфейса (шапка, карточка товара, модальное окно) со своим классом; страницы содержат компоненты (композиция).
  • Page Objects удобно отдавать тестам через фикстуры: async ({ cartPage }) => ….
  • Ценность POM растёт с числом тестов, использующих одну страницу; для пяти тестов маленького проекта он может быть лишним.
  • Антипаттерны: «божественный» PO, глубокое наследование, обёртка над каждым методом , проверки всего подряд внутри PO.

Термины

Page Object Model
Паттерн: каждая страница описывается классом с локаторами и действиями пользователя; тесты используют эти методы и не знают о вёрстке.
Page Component
Класс для повторяющейся части интерфейса (шапка, карточка товара, модальное окно), который получает корневой локатор и используется разными страницами.
Separation of Concerns
Принцип: разные задачи — в разных слоях. В тестах: сценарии, фикстуры, страницы, компоненты, API-клиенты и данные меняются независимо.
Composition
Построение объекта из других объектов-компонентов («содержит») вместо наследования («является»). Гибче глубоких иерархий.

Важно: Page Object не должен прятать то, что тест проверяет. Если по тексту теста непонятно, какое поведение ожидается, абстракция зашла слишком далеко.

Зачем нужен Page Object Model#

Представьте 40 тестов, каждый из которых входит в систему через форму:

TypeScriptБез POM: знание о форме входа размазано по тестам
await page.getByLabel('Email').fill('anna@example.com');
await page.getByLabel('Пароль').fill('Str0ngPass!');
await page.getByRole('button', { name: 'Войти' }).click();

Дизайнер переименовал кнопку «Войти» в «Продолжить». Нужно найти и поправить 40 мест. решает это: знание о том, как устроена страница входа, живёт в одном классе.

TypeScriptsrc/pages/LoginPage.ts
import { expect, type Locator, type Page } from '@playwright/test';

export class LoginPage {
  readonly email: Locator;
  readonly password: Locator;
  readonly submit: Locator;
  readonly error: Locator;

  constructor(private readonly page: Page) {
    this.email = page.getByLabel('Email');
    this.password = page.getByLabel('Пароль');
    this.submit = page.getByRole('button', { name: 'Войти' });
    this.error = page.getByRole('alert');
  }

  async open() {
    await this.page.goto('/login');
    await expect(this.submit).toBeVisible();   // страница действительно открылась
  }

  async login(email: string, password: string) {
    await this.email.fill(email);
    await this.password.fill(password);
    await this.submit.click();
  }
}
TypeScripttests/login.spec.ts
import { test, expect } from '@playwright/test';
import { LoginPage } from '../src/pages/LoginPage';

test('неверный пароль показывает ошибку', async ({ page }) => {
  const login = new LoginPage(page);
  await login.open();
  await login.login('anna@example.com', 'wrong-password');
  await expect(login.error).toHaveText('Неверный email или пароль');
  await expect(page).toHaveURL(/\/login/);
});

Тест читается как сценарий, а переименование кнопки затрагивает одну строку в LoginPage.

Что кладут в Page Object#

В Page Object В тесте
Локаторы элементов Сценарий: последовательность шагов
Действия пользователя: login, search, addToCart, applyPromo Тестовые данные
Навигацию: open() и ожидание признака загрузки Проверки бизнес-результата
Локаторы, которые тест использует в проверках (error, total) Ожидаемые значения

Спорный вопрос — проверки внутри Object. Практичное правило:

  • допустимо: проверить, что страница открылась (open() ждёт характерный элемент), или вспомогательная проверка внутри шага, без которой шаг бессмыслен;
  • не стоит: проверять бизнес-результат («сумма равна 900») внутри метода — тогда из теста не видно, что именно проверяется, а метод нельзя переиспользовать в негативном сценарии.

Методы называют по намерению пользователя: applyPromo('SALE10'), а не fillInput3AndClickButton().

Page Components#

Многие части интерфейса повторяются на разных страницах: шапка с поиском и корзиной, карточка товара, модальное окно подтверждения, таблица с пагинацией. — класс для такой части, который получает корневой локатор и ищет элементы внутри него.

TypeScriptsrc/components/ProductCard.ts
import type { Locator } from '@playwright/test';

export class ProductCard {
  readonly title: Locator;
  readonly price: Locator;
  readonly addButton: Locator;

  constructor(readonly root: Locator) {
    this.title = root.getByRole('heading');
    this.price = root.getByTestId('product-price');
    this.addButton = root.getByRole('button', { name: 'В корзину' });
  }

  async addToCart() {
    await this.addButton.click();
  }
}
TypeScriptsrc/components/Header.ts
import type { Locator, Page } from '@playwright/test';

export class Header {
  readonly search: Locator;
  readonly cartBadge: Locator;

  constructor(page: Page) {
    const root = page.getByRole('banner');
    this.search = root.getByRole('searchbox', { name: 'Поиск' });
    this.cartBadge = root.getByTestId('cart-count');
  }

  async searchFor(text: string) {
    await this.search.fill(text);
    await this.search.press('Enter');
  }
}
TypeScriptsrc/pages/CatalogPage.ts
import type { Page } from '@playwright/test';
import { Header } from '../components/Header';
import { ProductCard } from '../components/ProductCard';

export class CatalogPage {
  readonly header: Header;

  constructor(private readonly page: Page) {
    this.header = new Header(page);           // композиция, не наследование
  }

  async open() {
    await this.page.goto('/catalog');
  }

  card(title: string): ProductCard {
    return new ProductCard(this.page.getByTestId('product-card').filter({ hasText: title }));
  }
}

Компоненты используют принцип из главы «Организация кода»: страница содержит шапку и карточки, а не наследует их методы.

Подключение через фикстуры#

Создавать new CatalogPage(page) в каждом тесте не нужно — это работа для фикстур:

TypeScriptsrc/fixtures/pages.ts
import { test as base } from '@playwright/test';
import { CatalogPage } from '../pages/CatalogPage';
import { LoginPage } from '../pages/LoginPage';

type Pages = { catalogPage: CatalogPage; loginPage: LoginPage };

export const test = base.extend<Pages>({
  catalogPage: async ({ page }, use) => { await use(new CatalogPage(page)); },
  loginPage: async ({ page }, use) => { await use(new LoginPage(page)); },
});
export { expect } from '@playwright/test';
TypeScripttests/catalog-cart.spec.ts
import { test, expect } from '../src/fixtures/pages';

test('добавление товара увеличивает счётчик корзины', async ({ catalogPage }) => {
  await catalogPage.open();
  await catalogPage.card('Наушники Pulse').addToCart();
  await expect(catalogPage.header.cartBadge).toHaveText('1');
});

Разделение ответственности#

в тестовом проекте выглядит как набор слоёв:

Текст
tests/            — сценарии и ожидания: ЧТО проверяем
src/fixtures/     — подготовка окружения: пользователи, данные, страницы
src/pages/        — страницы: КАК устроен интерфейс
src/components/   — повторяющиеся части интерфейса
src/api/          — клиенты API для подготовки данных и API-тестов
src/data/         — фабрики тестовых данных

Каждый слой меняется по своей причине: редизайн затрагивает pages и components, изменение контракта API — api, новое бизнес-правило — tests. Подробная структура проекта — в главе «Архитектура тестового проекта».

Интерактив требует JavaScriptСтоимость изменения интерфейса: выберите изменение (переименовали кнопку, поменяли форму входа, новая шапка) и число тестов — сравните, сколько мест нужно править без POM, с POM и с компонентами.

Когда POM избыточен#

POM — инструмент, а не обязательный ритуал. Признаки, что абстракция мешает:

  • Обёртки над каждым методом : async clickLoginButton() { await this.loginButton.click() } для каждой кнопки. Тест не стал понятнее, а кода стало вдвое больше.
  • Глубокая иерархия BasePage → AuthenticatedPage → ShopPage → CatalogPage, где изменения базовых классов ломают всё.
  • «Божественный» Object на 1000 строк, описывающий весь сайт.
  • Скрытые проверки: await cart.verifyEverything() — из теста непонятно, что проверено.
  • Маленький проект: пять тестов на два экрана. Локаторы в тесте или общие хелперы дешевле, чем инфраструктура классов. POM можно ввести, когда появится дублирование.
  • Одноразовые страницы: экран, который используется в одном тесте, не нуждается в отдельном классе.

Альтернативы и дополнения: функции-хелперы для сценариев (loginViaApi(request, user)), паттерн Screenplay (акторы и задачи) для очень больших наборов, фикстуры, которые готовят состояние в обход UI.

Пример: рефакторинг теста корзины#

TypeScriptДо
test('корзина', async ({ page }) => {
  await page.goto('/catalog');
  await page.locator('[data-testid="product-card"]:has-text("Наушники Pulse") button').click();
  await page.locator('[data-testid="product-card"]:has-text("Мышь Click") button').click();
  await page.locator('header a[href="/cart"]').click();
  await expect(page.locator('.cart-row')).toHaveCount(2);
  await expect(page.locator('[data-testid="cart-total"]')).toHaveText('6 280 ₽');
});
TypeScriptПосле
test('сумма корзины складывается из позиций', async ({ catalogPage, cartPage }) => {
  await catalogPage.open();
  await catalogPage.card('Наушники Pulse').addToCart();
  await catalogPage.card('Мышь Click').addToCart();
  await catalogPage.header.openCart();
  await expect(cartPage.rows).toHaveCount(2);
  await expect(cartPage.total).toHaveText('6 280 ₽');
});

Изменилась вёрстка карточки — правим ProductCard. Ссылка на корзину переехала — правим Header. Сам тест не меняется, а его название и шаги объясняют, что проверяется.

Типичные ошибки#

Page Object возвращает «сырые» значения для проверок

async getTotal(): Promise<string> { return this.total.textContent() } и затем expect(await cart.getTotal()).toBe(…) — однократное чтение и гонка. Отдавайте локатор и проверяйте .

Хранить состояние в Page Object

Object, который «помнит» добавленные товары в поле класса, расходится с реальным состоянием страницы. Источник правды — сама страница.

Page Object знает о тестовых данных и окружении

LoginPage.loginAsAdmin() с захардкоженным паролем смешивает слой страницы и данные. Передавайте данные параметрами или используйте фикстуры.

Что важно для собеседования#

JuniorЧто такое Page Object Model и зачем он нужен?

Ответ

Паттерн, в котором каждая страница (или её часть) описывается классом: локаторы и действия пользователя. Тесты вызывают методы (login, addToCart) и проверяют результат, не зная о вёрстке. Плюсы: изменение интерфейса правится в одном месте, тесты читаются как сценарии, код переиспользуется.

MiddleНужно ли писать проверки внутри Page Object?

Ответ

Бизнес-проверки — в тесте: так видно, что проверяется, и методы PO можно использовать и в позитивных, и в негативных сценариях. В PO допустимы проверки готовности (open() ждёт характерный элемент) и вспомогательные ожидания внутри шага. Для проверок PO отдаёт локаторы, а не прочитанные значения, чтобы работали web-first assertions.

MiddleКогда POM приносит больше вреда, чем пользы?

Ответ

Когда превращается в обёртку над каждым методом , в глубокую иерархию наследования или «божественный» класс на весь сайт; когда скрывает проверки (verifyAll()); в маленьких проектах и для одноразовых экранов. Признак — тест стал менее понятен, а изменение затрагивает больше файлов.

Middle+Как организовать Page Objects для большого SPA с повторяющимися виджетами?

Ответ

Компоненты (шапка, таблица с фильтрами, модальные окна, карточки) — отдельные классы с корневым локатором; страницы собираются из компонентов композицией. Objects выдаются тестам через фикстуры. Подготовка состояния — через API, а не через цепочки PO. Наследование — максимум один уровень. Для локаторов — договорённость о и ролях с командой фронтенда.

Проверьте себя#

Тест
1
Что из этого правильнее разместить в Page Object?

Page Object знает устройство страницы и действия на ней. Ожидаемые значения и тестовые данные принадлежат тестам и фикстурам.

2
Как правильно отдать тесту значение суммы корзины для проверки?

Локатор позволяет использовать web-first проверку с автоожиданием, а ожидаемое значение остаётся в тесте.

3
Что такое Page Component?

Компонент получает корневой локатор и ищет элементы внутри него; страницы содержат компоненты.

Когда вы бы не стали вводить POM?

В маленьком проекте с несколькими тестами, для одноразовых экранов, в API-тестах (там свои клиенты) и когда обёртки не добавляют смысла. POM окупается, когда одну страницу используют много тестов и её структура меняется.

Почему композиция компонентов предпочтительнее наследования от BasePage?

Компоненты переиспользуются там, где они реально есть, и меняются независимо. Наследование связывает страницы общим базовым классом: в нём копятся методы, нужные не всем, а изменение базового класса затрагивает все страницы.
