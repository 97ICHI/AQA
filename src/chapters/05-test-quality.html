Качество и эффективность автотестов

Test Coverage и Code Coverage, поддерживаемость, надёжность, время выполнения, нестабильность и окупаемость: как оценивать набор автотестов и почему «много тестов и высокий coverage» ещё не означает высокое качество.

≈ 10 мин чтенияJ–M
Опирается на: Введение в AQAВиды тестированияTest Design
Основная идея

Набор автотестов хорош, если он быстро и надёжно сообщает о существенных регрессиях и недорого обходится в поддержке. Количество тестов и процент покрытия — лишь косвенные признаки.

Цель главы: оценивать набор по нескольким метрикам одновременно и объяснять, почему 100% coverage не гарантирует отсутствие дефектов.

Кратко

Качество набора тестов складывается из того, какие риски он покрывает, насколько ему можно доверять, как быстро он отвечает и сколько стоит его поддержка.

Главное

  • — доля требований или рисков, для которых есть проверки; — доля кода, выполненного во время тестов.
  • Code Coverage показывает, что код выполнялся, но не то, что результат проверялся: тест без assertions даёт покрытие без защиты.
  • Branch coverage строже line coverage; mutation testing проверяет, ловят ли тесты намеренно внесённые ошибки.
  • Надёжность: вероятность зелёного прогона набора из N тестов при отсутствии дефектов ≈ (1 − p)^N, где p — доля ложных падений теста.
  • Ретраи повышают долю зелёных прогонов, но скрывают нестабильность и увеличивают время.
  • Поддерживаемость: понятные имена, отсутствие дублирования, устойчивые локаторы, независимость тестов.

Термины

Test Coverage
Доля требований, сценариев или рисков, для которых существуют проверки. Считается по трассировке «требование → тесты».
Code Coverage
Доля кода приложения, выполненного во время тестов (строки, ветви, функции). Показывает непроверенный код, но не качество проверок.
Branch Coverage
Доля пройденных ветвей условий (if/else, ?:, &&, ||). Строже покрытия строк.
Mutation Testing
Оценка силы тестов: в код вносятся небольшие изменения (мутанты), и проверяется, падают ли тесты. Доля «убитых» мутантов — mutation score.
Test Maintainability
Насколько легко понять, изменить и починить тест: читаемость, отсутствие дублирования, устойчивые локаторы, независимость.

Важно: Метрика, ставшая целью, перестаёт быть хорошей метрикой: требование «80% coverage любой ценой» порождает тесты без проверок.

Что значит «хорошие автотесты»#

Набор автотестов — продукт для команды. Его «пользователи» — разработчики и тестировщики, которые по результатам решают, можно ли сливать изменения и выпускать релиз. Хороший набор:

  1. Ловит существенные регрессии — покрывает важные риски, а не просто много кода.
  2. Не врёт — падает только при реальных проблемах (высокая ).
  3. Отвечает быстро — сигнал приходит, пока разработчик помнит контекст изменения.
  4. Понятен при падении — по отчёту ясно, что сломалось и где.
  5. Дёшев в поддержке — изменение интерфейса не требует правки десятков файлов ().

Ни одна метрика по отдельности это не измеряет. Дальше разберём каждую и её слепые зоны.

Test Coverage#

— доля требований, пользовательских сценариев или рисков, для которых есть проверки. Её считают по трассировке «требование → тесты»: в тест-менеджменте (TestRail, Allure TestOps, Xray) или по тегам в коде.

TypeScripttests/checkout.spec.ts
import { test, expect } from '@playwright/test';

test('оплата картой создаёт заказ', { tag: ['@checkout', '@REQ-142'] }, async ({ page }) => {
  await page.goto('/checkout');
  // ...
  await expect(page.getByRole('heading', { name: 'Заказ оформлен' })).toBeVisible();
});

Теги позволяют запускать подмножества (npx playwright test --grep @checkout) и строить отчёт о покрытии требований.

Слепая зона: «требование покрыто» не говорит, насколько хорошо. Один позитивный тест и двадцать проверок с граничными значениями засчитываются одинаково.

Code Coverage#

показывает, какая доля кода приложения выполнилась во время тестов. Основные виды:

Вид Что считает Слабость
Line / Statement Выполненные строки (инструкции) Не видит невыполненные ветви условий в одной строке
Пройденные ветви if/else, ?:, &&, || Не видит комбинации условий
Function Вызванные функции Очень грубая

Покрытие собирают инструментированием кода (Istanbul/nyc) или средствами движка V8 (c8; умеет собирать JS-покрытие в Chromium через page.coverage). Для AQA важно понимать, что Code Coverage обычно считают по unit- и интеграционным тестам; для E2E-набора через браузер её собирают редко и интерпретируют осторожно.

Почему 100% не значит «без ошибок»#

TypeScriptshipping.ts
export function shippingCost(total: number, isMember: boolean): number {
  if (isMember || total >= 3000) return 0;
  return 300;
}
TypeScriptshipping.spec.ts
import { test, expect } from '@playwright/test';
import { shippingCost } from './shipping';

test('участник — бесплатно', () => {
  shippingCost(100, true); // нет проверки!
});

test('обычный клиент — 300', () => {
  expect(shippingCost(100, false)).toBe(300);
});

Оба теста вместе выполняют каждую строку и обе ветви if — line и Branch Coverage 100%. Но:

  • первый тест ничего не проверяет: если функция вернёт 500, он пройдёт;
  • граница total >= 3000 не проверена: замена на > не будет замечена.

Покрытие говорит, какой код не проверен (это полезно!), но не говорит, что проверенный код проверен хорошо.

Mutation Testing#

отвечает на вопрос «поймают ли мои тесты ошибку?». Инструмент (для — Stryker) вносит в код небольшие изменения — мутанты: >= → >, || → &&, return 0 → return 1 — и запускает тесты. Если тесты упали, мутант «убит»; если прошли — тесты слабые. Доля убитых мутантов (mutation score) — гораздо более честная метрика, чем coverage, но дорогая в вычислении, поэтому её применяют к критичным модулям.

Надёжность и нестабильность#

— тест, который при одинаковом коде и окружении то проходит, то падает. Причины разобраны в главе «Flaky Tests и диагностика»; здесь важна арифметика.

Если каждый из N тестов независимо даёт ложное падение с вероятностью p, то вероятность полностью зелёного прогона при отсутствии дефектов:

P(зелёный) = (1 − p)^N

При p = 0,5% и N = 300 получается 0,995^300 ≈ 0,22: почти 4 из 5 прогонов красные без причины. Набор, где отдельные тесты «почти стабильны», в целом нестабилен.

Ретраи (retries в ) повторяют упавший тест. С r ретраями тест ложно падает, только если упали все r + 1 попыток: p^(r+1). Это резко повышает долю зелёных прогонов, но:

  • нестабильность никуда не делась — просто стала невидимой (Playwright помечает такие тесты как flaky, и это нужно отслеживать);
  • реальный периодический дефект (гонка в коде продукта) тоже будет скрыт;
  • время прогона растёт.
Интерактив требует JavaScriptКалькулятор надёжности набора: число тестов, доля ложных падений одного теста и число ретраев → вероятность зелёного прогона, ожидаемое число повторов и время.

Время выполнения#

Время прогона определяет, как используется набор. Ориентиры для большинства команд:

Набор Где запускается Желаемое время
Unit Локально и на каждый коммит Секунды – пара минут
Smoke После деплоя До 5 минут
Регрессия API + ключевой UI На каждый 10–20 минут
Полная регрессия Ночью / перед релизом Часы допустимы

Если тесты на Merge Request идут час, разработчики начинают сливать изменения без них. Способы ускорения — параллелизм, шардирование, перенос проверок на нижние уровни — разобраны в главах «Параллельное выполнение» и «Оптимизация».

Поддерживаемость#

— сколько усилий нужно, чтобы понять, изменить и починить тест. Признаки хорошей поддерживаемости:

  • Имя теста описывает поведение: «просроченный промокод не применяется», а не test_47.
  • Тест читается как сценарий: подготовка → действие → проверка (Arrange–Act–Assert).
  • Нет дублирования: шаги входа или создания заказа вынесены в fixtures и page objects.
  • Устойчивые локаторы: по роли и тексту, а не по случайным CSS-классам (глава 14).
  • Независимость: тест не зависит от порядка запуска и данных других тестов.
  • Понятное падение: сообщение говорит, что ожидалось и что получено.

Метрики набора и ROI#

Полезно смотреть на несколько метрик вместе:

Метрика Что показывает Хороший тренд
Доля нестабильных тестов Доверие к сигналу Падает
Время до обратной связи на MR Удобство для разработчиков Падает
Регрессии, пойманные автотестами Реальная польза Растёт
Дефекты, ушедшие в прод (defect escape) Пробелы в покрытии рисков Падает
Время на поддержку тестов в спринте Стоимость Стабильно или падает
Покрытие требований и рисков Широта Растёт по критичным областям

из первой главы складывается из этих же величин: поддержка и разбор ложных падений — это затраты, пойманные регрессии и ускорение релизов — выгода.

Пример: две команды#

Команда А Команда Б
Тестов 1200, в основном UI 450: 300 API, 120 компонентных, 30 UI
(unit) 85% 70%
Время на MR 75 минут 12 минут
Нестабильных 6% 0,5%
Перезапусков «на всякий случай» Почти каждый MR Редко

Команда А выглядит сильнее по количеству и покрытию, но её набор почти бесполезен как ворота: он долгий и шумный, поэтому разработчики его обходят. Команда Б получает быстрый и надёжный сигнал. Задача AQA в команде А — не дописывать тесты, а переносить проверки на API, удалять дубли и чинить нестабильные тесты.

Типичные ошибки#

Ставить coverage целью

Требование «не ниже 90%» приводит к тестам, которые вызывают код без проверок. Используйте coverage для поиска непроверенного кода, а не как KPI.

Скрывать нестабильность ретраями

Ретраи — временная мера с обязательным мониторингом тестов со статусом flaky. Без мониторинга они маскируют и нестабильные тесты, и периодические дефекты продукта.

Считать тест полезным, потому что он ни разу не падал

Тест, который никогда не падает, может проверять несущественное или ничего (как первый тест в примере с coverage). Периодически проверяйте тесты мутациями: сломайте условие вручную и убедитесь, что тест покраснел.

Что важно для собеседования#

JuniorУ проекта 100% code coverage. Значит ли это, что дефектов нет?

Ответ

Нет. Coverage показывает, что код выполнялся во время тестов, а не что результат проверялся. Тест без assertions даёт покрытие без защиты; проверки могут не затрагивать границы условий; покрытие не учитывает комбинации ветвей, требования, которые вообще не реализованы, и интеграцию с другими системами. Coverage полезен, чтобы найти непроверенный код; силу тестов лучше оценивать .

JuniorЧем Test Coverage отличается от Code Coverage?

Ответ

— доля требований, сценариев или рисков, для которых есть тесты; считается по трассировке требований. — доля кода, выполненного тестами; считается инструментами (Istanbul, c8). Первая отвечает на вопрос «что из нужного проверено», вторая — «какой код вообще не исполнялся».

MiddleПочему набор из 300 «почти стабильных» тестов постоянно красный?

Ответ

Ложные падения складываются. Если у каждого теста вероятность ложного падения p, вероятность зелёного прогона (1 − p)^N. При p = 0,5% и N = 300 это около 22%. Поэтому важна стабильность каждого теста, измерение доли flaky и ограничение числа медленных верхнеуровневых тестов.

MiddleКакими метриками вы оцениваете эффективность автоматизации?

Ответ

Набор метрик, а не одна: доля нестабильных тестов и ложных падений, время обратной связи на , число регрессий, пойманных автотестами, дефекты, ушедшие в прод (defect escape rate), покрытие критичных требований и рисков, время на поддержку тестов. Количество тестов и Code Coverage — вспомогательные показатели.

Частая ошибка

Назвать только «количество тестов» и «процент покрытия».
Middle+Какую политику ретраев вы бы предложили для CI?

Ответ

Локально — 0 ретраев, чтобы видеть нестабильность сразу. В CI — 1–2 ретрая как страховка от инфраструктурных сбоев, но с обязательной обработкой статуса flaky: отчёт о тестах, прошедших со второй попытки, задачи на их починку, порог, при превышении которого тест уходит в карантин. Для тестов, падающих детерминированно, ретраи только удлиняют прогон. Можно включить failOnFlakyTests, чтобы сделать нестабильность видимой как ошибку.

Middle+Руководитель просит «довести покрытие автотестами до 90% к концу квартала». Как ответите?

Ответ

Уточню цель: скорее всего, нужно меньше дефектов в продакшене и быстрее релизы. Процент покрытия легко нарастить бесполезными тестами без проверок, и он не говорит о рисках. Предложу метрики, связанные с целью: покрытие критичных бизнес-потоков и требований, defect escape rate по областям, время обратной связи на MR, доля flaky. Покрытие кода оставить как индикатор непроверенных мест (особенно для изменённого кода), а не как цель. Покажу план: какие риски закрываем и на каких уровнях.

Проверьте себя#

Тест
1
Тест вызывает функцию со всеми ветвями, но не содержит ни одного expect. Что верно?

Coverage учитывает выполнение кода, а не проверки. Playwright Test по умолчанию не требует наличия assertions. Mutation Testing покажет, что мутанты выживают.

2
В наборе 100 тестов, у каждого 1% ложных падений. Какая вероятность зелёного прогона без дефектов?

0,99^100 ≈ 0,366. Нестабильность складывается: «почти стабильные» тесты дают нестабильный набор.

3
Чем branch coverage строже line coverage?

В строке return a > 0 ? x : y line coverage засчитает строку после одного вызова, а Branch Coverage потребует пройти обе ветви тернарного оператора.

Как убедиться, что новый тест действительно может упасть?

Временно сломать проверяемое поведение (изменить ожидаемое значение, условие в коде или ответ мока) и убедиться, что тест покраснел с понятным сообщением. Это ручная версия . Тест, который нельзя заставить упасть, ничего не проверяет.

Почему ретраи увеличивают время прогона даже при стабильных тестах в целом?

Повтор выполняется для каждого упавшего теста. Если в прогоне есть реальный дефект, все задетые им тесты будут прогнаны r + 1 раз, и прогон станет заметно дольше именно тогда, когда нужен быстрый сигнал. Поэтому в CI обычно ставят 1–2 ретрая, а локально — 0.
