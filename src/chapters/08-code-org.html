Глава 7 · Раздел II · Программирование для AQA

Структуры данных и организация кода

Map и Set, JSON, классы и композиция, DRY, SOLID и чистый код — только то, что нужно для поддерживаемого тестового проекта, и только на примерах из автоматизации.

≈ 10 мин чтенияM
Опирается на: Основы TypeScript
Основная идея

Тестовый код живёт годами и меняется вместе с продуктом. Правильные структуры данных и разделение ответственности определяют, сколько стоит каждое изменение интерфейса или API.

Цель главы: выбирать подходящую структуру данных, разделять код тестов на понятные части и понимать, когда принцип DRY в тестах вредит.

Кратко

Хороший тестовый код легко читать как сценарий и легко менять в одном месте при изменении продукта.

Главное

  • Map — словарь с ключами любого типа и сохранением порядка; Set — множество уникальных значений (поиск дубликатов, сравнение наборов).
  • — текстовый формат обмена; JSON.parse возвращает данные без проверки формы, JSON.stringify теряет undefined, функции и превращает Date в строку.
  • Класс объединяет данные и поведение; private/readonly защищают внутреннее состояние page object или клиента API.
  • Композиция (объект содержит компоненты) гибче глубокого наследования (BasePage → AuthPage → AdminPage → …).
  • в инфраструктуре теста (клиенты, фикстуры, локаторы), но в самих тестах: тело теста должно читаться без прыжков по файлам.
  • : одна ответственность у класса, расширение без правки, зависимость от абстракций — например, клиента API, который можно подменить.

Термины

Map / Set
Коллекции JavaScript: Map хранит пары «ключ → значение» с ключами любого типа, Set — уникальные значения.
JSON
Текстовый формат обмена данными (объекты, массивы, строки, числа, true/false, null). Основной формат тел запросов и ответов REST API.
DRY
Don't Repeat Yourself: каждое знание описано в одном месте. В тестах применяется к инфраструктуре: локаторам, клиентам, фикстурам.
DAMP
Descriptive And Meaningful Phrases: тело теста должно читаться как самостоятельный сценарий, даже ценой небольшого повтора.
SOLID
Пять принципов проектирования: единственная ответственность, открытость/закрытость, подстановка Лисков, разделение интерфейсов, инверсия зависимостей.

Важно: Абстракция ради абстракции вредит: три уровня наследования и универсальный «BaseHelper» усложняют тесты сильнее, чем умеренное дублирование.

Map и Set#

Массивы и объекты закрывают большинство задач, но для двух случаев есть более подходящие коллекции ():

  • Set — множество уникальных значений. Проверка дубликатов, сравнение наборов, «встречалось ли значение».
  • Map — словарь «ключ → значение», где ключ может быть любого типа, порядок вставки сохраняется, а размер доступен через size.
JavaScript
// Set: в выдаче каталога не должно быть дубликатов
const ids = [101, 102, 103, 102, 104];
const unique = new Set(ids);
console.log('дубликаты есть:', unique.size !== ids.length);

// Сравнение наборов: какие товары пропали после фильтрации
const before = new Set(['A', 'B', 'C']);
const after = new Set(['A', 'C']);
console.log('пропали:', [...before].filter((x) => !after.has(x)));

// Map: подсчёт статусов заказов в ответе
const statuses = ['paid', 'shipped', 'paid', 'cancelled', 'paid'];
const counts = new Map();
for (const s of statuses) counts.set(s, (counts.get(s) ?? 0) + 1);
console.log(Object.fromEntries(counts));

// Map как реестр созданных в тесте сущностей для очистки
const created = new Map([['user', 17], ['order', 920]]);
for (const [kind, id] of created) console.log(`удалить ${kind} #${id}`);
Текст
дубликаты есть: true
пропали: [ 'B' ]
{ paid: 3, shipped: 1, cancelled: 1 }
удалить user #17
удалить order #920

JSON#

— текстовый формат, в котором приходят почти все ответы API и хранятся тестовые данные. Важные детали:

JavaScript
const order = { id: 1, createdAt: new Date('2026-01-15T10:00:00Z'), note: undefined, total: 0.1 + 0.2 };
const text = JSON.stringify(order);
console.log(text);
const back = JSON.parse(text);
console.log(typeof back.createdAt, 'note' in back);
console.log(JSON.stringify({ a: 1, b: [1, 2] }, null, 2));
Текст
{"id":1,"createdAt":"2026-01-15T10:00:00.000Z","total":0.30000000000000004}
string false
{
  "a": 1,
  "b": [
    1,
    2
  ]
}
  • JSON.stringify превращает Date в строку ISO, выбрасывает поля со значением undefined и функции.
  • JSON.parse возвращает данные без проверки формы — для это фактически any. Проверка формы — задача валидации схемы (глава 21).
  • Числа с плавающей точкой неточны: 0.1 + 0.2 не равно 0.3. Для денег сравнивайте в копейках или используйте toBeCloseTo.
  • Сравнение объектов: toEqual сравнивает содержимое рекурсивно, toBe — ссылку. Для ответов API почти всегда нужен toEqual или toMatchObject (частичное совпадение).

Классы и основы ООП#

в тестах встречается в трёх местах: objects, клиенты API и построители тестовых данных. Класс объединяет данные (поля) и поведение (методы).

TypeScriptsrc/api/CartClient.ts
import type { APIRequestContext } from '@playwright/test';

export interface CartItem { productId: number; qty: number }

export class CartClient {
  // private: внешний код не должен трогать запросный контекст напрямую
  constructor(private readonly request: APIRequestContext) {}

  async add(item: CartItem): Promise<void> {
    const res = await this.request.post('/api/cart/items', { data: item });
    if (!res.ok()) throw new Error(`Не удалось добавить товар: HTTP ${res.status()} ${await res.text()}`);
  }

  async items(): Promise<CartItem[]> {
    const res = await this.request.get('/api/cart/items');
    return (await res.json()) as CartItem[];
  }

  async clear(): Promise<void> {
    await this.request.delete('/api/cart/items');
  }
}

Ключевые слова, которые стоит знать:

Конструкция Зачем в тестах
constructor(private readonly x: T) Короткая запись поля, которое задаётся один раз
private / protected Скрыть детали: локаторы, сырой HTTP-клиент
readonly Запретить переназначение (локаторы Page object)
static Общие для класса значения или фабричные методы
extends Наследование — используйте осторожно (см. ниже)
implements Класс обещает соответствовать интерфейсу

Композиция вместо наследования#

Частый путь в тестовых проектах: BasePage с общими методами → AuthorizedPage extends BasePage → AdminPage extends AuthorizedPage → … Через год в BasePage 60 методов, которые нужны разным страницам, а изменение одного ломает десятки тестов.

решает это иначе: страница содержит компоненты, а не наследует их.

TypeScriptsrc/pages/components.ts
import type { Locator, Page } from '@playwright/test';

export class Header {
  readonly cartLink: Locator;
  readonly searchBox: Locator;
  constructor(page: Page) {
    this.cartLink = page.getByRole('link', { name: /Корзина/ });
    this.searchBox = page.getByRole('searchbox', { name: 'Поиск' });
  }
  async search(text: string) {
    await this.searchBox.fill(text);
    await this.searchBox.press('Enter');
  }
}

export class ProductCard {
  constructor(private readonly root: Locator) {}
  title() { return this.root.getByRole('heading'); }
  async addToCart() { await this.root.getByRole('button', { name: 'В корзину' }).click(); }
}

export class CatalogPage {
  readonly header: Header;
  constructor(private readonly page: Page) {
    this.header = new Header(page);           // композиция: страница содержит шапку
  }
  card(name: string) {
    return new ProductCard(this.page.getByTestId('product-card').filter({ hasText: name }));
  }
}

Шапка используется на всех страницах, но ни одна страница не наследует её методы — она просто содержит объект Header. Подробнее о такой архитектуре — в главе «Page Object Model».

DRY и DAMP#

(Don't Repeat Yourself) — каждое знание должно быть описано в одном месте. В тестовом проекте это относится к:

  • адресам, учётным данным, конфигурации;
  • локаторам элементов (в objects);
  • шагам подготовки (вход, создание заказа) — в fixtures и хелперах;
  • клиентам API и общим проверкам.

Но в теле теста работает другой принцип — (Descriptive And Meaningful Phrases): тест должен читаться как самостоятельный сценарий, даже ценой небольшого повтора.

TypeScriptСлишком DRY: тест нельзя прочитать
test('скидка', async ({ page }) => {
  await runScenario(page, SCENARIOS.discount, { variant: 3, check: true });
});
TypeScriptDAMP: сценарий виден в тесте
test('промокод SALE10 уменьшает сумму на 10%', async ({ cartPage }) => {
  await cartPage.open();
  await cartPage.applyPromo('SALE10');
  await expect(cartPage.total).toHaveText('900 ₽');
});

Правило: выносите как (механику), оставляйте в тесте что (шаги и ожидания).

SOLID в тестовом коде#

— пять принципов проектирования. В автоматизации полезно понимать их на конкретных примерах:

Принцип Суть В тестовом проекте
S — Single Responsibility У класса одна причина для изменения LoginPage знает о странице входа, но не создаёт пользователей в БД
O — Open/Closed Расширяем, не изменяя Новый способ авторизации — новая фикстура, а не if в старой
L — Liskov Substitution Наследник заменяет родителя без сюрпризов Если AdminPage extends BasePage ломает метод open(), наследование неверно
I — Segregation Маленькие специализированные интерфейсы Тесту корзины нужен CartClient, а не клиент на 80 методов всех API
D — Dependency Inversion Зависеть от абстракций Сервис данных принимает интерфейс UsersApi; в тесте его можно подменить заглушкой
TypeScriptsrc/data/UserFactory.ts
export interface UsersApi {
  create(email: string): Promise<{ id: number; email: string }>;
  remove(id: number): Promise<void>;
}

// Зависит от интерфейса, а не от конкретного HTTP-клиента (принцип D)
export class UserFactory {
  private readonly created: number[] = [];
  constructor(private readonly api: UsersApi) {}

  async create(prefix = 'qa') {
    const user = await this.api.create(`${prefix}+${Date.now()}@example.com`);
    this.created.push(user.id);
    return user;
  }

  async cleanup() {
    for (const id of this.created.splice(0)) await this.api.remove(id);
  }
}

Чистый код в тестах#

Принципы , которые сильнее всего влияют на автотесты:

  1. Имена говорят о поведении. test('заблокированный пользователь не может войти'), а не test('login 3'). Переменная adminUser, а не u2.
  2. Без магических значений. const FREE_SHIPPING_THRESHOLD = 3000 вместо 3000 в пяти местах.
  3. Маленькие функции с одной задачей. createPaidOrder() вместо prepare(type, flags…).
  4. Структура Arrange–Act–Assert. Подготовка, действие, проверка — визуально разделены.
  5. Сообщения проверок помогают. expect(total, 'сумма после промокода').toBe(900) — второй аргумент expect попадёт в отчёт.
  6. Комментарии объясняют «почему», а не «что»: // сервер округляет вниз до рубля — см. REQ-212.
  7. Удаляйте мёртвый код. Закомментированные тесты и test.skip без причины и ссылки на задачу засоряют проект.

Пример: рефакторинг дублирования#

Было: в 15 тестах повторяется блок из 6 строк входа через форму. Изменили страницу логина — пришлось править 15 файлов.

Стало:

  1. Локаторы формы входа — в LoginPage (одно место).
  2. Вход как предусловие — фикстура authenticatedPage, которая использует сохранённое состояние авторизации (глава «Продвинутый Playwright»), а не проходит форму в каждом тесте.
  3. Сам тест входа через форму — один отдельный тест, который проверяет именно форму.

Результат: изменение страницы логина затрагивает один класс, тесты стали быстрее, а тест формы входа явно проверяет то, что раньше проверялось «попутно».

Типичные ошибки#

God-объект BaseHelper

Класс на тысячу строк со всеми хелперами проекта нарушает Single Responsibility: его меняют все, и любое изменение рискованно. Разделяйте по предметным областям: CartClient, UserFactory, PaymentStub.

Логика в тестах

Циклы с условиями, вычисление ожидаемого результата той же формулой, что и в продукте. Если формула в продукте неверна, тест повторит ошибку. Ожидания должны быть конкретными значениями.

Сравнение объектов через toBe

expect(await res.json()).toBe({ id: 1 }) всегда падает: toBe сравнивает ссылки. Используйте toEqual или toMatchObject.

Что важно для собеседования#

JuniorЧем toBe отличается от toEqual и toMatchObject?

Ответ

toBe сравнивает через Object.is — для объектов это сравнение ссылок. toEqual рекурсивно сравнивает содержимое (игнорируя поля со значением undefined), toStrictEqual учитывает и их, и классы. toMatchObject проверяет, что объект содержит указанное подмножество полей — удобно для ответов API, где есть лишние поля вроде createdAt.

MiddleВсегда ли нужно устранять дублирование в тестах?

Ответ

Нет. Дублирование механики (локаторы, HTTP-клиенты, подготовка данных) устраняется — это . Но тело теста должно читаться как сценарий без прыжков по файлам — это . Чрезмерная абстракция вроде runScenario(page, config) прячет шаги и проверки, и тест становится непонятным при падении. Выношу «как», оставляю в тесте «что».

MiddleПочему в page objects композицию часто предпочитают наследованию?

Ответ

Глубокие иерархии (BasePage → AuthPage → AdminPage) накапливают методы, которые нужны не всем наследникам, и связывают страницы: изменение базового класса ломает многие тесты. С композицией страница содержит компоненты (Header, ProductCard, Modal), которые переиспользуются на любых страницах независимо. Наследование оставляю для одного уровня с действительно общим поведением.

MiddleПриведите пример применения SOLID в тестовом фреймворке.

Ответ

Single Responsibility: LoginPage описывает только страницу входа, а пользователи создаются через UserFactory. Dependency Inversion: UserFactory принимает интерфейс UsersApi, поэтому в unit-тестах фабрики его можно подменить заглушкой, а в интеграционных — использовать HTTP-клиент. Segregation: тесту корзины передаётся CartClient, а не универсальный клиент всех API.

Проверьте себя#

Тест
1
Какая структура лучше всего подходит для быстрой проверки «встречался ли этот id раньше»?

Set.has проверяет наличие за константное в среднем время и сразу гарантирует уникальность значений.

2
Что произойдёт с полем note: undefined после JSON.stringify?

JSON.stringify пропускает поля со значением undefined и функции. Это важно, когда тест проверяет наличие поля в теле запроса.

3
Какой принцип нарушает LoginPage, который ещё и создаёт пользователей в базе данных?

У класса две причины для изменения: страница входа и схема хранения пользователей.

Почему ожидаемое значение в тесте лучше записать числом, а не вычислить той же формулой, что в продукте?

Если формула в продукте ошибочна, та же формула в тесте даст ту же ошибку, и тест пройдёт. Конкретное значение, полученное из требований или ручного расчёта (oracle), независимо от реализации.

Когда наследование page objects всё же уместно?

Когда отношение действительно «является» и поведение наследника не противоречит родителю: например, базовый класс с общим методом open() и проверкой загрузки страницы. Как только наследники начинают переопределять методы с другим смыслом или иерархия глубже двух уровней, лучше перейти к композиции.
