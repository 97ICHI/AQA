Архитектура веб-приложений

Client-server, frontend, backend и база данных; DNS, TCP/IP, HTTP и HTTPS; cookies, сессии, аутентификация и авторизация. Что происходит между вводом адреса и появлением страницы — и где на этом пути ломаются тесты.

≈ 9 мин чтенияJ
Основная идея

Веб-приложение — цепочка компонентов: браузер, DNS, сеть, балансировщик, фронтенд, бэкенд, база данных. Автотест взаимодействует с её началом, а падать может из-за любого звена. Понимание цепочки превращает «тест упал» в «запрос не прошёл авторизацию на бэкенде».

Цель главы: представлять путь запроса через систему и по симптому определять, какое звено вероятнее всего сломалось.

Кратко

Запрос проходит → TCP → TLS → → балансировщик → бэкенд → база данных и обратно; на каждом звене возможна своя ошибка.

Главное

  • выполняется в браузере и вызывает backend по HTTP; бизнес-правила и права доступа должны проверяться на backend.
  • DNS превращает имя в IP-адрес; TCP устанавливает соединение; TLS шифрует его и проверяет сертификат (HTTPS).
  • HTTP не хранит состояние; состояние пользователя переносят cookies или токены в заголовке Authorization.
  • Cookie-атрибуты: HttpOnly (недоступна JS), Secure (только HTTPS), SameSite (защита от CSRF), Domain/Path/Expires.
  • — кто вы (401 при неудаче), — что вам можно (403).
  • Сессия на сервере хранит состояние по id из cookie; содержит данные пользователя в подписанном токене.

Термины

Frontend
Часть приложения, выполняемая в браузере: HTML, CSS, JavaScript. Показывает интерфейс и вызывает backend по HTTP.
Backend
Серверное приложение: принимает запросы, проверяет права, выполняет бизнес-логику и работает с базой данных.
DNS
Domain Name System: переводит доменное имя (shop.example.com) в IP-адрес. Ответы кэшируются на время TTL.
HTTP
Протокол «запрос–ответ» без хранения состояния: метод, URL, заголовки и тело запроса; код статуса, заголовки и тело ответа.
HTTPS / TLS
HTTP поверх TLS: шифрование трафика, проверка подлинности сервера по сертификату и защита целостности данных.

Важно: Кнопка, скрытая в интерфейсе для обычного пользователя, не означает запрет: права проверяются на сервере, и это нужно тестировать через API.

Client-server архитектура#

В модели клиент (браузер, мобильное приложение, автотест) отправляет запросы, а сервер их обрабатывает и отвечает. Типичное веб-приложение состоит из трёх слоёв:

  • — код, выполняемый в браузере: HTML, CSS, JavaScript. Современные приложения часто SPA (Single Application): страница загружается один раз, а данные подгружаются запросами к API.
  • — серверное приложение: принимает HTTP-запросы, проверяет права, выполняет бизнес-логику, читает и записывает данные.
  • Database — хранилище данных (PostgreSQL, MySQL, MongoDB). Напрямую с браузером не общается.

Между ними часто стоят: CDN (раздаёт статику ближе к пользователю), балансировщик нагрузки (распределяет запросы между экземплярами бэкенда), кэш (Redis), очереди сообщений и внешние сервисы (платежи, почта, SMS).

Что это значит для тестировщика

Одно и то же поведение можно проверить на разных слоях. Сообщение «недостаточно средств» показывает фронтенд, но решение принимает бэкенд. Если проверить правило только через UI, вы проверите и фронтенд, и бэкенд вместе — и при падении не будете знать, кто виноват. Если проверить только через API, не узнаете, правильно ли сообщение показано пользователю.

Путь запроса#

Что происходит, когда тест выполняет page.goto('https://shop.example.com/catalog'):

  1. . Браузер узнаёт IP-адрес домена shop.example.com.
  2. TCP. Устанавливается соединение с сервером на порту 443.
  3. TLS. Стороны договариваются о шифровании; браузер проверяет сертификат сервера.
  4. HTTP-запрос. GET /catalog с заголовками и cookies.
  5. Балансировщик / прокси передаёт запрос одному из экземпляров приложения.
  6. проверяет сессию, выполняет логику, обращается к базе данных.
  7. Ответ. HTML-страница, затем браузер загружает CSS, JS и выполняет запросы к API за данными.
  8. Рендеринг. Браузер строит DOM и показывает страницу; JS навешивает обработчики событий.
Интерактив требует JavaScriptПуть запроса: включайте и выключайте условия (кэш DNS, HTTPS, наличие сессии, права пользователя, состояние базы) и смотрите, на каком звене запрос проходит или ломается и с каким кодом.

DNS#

(Domain Name System) переводит доменное имя в IP-адрес. Результат кэшируется в браузере, операционной системе и у провайдера на время TTL.

Почему это важно в автоматизации:

  • тестовые стенды часто доступны по внутренним доменам — без VPN или правильного DNS тест упадёт с net::ERR_NAME_NOT_RESOLVED;
  • после переключения стенда на новый IP старые записи в кэше какое-то время ведут на старый сервер;
  • в Docker-сетях имя сервиса (app, db) — тоже DNS-имя внутри сети (глава 27).

TCP/IP#

— стек протоколов передачи данных. Упрощённо:

Уровень Протоколы Что делает
Прикладной , , WebSocket Смысл сообщений
Транспортный TCP, UDP Доставка между процессами (порты); TCP гарантирует порядок и доставку
Сетевой IP Маршрутизация между компьютерами по IP-адресам
Канальный Ethernet, Wi-Fi Передача в локальной сети

TCP устанавливает соединение «тройным рукопожатием» (SYN → SYN-ACK → ACK). Порт определяет процесс на сервере: 80 — HTTP, 443 — HTTPS, 5432 — PostgreSQL, 3000 — частый порт локального dev-сервера.

Типичные сетевые ошибки в тестах: ECONNREFUSED / ERR_CONNECTION_REFUSED — на порту никто не слушает (приложение не запущено, неверный порт); ETIMEDOUT — пакеты не доходят (firewall, недоступная сеть); ECONNRESET — соединение оборвано (перезапуск сервера, прокси).

HTTP и HTTPS#

— протокол «запрос–ответ» поверх TCP. Подробно он разобран в следующей главе «HTTP и REST API». Ключевое свойство: HTTP не хранит состояния — каждый запрос независим, сервер «не помнит» предыдущие.

— HTTP поверх TLS. TLS:

  • шифрует трафик — посторонние не прочитают пароль и cookies;
  • проверяет подлинность сервера по сертификату, выданному доверенным центром сертификации;
  • защищает целостность — данные нельзя незаметно изменить.

На тестовых стендах часто используют самоподписанные сертификаты; браузер их отвергнет (ERR_CERT_AUTHORITY_INVALID). В для таких стендов есть опция ignoreHTTPSErrors: true — её включают только для тестовых окружений, где это осознанное решение.

Cookies и сессии#

Раз не хранит состояние, как сайт «помнит», что вы вошли? Сервер выдаёт браузеру заголовком Set-Cookie, а браузер автоматически отправляет её в каждом следующем запросе к этому домену.

HTTP
HTTP/1.1 200 OK
Set-Cookie: sid=8f3a9c…; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=86400
Атрибут Значение Почему важно
HttpOnly JavaScript на странице не может прочитать Cookie Защита от кражи сессии при XSS
Secure Отправляется только по HTTPS Не утечёт в открытом HTTP
SameSite Strict / Lax / None — отправлять ли при запросах с других сайтов Защита от CSRF
Domain, Path Для каких адресов отправлять Cookie стенда A не попадёт на стенд B
Expires / Max-Age Срок жизни Без них — до закрытия браузера

Два основных подхода к хранению состояния входа:

  • Серверная : Cookie содержит только случайный идентификатор, а данные сессии лежат на сервере (в памяти, Redis, БД). Выход — удаление сессии на сервере.
  • Токен (): сервер выдаёт подписанный токен с данными пользователя и сроком действия; клиент отправляет его в заголовке Authorization: Bearer … или в Cookie. Сервер проверяет подпись, не обращаясь к хранилищу. Отозвать JWT до истечения срока сложнее.
Как это использовать в тестах

Раз состояние входа — это cookies или токен, вход через форму в каждом тесте не нужен: можно один раз войти, сохранить состояние (cookies и localStorage) и подставлять его в новые контексты браузера. В это storageState — разбор в главе «Продвинутый Playwright».

Authentication и Authorization#

Два разных вопроса:

  • — «кто вы?» Проверка учётных данных: пароль, токен, сертификат, второй фактор. Неудача — 401 Unauthorized (название исторически неточное: речь именно об аутентификации).
  • — «что вам можно?» Проверка прав аутентифицированного пользователя на действие или ресурс. Неудача — 403 Forbidden; иногда сервер намеренно отвечает 404, чтобы не раскрывать существование чужого ресурса.

Матрица проверок доступа, которую стоит автоматизировать через API для каждого важного ресурса:

Кто Свой ресурс Чужой ресурс Админ-операция
Без токена 401 401 401
Истёкший токен 401 401 401
Обычный пользователь 200 403 / 404 403
Администратор 200 200 200

Отдельная частая уязвимость — IDOR (Insecure Direct Object Reference): пользователь меняет id в URL (/api/orders/1042 → /api/orders/1043) и получает чужой заказ. Тест на неё прост и очень ценен.

Пример: диагностика по симптому#

Симптом в тесте Звено Что проверить
ERR_NAME_NOT_RESOLVED Домен стенда, VPN, /etc/hosts, имя сервиса в Docker
ERR_CONNECTION_REFUSED TCP Запущено ли приложение, порт, baseURL
ERR_CERT_AUTHORITY_INVALID TLS Сертификат стенда, ignoreHTTPSErrors для теста
Редирект на /login посреди теста Сессия Истёк срок Cookie/токена, тесты делят одну сессию, выход в другом тесте
403 при действии, которое раньше работало Авторизация Роль тестового пользователя, изменение прав
502 Bad Gateway / 504 Gateway Timeout Балансировщик / бэкенд Бэкенд упал или не успевает ответить
Данные на странице не обновились Кэш / Кэширование ответов, повторный запрос, ожидание в тесте

Типичные ошибки#

Проверять права только через UI

Скрытая кнопка «Удалить» не мешает отправить DELETE /api/users/5 напрямую. Проверки доступа автоматизируют на уровне API.

Путать 401 и 403

401 — не удалось установить, кто вы; 403 — вы известны, но действие запрещено. Тест, ожидающий 403 без токена, проверяет неправильное поведение.

Включить ignoreHTTPSErrors везде

Опция маскирует реальную проблему с сертификатом на стенде, где он должен быть корректным, — например, перед релизом.

Что важно для собеседования#

JuniorЧто происходит, когда вы вводите адрес сайта в браузере?

Ответ

Браузер получает IP через (с учётом кэша), устанавливает TCP-соединение, для HTTPS выполняет TLS-рукопожатие с проверкой сертификата, отправляет HTTP-запрос с заголовками и cookies. Запрос проходит через балансировщик к бэкенду, тот проверяет сессию, выполняет логику и обращается к базе. Ответ — HTML; затем браузер загружает CSS и JS, выполняет запросы к API и отрисовывает страницу.

JuniorЧем аутентификация отличается от авторизации? Какие коды ответа им соответствуют?

Ответ

Аутентификация — установить, кто пользователь (пароль, токен); при неудаче — 401. Авторизация — проверить, что можно этому пользователю; при отказе — 403 (иногда 404, чтобы не раскрывать существование ресурса). Проверки доступа тестирую через API матрицей: без токена, с истёкшим, с чужим ресурсом, с недостаточной ролью.

JuniorЧто такое cookies и какие у них важные атрибуты?

Ответ

Данные, которые сервер сохраняет в браузере заголовком Set-Cookie, а браузер отправляет обратно с запросами к домену. Важные атрибуты: HttpOnly (недоступна JS — защита от XSS), Secure (только HTTPS), SameSite (не отправлять с чужих сайтов — защита от CSRF), Domain/Path (область), Expires/Max-Age (срок).

MiddleЧем серверная сессия отличается от JWT и что это меняет для тестов?

Ответ

Серверная сессия: в только идентификатор, состояние на сервере, выход — удаление сессии. : подписанный токен содержит данные и срок, сервер проверяет подпись без хранилища, отзыв до истечения требует отдельного механизма. Для тестов: проверяю выход (старый токен/сессия не работает), истечение срока, подмену данных в токене (подпись должна не сойтись) и могу готовить авторизацию через API или сохранённый storageState.

Middle+Как автоматизировать проверку, что пользователь не видит чужие данные?

Ответ

Через API: создаю два пользователя и ресурс у первого, затем запрашиваю, изменяю и удаляю этот ресурс токеном второго — ожидаю 403 или 404 и неизменность данных. Повторяю для всех чувствительных эндпоинтов (лучше параметризованным тестом по списку маршрутов). Это ловит IDOR — частую уязвимость, которую UI-тесты не находят, потому что интерфейс просто не показывает чужие id.

Проверьте себя#

Тест
1
Тест получает ERR_CONNECTION_REFUSED. Что вероятнее всего?

Отказ в соединении означает, что на указанном адресе и порту никто не принимает TCP-соединения.

2
Какой атрибут cookie не даёт JavaScript на странице прочитать значение сессии?

HttpOnly запрещает доступ к Cookie из document.cookie, что защищает сессию при XSS.

3
Пользователь с ролью «покупатель» запрашивает GET /api/admin/reports с валидным токеном. Какой ответ корректен?

Аутентификация прошла (токен валиден), но прав нет — это 403.

Почему после входа через UI тест можно не логинить заново в каждом следующем тесте?

Состояние входа хранится в cookies или localStorage (токен). Его можно сохранить после одного входа и подставлять в новые контексты браузера — так тесты становятся быстрее и не зависят от формы входа. Саму форму входа проверяют отдельными тестами.

Чем серверная сессия отличается от JWT с точки зрения тестирования выхода из системы?

При серверной сессии выход удаляет сессию на сервере, и старая сразу перестаёт работать — это легко проверить. действителен до истечения срока, если сервер не ведёт список отозванных токенов. Тест «после выхода старый токен не даёт доступа» для JWT особенно важен: он часто находит проблему.
