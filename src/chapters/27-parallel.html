Параллельное выполнение

Workers, распределение тестов, fullyParallel и режимы describe, шардирование между машинами, общее состояние и гонки между тестами. Как ускорить прогон в разы и не получить случайные падения.

≈ 8 мин чтенияM
Опирается на: Изоляция и данные
Основная идея

Параллельность умножает скорость, но и проверяет изоляцию: всё, что тесты незаметно делили при последовательном запуске, при параллельном превращается в гонки. Сначала изоляция, потом параллелизм.

Цель главы: настраивать воркеры и шардирование, понимать, как Playwright распределяет тесты, и находить конфликты общего состояния.

Кратко

Воркеры — параллельные процессы на одной машине, шарды — части набора на разных машинах. Ускорение ограничено самым долгим файлом или тестом, ресурсами и общим состоянием.

Главное

  • По умолчанию: файлы распределяются между воркерами, тесты файла идут последовательно в одном воркере; fullyParallel: true распределяет отдельные тесты.
  • Число воркеров по умолчанию — половина логических ядер; в CI задают явно (workers: 4 или '50%').
  • test.describe.configure({ mode: 'serial' }) — тесты группы последовательно и падают вместе; использовать только при неустранимой зависимости.
  • testInfo.workerIndex и parallelIndex позволяют выделять ресурсы на воркер (аккаунты, порты, префиксы данных).
  • Шардирование: --shard=2/4 на каждой машине; blob-репортер и merge-reports собирают единый отчёт.
  • Признаки гонки между тестами: падает только при нескольких воркерах, «чужие» данные, 409 и дубликаты, разные тесты падают в разных прогонах.

Термины

Worker
Отдельный процесс ОС, в котором Playwright Test выполняет тесты. Браузер переиспользуется тестами одного воркера; после падения теста воркер перезапускается.
Parallel Execution
Одновременный запуск тестов в нескольких воркерах на одной машине и/или в нескольких шардах на разных машинах.
fullyParallel
Опция Playwright, при которой между воркерами распределяются отдельные тесты, а не файлы.
Test Sharding
Разбиение набора на части (--shard=2/4), выполняемые на разных машинах; отчёты затем объединяются.
Merge Reports
Сборка единого отчёта из blob-отчётов шардов командой npx playwright merge-reports.

Важно: Нельзя «чинить» гонки уменьшением воркеров до одного: набор станет медленным, а скрытая зависимость останется и проявится снова.

Как Playwright распределяет тесты#

— отдельный процесс Node.js со своим браузером. в Playwright Test происходит между воркерами; внутри воркера тесты выполняются по одному.

Режимы распределения:

Режим Что параллельно Как включить
По умолчанию Файлы (тесты файла — последовательно в одном воркере, в порядке объявления) —
Отдельные тесты, даже из одного файла fullyParallel: true в конфиге или проекте
Параллельно в файле Тесты конкретного файла test.describe.configure({ mode: 'parallel' })
Последовательно, связанно Тесты группы по порядку; при падении остальные пропускаются test.describe.configure({ mode: 'serial' })
Без параллельности Всё по очереди workers: 1
TypeScriptplaywright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  fullyParallel: true,
  workers: process.env.CI ? 4 : undefined,   // локально — половина ядер; можно '50%'
  projects: [
    { name: 'api', testDir: './tests/api' },                                         // быстрые тесты
    { name: 'payments', testDir: './tests/payments', fullyParallel: false, workers: 1 }, // общий ресурс провайдера
  ],
});

Параметр workers можно задать и в отдельном проекте — так набор с общим ресурсом выполняется последовательно, не замедляя остальное.

Индексы воркеров#

testInfo.workerIndex — уникальный номер процесса-воркера (растёт при перезапусках), testInfo.parallelIndex — номер «слота» от 0 до workers − 1, который переиспользуется новым воркером на месте упавшего. parallelIndex удобен, чтобы выделить каждому параллельному слоту свой ресурс:

TypeScripttests/fixtures/per-worker-account.ts
import { test as base } from '@playwright/test';

export const test = base.extend<{}, { account: { email: string; password: string } }>({
  account: [async ({}, use, workerInfo) => {
    // Заранее созданные аккаунты qa-slot-0 … qa-slot-7 — по одному на параллельный слот
    await use({ email: `qa-slot-${workerInfo.parallelIndex}@example.com`, password: process.env.SLOT_PASSWORD ?? '' });
  }, { scope: 'worker' }],
});

Shared State и гонки между тестами#

— всё, что несколько тестов читают и изменяют одновременно:

Общее состояние Как проявляется Решение
Один пользователь у всех тестов Чужие товары в корзине, неожиданный профиль Пользователь на тест или на воркер
Фиксированные уникальные значения 409 Conflict, «email уже занят» Уникальные значения с меткой
Глобальные настройки системы (фича-флаг, тариф) Тест А включил флаг, тест Б ожидает выключенным Изолировать в отдельный последовательный проект или использовать флаги на уровне пользователя
Ограниченные ресурсы (остаток товара, лимит промокода) «Товар закончился» в случайном тесте Свои товары и промокоды для теста
Переменные модуля в коде тестов Значение из теста другого файла Фикстуры области test
Файлы на диске Перезапись отчёта или выгрузки Уникальные пути: testInfo.outputPath()
Порты, внешние песочницы Занят порт, лимиты провайдера Порт 0 (случайный), ресурс на воркер, ограничение параллелизма

между тестами коварна: при последовательном запуске она не видна, а при параллельном зависит от того, какие тесты случайно оказались одновременно в разных воркерах. Поэтому «падает то один, то другой тест» — характерный признак.

Интерактив требует JavaScriptTest Execution Visualizer: набор из 12 тестов разной длительности на 1–6 воркерах — последовательно, по файлам или fullyParallel. Тесты с общим ресурсом подсвечиваются, а пересечения во времени показывают потенциальные конфликты.

Шардирование#

Воркеры ограничены ресурсами одной машины. делит набор на части, которые выполняются на разных машинах CI:

Shell
npx playwright test --shard=1/4   # первая четверть набора
npx playwright test --shard=2/4   # вторая и т. д. — каждая на своём агенте

С fullyParallel: true набор делится по тестам, иначе — по файлам (и тогда большие файлы делают шарды неравными). Каждый шард выполняется со своими воркерами.

Отчёт собирают из частей:

TypeScriptshard.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  // на шардах — blob-отчёт для последующего объединения
  reporter: process.env.CI ? [['blob'], ['list']] : [['html']],
});
Shell
# после всех шардов: скачать артефакты blob-report из каждой задачи в all-blob-reports/
npx playwright merge-reports --reporter html ./all-blob-reports

объединяет blob-отчёты в единый HTML (или другой) отчёт с общей статистикой и трассировками.

Сколько воркеров и шардов нужно#

Время прогона приблизительно:

T ≈ подготовка шарда + max(самый долгий тест, сумма длительностей / (шарды × воркеры))

Отсюда практические выводы:

  • Предел ускорения — самый долгий тест (или файл без fullyParallel): 10-минутный тест не станет быстрее при любом числе воркеров.
  • Воркеров не больше, чем выдерживают ресурсы: браузеры требуют CPU и памяти; перегруженная машина делает тесты медленными и нестабильными. Ориентир для UI — не больше воркера на ядро (по умолчанию берёт половину логических ядер); API-тесты легче и допускают больше.
  • Нагрузка на тестируемую систему: 32 параллельных воркера на маленьком staging — это нагрузочный тест, а не функциональный; появятся таймауты и 429.
  • Подготовка шарда (установка зависимостей, подъём окружения) не параллелится — шарды выгодны, когда тесты идут намного дольше подготовки.

Экономика времени и стоимости разобрана в главе «Оптимизация».

Пример: переход от 1 к 8 воркерам#

Набор: 300 тестов, 40 минут на одном воркере.

  1. Включили 4 воркера — 14 минут, но 6–10 падений за прогон.
  2. Разбор падений (по trace): 70% — общий аккаунт (корзина), 20% — фиксированные email, 10% — один тест меняет глобальную настройку валюты.
  3. Исправления: аккаунт на воркер (parallelIndex), уникальные email, тесты валюты — в отдельный проект с workers: 1.
  4. 8 воркеров + fullyParallel — 6 минут; самый долгий тест (экспорт отчёта, 4 минуты) стал пределом.
  5. Самый долгий тест переписан: подготовка через API вместо UI — 50 секунд. Итог — 4 минуты 30 секунд.

Типичные ошибки#

mode: 'serial' как способ починить зависимость

Последовательный режим закрепляет зависимость: падение одного теста пропускает остальные, ретраи повторяют всю группу. Исправляйте данные, а не режим.

Слишком много воркеров на слабом агенте

Тесты становятся медленными, таймауты срабатывают на перегруженной машине — и это выглядит как нестабильность тестов.

Шардирование без объединения отчёта

Четыре отдельных отчёта — четыре места, где искать падения. Используйте blob-репортер и merge-reports.

Предполагать порядок тестов

Тесты внутри файла по умолчанию выполняются по порядку, но с fullyParallel и шардированием порядок не гарантирован. Никакой тест не должен рассчитывать на результат предыдущего.

Что важно для собеседования#

JuniorКак Playwright запускает тесты параллельно?

Ответ

В нескольких процессах-воркерах (по умолчанию — половина логических ядер). По умолчанию между воркерами распределяются файлы, тесты внутри файла идут последовательно в одном воркере. fullyParallel: true распределяет отдельные тесты. Для нескольких машин — шардирование --shard=x/y.

MiddleТесты стабильны на одном воркере и случайно падают на нескольких. Как будете разбираться?

Ответ

Это почти всегда общее состояние. Сравню падения: какие тесты, с какими ошибками (409, чужие данные, неожиданные значения), какие тесты выполнялись одновременно (timeline в отчёте). Ищу общий аккаунт, фиксированные уникальные значения, глобальные настройки, переменные модулей, общие файлы. Исправляю изоляцией: данные на тест, аккаунт на воркер (parallelIndex), уникальные значения, отдельный последовательный проект для неустранимо общих ресурсов.

MiddleКак организовать шардирование в CI и получить один отчёт?

Ответ

Параллельные задачи CI (matrix) запускают npx playwright test --shard=${index}/${total} с blob-репортером, загружают blob-report как артефакты; итоговая задача скачивает все артефакты и выполняет npx playwright merge-reports --reporter html. С fullyParallel шарды получаются равными по тестам.

Middle+Почему увеличение воркеров с 8 до 32 может не ускорить прогон или ухудшить его?

Ответ

Предел — самый долгий тест или файл; ресурсы агента (CPU, память) — перегрузка замедляет браузеры и вызывает таймауты; тестируемая система не выдерживает нагрузку (медленные ответы, 429, 503); общие ресурсы требуют сериализации. Нужно смотреть на распределение длительностей, загрузку агента и системы и масштабировать шардами на разные машины, а не только воркерами.

Middle+Четыре шарда e2e: три заканчиваются за 6 минут, один — за 19. Почему и что делать?

Ответ

Скорее всего, нет , и набор делится по файлам: в один шард попал большой файл или файл с долгими тестами, и его тесты идут последовательно в одном воркере. Варианты: включить fullyParallel (если тесты независимы), разбить большой файл, ускорить самые долгие тесты (подготовка через API, storageState). Проверить и сами долгие тесты: возможно, это ожидания по таймауту. После изменений — сравнить длительности шардов по blob-отчётам.

Проверьте себя#

Тест
1
Как Playwright распределяет тесты между воркерами по умолчанию?

fullyParallel: true меняет это поведение и распределяет отдельные тесты.

2
Набор: 60 тестов по 1 минуте и один тест на 12 минут. Сколько минимум займёт прогон при неограниченном числе воркеров?

Предел — самый долгий тест. Ускорить можно только разбив или оптимизировав его.

3
Тесты стабильны на 1 воркере и падают на 4. Что вероятнее всего?

Параллельный запуск выявляет гонки за общие данные: один аккаунт, фиксированные значения, глобальные настройки.

Чем workerIndex отличается от parallelIndex?

workerIndex уникален для каждого запущенного процесса-воркера и растёт, когда воркер перезапускается после падения теста. parallelIndex — номер параллельного слота от 0 до workers − 1, и новый воркер на месте упавшего получает тот же номер. Для выделения постоянных ресурсов на слот (аккаунт, порт) удобнее parallelIndex.

Почему шардирование без fullyParallel может дать неравные по времени шарды?

Без fullyParallel единица распределения — файл. Если в одном файле 50 тестов, а в других по 3, шард с большим файлом будет идти намного дольше. С fullyParallel набор делится по тестам и шарды выравниваются.
