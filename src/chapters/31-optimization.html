Оптимизация выполнения автотестов

Параллелизация и шардирование, перенос проверок на нижние уровни, ускорение отдельных тестов, безопасное переиспользование окружения, приоритизация и оптимизация pipeline. И главный компромисс: время прогона, стоимость инфраструктуры и скорость обратной связи.

≈ 9 мин чтенияM+
Опирается на: ПараллельностьCI/CD
Основная идея

Оптимизация начинается с измерения: какие тесты самые долгие, где время уходит на подготовку, что можно не запускать на каждом изменении. Самое дешёвое ускорение — не выполнять лишнюю работу, самое дорогое — добавлять машины.

Цель главы: находить узкие места прогона и выбирать между оптимизацией тестов, параллелизмом, шардированием и приоритизацией с учётом стоимости.

Кратко

Время обратной связи = ожидание агента + подготовка + выполнение самого медленного шарда + отчёт. Ускоряют, убирая лишнюю работу, распараллеливая и запуская нужное подмножество раньше.

Главное

  • Сначала измерить: самые медленные тесты (Speedboard/отчёт), время подготовки шарда, загрузку агентов.
  • Перенос проверок с UI на API/unit даёт выигрыш в десятки раз и повышает стабильность.
  • Ускорение тестов: авторизация через storageState, подготовка данных через API, блокировка сторонних ресурсов, отсутствие лишних переходов и пауз.
  • Безопасное переиспользование: worker-фикстуры для дорогих неизменяемых ресурсов, сид-данные только для чтения, reuseExistingServer локально.
  • Приоритизация: smoke первым, теги и наборы по рискам, --only-changed и --last-failed, maxFailures для быстрого провала.
  • Стоимость ≈ шарды × время шарда × цена минуты; после некоторого числа шардов время почти не падает, а стоимость растёт.

Термины

Test Execution Time
Длительность прогона набора. Для шарда ограничена снизу самым долгим тестом; для pipeline включает очередь, подготовку и сбор отчёта.
Test Sharding
Разбиение набора на части (--shard=2/4), выполняемые на разных машинах; отчёты затем объединяются.
Parallel Execution
Одновременный запуск тестов в нескольких воркерах на одной машине и/или в нескольких шардах на разных машинах.
Test Prioritization
Выбор, какие тесты запускать раньше и какие — на каком событии: smoke первым, наборы по тегам и рискам, изменённые тесты, быстрый провал.
Feedback Loop
Время от изменения кода до результата проверок, на который можно опереться. Чем короче, тем дешевле исправление.

Важно: Ускорение за счёт удаления проверок или ослабления ожиданий — не оптимизация, а снижение покрытия. Сначала убирайте лишнюю работу, а не проверки.

Из чего складывается время#

— время от push до результата, на который можно опереться. Для набора UI-тестов в CI:

Текст
очередь агента + подготовка (образ, npm ci, окружение) + выполнение (самый долгий шард) + сбор отчёта

одного шарда ≈ max(самый долгий тест, сумма длительностей / воркеры) × коэффициент неравномерности.

Что обычно съедает время, по убыванию частоты:

  1. Подготовка через UI (вход, создание данных кликами) в каждом тесте.
  2. Избыточные UI-тесты, дублирующие API- и unit-проверки.
  3. Фиксированные паузы и лишние ожидания.
  4. Сторонние ресурсы: аналитика, виджеты, медленные картинки.
  5. Подготовка агента: установка браузеров и зависимостей без кэша.
  6. Последовательные части: mode: 'serial', workers: 1, большие файлы без fullyParallel.

Измерить, прежде чем ускорять#

  • HTML-отчёт показывает длительность каждого теста; в свежих версиях есть вкладка Speedboard с тестами, отсортированными по времени, и шкала выполнения по воркерам.
  • - или JUnit-отчёты за несколько прогонов дают устойчивую статистику (среднее, перцентили).
  • Время задач CI разделяет подготовку и выполнение.
  • Загрузка агента (CPU, память) показывает, не упираются ли воркеры в ресурсы.

Правило Парето работает и здесь: 10% самых медленных тестов часто занимают половину времени.

Перенос проверок на нижние уровни#

Самая выгодная оптимизация — проверять на правильном уровне (глава 2):

Проверка UI-тест API-тест Выигрыш
20 комбинаций правил скидки 20 × 8 с = 160 с 20 × 0,1 с = 2 с ×80
Валидация 12 полей формы на сервере 12 × 6 с 12 × 0,08 с ×75
Права доступа к 30 эндпоинтам Невозможно полноценно 30 × 0,05 с —

UI оставляет за собой то, что видит пользователь: что форма показывает ошибку, кнопка доступна, сценарий проходит целиком.

Ускорение отдельных тестов#

Приём Как Типичный выигрыш
Авторизация через storageState Setup-проект, вход один раз (глава 18) 2–5 с на тест
Данные через API Фикстуры создают заказ, корзину, пользователя запросами Секунды–десятки секунд
Сразу на нужную страницу page.goto('/cart') вместо навигации через меню 1–3 с
Блокировка сторонних ресурсов page.route → abort для аналитики, чатов, рекламы 0,5–2 с и меньше оверлеев
Ожидание состояния вместо пауз Web-first assertions вместо waitForTimeout Вся длина паузы
Меньше лишних проверок Не проверять в каждом тесте то, что проверено отдельно Зависит
TypeScripttests/fast-setup.spec.ts
import { test, expect } from '@playwright/test';

test.beforeEach(async ({ page }) => {
  // Сторонние скрипты не нужны для проверки корзины
  await page.route(/(google-analytics|googletagmanager|mc\.yandex|widget\.chat)/, (r) => r.abort());
});

test('промокод в корзине', async ({ page }) => {
  // Состояние готовится запросом, а не кликами по каталогу
  const res = await page.request.post('/api/cart/items', { data: { productId: 1, qty: 2 } });
  await expect(res).toBeOK();
  await page.goto('/cart');                              // сразу нужная страница
  await page.getByLabel('Промокод').fill('SALE10');
  await page.getByRole('button', { name: 'Применить' }).click();
  await expect(page.getByTestId('cart-total')).toHaveText('8 982 ₽');
});

Безопасное переиспользование окружения#

Переиспользование экономит время, но угрожает изоляции. Безопасно переиспользовать то, что тесты не изменяют:

Можно переиспользовать Нельзя (или только с изоляцией)
Браузер в воркере ( делает сам) Страницу и контекст между тестами
Пул подключений к БД, мок-сервер (Worker-фикстура) Корзину, профиль, заказы одного пользователя
Сид-справочники и каталог Глобальные настройки, фича-флаги
Запущенное локально приложение (reuseExistingServer) Окружение после теста, который его «испортил»
Docker-образ с браузерами и node_modules (кэш) Общий staging для конфликтующих наборов одновременно

Приоритизация#

— запускать самое важное раньше и не запускать лишнее:

  • Smoke первым. Если стенд не жив, остальное не нужно — maxFailures или отдельная стадия.
  • Теги и наборы. @smoke, @critical, @slow и проекты: на MR — критичное, ночью — всё.
  • Изменённые тесты. npx playwright test --only-changed=origin/main запускает тесты из изменённых файлов и тех, что их импортируют — полезно для быстрой проверки MR тестового репозитория.
  • Повтор упавших. --last-failed — после исправления.
  • Быстрый провал. --max-failures=10 (или maxFailures в конфиге) останавливает прогон, когда уже ясно, что сборка сломана.
  • Test impact analysis. Выбор тестов по изменённому коду продукта (по покрытию или карте «модуль → тесты») — мощно, но требует инфраструктуры и честной оценки риска пропуска.

Оптимизация pipeline#

:

  • Кэш и готовые образы: образ с браузерами, кэш npm по package-lock.json.
  • Граф needs вместо строгих стадий: задачи стартуют, как только готовы их зависимости.
  • Параллельные задачи для независимых наборов (API и UI одновременно).
  • Запуск по изменениям: rules: changes в GitLab, paths в — изменение только документации не запускает E2E.
  • Отмена устаревших : новый push в ветку отменяет предыдущий (interruptible в GitLab, concurrency в GitHub Actions).
  • Размер артефактов: trace и видео только для упавших тестов.

Время, стоимость и обратная связь#

Шардирование уменьшает время, но не бесплатно: каждый шард тратит время на подготовку, а минуты агентов стоят денег.

время ≈ подготовка + max(самый долгий тест, сумма / (шарды × воркеры))

стоимость ≈ шарды × время × цена минуты агента

Интерактив требует JavaScriptВремя, стоимость и обратная связь: число тестов, средняя длительность, самый долгий тест, воркеры на агенте, подготовка шарда и цена минуты → график времени прогона и стоимости в зависимости от числа шардов.

Модель показывает типичную картину: первые шарды резко сокращают время почти без роста стоимости, затем время упирается в подготовку и самый долгий тест, а стоимость растёт линейно. Оптимальное число шардов — там, где дальнейшее ускорение уже не стоит денег.

Пример: с 55 до 11 минут#

UI-набор на MR: 400 тестов, 55 минут на 2 шардах по 4 воркера.

Шаг Время Комментарий
Исходно 55 мин Каждый тест логинится через форму
storageState + setup-проект 41 мин −3,5 с на тест
Данные через API в 120 тестах 29 мин Убраны «прогулки» по каталогу
140 UI-тестов бизнес-правил → 160 API-тестов 18 мин UI остался для пользовательских сценариев
Блокировка аналитики и чата 16 мин И −30% «случайных» падений от оверлеев
fullyParallel + 4 шарда 11 мин Шарды выровнены, подготовка 2 мин

Стоимость минут CI выросла на 20%, время обратной связи сократилось в 5 раз — и большая часть выигрыша получена без добавления машин.

Типичные ошибки#

Масштабировать железом, не измерив

Удвоение шардов при 10-минутном тесте и 4-минутной подготовке почти не даст ускорения, но удвоит стоимость.

Ускорять за счёт проверок

Удалить «долгие» проверки или заменить ожидания короткими паузами — значит снизить покрытие и стабильность.

Переиспользовать то, что тесты изменяют

Общий пользователь «для скорости» превращается в гонки при параллельном запуске.

Один набор на все случаи

Полная регрессия на каждый коммит или, наоборот, только ночью. Разные события — разные наборы.

Что важно для собеседования#

MiddleUI-регрессия идёт 50 минут. Как будете ускорять?

Ответ

Сначала измерю: топ медленных тестов, подготовка vs выполнение, загрузка агентов. Затем по убыванию выгоды: авторизация через storageState, подготовка данных через API, перенос проверок бизнес-правил на API/unit, убрать паузы и лишнюю навигацию, заблокировать сторонние ресурсы. Потом параллелизм: fullyParallel, воркеры по ресурсам, шардирование с merge-reports. И приоритизация: на MR — критичный набор, полная регрессия — после деплоя и ночью.

MiddleКак приоритизировать запуск тестов, если полный набор не помещается в время MR?

Ответ

Наборы по событиям: на MR — smoke и критичные сценарии по рискам (теги @critical), API-тесты затронутых областей; после слияния — расширенная регрессия; ночью — всё. Быстрый провал (maxFailures) при сломанной сборке. Для тестового репозитория — --only-changed. Test impact analysis — при наличии надёжной карты зависимостей и с осознанием риска пропуска.

Middle+Как выбрать число шардов для набора?

Ответ

Время ≈ подготовка + max(самый долгий тест, сумма / (шарды × воркеры)), стоимость ≈ шарды × время × цена минуты. Увеличиваю шарды, пока это заметно сокращает время; когда время упирается в подготовку и самый долгий тест, дальнейшие шарды только увеличивают стоимость. Параллельно сокращаю подготовку (кэш, образы) и разбиваю самые долгие тесты.

Middle+UI-регрессия идёт 70 минут, 600 тестов. Как сократить, не потеряв в качестве?

Ответ

Измерить: какие тесты самые долгие и что в них занимает время. Типичные шаги по убыванию эффекта: вход через storageState и данные через API вместо UI; перенос проверок бизнес-правил (расчёты, валидации, права) на API-уровень, оставив в UI пользовательские сценарии и отображение; блокировка сторонних ресурсов; удаление фиксированных пауз; и выравнивание шардов; приоритизация — быстрый набор на MR, полный — после слияния и по расписанию. Каждое изменение сопровождается проверкой, что ни один риск не остался без проверки.

Проверьте себя#

Тест
1
Набор: подготовка шарда 3 минуты, самый долгий тест 6 минут, сумма 120 минут, 4 воркера на шард. Сколько примерно займёт прогон на 10 шардах?

120 / (10 × 4) = 3 минуты меньше самого долгого теста (6), поэтому выполнение ≈ 6 минут + 3 минуты подготовки ≈ 9.

2
Какая оптимизация обычно даёт наибольший выигрыш при минимальной стоимости?

Уровень проверки и подготовка состояния определяют время сильнее, чем число машин.

3
Что из этого безопасно переиспользовать между тестами?

Тесты не изменяют пул подключений; остальное — изменяемое общее состояние.

Как найти, на что тратится время прогона?

Отсортировать тесты по длительности (HTML-отчёт, Speedboard, за несколько прогонов), сравнить время подготовки и выполнения задач CI, посмотреть шкалу воркеров (неравномерность, простаивающие слоты), загрузку агента. Затем разобрать топ медленных тестов: подготовка через UI, паузы, лишние переходы, неправильный уровень проверки.

Почему после некоторого числа шардов время почти перестаёт уменьшаться?

Время шарда ограничено снизу подготовкой (установка, окружение) и самым долгим тестом. Когда сумма длительностей, делённая на число слотов, становится меньше самого долгого теста, дальнейшее деление не помогает, а каждый новый шард добавляет стоимость подготовки.
