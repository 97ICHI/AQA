:::why
Иногда результат действия не виден на странице: важен ответ сервера, переход на новый адрес, открытие вкладки или скачивание файла. Для этого есть явные ожидания событий. У них одно правило, нарушение которого даёт самые коварные нестабильные тесты: начинать ждать нужно **до** действия, которое вызывает событие.
:::

## Ожидание состояния и ожидание события

**Состояние** — то, что можно проверить в любой момент: текст счётчика, видимость сообщения, адрес страницы. Его ждут проверки `expect` — они сами повторяют сравнение:

```ts
await expect(page.getByTestId('cart-count')).toHaveText('1');
await expect(page).toHaveURL(/\/cart$/);
```

**Событие** — то, что происходит один раз в определённый момент: пришёл ответ сервера, открылась вкладка, начался диалог, начато скачивание. Если вы начали слушать после того, как событие случилось, вы его уже не увидите. Для событий есть [[explicit-wait|явные ожидания]]:

| Ожидание | Чего ждёт |
|---|---|
| `page.waitForResponse(urlOrPredicate)` | ответ сервера, подходящий под условие |
| `page.waitForRequest(urlOrPredicate)` | исходящий запрос |
| `page.waitForEvent('popup')` | новую вкладку, открытую страницей |
| `page.waitForEvent('download')` | начало скачивания |
| `page.waitForURL(url)` | переход страницы на адрес |

## Правило: сначала ждать, потом действовать

Неправильно:

```ts
await page.getByRole('button', { name: 'Оформить заказ' }).click();
const response = await page.waitForResponse('**/api/orders');  // ответ мог уже прийти
```

Клик завершился, запрос ушёл, на быстром стенде ответ уже получен — и `waitForResponse` ждёт *следующий* такой ответ, которого не будет. Тест падает по таймауту. На медленном стенде тот же код проходит: ответ приходит позже, чем начинается ожидание. Это [[race-condition|состояние гонки]].

Правильно: создать ожидание (Promise) до действия, а дождаться его после.

```ts tests/order.spec.ts
const orderResponse = page.waitForResponse(
  (r) => r.url().endsWith('/api/orders') && r.request().method() === 'POST',
);                                                          // 1. начали слушать (без await!)
await page.getByRole('button', { name: 'Оформить заказ' }).click(); // 2. действие
const response = await orderResponse;                       // 3. дождались ответа
expect(response.status()).toBe(201);
```

Обратите внимание: в шаге 1 нет `await`. Мы сохраняем Promise в переменную, чтобы ожидание шло параллельно с кликом.

## Когда событие ждать не нужно

Если результат виден на странице, проверяйте страницу: это ближе к пользователю и проще. `waitForResponse` нужен, когда:

- важны данные ответа (статус `201`, `id` заказа, тип поля);
- интерфейс ничего не показывает о результате;
- нужно дождаться завершения запроса перед следующим шагом, а видимого признака нет.

Для навигации обычно хватает `await expect(page).toHaveURL(...)`: проверка повторяется сама и не может «пропустить» переход.

## Задание

В магазине есть два дефекта, невидимых в интерфейсе: сервер отвечает на создание заказа статусом 200 вместо 201, и поле `total` приходит строкой `"390.00"` вместо числа. Сообщение на странице в обоих случаях правильное.


:::mistake
**`await` сразу перед `waitForResponse`, а действие после.** `await page.waitForResponse(...)` в отдельной строке *перед* кликом остановит тест: ответ ждётся, а кликать некому. Тест упадёт по таймауту. Promise создают без `await`, действие выполняют, затем `await` на сохранённом Promise. Альтернатива — `Promise.all([page.waitForResponse(...), button.click()])`: оба начнутся одновременно.
:::

:::deep Почему проверка через предикат надёжнее строки
`waitForResponse('**/api/orders')` совпадёт с любым ответом на этот адрес, в том числе на `GET`. Предикат `(r) => r.url().endsWith('/api/orders') && r.request().method() === 'POST'` точно описывает нужный запрос. На странице со множеством запросов (аналитика, подгрузка картинок, повторные попытки) точность условия решает, какой ответ будет пойман.
:::

:::tech Что ещё возвращает ответ
Объект `Response` даёт `status()`, `ok()` (статус 200–299), `headers()`, `json()`, `text()`, а через `request()` — исходный запрос с `method()`, `postData()` и `postDataJSON()`. Ожидания событий тоже ограничены таймаутом: опция `timeout` или общий таймаут теста. Для `waitForEvent` можно передать `predicate`, чтобы поймать конкретное событие, например скачивание с нужным именем файла.
:::

:::interview
**Вопрос:** «Почему `waitForResponse` после клика иногда не срабатывает?» **Ответ по сути:** ответ может прийти раньше, чем начнётся ожидание, — тогда событие пропущено, и тест ждёт следующего до таймаута. Ожидание нужно начинать до действия: сохранить Promise, выполнить действие, затем `await`. Это гонка, поэтому проявляется нестабильно — чаще на быстрых машинах.
:::
