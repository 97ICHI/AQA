:::why
Интерфейс и API показывают то, что система *сообщила*. База данных показывает то, что она *сделала*. Тестировщик заглядывает в базу, чтобы найти данные для теста и проверить результат действия, — и почти всегда начинает с `SELECT`.
:::

## База учебного магазина

[[sql|SQL]] — язык запросов к реляционной базе. Данные лежат в таблицах: строки — это записи (один товар, один заказ), столбцы — их свойства. В тренажёре работает настоящий PostgreSQL 17 (PGlite) прямо в браузере. В нём пять таблиц:

| Таблица | Что хранит |
|---|---|
| `users` | покупатели: `email`, `name`, `city` (может быть пустым), `is_active` |
| `products` | товары: `sku`, `title`, `category`, `price`, `stock` (остаток) |
| `orders` | заказы: `user_id`, `status` (new/paid/shipped/cancelled), `promo_code` |
| `order_items` | позиции заказа: `order_id`, `product_id`, `qty`, `price` |
| `payments` | оплаты: `order_id`, `amount`, `method`, `status` (ok/failed/refunded) |

Есть три набора данных: «Основной», «Граничные случаи» и «Без заказов». Запрос, который правильно работает только на одном из них, задания не засчитывают — как и в реальной работе, где завтра в базе будут другие строки.

## Из чего состоит SELECT

```sql queries/cheap-goods.sql
SELECT title, price          -- 1. какие столбцы показать
FROM products                -- 2. из какой таблицы
WHERE price < 1000           -- 3. какие строки оставить
ORDER BY price, title        -- 4. в каком порядке
LIMIT 3;                     -- 5. сколько строк вернуть
```

- `SELECT` перечисляет столбцы. `SELECT *` — все столбцы; в тестах лучше называть нужные явно: запрос не сломается, если в таблицу добавят столбец.
- `WHERE` — условие для каждой строки. Строки сравнивают через `=`, `<>` (не равно), `<`, `>=`; условия соединяют `AND` и `OR`; список значений — `status IN ('paid', 'shipped')`; поиск по части строки — `title LIKE 'Наушники%'`. Строковые значения пишутся в **одинарных** кавычках.
- [[order-by|ORDER BY]] задаёт порядок: по возрастанию по умолчанию, `DESC` — по убыванию.
- `LIMIT n` оставляет первые `n` строк уже отсортированного результата.

:::warn Без ORDER BY порядка нет
Если в запросе нет `ORDER BY`, база вправе вернуть строки в любом порядке, и он может поменяться после обновления данных. Тест, который сравнивает «первую строку» без сортировки, рано или поздно станет нестабильным.
:::

### Равные значения и второй ключ

`ORDER BY price` упорядочивает по цене, но что делать с товарами одной цены? Их порядок не определён. Поэтому в `ORDER BY` добавляют второй ключ (его называют tie-breaker): `ORDER BY price, title`. Второй ключ работает только тогда, когда первый одинаковый. На наборе «Граничные случаи» две книги стоят по 990 — это ровно такой случай.

:::try Попробуйте сами
Запустите запрос, затем переключите набор данных на «Граничные случаи». Уберите `title` из `ORDER BY` и подумайте, почему результат теперь не гарантирован, даже если выглядит так же.
:::

```widget
{"type":"playground","lang":"sql","title":"Каталог: фильтр и сортировка","dataset":"base","code":"SELECT sku, title, category, price, stock\nFROM products\nWHERE stock > 0\nORDER BY price DESC, title;\n"}
```

:::happened
`WHERE stock > 0` убрал товары, которых нет в наличии (в основном наборе это лампа с остатком 0). Затем строки отсортированы по цене от дорогой к дешёвой, а при равной цене — по названию. В граничном наборе книга о SQL выпала: её остаток 0. Порядок выполнения внутри базы не совпадает с порядком слов в запросе: сначала `FROM`, потом `WHERE`, потом `SELECT`, `ORDER BY` и в конце `LIMIT`.
:::

## Как это выглядит в тесте

Запрос в тесте почти всегда отвечает на конкретный вопрос: «есть ли такой товар», «сколько осталось на складе», «какой статус у заказа». Поэтому он узкий: конкретные столбцы, точное условие, однозначный порядок.

```sql queries/stock-check.sql
-- остаток товара после покупки: тест сравнит его с ожидаемым
SELECT sku, stock
FROM products
WHERE sku = 'NOTE-A5';
```


:::deep Логический порядок выполнения
Запрос читается сверху вниз, но выполняется в другом порядке: `FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`. Отсюда два следствия. Псевдоним столбца из `SELECT` (`price * 2 AS double`) нельзя использовать в `WHERE` — на этом шаге его ещё нет, а в `ORDER BY` — можно. И `LIMIT` применяется к уже отсортированному результату, поэтому «три самых дорогих» — это `ORDER BY price DESC LIMIT 3`, а не наоборот.
:::

:::tech Как тренажёр сравнивает результат
Запрос ученика и эталон выполняются на свежей базе для каждого набора данных. Сравниваются число столбцов и значения строк; имена столбцов (`AS …`) не важны. Если в задании важен порядок, строки сравниваются по порядку, иначе — как множества. Числа `numeric` приходят строками вида `390.00`, даты — `2026-04-01`.
:::

:::interview
**Вопрос:** «Почему тест, проверяющий первую строку результата, иногда падает без изменений в коде?» **Ответ по сути:** без `ORDER BY` порядок строк в SQL не гарантирован, а при равных значениях ключа сортировки порядок равных строк тоже не определён. Нужен полный порядок: `ORDER BY` с уникальным последним ключом, например `id`.
:::
