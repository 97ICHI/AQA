:::why
В тестах SQL-запрос почти всегда зависит от данных: `id` заказа из ответа API, email созданного пользователя. Самый простой способ подставить значение — склеить строку — одновременно самый опасный. Он создаёт уязвимость, ломается на кавычках в данных и приучает к коду, который нельзя переносить в приложение.
:::

## Склейка строк и SQL-инъекция

Представьте вспомогательную функцию в тестах:

```ts tests/support/orders.ts
// ПЛОХО: значение вклеивается в текст SQL
export function ordersByEmail(email: string) {
  return db.query("SELECT id, status FROM orders o JOIN users u ON u.id = o.user_id " +
                  "WHERE u.email = '" + email + "'");
}
```

С обычным email всё работает. Теперь передадим строку `x' OR '1'='1`. Текст запроса станет таким:

```sql text
WHERE u.email = 'x' OR '1'='1'
```

Кавычка из данных закрыла строку, и остаток данных стал частью SQL. Условие `'1'='1'` истинно всегда — запрос вернёт заказы **всех** пользователей. Это [[sql-injection|SQL-инъекция]]: данные меняют смысл запроса. В приложении она позволяет читать чужие данные или удалять таблицы; в тестах — как минимум даёт ложные результаты, когда в данных встречается апостроф (фамилия `O'Brien`, название «Кружка 'Утро'»).

:::try Посмотрите на инъекцию
Первый запрос — то, что получилось после склейки. Запустите его. Затем запустите второй вариант: тот же «опасный» текст передан как значение.
:::

```widget

```

:::happened
Первый запрос вернул все пять заказов: к условию на email добавилось «или истина». Во втором варианте (раскомментируйте его, а первый закомментируйте) `PREPARE` создаёт запрос с плейсхолдером `$1`, а `EXECUTE` передаёт значение отдельно. База ищет пользователя с email, буквально равным `x' OR '1'='1`, и честно не находит ни одного. Удвоенные кавычки `''` внутри строкового литерала — это запись одной кавычки в SQL; в коде теста их писать не нужно, драйвер передаёт значение как есть.
:::

## Параметры: текст отдельно, значения отдельно

[[parameterized-query|Параметризованный запрос]] состоит из двух частей. Текст запроса постоянный, на месте значений стоят плейсхолдеры `$1`, `$2`, … (такой синтаксис у PostgreSQL и драйверов node-postgres и PGlite). Значения передаются вторым аргументом — массивом, где `$1` — первый элемент:

```ts tests/support/orders.ts
export async function ordersByEmail(email: string, status: string) {
  const res = await db.query(
    'SELECT o.id, o.status FROM orders o JOIN users u ON u.id = o.user_id ' +
    'WHERE u.email = $1 AND o.status = $2',
    [email, status],
  );
  return res.rows;
}
```

База получает текст и значения по отдельности, разбирает текст **до** того, как увидит значения, и никогда не интерпретирует значения как SQL. Поэтому никакое содержимое `email` не может изменить запрос. Заодно не нужно думать о кавычках, датах и экранировании.

В node-postgres тот же запрос можно передать объектом `{ text, values }` — такой объект удобно строить в функции и проверять в юнит-тесте, не подключаясь к базе.

```ts tests/support/orders.ts
const query = {
  text: 'SELECT id, status FROM orders WHERE id = $1',
  values: [order.id],
};
const res = await client.query(query);
```

:::mistake Плейсхолдер в кавычках
`WHERE email = '$1'` — это сравнение со строкой из двух символов «$1», а не параметр. Плейсхолдер пишется без кавычек: `WHERE email = $1`. Тип значения база выводит из контекста, при необходимости уточняют: `$1::date`.
:::

## Что нельзя параметризовать

Параметр заменяет только **значение**. Имя таблицы, столбца или направление сортировки (`ASC`/`DESC`) плейсхолдером передать нельзя. Если такая часть запроса зависит от входных данных, её выбирают из фиксированного списка в коде: `const column = ['price', 'title'].includes(sort) ? sort : 'id'`. Значения пользователя в текст SQL не попадают никогда.

:::deep Подготовленные выражения
Параметризованный запрос часто выполняется как подготовленное выражение (prepared statement): база один раз разбирает и планирует текст, а затем выполняет его с разными значениями. Это немного быстрее при многократном вызове. В SQL то же самое делают `PREPARE имя(типы) AS …` и `EXECUTE имя(значения)`, как в песочнице выше. Драйверы делают это сами.
:::

:::tech Как это выглядит в других стеках
Синтаксис плейсхолдеров зависит от драйвера: `$1` — PostgreSQL (node-postgres, PGlite, asyncpg), `?` — MySQL и SQLite, `%s` или `%(name)s` — psycopg в Python. Принцип одинаковый: текст отдельно, значения отдельно. В Python `cursor.execute("… WHERE id = %s", (order_id,))` — правильно, а `cursor.execute(f"… WHERE id = {order_id}")` — та же склейка, что и в примере выше.
:::

:::interview
**Вопрос:** «Что такое SQL-инъекция и как от неё защищаются?» **Ответ по сути:** это ситуация, когда данные попадают в текст SQL и меняют его смысл (например, `' OR '1'='1`). Защита — параметризованные запросы: текст с плейсхолдерами и значения передаются отдельно, база не разбирает значения как SQL. Ручное экранирование — ненадёжная замена. Для имён столбцов и таблиц — белый список в коде.
:::
