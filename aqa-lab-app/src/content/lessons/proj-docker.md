:::why
«На моей машине тесты проходят» — потому что на ней своя версия Node.js, свой браузер и запущенный вручную сервер. Docker упаковывает приложение и тесты вместе со всем окружением, и прогон одинаков на ноутбуке, у коллеги и в CI. Compose запускает несколько контейнеров вместе и следит, чтобы тесты стартовали только когда приложение готово.
:::

## Образ и контейнер

[[docker-image|Образ]] — неизменяемый шаблон: операционная система, Node.js, зависимости, код. [[container|Контейнер]] — запущенный экземпляр образа со своей файловой системой, процессами и сетью. Из одного образа можно запустить сколько угодно контейнеров; после остановки изменения внутри контейнера пропадают, если их не сохранить в [[volume|том]].

Образ собирается по [[dockerfile|Dockerfile]]. В учебном проекте он такой:

```text Dockerfile
FROM node:22-bookworm
WORKDIR /app
COPY package*.json ./
RUN npm ci
RUN npx playwright install --with-deps chromium
COPY . .
RUN npm run lint && npm run typecheck
CMD ["npm", "test"]
```

Порядок инструкций выбран из-за кэша. Docker пересобирает слой, только если изменилось то, от чего он зависит. Сначала копируются только `package.json` и `package-lock.json`, затем `npm ci` и установка браузера — самые долгие шаги. Пока зависимости не менялись, эти слои берутся из кэша, а изменение теста пересобирает лишь `COPY . .` и проверки. Если скопировать весь проект первой строкой, любая правка теста будет запускать `npm ci` заново.

Файл `.dockerignore` исключает из сборки `node_modules`, `.git` и каталоги отчётов: они не нужны внутри образа и замедляют сборку.

:::note
Вместо `node` + `playwright install --with-deps` можно взять официальный образ Playwright (`mcr.microsoft.com/playwright:v<версия>-noble`), где браузеры и системные библиотеки уже установлены. Версия образа должна совпадать с версией `@playwright/test` в `package-lock.json`, иначе тесты не найдут подходящий браузер.
:::

## Compose: приложение и тесты вместе

[[docker-compose|Compose]] описывает несколько сервисов в одном файле. В учебном проекте их два: `app` (магазин) и `tests` (Playwright).

```yaml compose.yaml
services:
  app:
    image: node:22-bookworm
    working_dir: /app
    volumes: ["./server.mjs:/app/server.mjs:ro"]
    command: ["node", "server.mjs"]
    environment:
      HOST: 0.0.0.0
    ports: ["3000:3000"]
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:3000/ready').then(r=>{if(!r.ok)process.exit(1)}).catch(()=>process.exit(1))"]
      interval: 2s
      timeout: 2s
      retries: 15
  tests:
    build: .
    environment:
      BASE_URL: http://app:3000
    depends_on:
      app:
        condition: service_healthy
    volumes:
      - ./playwright-report:/app/playwright-report
      - ./test-results:/app/test-results
      - ./allure-results:/app/allure-results
```

Что здесь важно:

- **Сеть.** Сервисы одного Compose-проекта находятся в общей [[docker-network|сети]] и видят друг друга по имени. Поэтому тесты ходят на `http://app:3000`, а не на `localhost` — внутри контейнера `tests` адрес `localhost` указывает на сам контейнер тестов.
- **`HOST: 0.0.0.0`.** Сервер по умолчанию слушает только `127.0.0.1` — внутри своего контейнера. Чтобы его было видно из соседнего контейнера, он должен слушать все интерфейсы.
- **Готовность.** `depends_on` без условия ждёт только *запуска* контейнера, а не готовности приложения. [[healthcheck|Healthcheck]] раз в 2 секунды запрашивает `/ready`, и `condition: service_healthy` пускает тесты только после успешной проверки.
- **Тома.** Отчёты пишутся в каталоги, подключённые с хоста, — после остановки контейнеров они остаются и попадают в артефакты CI.
- **`BASE_URL`.** Когда переменная задана, `playwright.config.ts` не запускает свой `webServer`: приложение уже работает в соседнем контейнере.

## Запуск и код возврата

```bash
docker compose up --build --abort-on-container-exit --exit-code-from tests
status=$?                    # сохранить код ДО очистки
docker compose logs --no-color > compose.log
docker compose down --volumes
exit $status
```

`--abort-on-container-exit` останавливает всё, когда тесты завершились (иначе сервер `app` работал бы бесконечно). `--exit-code-from tests` делает [[exit-code|код возврата]] команды равным коду сервиса `tests`: 0 — тесты прошли, иначе — упали. Код сохраняют до `down`: успешная очистка вернула бы 0 и спрятала упавшие тесты.

:::mistake
`sleep 10` перед тестами вместо проверки готовности. На быстрой машине это лишние 10 секунд, на медленной — недостаточно, и тесты падают с `ECONNREFUSED`. Ждать нужно состояния (`/ready` отвечает 200), а не времени.
:::

:::try Тесты для ожидания с повторами
Healthcheck в Compose — это повторы с интервалом. Тот же приём нужен в скриптах подготовки: дождаться стенда, повторить запрос к нестабильной зависимости. Ниже — помощник `retry` с нарастающей паузой. Напишите тесты, которые отличат его от пяти сломанных версий.
:::

```widget

```

:::happened
Сломанные версии отличаются от правильной мелочами: на одну попытку больше, пауза не растёт, лишняя пауза в конце, ошибка теряется. Тест «успех с первой попытки» не видит ни одной из них — повторы в нём просто не происходят. Ловят их только сценарии, где сервис сначала не готов, и проверки числа вызовов, пауз и итоговой ошибки.
:::

:::deep Повторы: где уместны, где вредны
[[exponential-backoff|Нарастающая пауза]] уместна для ожидания готовности и для временных сбоев зависимостей (503, 429): она не заваливает сервис запросами и даёт ему восстановиться. Неуместна вокруг проверок теста: повтор assertion до «зелёного» прячет дефект. Повторять стоит только [[idempotency|идемпотентные]] операции: повтор `POST /api/orders` после таймаута может создать два заказа. В проде к паузе часто добавляют случайный разброс (jitter), чтобы множество клиентов не повторяли запросы синхронно.
:::

:::tech Отладка контейнеров
`docker compose ps` — состояние сервисов и healthcheck (`healthy`/`unhealthy`). `docker compose logs app` — логи сервиса. `docker compose exec app sh` — оболочка внутри работающего контейнера (проверить `curl`, переменные, файлы). `docker compose run --rm tests npx playwright test tests/shop.spec.ts` — запустить один тест в контейнере тестов. Если браузер падает с нехваткой памяти, причина часто в маленьком `/dev/shm`: помогает `--ipc=host` или `shm_size` в Compose.
:::

:::interview
**Вопрос:** «Зачем запускать тесты в Docker и как дождаться готовности приложения?» **Ответ по сути:** одинаковое окружение везде — версии Node.js, браузера, зависимостей закреплены в образе. Приложение и тесты описываются в Compose, тесты обращаются к приложению по имени сервиса. Готовность — через healthcheck на `/ready` и `depends_on: condition: service_healthy`, а не через `sleep`. Код возврата берётся из сервиса тестов, отчёты сохраняются в тома.
:::
