:::why
HTTP не помнит, кто вы: каждый запрос сам по себе. Но магазин узнаёт вас после входа, держит вашу корзину и не показывает чужие заказы. Тестировщику нужно понимать, как это устроено: от этого зависит, как готовить вход в тестах, почему тесты не должны делить одну сессию и как проверять права доступа.
:::

## Cookie и сессия

При первом запросе учебный магазин отвечает заголовком:

```http
HTTP/1.1 200 OK
Set-Cookie: sid=4f1c9a…; Path=/; HttpOnly; SameSite=Lax
```

Браузер сохраняет эту [[cookie|cookie]] и сам добавляет её ко всем следующим запросам к этому сайту:

```http
GET /cart HTTP/1.1
Cookie: sid=4f1c9a…
```

Значение `sid` — случайный идентификатор. На сервере по нему хранится [[session|сессия]]: кто вошёл, что лежит в корзине. Cookie — только «номерок из гардероба», вещи — на сервере.

Атрибуты cookie тоже важны: `HttpOnly` запрещает читать её из JavaScript страницы (защита от кражи скриптом), `SameSite=Lax` не даёт отправлять её из большинства запросов, начатых другими сайтами, `Path=/` — cookie действует на весь сайт.

## Вход

Форма входа отправляет `POST /api/login` с email и паролем. Если они верны, сервер записывает в сессию `userId` и отвечает 200. Cookie при этом та же — изменилось то, что за ней хранится на сервере. Следующий запрос с этой cookie уже от имени пользователя.

Значит, «быть вошедшим» = «отправлять cookie, за которой на сервере записан пользователь». Новый браузерный контекст без cookie — гость, даже если в соседнем контексте вы вошли.

## Аутентификация и авторизация

Два разных вопроса, которые часто путают:

- [[authentication|Аутентификация]] — **кто вы?** Проверка пароля, токена, второго фактора. Не удалось — `401 Unauthorized`.
- [[authorization|Авторизация]] — **что вам можно?** Проверка прав уже известного пользователя на конкретный ресурс. Нельзя — `403 Forbidden`.

В магазине это видно на заказах:

| Кто запрашивает `GET /api/orders/101` (заказ Анны) | Ответ |
|---|---|
| гость без входа | 401 — сервер не знает, кто это |
| Борис после входа | 403 — сервер знает Бориса, но заказ не его |
| Анна после входа | 200 — свой заказ |

Проверки доступа — одни из самых важных негативных проверок: дефект авторизации означает, что один покупатель видит адрес и покупки другого.

## Вход в тесте через API

Входить через форму в каждом тесте долго. Фикстура `request` в Playwright хранит cookie, как браузер: после `POST /api/login` все её следующие запросы идут от имени пользователя.

```ts tests/orders-api.spec.ts
import { test, expect } from '@playwright/test';

test('гость не может оформить заказ', async ({ request }) => {
  const res = await request.post('/api/orders');
  expect(res.status()).toBe(401);
});

test('после входа заказ оформляется', async ({ request }) => {
  await request.post('/api/login', { data: { email: 'anna@example.test', password: 'learn-123' } });
  await request.post('/api/cart', { data: { productId: 3 } });
  const res = await request.post('/api/orders');
  expect(res.status()).toBe(201);
});
```

Каждый тест получает свой `request` со своими cookie — тесты не делят сессию и корзину. В уроке про `storageState` вы увидите, как один раз войти и переиспользовать сохранённые cookie в браузерных тестах.

:::note
`learn-123` — учебный пароль учебного магазина, не секрет. Настоящие пароли и токены в код тестов не пишут: их передают через переменные окружения или хранилище секретов.
:::

:::try Проверьте права на заказы
Тест входит как Борис и оформляет заказ. Допишите проверки: оформление — 201, свой заказ — 200, заказ Анны №101 — 403. Тест должен поймать дефект, при котором заказ записывается не тому пользователю.
:::

```widget
{"type":"exercise","id":"m4-order-access"}
```

:::happened
На исправном магазине Борис открывает свой заказ (200) и не может открыть заказ Анны (403). На варианте с дефектом заказ записывается пользователю №1 — и Борис получает 403 на **свой** только что созданный заказ. Проверка «свой — 200» кажется очевидной, но именно она ловит этот дефект: без неё тест прошёл бы, хотя заказ ушёл чужому человеку. Гость без cookie получает 401 — отдельный контекст `playwright.request.newContext()` не знает о входе Бориса.
:::

:::mistake
Делить одного пользователя между параллельными тестами. Тест А кладёт товар в корзину, тест Б в это время оформляет заказ той же учётной записью — и оба падают случайным образом. Каждому тесту — своя сессия, а лучше и свой пользователь.
:::

:::deep Токены вместо cookie
Многие API вместо cookie используют токен в заголовке `Authorization: Bearer <токен>`. Это может быть [[jwt|JWT]] — подписанная строка, внутри которой записаны пользователь и срок действия; сервер проверяет подпись и не хранит сессию. Принципы для тестов те же: получить токен входом, передавать его в каждом запросе, проверять 401 без токена и с просроченным токеном, 403 — с токеном пользователя без прав.
:::

:::tech Безопасность сессии
Идентификатор сессии должен быть длинным и случайным, чтобы его нельзя было угадать. В учебном магазине он не меняется при входе; в настоящих системах его обычно выдают заново после входа, чтобы защититься от фиксации сессии — атаки, при которой злоумышленник заранее подсовывает жертве известный ему `sid`. После выхода сессия на сервере должна перестать действовать — это тоже проверяемое требование: старая cookie после `/logout` не должна давать доступ.
:::

:::interview
**Вопрос:** «Чем 401 отличается от 403? Как сервер узнаёт пользователя?» **Ответ по сути:** 401 — сервер не знает, кто вы (нет или неверные учётные данные); 403 — знает, но прав нет. Пользователь узнаётся по cookie с идентификатором сессии или по токену в заголовке Authorization. В тестах вхожу через API, держу отдельную сессию на тест и обязательно проверяю доступ к чужим ресурсам.
:::
