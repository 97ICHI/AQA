:::why
Слово «Playwright» обозначает две вещи: библиотеку, которая просто управляет браузером, и тестовый раннер поверх неё. Если их путать, легко написать скрипт, который «что-то делает в браузере», но ничего не проверяет и никогда не падает. В этом уроке вы увидите разницу на настоящем запуске.
:::

## Два слоя одного инструмента

**[[playwright-library|Playwright Library]]** — набор команд для браузера: запустить его, открыть страницу, нажать кнопку, прочитать текст. Ничего больше: ни понятия «тест», ни проверок, ни отчёта. Всё, что вы запустили, вы сами и закрываете.

**[[playwright-test|Playwright Test]]** (пакет `@playwright/test`) — тестовый раннер. Он использует ту же библиотеку, но добавляет:

- функцию `test` — объявление теста с названием;
- функцию `expect` — проверки, которые *ждут* нужного состояния и роняют тест при несовпадении;
- fixtures — готовые объекты вроде `page`, которые раннер создаёт перед тестом и убирает после;
- конфигурацию, параллельный запуск, повторы, отчёты и trace.

## Тот же сценарий двумя способами

Вот скрипт на библиотеке. Его запускают обычным `node`, а не раннером:

```ts scripts/add-mug.ts
import { chromium } from 'playwright';

const browser = await chromium.launch();
const page = await browser.newPage();
await page.goto('http://127.0.0.1:3000/');
await page.getByRole('listitem').filter({ hasText: 'Кружка' })
  .getByRole('button', { name: 'В корзину' }).click();
console.log('Счётчик:', await page.getByTestId('cart-count').textContent());
await browser.close();
```

Что здесь сделано вручную: запуск и закрытие браузера, полный адрес вместо `baseURL`, вывод результата в консоль. Если товар не добавится, скрипт напечатает `Счётчик: 0` и спокойно завершится с кодом 0 — для CI это «всё хорошо».

Тот же сценарий в Playwright Test:

```ts tests/cart.spec.ts
import { test, expect } from '@playwright/test';

test('кружка добавляется в корзину', async ({ page }) => {
  await page.goto('/');
  await page.getByRole('listitem').filter({ hasText: 'Кружка' })
    .getByRole('button', { name: 'В корзину' }).click();
  await expect(page.getByTestId('cart-count')).toHaveText('1');
});
```

Браузер, контекст и страницу создаёт раннер и передаёт `page` в тест. Адрес дополняется из `baseURL`. А вместо печати стоит **проверка**: если счётчик не станет `1`, тест упадёт, раннер вернёт ненулевой код выхода, и CI покажет красный статус.

## Роли трёх частей

| Часть | Что делает | Откуда берётся |
|---|---|---|
| `test(...)` | объявляет тест: название и функция с шагами | `@playwright/test` |
| `{ page }` | fixture: свежая страница в отдельном контексте браузера | раннер создаёт до теста и закрывает после |
| `expect(...)` | проверка ожидаемого результата | `@playwright/test` |
| `playwright.config.ts` | где тесты, `baseURL`, таймауты, браузеры, отчёты | читает раннер при запуске |

Тест запускается командой `npx playwright test`. Раннер читает конфигурацию, находит файлы `*.spec.ts`, для каждого теста готовит fixtures, выполняет функцию теста и собирает результат в отчёт.

:::try Тест, который не умеет падать
Ниже — тест в стиле «скрипта»: вместо `expect` стоит `if` с `console.log`. Он запущен на магазине с дефектом: товар **не добавляется** в корзину. Посмотрите на результат.
:::

:::happened
Тест прошёл, хотя корзина пуста. Для раннера тест успешен, если функция теста завершилась без исключения. `console.log` — это просто текст в журнале; никто его не читает, когда в CI прогоняются сотни тестов. Дефект пропущен.

Есть и вторая проблема: `textContent()` читает значение **один раз**, сразу после клика. Даже на исправном магазине запрос в корзину может ещё не завершиться, и в счётчике окажется `0`. Проверка `expect(...).toHaveText('1')` повторяет чтение, пока значение не совпадёт или не истечёт таймаут.
:::

:::mistake
**Смешивать два способа.** Внутри Playwright Test не нужно вызывать `chromium.launch()` и `browser.close()` — для этого есть fixtures `page`, `context` и `browser`. Если запустить браузер вручную, раннер о нём не знает: не применит настройки из `use`, не закроет его при падении, не запишет trace.
:::

:::deep Когда нужна именно библиотека
Библиотека уместна там, где нет тестов в привычном смысле: скрипт, который делает скриншоты страниц для документации, собирает данные, готовит учётную запись перед ручным тестированием. Тесты почти всегда пишут на Playwright Test: изоляция, ожидающие проверки, повторы, параллельность и отчёты там уже есть. Пакет `playwright` (библиотека) и `@playwright/test` (раннер) ставятся отдельно; раннер использует ту же внутреннюю часть и реэкспортирует, например, `chromium` и `devices`.
:::

:::tech Что значит «тест упал»
Тест считается упавшим, если функция теста выбросила исключение или превысила таймаут. Проверка `expect` при несовпадении выбрасывает исключение с текстом «что ожидалось и что получено». В конце прогона раннер завершается с кодом 1, если упал хотя бы один тест. По этому коду CI решает, красная сборка или зелёная.
:::

:::interview
**Вопрос:** «Чем `@playwright/test` отличается от пакета `playwright`?» **Ответ по сути:** `playwright` — библиотека автоматизации браузера; `@playwright/test` — раннер на её основе: `test`, web-first `expect`, fixtures с изоляцией каждого теста, конфигурация, параллельность, повторы, отчёты и trace. Для автотестов используют раннер; библиотеку — для скриптов, где нет понятия теста.
:::
