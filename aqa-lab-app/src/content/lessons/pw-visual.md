:::why
Функциональный тест проверит, что кнопка есть и нажимается, но не заметит, что она уехала за край экрана или стала белой на белом. Визуальная проверка сравнивает снимок экрана с эталоном и ловит такие поломки. Она же чаще всего «краснеет» без дефекта — из-за шрифтов, анимаций и окружения. В этом уроке — как она работает и от чего зависит результат.
:::

## Как работает визуальная проверка

[[visual-testing|Визуальная проверка]] в Playwright — это assertion `toHaveScreenshot`:

```ts tests/visual.spec.ts
import { test, expect } from '@playwright/test';

test('карточка блокнота выглядит как раньше', async ({ page }) => {
  await page.goto('/');
  const card = page.getByRole('listitem').filter({ hasText: 'Блокнот A5' });
  await expect(card).toHaveScreenshot('notebook-card.png');
});
```

Работает она так:

1. Playwright делает снимок элемента (или всей страницы — `expect(page).toHaveScreenshot()`).
2. Ищет [[screenshot-baseline|эталонный снимок]] — PNG-файл рядом с тестом, в папке `visual.spec.ts-snapshots/`.
3. Сравнивает попиксельно. Если отличий больше допуска — тест падает и прикладывает к отчёту три картинки: эталон, текущий снимок и разницу.

Как и другие проверки `expect`, `toHaveScreenshot` **ждёт**: делает снимки, пока два подряд не совпадут, и только потом сравнивает с эталоном. Так проверка не ловит страницу «на полпути».

## Первый запуск: эталона ещё нет

Эталон не пишут руками — его создаёт сам Playwright при первом запуске. Посмотрим, что происходит, когда эталона нет.

:::happened
Тест упал: эталонного файла нет, и Playwright записал текущий снимок как кандидат в эталон. Это ожидаемое поведение первого запуска. Дальше человек **смотрит** на снимок, и если он верный — добавляет его в репозиторий. Следующие запуски будут сравнивать с ним.

В тренажёре каждый запуск идёт во временной папке, которая удаляется после прогона. Эталон здесь не сохранится, поэтому визуальную проверку в этом уроке разбираем на записанном запуске и на модели сравнения.
:::

Обновить эталоны после **намеренного** изменения дизайна:

```bash
npx playwright test --update-snapshots
```

Новые снимки попадают в коммит, и ревьюер видит изменения картинок рядом с изменением кода.

## От чего зависит снимок

Один и тот же код страницы даёт разные пиксели в разных условиях. Поэтому имя эталона содержит браузер и платформу: `notebook-card-chromium-linux.png`. Снимок зависит от:

- **браузера и ОС** — сглаживание шрифтов и отрисовка отличаются;
- **шрифтов** — на машине CI может не быть шрифта, который есть у вас;
- **размера окна и масштаба** — `viewport`, `deviceScaleFactor`;
- **данных** — дата, счётчики, случайные рекомендации;
- **анимаций и курсора** — мигающий курсор в поле ввода, плавные переходы.

Отсюда правила: эталоны снимают **в том же окружении, где идёт сравнение** (обычно в Docker-образе CI), а изменчивые части стабилизируют.

```ts tests/visual.spec.ts
await expect(page).toHaveScreenshot('catalog.png', {
  mask: [page.getByTestId('cart-count')],   // закрыть изменчивый элемент плашкой
  animations: 'disabled',                   // остановить анимации (по умолчанию и так 'disabled')
  maxDiffPixels: 50,                        // допуск: до 50 отличающихся пикселей
});
```

## Допуски сравнения

У `toHaveScreenshot` три параметра сравнения:

- `threshold` — насколько должен отличаться **один** пиксель, чтобы считаться отличием (от 0 до 1, по умолчанию `0.2`);
- `maxDiffPixels` — сколько отличающихся пикселей допустимо;
- `maxDiffPixelRatio` — то же, но долей от всех пикселей (от 0 до 1).

Допуск — компромисс. Слишком строгий — тест краснеет от сглаживания шрифта. Слишком мягкий — пропустит кнопку, сдвинутую на пару пикселей. Разберитесь, как эти параметры работают вместе, на упрощённой модели сравнения.

:::mistake Снять эталоны на своём ноутбуке
Эталон с macOS почти наверняка не совпадёт со снимком на Linux в CI: другие шрифты и сглаживание. Тест будет падать у всех, кроме автора. Снимайте и обновляйте эталоны в том же Docker-образе, что и CI.
:::

:::mistake Принять новые снимки не глядя
`--update-snapshots` после каждого красного прогона превращает визуальную проверку в формальность: эталон всегда совпадает с текущим, каким бы он ни был. Обновлять эталон можно только после того, как человек посмотрел на разницу и согласился с ней.
:::

:::deep Где визуальные проверки окупаются
Снимок целой страницы с данными ломается от любого изменения текста. Лучше работают снимки **стабильных компонентов**: кнопки, карточки, шапки, состояния формы с ошибкой. Ещё один удачный случай — дизайн-система: библиотека компонентов в изолированном окружении без живых данных. Снимок не заменяет функциональные проверки: он скажет «стало иначе», но не скажет «правильно ли».
:::

:::tech Хранение и CSS для снимков
Путь эталона настраивается `snapshotPathTemplate` в конфигурации. Опция `stylePath` подключает CSS-файл только на время снимка — например, чтобы скрыть баннер или виджет чата. Общие допуски для всех проверок задают в `expect: { toHaveScreenshot: { maxDiffPixelRatio: 0.01 } }`. Флаг `--ignore-snapshots` пропускает проверки снимков — пригодится для прогона на машине без нужного окружения.
:::

:::interview
**Вопрос:** «Почему визуальные тесты нестабильны и как с этим бороться?» **Ответ по сути:** снимок зависит от браузера, ОС, шрифтов, размера окна, данных и анимаций. Эталоны снимаю и сравниваю в одном Docker-окружении CI, маскирую изменчивые элементы (`mask`), отключаю анимации, подбираю допуски (`threshold`, `maxDiffPixels`), снимаю стабильные компоненты, а не страницы с живыми данными. Эталоны обновляю только после просмотра разницы.
:::
