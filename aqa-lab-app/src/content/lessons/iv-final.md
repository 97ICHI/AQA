:::why
Отдельные уроки учат приёмам, а работа требует собрать их вместе: выбрать, что проверять, написать устойчивые тесты, разобрать падение по отчёту и запустить всё в CI. Итоговая работа — это небольшой проект, который можно показать на собеседовании и о котором можно рассказать по схеме из прошлого урока.
:::

## Задание

Соберите набор автотестов учебного магазина: UI, API и проверку данных в базе, с отчётом, диагностикой и запуском в CI. Магазин запускается локально (`node runner/shop.mjs ok` в этом приложении или через runner), дефекты включаются вариантами — по ним проверяется, что ваш набор ловит то, что должен.

### Объём

1. **Сквозной сценарий (UI + API):** вход → корзина → заказ → проверка сохранённого заказа через API. Ниже — его ядро в виде задания.
2. **API-набор:** коды ответа и форма `POST /api/orders` (201, 401 без входа, 422 для пустой корзины), `POST /api/cart` (400, 404, 409), доступ к чужому заказу (`GET /api/orders/:id` → 403).
3. **Проверка данных (SQL):** после заказа запись в `orders` принадлежит вошедшему пользователю, сумма позиций в `order_items` совпадает с итогом. Учебный маршрут `POST /__test/sql` выполняет один `SELECT`.
4. **Изоляция:** корзины двух покупателей не пересекаются (два контекста).
5. **Инфраструктура:** структура проекта по слоям, конфигурация через переменные окружения, HTML- и JSON-отчёт, trace для упавших тестов, pipeline с quality gate.

### Критерии приёмки

[[acceptance-criteria|Критерии приёмки]] — проверяемые условия, а не пожелания:

| № | Критерий | Как проверить |
|---|---|---|
| 1 | Весь набор проходит на вариантах `ok`, `slow`, `markup-change`, `similar-names` | прогон на каждом варианте |
| 2 | Каждый дефект (`cart-not-add`, `wrong-total`, `auth-lost`, `api-status`, `api-json`, `order-user`, `shared-cart`) ловит хотя бы один тест | прогон на каждом дефектном варианте |
| 3 | Нет `waitForTimeout`, однократного чтения для проверок, `test.only` | ревью, `forbidOnly` в CI |
| 4 | Тесты независимы: проходят с `--workers=4 --repeat-each=5` | прогон |
| 5 | Падение понятно по отчёту без перезапуска: шаги, ожидаемое/фактическое, trace, ответ API во вложении | открыть отчёт упавшего прогона |
| 6 | Pipeline красный при упавших тестах и при пустом прогоне, артефакты загружаются всегда | намеренно сломать тест |
| 7 | В README: как запустить, что покрыто, что сознательно не покрыто и почему | чтение |

Критерий 7 часто пропускают, а на интервью именно он показывает инженерное мышление: «оплату не автоматизировал — в магазине её нет; визуальные проверки не делал — вёрстка учебная и меняется».

### Шкала самооценки

| Уровень | Признаки |
|---|---|
| Junior | сценарии проходят на `ok`; часть дефектов не ловится; подготовка через UI; отчёт по умолчанию |
| Middle | все дефекты ловятся; подготовка через API; изоляция данных; trace и вложения; CI с артефактами |
| Middle+ | quality gate по JSON-отчёту; flaky rate и карантин; контракт ответа «терпимый»; обоснованные компромиссы в README; проверка, что набор ловит внесённый дефект |

## Проверка данных в базе

## Как оформить и рассказать

Репозиторий с работой — аргумент на собеседовании, если его легко понять за пять минут. Минимум: README с командами запуска (`npm ci`, `npx playwright test`, `docker compose up …`), таблица «что покрыто и каким тестом», ссылка на зелёный pipeline и на пример отчёта с упавшим тестом. История коммитов — небольшие осмысленные шаги, а не один коммит «done».

Рассказ о работе — тот же STAR: задача (набор для магазина с семью дефектами), решения (подготовка через API, контексты для изоляции, проверка в базе для `order-user`), результат (все дефекты ловятся, прогон N секунд, 0 нестабильных на 50 повторах), что сделали бы дальше.

:::deep Что делать после итоговой работы
Расширяйте по рискам, а не по количеству: параметризованные API-проверки граничных значений корзины; проверка доступности ключевых страниц; нагрузочный сценарий для `/api/cart`. Внесите свой дефект в копию магазина и проверьте, поймает ли его набор, — это честная оценка полноты, лучше любого процента покрытия.
:::

:::tech Набор вариантов в одной команде
В собственном проекте варианты магазина удобно описать как [[project-pw|projects]] Playwright с разным `baseURL` или переменной окружения, а ожидаемые падения на дефектных вариантах — отдельным скриптом, который запускает набор и проверяет, что код возврата ненулевой. Тот же приём используется в CI учебного проекта: задача «контролируемое падение» убеждается, что тесты ловят внесённый дефект.
:::
