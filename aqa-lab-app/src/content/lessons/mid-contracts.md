:::why
Фронтенд, мобильное приложение и другие сервисы зависят от того, в каком виде API отдаёт данные. Если поле `total` вчера было числом, а сегодня стало строкой, код клиента, который складывает суммы, получит склейку строк `"780.00" + "390.00"`, а сервер при этом честно ответит 201. Проверки формы ответа и совместимости ловят такие поломки до того, как их увидят пользователи.
:::

## Контракт — это договорённость

[[contract-testing|Контракт]] API — договорённость между тем, кто отдаёт данные (провайдер), и тем, кто их использует (потребитель): какие запросы допустимы, какие коды ответа и какие поля с какими типами приходят. Обычно контракт записывают в [[openapi|OpenAPI]] — машиночитаемое описание путей, параметров и схем. Схема тела ответа — это [[json-schema|JSON Schema]].

Проверка контракта отвечает на вопрос «ответ имеет правильную форму?», а не «ответ правильный по смыслу?». Это разные проверки, и нужны обе: `total: 780` и `total: 390` одинаково соответствуют схеме, но только одно верно.

## Ответ API — это `unknown`

TypeScript проверяет типы при компиляции, а JSON приходит по сети во время работы. Запись `const body: Order = await res.json()` ничего не проверяет: она лишь обещает компилятору, что там `Order`. Если сервер прислал строку вместо числа, тест узнает об этом позже — или не узнает вовсе. Поэтому ответ считают `unknown` и проверяют [[runtime-validation|во время выполнения]]: вручную, сопоставлением в Playwright или библиотекой схем (zod, ajv).

В Playwright форму удобно проверять асимметричными сопоставлениями:

```ts tests/api/orders.api.spec.ts
const res = await request.post('/api/orders');
expect(res.status()).toBe(201);
expect(await res.json()).toMatchObject({
  id: expect.any(Number),
  status: 'new',
  total: expect.any(Number),
  totalText: expect.any(String),
  items: expect.any(Array),
});
```

`expect.any(Number)` проходит для любого числа и падает на строке `'780.00'`. `toMatchObject` проверяет перечисленные поля и не обращает внимания на остальные.

## Совместимость изменений

API меняется, и не каждое изменение ломает потребителей. Правило [[backward-compatibility|обратной совместимости]]:

| Изменение | Совместимо? |
|---|---|
| Добавить новое необязательное поле в ответ | да |
| Добавить новый эндпоинт | да |
| Удалить или переименовать поле ответа | нет |
| Изменить тип поля (`number` → `string`) | нет |
| Сделать необязательное поле запроса обязательным | нет |
| Добавить значение в перечисление (`status: 'refunded'`) | зависит от потребителя |

Отсюда правило для тестов-потребителей — «терпимый читатель»: проверять то, что действительно используется, и не падать на лишних полях. Тест с `toEqual` на всё тело упадёт, когда в ответ добавят поле, — хотя ни один клиент не сломался. Такой тест создаёт шум и приучает команду обновлять ожидания не глядя.

:::deep Контракты, управляемые потребителем
В [[consumer-driven-contracts|consumer-driven contracts]] потребитель сам записывает, какие запросы он делает и какие поля ему нужны; провайдер в своём pipeline проверяет, что выполняет контракты всех потребителей. Самый известный инструмент — [[pact|Pact]]. Плюс: провайдер узнаёт о поломке потребителя до выкладки, без общего тестового стенда. Минус: инфраструктура (брокер контрактов), дисциплина и время на внедрение. Для одной команды с одним фронтендом часто достаточно схемы OpenAPI и проверки ответов на соответствие ей в API-тестах.
:::

:::tech Валидация по OpenAPI в тестах
Если у сервиса есть OpenAPI, схему ответа можно не переписывать руками: из неё генерируют типы TypeScript (например, openapi-typescript) и проверяют ответы валидатором JSON Schema (ajv). Типы помогают при написании теста, валидатор — при выполнении. Важно проверять ответ теста той же версией схемы, что лежит в репозитории сервиса, иначе тест проверяет устаревший контракт.
:::

:::interview
**Вопрос:** «Чем контрактное тестирование отличается от функционального API-теста?» **Ответ по сути:** контрактная проверка — форма: коды ответа, обязательные поля, типы, совместимость изменений; функциональная — смысл: правильная сумма, права доступа, состояние после операции. Контракт проверяю «терпимо»: используемые поля и типы, без запрета новых полей. Ответ API — `unknown`, его проверяют во время выполнения, а не приведением типа.
:::
