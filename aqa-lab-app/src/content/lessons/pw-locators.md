:::why
Большая часть поломок UI-тестов — не дефекты, а локаторы, которые перестали находить элемент после безобидной правки вёрстки. Выбор локатора — главное решение в UI-тесте. В этом уроке вы сравните основные способы поиска, научитесь уточнять локатор и перепишете хрупкий тест так, чтобы он пережил новую вёрстку магазина.
:::

## Четыре основных способа

| Метод | Что ищет | Когда брать |
|---|---|---|
| `getByRole(role, { name })` | элемент по роли и доступному имени | по умолчанию: кнопки, ссылки, поля, заголовки, строки таблицы |
| `getByLabel(text)` | поле формы по подписи | поля ввода, особенно без роли (`type="password"`) |
| `getByText(text)` | элемент по видимому тексту | текст без интерактивной роли: сообщение, абзац |
| `getByTestId(id)` | элемент с атрибутом `data-testid` | нет устойчивой роли и текста: счётчик, сумма, динамический блок |

Есть и другие: `getByPlaceholder`, `getByAltText`, `getByTitle`. А `page.locator('css или xpath')` — запасной выход, когда пользовательских признаков нет.

Порядок предпочтения простой: сначала то, что видит пользователь (роль, подпись, текст), затем договорённость с разработчиками ([[test-id|test id]]), и только потом структура страницы ([[css-selector|CSS]], [[xpath|XPath]]).

## Почему CSS ломается

```ts tests/fragile.spec.ts
await page.locator('#product-3 .add-to-cart').click();
await expect(page.locator('.total strong')).toHaveText('780 ₽');
```

Здесь тест знает id карточки, имя класса кнопки и то, что сумма лежит в `<strong>` внутри `.total`. Ни одна из этих деталей не видна пользователю, и любую из них разработчик вправе поменять. В учебном магазине есть вариант «новая вёрстка»: роли и тексты те же, классы и id другие.

:::

## Уточнение: цепочки и filter

Одного признака часто мало: кнопок «В корзину» на странице пять. Локатор можно [[locator-filter|уточнить]].

**Цепочка** — искать внутри найденного:

```ts
const card = page.getByRole('listitem').filter({ hasText: 'Блокнот A5' });
await card.getByRole('button', { name: 'В корзину' }).click();   // кнопка только этой карточки
```

**filter** — оставить из найденных только подходящие:

```ts
page.getByRole('listitem').filter({ hasText: 'Кружка' });           // содержит текст
page.getByRole('listitem').filter({ hasNotText: 'Нет в наличии' }); // не содержит текст
page.getByRole('listitem').filter({                                  // содержит элемент
  has: page.getByRole('heading', { name: 'Кружка', exact: true }),
});
page.getByRole('listitem').filter({ has: page.getByRole('button') }); // товары, которые можно купить
```

`hasText` со строкой ищет подстроку без учёта регистра в тексте элемента и всех его потомков. `has` принимает другой локатор; он ищется *внутри* каждого кандидата.

Ещё два инструмента: `locator.and(other)` — элемент должен подходить под оба локатора; `locator.or(other)` — под любой из них (например, «кнопка „Войти“ или уже имя пользователя в шапке»).

## Когда нужен test id

Сумма корзины «780 ₽» — это просто текст в `<strong>`, без роли и подписи. Искать её `getByText('780 ₽')` бессмысленно: мы как раз проверяем, что там именно 780, а не другое число. Здесь уместен `data-testid="cart-total"` — устойчивая договорённость с разработчиками:

```ts
await expect(page.getByTestId('cart-total')).toHaveText('780 ₽');
```

Имя атрибута можно поменять в конфигурации: `use: { testIdAttribute: 'data-qa' }`.

:::mistake
**Скопировать селектор из DevTools.** «Copy selector» даёт что-то вроде `body > main > ul > li:nth-child(5) > button`. Такой путь ломается от любой новой обёртки или смены порядка карточек. Используйте DevTools, чтобы *посмотреть* роль и подпись элемента, а локатор пишите сами.
:::

:::deep Где test id лучше роли
Роль и текст хороши, пока текст стабилен. В многоязычном приложении текст кнопки зависит от языка; в таблице сотни одинаковых кнопок «Изменить». Там уместны test id на контейнере строки плюс роль внутри: `page.getByTestId('order-101').getByRole('button', { name: 'Изменить' })`. Test id — часть контракта с разработкой: их нельзя удалять «потому что не используются в коде приложения».
:::

:::tech Как filter({ visible }) и порядок работают
`filter({ visible: true })` оставляет только видимые элементы — полезно, когда в разметке есть скрытая мобильная копия меню. Локаторы `first()`, `last()` и `nth(i)` выбирают элемент по позиции в DOM; они зависят от порядка и данных, поэтому о них — отдельный урок про строгость. Локатор вычисляется заново при каждом действии, поэтому цепочку можно сохранить в переменную в начале теста.
:::

:::interview
**Вопрос:** «Как выбираете локатор?» **Ответ по сути:** от пользователя к реализации: роль и имя → подпись поля → текст → test id → CSS/XPath в крайнем случае. Неоднозначность снимаю цепочкой от устойчивого контейнера (карточка, строка таблицы) и `filter`, а не индексом. Локатор должен ломаться только тогда, когда поменялось поведение для пользователя.
:::
