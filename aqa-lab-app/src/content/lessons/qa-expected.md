:::why
Тест сравнивает фактический результат с ожидаемым. Если ожидаемый результат придуман после запуска — «ну, программа показала 2925, наверное, так и надо», — тест просто закрепляет то, что программа уже делает, вместе с её ошибками. Поэтому ожидание записывают заранее, из требования.
:::

## Требование — источник ожидания

[[requirement|Требование]] описывает, как система должна себя вести. Оно бывает в задаче, в спецификации API, в макете дизайна, в договорённости с аналитиком. Для тестировщика требование — главный [[test-oracle|оракул]]: из него выводится [[expected-result|ожидаемый результат]].

Хорошее ожидание — **конкретное**. Сравните:

| Расплывчато | Конкретно |
|---|---|
| «Скидка применяется» | «Сумма 2000 ₽ с промокодом SPRING → 1800 ₽» |
| «Заказ оформляется» | «Ответ 201, в теле `status: "new"`, в шапке корзины `0`» |
| «Ошибка показывается» | «Текст „Ошибка: нужно войти“, заказ в базе не создан» |

Расплывчатое ожидание нельзя проверить кодом: непонятно, с чем сравнивать. Конкретное превращается в одну строку `expect`.

## Пример: стоимость заказа

Возьмём требование к расчёту заказа (в учебном магазине доставки и промокодов нет, это правило для тренировки):

```text
R-7 «Сумма к оплате»
1. Сумма товаров = Σ цена × количество.
2. Промокод SPRING уменьшает сумму товаров на 10 %.
3. Доставка — 299 ₽; бесплатно, если сумма товаров после скидки не меньше 3000 ₽.
4. К оплате = сумма товаров после скидки + доставка.
```

Посчитаем ожидание для заказа «2 × Блокнот A5 по 390 ₽, без промокода» по пунктам: товары 780 ₽ → скидки нет → 780 < 3000, доставка 299 ₽ → к оплате **1079 ₽**.

Записываем это как test case: исходное состояние, шаги, ожидаемый результат.

```text
Дано:      корзина пуста, промокод не введён
Шаги:      добавить «Блокнот A5» (390 ₽) 2 раза
Ожидается: к оплате 1079 ₽ (780 ₽ товары + 299 ₽ доставка)
```

А так он выглядит в коде, когда ожидания собраны в таблицу:

```ts tests/order-total.spec.ts
import { test, expect } from '@playwright/test';
import { orderTotal } from '../src/order-total';

const cases = [
  { name: '2 блокнота, без промокода', items: [{ price: 390, qty: 2 }], promo: null, expected: 1079 },
  { name: 'наушники со SPRING', items: [{ price: 4990, qty: 1 }], promo: 'SPRING', expected: 4491 },
];

for (const c of cases) {
  test(c.name, () => {
    expect(orderTotal(c.items, c.promo)).toBe(c.expected);
  });
}
```

Числа в `expected` посчитаны вручную по требованию. Они не взяты из вывода `orderTotal` — иначе тест проверял бы функцию ею же самой.

## Неоднозначность — тоже находка

Пока вы считаете ожидание, всплывают вопросы. Порог доставки сравнивается с суммой до скидки или после? Скидка округляется до рубля или до копейки? Что, если промокод введён строчными буквами?

Если требование не отвечает, ожидаемый результат записать нельзя. Это не повод угадывать — это повод спросить аналитика или разработчика и дописать требование. Найденная неоднозначность до написания кода дешевле любого найденного потом дефекта. В R-7 автор заранее уточнил «после скидки», и это важно в одном из случаев задания ниже.

:::try Посчитайте ожидания
Программы нет — только требование R-7. Посчитайте сумму к оплате для четырёх заказов. Обратите внимание на последний случай.
:::

```widget
{"type":"exercise","id":"m2-expected-table"}
```

:::happened
Три случая считаются прямо. Четвёртый — ловушка: 3250 ₽ без скидки дают бесплатную доставку, а со SPRING сумма становится 2925 ₽ — ниже порога, и доставка снова 299 ₽. Программа, которая сравнивает порог с суммой до скидки, выдаст 2925. Если бы ожидание записывали после запуска, такой ответ легко принять за правильный. Записанное заранее — 3224 — сразу покажет расхождение.
:::

## Фактический результат и отчёт о дефекте

Когда фактический результат не совпал с ожидаемым, ожидание становится частью отчёта о дефекте. Минимальный отчёт содержит: шаги, ожидаемый результат (со ссылкой на требование), фактический результат, окружение. Без ожидания отчёт «сумма какая-то не такая» превращается в спор.

У дефекта две разные оценки: [[severity|серьёзность]] — насколько сильно он вредит, и [[priority|приоритет]] — насколько срочно его чинить. Неверная сумма к оплате — серьёзный дефект, даже если разница 299 ₽.

:::deep Когда требования нет
Бывает, что требования нет совсем: старая система, которую никто не документировал. Тогда оракулами служат прежняя версия системы (поведение «как было»), здравый смысл и согласованность («в корзине и в заказе сумма должна совпадать»), справочники и законы. Такие ожидания слабее: «как было» может быть ошибкой. Их стоит явно отмечать и подтверждать у владельца продукта.
:::

:::tech Ожидание в коде теста
Ожидаемое значение лучше писать в тесте литералом (`1079`) или выводить простой и очевидной формулой (`2 * 390 + 299`), а не копией логики приложения. Если в тесте повторить сложный расчёт из кода, ошибка в расчёте окажется и там и там, и тест её не увидит.
:::

:::interview
**Вопрос:** «Откуда вы берёте ожидаемый результат?» **Ответ по сути:** из требований и спецификаций; если их нет — уточняю у аналитика или владельца продукта; в крайнем случае — из согласованного поведения прежней версии с пометкой. Ожидание записываю до запуска, конкретно, чтобы его можно было проверить кодом. Неоднозначности в требованиях фиксирую как вопросы — это тоже результат тестирования.
:::
