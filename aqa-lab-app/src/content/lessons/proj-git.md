:::why
В команде тесты меняют несколько человек одновременно. Чтобы изменения не мешали друг другу, а каждое попадало в общий код только после проверки, используют Git, ветки и ревью. На собеседовании Middle-инженера почти всегда просят описать этот путь своими словами — от задачи до слияния.
:::

## Путь одного изменения

[[git|Git]] хранит историю проекта как цепочку снимков. Снимок называется [[commit|коммитом]]: в нём изменённые файлы, автор, время и сообщение «что и зачем». [[branch|Ветка]] — подвижный указатель на последний коммит линии работы. Основная ветка (`main`) — то, что считается рабочим кодом; новые изменения делаются в отдельной ветке и попадают в `main` через [[merge-request|merge request]] (в GitHub — pull request).

Типичный путь задачи «добавить тест итога корзины»:

```bash
git switch main
git pull --ff-only                      # свежий main без случайных merge-коммитов
git switch -c test/cart-total           # ветка под одну задачу
npx playwright test tests/cart.spec.ts   # пишем тест и запускаем локально
git status --short                      # что изменилось
git add tests/cart.spec.ts
git commit -m "test: итог корзины учитывает количество"
git push -u origin test/cart-total      # ветка на сервере, дальше — merge request
```

`git switch -c` создаёт ветку и переключается на неё. `--ff-only` запрещает `pull` создавать коммит слияния: если локальный `main` разошёлся с сервером, команда остановится и покажет это, а не смешает истории молча.

## Что коммитить, а что нет

В репозитории хранится то, из чего проект можно собрать заново: код тестов, конфигурация, `package.json` и `package-lock.json`. Результаты запусков и установленные зависимости не хранятся — они воспроизводимы и быстро устаревают. Список исключений — файл [[gitignore|.gitignore]]. В учебном проекте он такой:

```text .gitignore
node_modules/
playwright-report/
test-results/
allure-results/
allure-report/
*.log
.env
```

`.env` — файл с локальными [[environment-variable|переменными окружения]]: адреса стендов, логины, токены. Секреты в Git попадать не должны никогда: история хранит их и после удаления файла. Если секрет всё-таки закоммичен, его нужно отозвать и выпустить новый — удалить коммит недостаточно. Шаблон без значений (`.env.example`) коммитят, чтобы коллеги знали, какие переменные нужны.

:::mistake
`git add .` без взгляда на `git status`. Так в коммит попадают `test-results/`, локальный `.env` или случайный `test.only`. Перед коммитом смотрите `git status --short` и `git diff --staged`.
:::

## Merge request и ревью

Merge request — предложение влить ветку в `main`. К нему автоматически запускается [[pipeline|CI]], а коллеги проводят ревью. Что смотрит ревьюер в тестовом коде:

- проверяет ли тест результат, важный пользователю, а не «страница открылась»;
- нет ли `waitForTimeout`, однократного чтения и других источников нестабильности;
- независим ли тест от порядка и чужих данных;
- понятно ли из названия и сообщения о падении, что сломалось;
- не осталось ли `test.only`, отладочных `console.log`, закомментированного кода.

Хороший merge request маленький и про одно. Двадцать новых тестов, рефакторинг фикстур и обновление Playwright в одной ветке ревьюить тяжело, и ошибки проходят.

## Когда ветки расходятся

Пока вы работали, `main` ушёл вперёд. Есть два способа подтянуть изменения:

```bash
git fetch origin
git merge origin/main     # способ 1: коммит слияния, история сохраняется как была
git rebase origin/main    # способ 2 (вместо merge): ваши коммиты поверх свежего main
```

[[rebase|Rebase]] даёт линейную историю, но переписывает коммиты: после него нужен `git push --force-with-lease`. Его делают только в своей ветке, которую никто больше не использует. В общей ветке переписывать историю нельзя. Какой способ принят — решает команда; важно следовать одному.

[[merge-conflict|Конфликт]] возникает, когда обе стороны изменили одни и те же строки. Git помечает их маркерами `<<<<<<<`, `=======`, `>>>>>>>`. Разрешить конфликт — значит оставить правильный итоговый код (часто это комбинация обеих версий), удалить маркеры, **запустить тесты** и только потом продолжить `git rebase --continue` или закоммитить слияние.

:::happened
Формат `git status --porcelain` создан для программ: он не меняется между версиями Git и языками интерфейса. Два символа статуса (`??` — новый, `M` — изменён, `A` — добавлен, `R` — переименован), пробел, путь. Обычный `git status` для разбора не годится: его текст переводится и меняется.

:::deep Сообщения коммитов и история как инструмент
История нужна, чтобы через полгода ответить «почему тест стал таким». Сообщение `fix` на это не отвечает; `test: ждать ответа корзины вместо паузы 500 мс` — отвечает. Многие команды используют соглашение Conventional Commits (`test:`, `fix:`, `chore:`). Для поиска регрессий есть `git bisect`: он делит историю пополам и помогает найти коммит, после которого тест начал падать. `git blame` показывает, кто и в каком коммите менял строку, — это способ найти контекст, а не виноватого.
:::

:::tech Полезные команды на каждый день
`git log --oneline --graph -20` — короткая история с ветвлениями. `git diff main...HEAD` — что изменено в ветке относительно точки ответвления. `git stash` / `git stash pop` — временно убрать незакоммиченные изменения. `git restore <файл>` — отменить изменения в файле. `git commit --amend` — исправить последний коммит, пока он не отправлен. `git switch -` — вернуться на предыдущую ветку.
:::

:::interview
**Вопрос:** «Опишите ваш процесс работы с Git.» **Ответ по сути:** ветка от свежего `main` под одну задачу, небольшие коммиты с понятными сообщениями, перед коммитом — `git status` и `git diff`, локальный прогон затронутых тестов, merge request с описанием, CI и ревью. Конфликты разрешаю у себя в ветке и перезапускаю тесты; `rebase` — только своей ветки, в общей истории — `merge`. Секреты и артефакты прогонов в репозиторий не попадают.
:::
