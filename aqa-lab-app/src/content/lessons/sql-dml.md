:::why
Многие тесты начинаются не с клика, а с данных: «пользователь с пустой корзиной», «товар, которого нет в наличии», «заказ в статусе paid». Через интерфейс такое состояние готовить долго и ненадёжно. SQL-команды изменения данных создают его за миллисекунды, а после теста убирают.
:::

## Три команды

Команды, которые меняют строки, называют [[dml|DML]]: `INSERT` добавляет, `UPDATE` изменяет, `DELETE` удаляет. Каждая работает с одной таблицей.

### INSERT

```sql seed/order.sql
INSERT INTO orders (id, user_id, status, promo_code, created_at)
VALUES (900, 1, 'new', NULL, '2026-08-01');
```

Список столбцов после имени таблицы лучше писать всегда: запрос не зависит от порядка столбцов в таблице, а пропущенные столбцы получают значение по умолчанию (`DEFAULT`). Несколько строк вставляют одним `VALUES` через запятую.

Вместо `VALUES` можно вставить результат `SELECT`. Так значения берутся из базы, а не переписываются руками:

```sql seed/order-item.sql
INSERT INTO order_items (order_id, product_id, qty, price)
SELECT 900, id, 2, price          -- цена — текущая цена из каталога
FROM products
WHERE sku = 'NOTE-A5';
```

### UPDATE

```sql seed/out-of-stock.sql
UPDATE products
SET stock = 0
WHERE sku = 'LAMP-S';
```

`SET` перечисляет новые значения, `WHERE` — какие строки менять. Новое значение может зависеть от старого: `SET stock = stock - 1`.

### DELETE

```sql cleanup/orders.sql
DELETE FROM orders
WHERE user_id = 1 AND created_at >= '2026-08-01';
```

:::warn UPDATE и DELETE без WHERE
Без `WHERE` команда затрагивает **все** строки таблицы. На общем тестовом стенде это означает, что вы сломали данные коллегам и другим тестам. Перед запуском замените `DELETE` на `SELECT *` с тем же `WHERE` и посмотрите, что попадёт под удаление.
:::

## RETURNING и число затронутых строк

PostgreSQL сообщает, сколько строк изменила команда, а с `RETURNING` возвращает сами изменённые строки. Это удобно в тестах: можно сразу проверить, что `UPDATE` попал ровно в одну строку, или получить `id` созданной записи.

:::try Измените и посмотрите
Запустите скрипт. Он снижает цену и возвращает изменённые строки. Запустите ещё раз — цена снизится снова: изменения в песочнице сохраняются до кнопки «Сбросить базу».
:::

```widget
{"type":"playground","lang":"sql","title":"UPDATE … RETURNING","dataset":"base","code":"UPDATE products\nSET price = price - 100\nWHERE category = 'home'\nRETURNING id, title, price;\n"}
```

:::happened
Изменились две строки категории `home`, и `RETURNING` показал их новые значения. Повторный запуск снова отнял 100: `UPDATE` с `price = price - 100` не идемпотентен — результат зависит от того, сколько раз его выполнили. Подготовку данных стараются писать так, чтобы повтор давал то же состояние (`SET price = 590`, а не `price - 100`).
:::

## Порядок и связи

Таблицы связаны внешними ключами, поэтому порядок команд важен. Позицию нельзя вставить раньше заказа: `order_items.order_id` должен ссылаться на существующий заказ. Удалять — в обратном порядке, но в учебной базе у `order_items` и `payments` стоит `ON DELETE CASCADE`: при удалении заказа его позиции и оплаты удаляются сами.

```widget
{"type":"playground","lang":"sql","title":"Каскадное удаление","dataset":"base","code":"DELETE FROM orders WHERE id = 101;\n\nSELECT (SELECT COUNT(*) FROM orders)      AS orders,\n       (SELECT COUNT(*) FROM order_items) AS items,\n       (SELECT COUNT(*) FROM payments)    AS payments;\n"}
```

До удаления в основном наборе 5 заказов, 7 позиций и 4 оплаты. После — 4, 5 и 3: ушли две позиции и одна оплата заказа 101.

:::deep Свои данные — свои метки
На общем стенде тест должен удалять только то, что создал сам. Для этого данные помечают: уникальный email вида `qa+<run-id>@example.test`, отдельный диапазон `id`, промокод или префикс в названии. Очистка тогда ищет по метке, а не по «всё, что создано сегодня». Ещё надёжнее — запоминать `id`, возвращённые `INSERT … RETURNING id`, и удалять ровно их.
:::

:::tech Значения по умолчанию и последовательности
В учебной базе `id` задаются явно. В реальных схемах первичный ключ обычно генерируется (`GENERATED ALWAYS AS IDENTITY` или `serial`), и тест получает его через `RETURNING id`. Явная вставка `id` в такую таблицу либо запрещена, либо ломает счётчик: следующая автоматическая вставка может получить уже занятый номер.
:::

:::interview
**Вопрос:** «Как вы готовите и убираете тестовые данные в базе?» **Ответ по сути:** создаю данные перед тестом (`INSERT`, при необходимости `INSERT … SELECT` из справочников), помечаю их уникальной меткой, запоминаю `id` через `RETURNING`. После теста удаляю по этим `id` или метке. `UPDATE`/`DELETE` всегда с `WHERE`, предварительно проверенным через `SELECT`.
:::
