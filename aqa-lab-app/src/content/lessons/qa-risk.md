:::why
Времени на тесты всегда меньше, чем идей для тестов. Нужно решать две вещи: **что** проверять в первую очередь и **где** — в быстрых тестах функций, через API или в браузере. Неудачный выбор даёт медленный и хрупкий набор, который всё равно пропускает важное.
:::

## Риск: что проверять в первую очередь

Риск — это возможная проблема, оценённая по двум осям:

- **вероятность** — насколько вероятно, что здесь есть дефект: новый или сложный код, частые изменения, история багов;
- **влияние** — насколько плохо будет, если дефект попадёт к пользователям: потеря денег, данных, доверия; сколько людей заденет.

[[risk-based-testing|Тестирование на основе рисков]] ставит в начало то, где оба показателя высоки. Для магазина:

| Область | Вероятность | Влияние | Приоритет |
|---|---|---|---|
| Сумма к оплате, скидки | средняя (логика с условиями) | высокое (деньги) | высокий |
| Доступ к чужим заказам | низкая | очень высокое (персональные данные) | высокий |
| Добавление в корзину | средняя | высокое (нельзя купить) | высокий |
| Цвет кнопки «Найти» | низкая | низкое | низкий |

Таблица не точная наука — это способ договориться с командой о порядке работы и явно назвать, что остаётся без проверки.

## Уровни проверки

Одно и то же правило можно проверить на разных уровнях:

- **unit** — [[unit-testing|модульный тест]] вызывает функцию напрямую. Миллисекунды, никакого браузера и сервера, легко перебрать десятки значений.
- **API** — [[api-testing|тест API]] отправляет HTTP-запрос к работающему серверу и проверяет ответ. Секунды или доли секунды, видна логика сервера, права, формат данных.
- **UI** — [[ui-testing|тест интерфейса]] управляет браузером, как пользователь. Медленнее всего и больше всего зависимостей, зато проверяет то, что действительно видит человек. Тест целого пути пользователя называют [[e2e-testing|сквозным]].

Правило выбора: **проверяйте правило на самом дешёвом уровне, на котором оно видно**.

Расчёт скидки живёт в функции — unit-тест проверит десять граничных значений за миллисекунды. Через UI каждое значение — отдельный проход по страницам: вход, корзина, промокод, итог. Это в сотни раз медленнее, а при падении непонятно, что сломалось: расчёт, страница или вход.

Но счётчик корзины в шапке существует только на странице. Функция может считать верно, а страница — не обновляться. Это правило проверяет только UI.

## Пирамида

Из правила выбора получается форма набора тестов — [[test-pyramid|пирамида]]: много unit-тестов, меньше API, немного UI-тестов на ключевые пути пользователя.

```text
        ▲  UI / E2E   — несколько ключевых сценариев: вход → корзина → заказ
       ▲▲▲ API        — коды ответов, права, формат JSON, состояния заказа
     ▲▲▲▲▲▲ unit       — расчёты, валидация, границы, преобразования
```

Пирамида — эвристика, не закон. В проекте, где почти вся логика на сервере, «середина» может быть толще. Важна идея: не тащить в браузер то, что можно проверить ниже.

:::mistake
«Перевёрнутая пирамида»: всё проверяется через UI. Набор идёт час, падает от любого изменения вёрстки, и каждый красный тест требует долгого разбора. Обычно это следствие того, что тесты пишут только по пользовательским сценариям, не спрашивая, где живёт правило.
:::

:::try Выберите уровень
Шесть правил магазина. Для каждого выберите самый дешёвый уровень, на котором его можно надёжно проверить. Стартовый вариант — «всё через UI».
:::

```widget
{"type":"exercise","id":"m2-test-level"}
```

:::happened
Расчёт скидки и порог доставки — вычисления внутри функций: unit. Код 401 и тип поля `price` — свойства HTTP-ответа: API, браузер для этого не нужен. Счётчик в шапке и путь покупателя целиком существуют только на странице: UI. Получилась маленькая пирамида: правила распределились по уровням, и в браузере осталось только то, чего ниже не увидеть.
:::

## Сочетание уровней

Уровни дополняют друг друга. Типичный набор для оформления заказа:

- unit: расчёт суммы, скидок, доставки — все границы;
- API: 201 при успехе, 401 без входа, 422 с пустой корзиной, 403 на чужой заказ, тип `total` в JSON;
- UI: один сквозной сценарий «войти → добавить → оформить → увидеть номер заказа».

Если сквозной тест падает, а unit и API зелёные, проблема почти наверняка в интерфейсе. Такая раскладка сама подсказывает, где искать причину.

:::deep Регрессия и стоимость
[[regression-testing|Регрессионный набор]] запускается после каждого изменения, поэтому его скорость — ежедневные деньги команды. Медленный набор запускают реже, и дефекты находят позже, когда их дороже чинить. Поэтому при выборе уровня учитывают не только «можно ли проверить», но и «сколько раз в день это будут запускать».
:::

:::tech Integration и contract
Между unit и API есть [[integration-testing|интеграционные тесты]]: несколько модулей вместе, например код и настоящая база данных, без HTTP. А когда сервисов много, договорённость о формате запросов и ответов проверяют [[contract-testing|контрактными тестами]], не поднимая всю систему. Названия уровней в разных командах различаются — важнее, что именно тест изолирует и что запускает по-настоящему.
:::

:::interview
**Вопрос:** «Как вы решаете, писать UI-тест или API-тест?» **Ответ по сути:** смотрю, где реализовано правило и где его видно. Логику и данные проверяю на уровне API или unit — быстрее, стабильнее, точнее локализует дефект. UI-тестами покрываю ключевые пользовательские сценарии и то, что существует только в интерфейсе. Порядок работы определяю по риску: вероятность дефекта × влияние.
:::
