:::why
Проверка — то, ради чего пишется тест. Но проверка, которая прочитала значение один раз в неудачный момент, падает на исправном магазине, а слишком общая («сумма содержит знак ₽») проходит на сломанном. В этом уроке вы научитесь писать проверки, которые ждут нужного состояния и при этом точно ловят дефект.
:::

## Два вида проверок

В Playwright Test `expect` работает двумя способами — в зависимости от того, *что* в него передать.

**Ожидающая проверка** ([[web-first-assertion|web-first assertion]]) — в `expect` передан локатор или страница:

```ts
await expect(page.getByTestId('cart-count')).toHaveText('1');
```

Playwright повторяет «найти элемент → прочитать текст → сравнить», пока значение не совпадёт или не истечёт таймаут проверки (по умолчанию 5 с, в нашем runner — 3 с). Перед такой проверкой всегда стоит `await`.

**Обычная проверка значения** — в `expect` передано уже прочитанное значение:

```ts
const text = await page.getByTestId('cart-count').textContent();
expect(text).toBe('1');
```

Здесь текст прочитан **один раз**. `expect` сравнивает строку со строкой и ничего не ждёт: строка не может «обновиться».

:::try Разовое чтение против ожидающей проверки
Два теста делают одно и то же: добавляют кружку и проверяют счётчик. Первый читает текст сразу после клика, второй использует `toHaveText`.
:::

Клик завершился, но запрос в корзину ещё в пути, и счётчик на странице пока `0`. Разовое чтение застало именно этот момент. Проверка `toHaveText('1')` дождалась обновления. ## Основные ожидающие проверки

| Проверка | Что утверждает |
|---|---|
| `toBeVisible()` / `toBeHidden()` | элемент видим / скрыт или отсутствует |
| `toHaveText(t)` | текст элемента равен `t` (строка — полное совпадение после нормализации пробелов; RegExp — совпадение по шаблону) |
| `toContainText(t)` | текст содержит `t` |
| `toHaveValue(v)` | значение поля ввода |
| `toHaveCount(n)` | локатор находит ровно `n` элементов |
| `toBeEnabled()` / `toBeDisabled()` | доступность |
| `toBeChecked()` | флажок отмечен |
| `toHaveAttribute(name, value)` | значение атрибута |
| `toHaveURL(url)` / `toHaveTitle(t)` | адрес и заголовок страницы (для `page`) |

Отрицание — через `.not`: `await expect(page.getByRole('status')).not.toHaveText(/Ошибка/)`. Оно тоже ждёт — пока условие *перестанет* выполняться.

## Точность проверки

Проверка должна падать, когда нарушен результат, важный пользователю. Сравните:

```ts
// Слабо: пройдёт и при сумме 390 ₽ вместо 1 470 ₽
expect(await page.getByTestId('cart-total').textContent()).toContain('₽');

// Точно: ловит неверную сумму и ждёт, пока страница будет готова
await expect(page.getByTestId('cart-total')).toHaveText('1 470 ₽');
```

`toHaveText` со строкой нормализует пробелы: подряд идущие пробелы, переносы строк и неразрывные пробелы сравниваются как один обычный пробел. Поэтому ожидаемое значение можно писать так, как его видит человек, не думая о том, как сумма отформатирована в разметке.

Хороший набор проверок для корзины: количество строк в таблице, сумма и счётчик в шапке. Каждая ловит свой класс дефектов: товар не добавился, сумма не учитывает количество, счётчик рассинхронизирован.

:::mistake
**`expect(await locator.isVisible()).toBe(true)`.** Выглядит как проверка видимости, но это разовый вопрос без ожидания. Если элемент появится через 100 мс, тест упадёт. Правильно: `await expect(locator).toBeVisible()`. То же с `textContent()`, `count()`, `inputValue()` — для них есть ожидающие `toHaveText`, `toHaveCount`, `toHaveValue`.
:::

:::deep Мягкие проверки
`expect.soft(...)` не останавливает тест при несовпадении: ошибка запоминается, тест идёт дальше и в конце помечается упавшим со всеми ошибками сразу. Это удобно, когда на одной странице нужно проверить несколько независимых полей (название, цену, остаток) и увидеть все расхождения за один прогон. Но после мягкой проверки ключевого условия (вход выполнен, товар добавлен) продолжать тест бессмысленно — такие условия проверяют обычным `expect`.
:::

:::tech Сообщение и таймаут проверки
Вторым аргументом `expect` можно передать собственное сообщение: `expect(locator, 'счётчик корзины после добавления').toHaveText('1')` — оно появится в отчёте вместо общего текста. Таймаут меняют для одной проверки (`toHaveText('1', { timeout: 10_000 })`), для группы через `expect.configure({ timeout })` или для всего проекта через `expect: { timeout }` в конфигурации.
:::

:::interview
**Вопрос:** «Чем `await expect(locator).toHaveText('1')` отличается от `expect(await locator.textContent()).toBe('1')`?» **Ответ по сути:** первая — web-first проверка: Playwright повторяет поиск и сравнение до таймаута и пишет в сообщение локатор, ожидаемое и полученное. Вторая читает текст один раз в произвольный момент и сравнивает строку; она не ждёт обновления страницы и поэтому нестабильна.
:::
