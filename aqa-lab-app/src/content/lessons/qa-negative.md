:::why
Пользователи ошибаются, а злоумышленники пробуют запрещённое специально. Система должна не только правильно работать на правильных данных, но и правильно **отказывать**: понятно, предсказуемо и без побочных эффектов. Если это не проверять, первым это проверит production.
:::

## Позитивные и негативные проверки

[[positive-testing|Позитивная проверка]] подтверждает, что допустимое действие работает: промокод SPRING на 2000 ₽ даёт 1800 ₽, товар добавляется в корзину, заказ оформляется.

[[negative-testing|Негативная проверка]] подтверждает, что недопустимое действие отклоняется: неизвестный промокод не принимается, нельзя положить в корзину 0 штук, нельзя оформить заказ без входа.

Почему мало только позитивных? Представьте функцию промокода, которая на любой неизвестный код молча возвращает исходную сумму. Позитивные тесты проходят: SPRING работает, без кода — тоже. А пользователь вводит «SPRNG» с опечаткой, не видит ошибки, оплачивает полную сумму и пишет в поддержку. Дефект есть, позитивные тесты его не замечают.

## Что значит «правильно отказать»

Негативная проверка — это не только «случилась ошибка». У правильного отказа три признака:

1. **Ожидаемый вид отказа.** В API — определённый код ответа (400, 401, 404, 409, 422) и понятное сообщение. В UI — текст ошибки рядом с полем. В функции — исключение.
2. **Нет побочных эффектов.** Отказ не должен частично выполнить действие: заказ не создан, деньги не списаны, корзина не изменилась.
3. **Система продолжает работать.** После отказа можно исправить ввод и повторить.

API учебного магазина отказывает так:

| Запрос | Почему недопустим | Ответ |
|---|---|---|
| `POST /api/cart {"productId": 3, "qty": 0}` | количество меньше 1 | 400 |
| `POST /api/cart {"productId": 999}` | такого товара нет | 404 |
| `POST /api/cart {"productId": 2, "qty": 5}` | на складе 3 штуки | 409 |
| `POST /api/orders` без входа | пользователь неизвестен | 401 |
| `POST /api/orders` с пустой корзиной | нечего оформлять | 422 |

Хорошая негативная проверка смотрит и на код, и на отсутствие эффекта:

```ts tests/cart-api.spec.ts
import { test, expect } from '@playwright/test';

test('нельзя положить в корзину 0 штук', async ({ request }) => {
  const res = await request.post('/api/cart', { data: { productId: 3, qty: 0 } });
  expect(res.status()).toBe(400);
  const cart = await (await request.get('/api/cart')).json();
  expect(cart.count).toBe(0); // корзина не изменилась
});
```

## Где брать негативные случаи

Из тех же классов эквивалентности: каждый «недопустимый» класс — кандидат на негативную проверку. Ещё полезные источники:

- **пустое и отсутствующее**: пустая строка, `null`, поле не передано;
- **неверный тип**: строка вместо числа, дробное вместо целого;
- **неверное состояние**: оформить заказ с пустой корзиной, оплатить отменённый заказ;
- **чужие права**: открыть чужой заказ, действие без входа;
- **границы**: значение сразу за допустимым.

:::mistake
Перестараться с отказами. Если функция начинает отклонять пустое поле промокода, это тоже дефект: пользователь без промокода не сможет оформить заказ. Поэтому рядом с негативными проверками держат позитивные на соседних значениях: пустой код — сумма без изменений, ровно 1000 ₽ — скидка действует.
:::

:::try Проверьте отказы промокода
Правила: `null` или пустая строка — без скидки; `SPRING` — скидка 10 % при сумме от 1000 ₽, при меньшей — ошибка; любой другой код — ошибка. Стартовые тесты только позитивные. Допишите проверки, которые поймают четыре сломанные версии.
:::

```widget
{"type":"exercise","id":"m2-promo-negative"}
```

:::happened
Две сломанные версии «слишком добрые»: молча принимают неизвестный код и дают скидку на любую сумму. Их ловят негативные проверки с `expectThrows`. Две другие — «слишком строгие»: отклоняют пустое поле и ровно 1000 ₽. Их ловят позитивные проверки на значениях рядом с отказами. Полный набор проверяет обе стороны: что недопустимое отклоняется и что допустимое не задето.
:::

:::deep Негативное тестирование и безопасность
Многие уязвимости — это недостающие отказы: сервер принимает отрицательное количество (и возвращает деньги), отдаёт чужой заказ по номеру, принимает SQL в поле поиска. Негативные проверки прав доступа и некорректного ввода — первая линия, которую видит тестировщик. Глубокое тестирование безопасности — отдельная дисциплина, но базовые негативные случаи должны быть в обычном наборе.
:::

:::tech Отказ в коде и отказ в API
В коде отказ обычно — исключение, и тест проверяет, что оно брошено (`expectThrows`, в Playwright Test — `expect(() => …).toThrow()`). В HTTP отказ — код 4xx и тело с описанием ошибки. Сервер не должен отвечать 500 на неверный ввод клиента: 500 означает «сломался сервер», а не «клиент прислал плохие данные». Ответ 500 на негативный запрос — сам по себе дефект.
:::

:::interview
**Вопрос:** «Приведите негативные проверки для формы входа.» **Ответ по сути:** неверный пароль, несуществующий email, пустые поля, неактивный пользователь — во всех случаях отказ с понятным сообщением, без входа; одинаковый ответ для «нет пользователя» и «неверный пароль», чтобы не раскрывать, какие email зарегистрированы; поведение после нескольких неудачных попыток. И позитивная проверка рядом — правильные данные входят.
:::
