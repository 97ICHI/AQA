:::why
Код ответа — первое, что сообщает сервер: получилось, отказано или сломалось. Если тест проверяет только тело ответа или только то, что «нет ошибки», он пропускает целый класс дефектов: сервер отвечает 200 там, где должен 201, или 500 там, где должен вежливо отказать. А повтор одного и того же запроса — частая ситуация в сети, и поведение при повторе тоже нужно проверять.
:::

## Классы кодов

[[status-code|Код ответа]] — трёхзначное число. Первая цифра задаёт класс:

| Класс | Смысл | Примеры |
|---|---|---|
| 2xx | успех | 200 OK, 201 Created, 204 No Content |
| 3xx | перенаправление | 302 Found — «идите по другому адресу» |
| 4xx | ошибка клиента: запрос неправильный или недопустимый | 400, 401, 403, 404, 409, 422 |
| 5xx | ошибка сервера: запрос мог быть нормальным, сломался сервер | 500, 502, 503 |

Главное различие для тестировщика — **4xx или 5xx**. На неправильный ввод сервер должен ответить 4xx: «клиент, исправь запрос». Ответ 500 на неверные данные — дефект: сервер не проверил ввод и упал.

## Какой код ожидать

Код выбирают по смыслу ситуации. В учебном магазине:

| Ситуация | Код | Почему |
|---|---|---|
| `GET /api/products` | 200 | данные успешно получены |
| `POST /api/orders` — заказ создан | 201 | создан новый ресурс |
| `POST /api/cart` с `qty: 0` | 400 | запрос неверно составлен |
| `POST /api/orders` без входа | 401 | сервер не знает, кто вы |
| `GET /api/orders/101` чужой заказ | 403 | сервер знает вас, но это не ваше |
| `POST /api/cart` с несуществующим товаром | 404 | ресурс не найден |
| `POST /api/cart` больше, чем на складе | 409 | конфликт с текущим состоянием |
| `POST /api/orders` с пустой корзиной | 422 | запрос понятен, но выполнить нельзя |

Разница между соседними кодами важна клиенту: на 401 приложение покажет форму входа, на 403 — «нет доступа», на 404 — «не найдено». Если сервер на всё отвечает 400, клиент не может отреагировать правильно.

:::mistake
Проверять `response.ok()` вместо конкретного кода. `ok()` истинен для любого 2xx: тест пройдёт и при 200 вместо 201. В учебном магазине есть дефект «API создания заказа отвечает 200 вместо 201» — его ловит только `expect(res.status()).toBe(201)`.
:::

## Идемпотентность

Сеть ненадёжна. Клиент отправил запрос, ответ потерялся — и клиент (или прокси, или пользователь, нажав кнопку ещё раз) повторяет запрос. Что будет с данными?

Операция [[idempotency|идемпотентна]], если повтор не меняет результат: один раз или пять — состояние сервера одинаковое.

- `GET` — идемпотентен: чтение ничего не меняет.
- `PUT` и `DELETE` по смыслу идемпотентны: «установить количество = 2» или «удалить позицию» дважды дают то же, что один раз.
- `POST` — не идемпотентен: каждое «добавить в корзину» добавляет ещё одну штуку, каждое «оформить заказ» создаёт новый заказ.

Для тестировщика отсюда два вопроса: **не меняет ли данные то, что должно только читать?** И **что будет при повторе изменяющего запроса** — двойной клик «Оплатить» не должен списать деньги дважды. Серьёзные платёжные API для этого принимают ключ идемпотентности: повтор с тем же ключом не выполняет операцию заново.

:::deep 401 и 403: почему так называются
Исторически 401 называется «Unauthorized», хотя означает «не аутентифицирован» — сервер не знает, кто вы. 403 «Forbidden» — «знаю, кто вы, но нельзя». Подробнее — в следующем уроке. Встречается и сознательное отступление: на чужой ресурс некоторые API отвечают 404, чтобы не раскрывать, что такой ресурс существует. Какой код правильный в вашем проекте — решает требование, тест проверяет его.
:::

:::tech PUT, PATCH и безопасные методы
Кроме идемпотентности, методы делят на «безопасные» — не меняющие состояние (`GET`, `HEAD`, `OPTIONS`). Безопасный метод всегда идемпотентен, обратное неверно: `DELETE` идемпотентен, но не безопасен. `PATCH` в общем случае не идемпотентен (например, «увеличить на 1»). Это свойства, которые обещает спецификация HTTP; реализация сервера может их нарушать — именно это и проверяют тесты.
:::

:::interview
**Вопрос:** «Чем отличаются 400, 401, 403, 404 и 422? Что такое идемпотентность?» **Ответ по сути:** 400 — неверно составленный запрос; 401 — нет аутентификации; 403 — нет прав у известного пользователя; 404 — ресурс не найден; 422 — запрос понятен, но не проходит бизнес-правила. Идемпотентность — повтор операции не меняет итоговое состояние: GET, PUT, DELETE — да, POST — нет. Проверяю это повтором запроса и сравнением состояния.
:::
