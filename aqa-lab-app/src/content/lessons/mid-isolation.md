:::why
Тесты, которые по отдельности стабильны, начинают падать, когда их запускают параллельно или в другом порядке. Причина почти всегда одна: два теста трогают общие данные. Чем больше набор и workers, тем чаще такие конфликты, поэтому изоляция — обязательное свойство тестов уровня Middle, а не «приятное дополнение».
:::

## Что значит изолированный тест

[[test-isolation|Изолированный тест]] не зависит от других тестов и не влияет на них: его можно запустить первым, последним, отдельно, параллельно с любыми другими — результат тот же. Нарушают изоляцию:

- **общий пользователь** — два теста входят под одним аккаунтом и меняют одну корзину;
- **общие записи** — тест редактирует товар, который другой тест проверяет;
- **оставленное состояние** — тест не убрал за собой, следующий начинает «не с нуля»;
- **[[order-dependency|зависимость от порядка]]** — тест B рассчитывает, что тест A уже создал заказ.

Playwright по умолчанию даёт каждому тесту свой [[browser-context|контекст браузера]]: свои cookie, localStorage, кэш. Браузерная часть изолирована. Но данные на сервере общие для всех: если два теста работают под одним пользователем, сервер видит одного пользователя.

## Пример конфликта

Два теста параллельно входят под `anna@example.test`. Первый добавляет блокнот и ждёт итог 390 ₽. Второй в это же время очищает корзину Анны и проверяет «Корзина пуста». В зависимости от того, кто успел первым, падает то один, то другой. По отдельности оба зелёные — классическая картина [[shared-state|общего состояния]].

Способы развести тесты:

| Способ | Когда подходит |
|---|---|
| Уникальные данные на тест (новый пользователь, товар с уникальным именем) | есть API или фабрика для создания данных |
| Пул аккаунтов: по аккаунту на worker (`testInfo.parallelIndex`) | создавать пользователей дорого |
| Только чтение общих справочников | данные, которые никто не меняет |
| Очистка в фикстуре после теста | созданное нельзя оставлять (лимиты, отчёты) |
| `test.describe.configure({ mode: 'serial' })` | крайний случай: шаги действительно зависят друг от друга |

## Два пользователя в одном тесте

Иногда сама проверка — про изоляцию: «корзина одного покупателя не видна другому». Для этого нужны два независимых пользователя в одном тесте. Частая ошибка — открыть вторую вкладку:

```ts tests/cart-isolation.spec.ts
  const anna = await browser.newContext();
  const boris = await browser.newContext();
  try {
    // ... действия Анны в anna.newPage(), проверки Бориса в boris.newPage()

    await anna.close();
    await boris.close();
  }
});
```

Контексты, созданные вручную, закрывает тот, кто их создал: фикстура `page` закрывается сама, а эти — нет.

## Как найти конфликт

Конфликт данных воспроизводят давлением параллельности и сменой порядка:

```bash
npx playwright test --workers=4 --repeat-each=5        # больше одновременных тестов
npx playwright test tests/cart.spec.ts --workers=1      # проходит последовательно? значит, конфликт
npx playwright test -g "пустая корзина"                 # падает отдельно? значит, зависит от порядка
```

Если тест падает только в паре с конкретным другим тестом — ищите общий аккаунт или запись. В trace обоих тестов сравните время запросов: изменение, сделанное одним тестом, видно в ответах другого.

:::deep Аккаунт на worker
Создавать пользователя на каждый тест может быть дорого (регистрация, подтверждение почты). Компромисс — аккаунт на worker: фикстура с `{ scope: 'worker' }` берёт аккаунт из пула по `workerInfo.parallelIndex`. Тесты одного worker идут последовательно и не конфликтуют, разные workers работают с разными аккаунтами. Цена: тесты одного worker делят состояние аккаунта, поэтому каждый тест всё равно приводит его к известному состоянию в начале (например, очищает корзину через API).
:::

:::tech fullyParallel и порядок
По умолчанию Playwright распределяет по workers файлы, а тесты внутри файла выполняются по порядку. `fullyParallel: true` распределяет отдельные тесты, и скрытые зависимости внутри файла сразу проявляются. Поэтому включение `fullyParallel` — хороший тест на изоляцию: если после него что-то сломалось, это было сломано и раньше, просто не было видно.
:::

:::interview
**Вопрос:** «Тесты проходят по одному и падают параллельно. Что делаете?» **Ответ по сути:** это почти всегда общее состояние: один аккаунт, одна запись, неубранные данные или зависимость от порядка. Воспроизвожу (`--workers`, `--repeat-each`, запуск отдельно), нахожу общий ресурс по trace и логам. Исправляю изоляцией: уникальные данные на тест или аккаунт на worker, подготовка и очистка в фикстурах. `serial` и `workers: 1` — не исправление, а маскировка.
:::
