:::why
API ответил `201` и вернул сумму заказа — но сохранил ли магазин то же самое? Ответ API может быть правильным, а запись в базе — нет: потерялась позиция, цена взялась старая, оплата записалась дважды. Проверка в базе после API-действия ловит именно такие дефекты.
:::

## Сценарий проверки

Тест оформляет заказ через API, получает его `id` и по этому `id` проверяет базу. Четыре шага:

1. **Действие** — `POST /api/orders`, ответ `201` с `{ id, total, items }`.
2. **Найти запись** — только по `id` из ответа. Не «последний заказ пользователя» и не «заказ за сегодня»: при параллельном запуске это может оказаться чужой заказ.
3. **Сравнить поля** — статус, владелец, позиции, цены, сумма.
4. **Сверить связанные данные** — сумма позиций равна сумме в ответе API; оплаты, остатки.

```ts tests/api/order-db.spec.ts
import { test, expect, type APIRequestContext } from '@playwright/test';

// учебный магазин: POST /__test/sql выполняет один SELECT с параметрами
async function sql(request: APIRequestContext, text: string, params: unknown[]) {
  const res = await request.post('/__test/sql', { data: { sql: text, params } });
  expect(res.ok()).toBeTruthy();
  return (await res.json()).rows;
}

test('заказ сохраняется с теми же позициями и суммой', async ({ request }) => {
  await request.post('/api/login', { data: { email: 'anna@example.test', password: 'learn-123' } });
  await request.post('/api/cart', { data: { productId: 3, qty: 2 } }); // 2 × «Блокнот A5»
  const res = await request.post('/api/orders');
  expect(res.status()).toBe(201);
  const order = await res.json();

  const rows = await sql(request, 'SELECT status, user_id FROM orders WHERE id = $1', [order.id]);
  expect(rows).toEqual([{ status: 'new', user_id: 1 }]);

  const [{ total }] = await sql(request,
    'SELECT COALESCE(SUM(qty * price), 0) AS total FROM order_items WHERE order_id = $1', [order.id]);
  expect(Number(total)).toBe(order.total);   // numeric приходит строкой '780.00'
});
```

`$1` в запросе — параметр: значение `order.id` передаётся отдельно от текста SQL. Почему это обязательно — в следующем уроке.

## Что именно сравнивать

| Проверка | Запрос | Какой дефект ловит |
|---|---|---|
| Заказ существует, статус и владелец верные | `SELECT status, user_id FROM orders WHERE id = $1` | заказ создан не тому пользователю |
| Позиции совпадают с корзиной | `SELECT product_id, qty, price FROM order_items WHERE order_id = $1 ORDER BY product_id` | потерянная или лишняя позиция |
| Цена позиции = цена в каталоге на момент заказа | `JOIN products` и сравнение `i.price = p.price` | цена взята из устаревшего кеша |
| Сумма позиций = сумма в ответе API | `SUM(qty * price)` | API считает одно, сохраняет другое |
| Сумма успешных оплат = сумма позиций | `SUM(amount) … WHERE status = 'ok'` | двойное списание, оплата не записана |

Две ловушки, знакомые по прошлым урокам. Первая — **размножение строк**: если соединить заказ сразу с позициями и с оплатами, суммы умножатся. Каждую сумму считают отдельно. Вторая — **`NULL` вместо нуля**: у заказа без оплат `SUM(amount)` — `NULL`, и сравнение `<>` с ним ничего не находит. Помогает `COALESCE(SUM(…), 0)`.

У заказа 101 сумма позиций 5770 и успешно оплачено 5770 — данные согласованы. У 105 две попытки оплаты, но учтена только успешная, поэтому суммы снова совпадают. У 102 оплат нет, и `COALESCE` превратил `NULL` в 0 — для заказа в статусе `new` это нормально, а для `paid` было бы дефектом. ## Как тест получает доступ к базе

В учебном магазине есть маршрут `POST /__test/sql`, который выполняет один `SELECT` с параметрами — только для тестов. На реальных проектах варианты такие: прямое подключение к базе тестового стенда (строка подключения из переменных окружения), отдельная read-only учётная запись или служебный API. Писать в базу приложения из E2E-теста стоит только для подготовки и очистки своих данных.

:::deep Сравнение чисел и денег
`numeric` из PostgreSQL драйверы обычно отдают строкой (`'5770.00'`), чтобы не терять точность. В тесте его приводят к тому же виду, что и ответ API: `Number('5770.00') === 5770`. Для денег надёжнее сравнивать в копейках (`Math.round(Number(x) * 100)`) или строками с двумя знаками. Если API отдаёт сумму строкой, а контракт обещает число, это отдельный дефект — его ловит проверка типа в ответе, а не в базе.
:::

:::tech Задержка записи
Некоторые системы пишут в базу асинхронно: ответ API приходит раньше, чем фоновая задача сохранит заказ или оплату. Тогда проверка в базе сразу после ответа нестабильна. Правильный подход — опрашивать базу с таймаутом (`expect.poll` в Playwright) и явно указывать, сколько ждать, а не ставить фиксированную паузу.
:::

:::interview
**Вопрос:** «Как проверить, что API создал заказ корректно?» **Ответ по сути:** проверить ответ (статус, схему, поля), затем найти запись в базе по `id` из ответа и сравнить статус, владельца, позиции и суммы; сумму позиций сверить с ответом и с успешными оплатами. Запросы — параметризованные, суммы — каждая отдельно, чтобы соединение не размножило строки.
:::
