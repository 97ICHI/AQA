:::why
Пока тестов десять, их можно держать в одном файле. Когда их двести, каждое изменение интерфейса или API заставляет править десятки мест, а новичок в команде не понимает, куда положить новый тест. Структура проекта решает это: у каждой части своя ответственность, и изменение затрагивает одно место.
:::

## Слои тестового проекта

Тестовый проект удобно делить на слои — каждый знает только о соседнем снизу:

| Слой | Что в нём | Что не должно в нём быть |
|---|---|---|
| Тесты (`tests/`) | сценарий и проверки на языке предметной области | селекторы, URL, сборка JSON |
| Фикстуры (`fixtures/`) | подготовка и очистка: вошедший пользователь, корзина, API-клиент | проверки бизнес-результата |
| Страницы и компоненты (`pages/`) | Page Object: локаторы и действия страницы | `expect` бизнес-результата |
| API-клиенты (`api/`) | методы `addToCart`, `createOrder`, проверка кода ответа | сценарии из нескольких шагов |
| Данные (`data/`) | фабрики и константы тестовых данных | обращения к сети |
| Конфигурация | `playwright.config.ts`, переменные окружения | логика тестов |

[[fixture|Фикстуры]] готовят состояние, [[page-object-model|Page Object]] скрывает устройство страницы, [[api-client|API-клиент]] — устройство HTTP-запросов. Такое деление — [[separation-of-concerns|разделение ответственности]]. Изменилась вёрстка корзины — правим `pages/cart-page.ts`. Изменился путь API — правим `api/shop-api.ts`. Тесты остаются прежними.

```text
tests/
  cart.spec.ts
  order.spec.ts
  api/orders.api.spec.ts
fixtures/
  index.ts            # test = base.extend({...}) — один импорт для всех тестов
pages/
  catalog-page.ts
  cart-page.ts
api/
  shop-api.ts
data/
  users.ts
playwright.config.ts
```

## Как слои соединяются

Тест импортирует `test` не из `@playwright/test`, а из своих фикстур. Фикстура создаёт клиента и страницы и отдаёт их тесту:

```ts fixtures/index.ts
import { test as base, expect, type APIRequestContext } from '@playwright/test';

export class ShopApi {
  constructor(private readonly http: APIRequestContext) {}

  async addToCart(productId: number, qty = 1) {
    const res = await this.http.post('/api/cart', { data: { productId, qty } });
    // сбой подготовки должен быть понятен сразу, а не через три шага
    if (res.status() !== 200) throw new Error(`POST /api/cart: ожидался 200, получен ${res.status()} ${await res.text()}`);
    return res.json();
  }
}

export const test = base.extend<{ shopApi: ShopApi }>({
  shopApi: async ({ page }, use) => {
    await use(new ShopApi(page.request)); // page.request делит cookie со страницей
  },
});
export { expect };
```

```ts tests/cart.spec.ts
import { test, expect } from '../fixtures';

test('итог корзины учитывает количество', async ({ page, shopApi }) => {
  await shopApi.addToCart(3, 2);                                  // подготовка — через API
  await page.goto('/cart');
  await expect(page.getByTestId('cart-total')).toHaveText('780 ₽'); // проверка — в тесте
});
```

Тест читается как сценарий: подготовка, действие, проверка. Где лежит корзина в API, как называется поле — знает только клиент.

## Где проверки

Частый спор: можно ли писать `expect` в Page Object или клиенте? Практичное правило: **проверка бизнес-результата — в тесте**, а в нижних слоях — только проверки, без которых дальнейший шаг бессмысленен («подготовка удалась», «страница загрузилась»). Если Page Object сам проверяет итог корзины, тест, которому нужен другой итог или его отсутствие, уже не сможет его использовать.

:::mistake
«Божественный» Page Object на всё приложение: тысяча строк, методы `loginAndAddToCartAndCheckout()`. Такой класс невозможно переиспользовать и страшно менять. Делите по страницам и компонентам (шапка, карточка товара), а сценарии оставляйте тестам.
:::

:::try Слой API-клиента
Транспортный слой должен делать одно: превращать неожиданный ответ в понятную ошибку. Допишите клиента — транспорт передаётся снаружи, как `page.request` в примере выше.
:::

```widget
{"type":"exercise","id":"m9-structure-client"}
```

:::happened
Клиент сравнивает точный код ответа и бросает ошибку с методом, путём и статусом. Тест, у которого не удалась подготовка, падает на строке подготовки с сообщением «POST /api/cart: ожидался 200, получен 409», а не на проверке итога с непонятным `Received: "0 ₽"`. Время разбора падения сокращается с минут до секунд.
:::

:::deep Сколько абстракций достаточно
Каждый слой — это код, который нужно поддерживать. Для 20 тестов хватит фикстур и пары Page Object. Для сотен — добавляются фабрики данных, отдельные проекты Playwright для API и UI, общие компоненты страниц. Признак лишней абстракции: чтобы понять, что делает тест, нужно открыть пять файлов. Признак недостающей: одно изменение интерфейса требует правки в десяти тестах. Принцип DRY в тестах применяют осторожнее, чем в продукте: немного повторения в теле теста (DAMP) часто лучше, чем помощник с пятью флагами.
:::

:::tech Конфигурация и окружения
Адрес стенда, учётные данные и флаги приходят из переменных окружения, а не зашиты в тесты: `baseURL: process.env.BASE_URL || 'http://127.0.0.1:3000'`. Разные наборы (API, UI, smoke) удобно оформить как [[project-pw|projects]] в `playwright.config.ts` с разными `testMatch` и настройками. Секреты читаются из окружения CI; локально — из `.env`, который не коммитится.
:::

:::interview
**Вопрос:** «Как устроен ваш тестовый проект?» **Ответ по сути:** тесты описывают сценарии и проверки; фикстуры готовят и чистят состояние; Page Object и компоненты инкапсулируют локаторы; API-клиенты — запросы и проверку кодов ответа; данные — через фабрики; конфигурация — через переменные окружения. Проверки бизнес-результата — только в тестах. Изменение интерфейса или API правится в одном месте.
:::
