:::why
Если регрессия идёт час, её запускают раз в день, а разработчик узнаёт о поломке, когда уже переключился на другую задачу. Ускорить прогон просто, если выбросить проверки. Задача Middle-инженера — ускорить, **не потеряв** того, что тесты ловят, и уметь объяснить, где проходит граница.
:::

## Сначала измерить

Оптимизация без измерений — угадывание. Источники данных:

- HTML-отчёт и JSON-отчёт: длительность каждого теста — самые медленные 10 % обычно дают половину времени;
- trace медленного теста: какие шаги занимают время — вход, навигация, ожидания;
- время задачи CI целиком: установка зависимостей и браузеров, сборка образа, загрузка артефактов — иногда это дольше самих тестов.

Типичная картина UI-набора: 60–70 % времени каждого теста уходит на подготовку (вход через форму, наполнение корзины кликами), а сама проверка занимает секунды.

## Приёмы, которые не теряют проверок

| Приём | Что экономит | Цена |
|---|---|---|
| Подготовка через API вместо UI | клики по каталогу и формам в каждом тесте | UI подготовки проверяется отдельным тестом |
| Вход один раз: storageState | форма входа в каждом тесте | сессия общая — нельзя тестам, меняющим профиль |
| Ожидание состояния вместо `waitForTimeout` | «запасные» секунды пауз | нет |
| Проверка на нижнем уровне (пирамида) | браузер для проверки правила расчёта | нужен API- или unit-тест |
| Параллельность, шарды | время «по часам» | больше ресурсов, нужна изоляция |
| Кэш зависимостей и браузеров в CI | минуты установки | настройка кэша |

Подготовка через API — самый большой выигрыш. Сессию для входа сохраняют в [[storage-state|storageState]], правило «проверять как можно ниже» — это [[test-pyramid|пирамида тестов]], а [[sharding|шардирование]] делит набор между машинами. Тест «итог корзины» должен проверить итог, а не каталог; каталог и кнопку «В корзину» проверяет свой тест, один раз.

:::note
В таблице нет «удалить медленные тесты» и «уменьшить таймауты». Первое теряет проверки, второе делает тесты нестабильными: таймаут — это предел ожидания, а не его длительность. Хороший тест с таймаутом 10 с на исправной системе ждёт столько, сколько нужно, — обычно доли секунды.
:::

## API-подготовка и сессия браузера

Здесь легко ошибиться. В Playwright есть два HTTP-клиента:

- фикстура `request` — отдельный [[api-request-context|APIRequestContext]] со своим хранилищем cookie;
- `page.request` (то же, что `page.context().request`) — клиент, который делит cookie с контекстом страницы.

Вход через `request` создаёт сессию, о которой браузер ничего не знает.

:::try Подготовка, которую страница не видит
Тест входит через API и кладёт в корзину два блокнота, затем открывает корзину в браузере. Запустите его.
:::

## Вход один раз на весь прогон

Если сценарию нужен вошедший пользователь, но не нужна сама форма входа, вход выполняют один раз в setup-проекте и сохраняют cookie в файл:

```ts tests/auth.setup.ts
import { test as setup, expect } from '@playwright/test';

setup('вход Анны', async ({ page }) => {
  const res = await page.request.post('/api/login', { data: { email: 'anna@example.test', password: process.env.SHOP_PASSWORD } });
  await expect(res).toBeOK();
  await page.context().storageState({ path: '.auth/anna.json' });
});
```

Проект с тестами указывает `dependencies: ['setup']` и `use: { storageState: '.auth/anna.json' }` — каждый тест стартует уже вошедшим. Каталог `.auth/` добавляют в `.gitignore`: в нём действующая сессия.

Ограничение: все тесты получают одного пользователя. Тесты, меняющие его данные (корзину, профиль), снова конфликтуют при параллельном запуске — нужны аккаунты на worker или своя подготовка состояния.

:::deep Что можно и что нельзя перенести вниз
Правило расчёта суммы (скидки, округление, количество) — логика сервера: её дешевле и полнее проверить API- или unit-тестами на десятках комбинаций. В UI достаточно одного теста, что итог из API **отображается**. А вот то, что существует только в браузере — блокировка кнопки, валидация формы на клиенте, переходы, доступность, — переносить вниз нельзя. Граница проходит по вопросу: «где живёт поведение, которое я проверяю?».
:::

:::tech Где ещё теряется время в CI
Установка браузеров: кэшируйте `~/.cache/ms-playwright` по версии Playwright или используйте официальный образ. `npm ci` с кэшем npm. Сборка Docker-образа: порядок слоёв и кэш сборки. Видео (`video: 'on'`) заметно замедляет прогон — включайте `retain-on-failure` или только для отладки. Ресурсы исполнителя: workers больше, чем ядер, не ускоряют, а приводят к таймаутам.
:::

:::interview
**Вопрос:** «Регрессия идёт 90 минут. Как ускорить?» **Ответ по сути:** измерить, где время (отчёт, trace, этапы CI). Затем: подготовка данных через API, вход один раз через storageState, убрать паузы, перенести проверки правил на API/unit-уровень, параллельность и шардирование при изолированных данных, кэш зависимостей. Не удалять проверки и не уменьшать таймауты вслепую; сравнить, что набор ловит те же дефекты.
:::
