:::why
На новом проекте никто не скажет, какие тесты писать первыми. Можно месяц автоматизировать всё подряд через интерфейс и получить медленный, хрупкий набор, который не ловит главного. Стратегия отвечает на вопросы «что, на каком уровне, в каком порядке и зачем» — и её на собеседовании Middle-уровня просят набросать за 10–15 минут.
:::

## С чего начать: вопросы, а не инструменты

Первые дни уходят не на код, а на понимание продукта и рисков:

- **Что критично для бизнеса?** Для магазина — вход, корзина, оформление заказа, оплата. Поломка здесь стоит денег каждую минуту.
- **Где чаще ломается?** История дефектов, частые изменения, сложные модули, интеграции.
- **Как устроена система?** Есть ли API, отдельный фронтенд, база, внешние сервисы; есть ли тестовый стенд и способ создавать данные.
- **Как выпускается продукт?** Как часто релизы, есть ли CI, кто и когда запускает проверки.
- **Что уже есть?** Unit-тесты разработчиков, ручные чек-листы, мониторинг.

Ответы дают карту [[risk-based-testing|рисков]]: вероятность поломки × цена поломки. Автоматизация начинается с верхнего правого угла этой карты.

## Уровни: что где проверять

[[test-pyramid|Пирамида]] — не догма, а принцип: проверяйте на самом низком уровне, где живёт поведение.

| Уровень | Что проверяем в магазине | Свойства |
|---|---|---|
| Unit (разработчики) | расчёт суммы, скидки, округление | миллисекунды, сотни комбинаций |
| API | коды ответов, права доступа, контракт, сохранение заказа | секунды, без браузера |
| UI / E2E | вход → корзина → заказ глазами пользователя, критичные формы | дорого, мало, но «как у пользователя» |
| Ручное / исследовательское | новое, удобство, визуальное | человек, не автоматизируется |

На учебном магазине: правило «сумма учитывает количество» — API-тест с разными количествами; «итог виден в корзине» — один UI-тест; «чужой заказ недоступен» — API-тест на 403; сквозной сценарий заказа — один E2E-тест в smoke-наборе.

## План по этапам

1. **Каркас (1–2 недели).** Проект, линтер, проверка типов, конфигурация окружений, запуск в CI с отчётом и trace. Один сквозной smoke-тест критичного пути. Без каркаса каждый следующий тест дороже.
2. **API-слой критичных функций.** Клиенты, фабрики данных, тесты прав доступа и контрактов. Здесь больше всего проверок на единицу времени.
3. **UI критичных сценариев.** Page Object и компоненты, подготовка через API, вход через storageState.
4. **Расширение по рискам** и регулярный пересмотр: что ловит набор, что пропускает, какие тесты нестабильны.

Каждый этап заканчивается работающим результатом в CI, а не «фреймворком, который скоро заработает».

## Компромиссы, которые надо проговорить

- **Скорость против полноты.** Smoke на каждый merge request (минуты), полная регрессия по расписанию (десятки минут).
- **Изоляция против стоимости данных.** Уникальные пользователи на тест надёжнее, аккаунт на worker дешевле.
- **Стабильность против реалистичности.** Мок внешней оплаты стабилен, но не проверяет интеграцию — её проверяют отдельным небольшим набором на песочнице.
- **Окупаемость.** [[test-automation-roi|Автоматизация окупается]], когда проверку повторяют часто, а поддержка теста дешевле ручного прогона. Разовые проверки и активно меняющиеся фичи автоматизировать рано.

:::mistake
«Автоматизируем 100 % ручных тест-кейсов через UI». Получается медленный, хрупкий набор, дублирующий проверки, которые дешевле сделать на API, а метрика «процент автоматизации» ничего не говорит о том, ловятся ли важные дефекты.
:::

## Smoke-набор в бюджете времени

Типичная задача из стратегии: «smoke на каждый merge request — не дольше двух минут». Критичный путь входит всегда, остальное — по риску и стоимости.

:::try Выбор smoke-проверок
Формализуйте этот выбор: критичные проверки обязательны, остальные — по убыванию риска, при равном риске — более дешёвые.
:::

```widget
{"type":"exercise","id":"m10-design-smoke"}
```

:::happened
Жадный выбор не даёт математического оптимума, зато предсказуем и легко объясним команде: «вход и заказ — всегда; дальше — промокоды и итог корзины, потому что они ломались чаще всего». Если критичные проверки не помещаются в бюджет, функция падает: это повод обсудить бюджет или ускорить тесты, а не молча убрать оплату из smoke.
:::

:::deep Как понять, что стратегия работает
Метрики, которые что-то значат: доля дефектов, найденных автотестами до релиза; время от коммита до результата (feedback loop); доля нестабильных прогонов; время разбора падения. Метрики, которые вводят в заблуждение: число тестов, процент автоматизации тест-кейсов, покрытие кода само по себе. Полезная практика — [[mutation-testing|контролируемое внесение дефектов]]: сломать расчёт суммы и убедиться, что набор это поймал (в учебном проекте это делает отдельная задача CI).
:::

:::tech Выбор инструментов
Выбор стека определяют команда и продукт: на чём пишут разработчики (общий язык упрощает ревью и помощь), какие браузеры и платформы нужны, есть ли мобильные клиенты. Playwright + TypeScript закрывает UI и API в одном проекте, с trace, параллельностью и отчётами из коробки. Для нагрузочного тестирования, мобильных приложений и контрактов нужны отдельные инструменты — в стратегии их стоит назвать, даже если внедрение позже.
:::

:::interview
**Вопрос:** «Вы первый AQA на проекте интернет-магазина. Что будете делать?» **Ответ по сути:** разберусь в рисках — критичные сценарии, история дефектов, архитектура, процесс релизов. Подниму каркас с CI и отчётами и один smoke-тест критичного пути. Затем API-тесты критичных функций (права, контракты, расчёты), потом немного UI-тестов ключевых сценариев с подготовкой через API. Smoke — на каждый merge request, регрессия — по расписанию. Оцениваю по найденным дефектам, стабильности и времени обратной связи, а не по числу тестов.
:::
