:::why
Часть проверок звучит как «первый», «последний» или «самый»: последний заказ пользователя, самый дорогой товар в категории, вторая попытка оплаты. `GROUP BY` здесь не помогает — он схлопывает строки и теряет детали. Оконные функции решают такие задачи, не теряя строк. А индексы объясняют, почему проверочный запрос на большой базе вдруг выполняется минуту.
:::

## Окно: считать по группе, не схлопывая строки

[[window-function|Оконная функция]] считает значение для каждой строки по набору связанных с ней строк — *окну*. В отличие от `GROUP BY`, все строки остаются в результате, просто у каждой появляется новый столбец.

```sql queries/orders-numbered.sql
SELECT user_id, id, created_at,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at, id) AS n,
       COUNT(*)     OVER (PARTITION BY user_id)                         AS user_orders
FROM orders
ORDER BY user_id, n;
```

Разберём `OVER (…)`:

- `PARTITION BY user_id` — делит строки на окна: у каждого пользователя своё.
- `ORDER BY created_at, id` — порядок внутри окна. `id` добавлен как второй ключ: если два заказа созданы в один день, нумерация всё равно однозначна.
- `ROW_NUMBER()` — номер строки в окне: 1, 2, 3…
- `COUNT(*) OVER (PARTITION BY user_id)` — обычный агрегат, но посчитанный по окну и записанный в каждую строку.

Полезные функции: `ROW_NUMBER()` (номера без повторов), `RANK()` (равные значения получают один номер, следующий пропускается: 1, 1, 3), `DENSE_RANK()` (1, 1, 2), `LAG(col)` / `LEAD(col)` — значение из предыдущей / следующей строки окна, `SUM(col) OVER (… ORDER BY …)` — накопительная сумма.

## «Первый в группе»

Типичный приём: пронумеровать строки в каждом окне и оставить номер 1. Оконные функции вычисляются **после** `WHERE`, поэтому фильтр по номеру ставят во внешнем запросе или в CTE:

```sql queries/last-order.sql
WITH ranked AS (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC, id DESC) AS rn
  FROM orders o
)
SELECT user_id, id, status, created_at
FROM ranked
WHERE rn = 1;            -- последний заказ каждого пользователя
```

## Индексы: почему запрос медленный

Чтобы выполнить `WHERE user_id = 42`, база без подсказок просматривает таблицу целиком — Seq Scan. На пяти строках это мгновенно, на десяти миллионах — секунды. [[db-index|Индекс]] — отдельная упорядоченная структура (обычно B-tree), по которой нужные строки находятся сразу:

```sql migrations/orders-index.sql
CREATE INDEX orders_user_id_idx ON orders (user_id);
```

Первичный ключ и `UNIQUE` создают индекс автоматически. Для внешних ключей PostgreSQL индекс **не** создаёт — его добавляют вручную, если по столбцу ищут.

Понять, как база выполняет запрос, помогает `EXPLAIN`: он показывает план, не выполняя запрос (`EXPLAIN ANALYZE` — выполняет и показывает реальное время).


На маленькой таблице планировщик выберет полный просмотр даже при наличии индекса — так дешевле. Поэтому выводы о производительности делают на объёме данных, близком к реальному.

Для тестировщика индексы важны в двух случаях. Проверочные запросы на стенде с большой базой: условие по неиндексированному столбцу превращает быстрый тест в медленный. И нагрузочные/регрессионные проверки: медленный эндпоинт часто объясняется отсутствующим индексом, а `EXPLAIN` даёт разработчику конкретное доказательство.

:::deep Индекс — не бесплатно
Каждый индекс замедляет `INSERT`, `UPDATE` и `DELETE`: при изменении строки обновляются и все её индексы. Индекс занимает место и может не использоваться, если условие обёрнуто функцией (`WHERE lower(email) = …` не использует индекс по `email`; нужен индекс по выражению `lower(email)`). Уникальный индекс заодно является ограничением: он запрещает дубли.
:::

:::tech Порядок вычисления
Логический порядок с окнами: `FROM` → `WHERE` → `GROUP BY` → `HAVING` → **оконные функции** → `SELECT` → `DISTINCT` → `ORDER BY` → `LIMIT`. Поэтому `WHERE ROW_NUMBER() OVER (…) = 1` — ошибка: на шаге `WHERE` номеров ещё нет. В PostgreSQL для «первого в группе» есть и короткая форма `SELECT DISTINCT ON (category) … ORDER BY category, price DESC, title` — она тоже требует полного порядка внутри группы.
:::

:::interview
**Вопрос:** «Как найти последний заказ каждого пользователя?» **Ответ по сути:** `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC, id DESC)` в подзапросе или CTE и фильтр `rn = 1` снаружи; второй ключ сортировки обязателен для однозначности. В PostgreSQL также `DISTINCT ON (user_id)`. Вопрос-продолжение про скорость — индекс по `(user_id, created_at)` и проверка плана через `EXPLAIN`.
:::
