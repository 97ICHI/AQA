:::why
Когда тест падает «иногда», хочется увеличить таймаут, добавить паузу или включить повторы — и тест позеленеет. Причина при этом останется: тест по-прежнему не ждёт нужного состояния, а дефект, если он был, спрятан. В этом уроке вы разберёте, какие пределы времени есть в Playwright, что такое опрос (polling) и почему повтор прогона — диагностика, а не лечение.
:::

## Какие бывают таймауты

[[timeout|Таймаут]] — предел, после которого ожидание считается неудачным. В Playwright Test их несколько, и они вложены друг в друга:

| Таймаут | По умолчанию | В нашем runner | Где задаётся |
|---|---|---|---|
| Тест целиком (включая fixtures) | 30 с | 10 с | `timeout` в конфигурации, `test.setTimeout()` |
| Одна проверка `expect` | 5 с | 3 с | `expect: { timeout }`, опция `timeout` у проверки |
| Действие (`click`, `fill`…) | без отдельного предела | — | `use: { actionTimeout }`, опция `timeout` у действия |
| Навигация (`goto`, `waitForURL`) | без отдельного предела | — | `use: { navigationTimeout }` |
| Весь прогон | без предела | — | `globalTimeout` |

«Без отдельного предела» означает, что действие ограничено только таймаутом теста. Для медленного теста есть `test.slow()` — он утраивает таймаут этого теста — и `test.setTimeout(мс)`.

## Слишком маленький таймаут

Локальный таймаут на действии выглядит как способ «ускорить» тест. Но он задаёт, сколько вы готовы ждать *приложение*, — и если стенд немного медленнее, тест упадёт без дефекта.

:::try Таймаут 1 секунда на медленном магазине
Тест кликает с `timeout: 1000`, затем делает паузу и один раз читает корзину через API. Запуск — на медленном магазине, где кнопка активна через 1,5 с.
:::

## Polling: опрос значения

Ожидающие проверки работают с локатором и страницей. А если нужно дождаться значения, которого на странице нет, — например, количества товаров в корзине *на сервере*? Для этого есть [[expect-poll|expect.poll]]: он вызывает вашу функцию снова и снова, пока результат не совпадёт с ожидаемым или не истечёт таймаут.

```ts tests/cart-api.spec.ts
await expect
  .poll(async () => {
    const response = await page.request.get('/api/cart');
    return (await response.json()).count;
  }, { message: 'количество товаров в корзине на сервере', timeout: 5_000 })
  .toBe(1);
```

`page.request` отправляет HTTP-запросы с cookies контекста страницы — сервер видит того же посетителя. Интервалы между попытками можно задать опцией `intervals` (например, `[100, 250, 500]`).

Родственник — `expect(async () => { … }).toPass()`: повторяет блок с обычными проверками внутри, пока он не пройдёт целиком. Удобен, когда нужно повторить несколько шагов вместе.

## Повторы прогона

Опция `retries` в конфигурации перезапускает упавший тест. Если он прошёл со второй попытки, отчёт пометит его как **flaky** — [[flaky-test|нестабильный]]. Это полезно в CI: один сбой сети не блокирует сборку, а отчёт честно показывает проблему.

Но повтор ничего не исправляет:

- если тест нестабилен из-за гонки, он продолжит падать «иногда» — просто реже на виду;
- если дефект проявляется не всегда (гонка в приложении), повтор его **скроет**;
- время прогона растёт.

Флаки-тест — это задача: найти, *чего* тест не дождался, и заменить паузу или разовое чтение ожиданием состояния. Чтобы воспроизвести нестабильность, тест запускают много раз подряд: `npx playwright test tests/cart.spec.ts --repeat-each=20`.

:::mistake
**«Увеличу таймаут до минуты — и всё».** Если тест ждёт не то условие, длинный таймаут лишь замедлит падение. Если ждёт правильное, но приложение и правда отвечает 40 секунд, — это повод для вопроса разработчикам о производительности, а не для молчаливого `test.setTimeout(120_000)`. Каждый увеличенный таймаут в коде должен сопровождаться комментарием, почему он нужен.
:::

:::deep Как выбрать значения
Таймаут проверки должен покрывать нормальное время реакции приложения с запасом на загруженный CI, но не настолько большой, чтобы при дефекте тест «висел» долго. Таймаут теста — сумма шагов с запасом. Признак плохого таймаута: тесты падают по нему без дефекта (мал) или падение длится минуты (велик). Повторы в CI обычно ограничивают 1–2 попытками, а flaky-тесты отслеживают и чинят, иначе к ним привыкают и перестают читать отчёт.
:::

:::tech Чем expect.poll отличается от цикла с паузой
Самописный цикл `for (…) { if (ok) break; await page.waitForTimeout(500); }` делает то же, но без сообщения об ошибке, без учёта таймаута теста и с фиксированным шагом. `expect.poll` пишет в отчёт последнее полученное значение и ожидаемое, уважает `timeout` и `intervals`, а при падении показывает ваше `message`. По умолчанию его таймаут равен таймауту `expect`.
:::

:::interview
**Вопрос:** «Тест падает в CI один раз из десяти. Включим `retries: 3`?» **Ответ по сути:** retries можно включить, чтобы сборка не блокировалась, но тест останется помеченным flaky, и его надо разобрать: воспроизвести (`--repeat-each`), посмотреть trace упавшей попытки, найти, какое состояние не дождались (разовое чтение, пауза, ожидание события после действия), и заменить на ожидающую проверку. Повтор не устраняет причину и может скрыть настоящий дефект.
:::
