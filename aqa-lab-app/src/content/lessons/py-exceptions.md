:::why
Ошибки в тестовом коде неизбежны: файл не найден, в ответе нет поля, строка не превращается в число. Плохо не то, что ошибка возникла, а то, что её спрятали: тест продолжил работу с «нулём по умолчанию» и прошёл, хотя проверял мусор. Этот урок — о том, как обработать ошибку и не потерять её.
:::

## Что такое исключение

Когда Python не может выполнить операцию, он создаёт [[exception|исключение]] — объект с типом и сообщением — и прерывает выполнение. Если его никто не перехватил, программа (или тест) останавливается и печатает traceback:

```text
Traceback (most recent call last):
  File "main.py", line 3, in <module>
    qty = int("два")
ValueError: invalid literal for int() with base 10: 'два'
```

Читать traceback нужно снизу вверх: последняя строка — тип и сообщение, выше — где это случилось. Частые типы:

| Исключение | Когда |
|---|---|
| `ValueError` | значение неподходящее: `int("abc")` |
| `TypeError` | тип неподходящий: `390 + "1"` |
| `KeyError` | нет ключа в словаре: `order["promo"]` |
| `IndexError` | нет индекса в списке: `items[10]` |
| `AttributeError` | нет атрибута: `None.strip()` |
| `FileNotFoundError` | нет файла |
| `AssertionError` | не прошёл `assert` — так падают тесты |

## try / except

Перехват выглядит так:

```py tests/parse.py
def parse_qty(raw):
    try:
        qty = int(raw)
    except ValueError:
        raise ValueError(f"некорректное количество: {raw!r}") from None
    if qty <= 0:
        raise ValueError(f"количество должно быть больше нуля: {raw!r}")
    return qty
```

- В `try` — код, который может упасть.
- `except ValueError:` ловит **только** этот тип. Остальные ошибки пройдут дальше, как и должны.
- `raise` создаёт исключение. Здесь мы заменяем техническое сообщение понятным и добавляем исходное значение (`{raw!r}` выводит его в кавычках, видно даже пробелы).

Есть ещё `else` (выполняется, если исключения не было) и `finally` (выполняется всегда — для освобождения ресурсов).

## Обработать или пробросить

Главный вопрос: **знает ли этот код, что делать с ошибкой?**

- `parse_qty` не знает, что делать с плохой строкой, — она сообщает об ошибке через `raise`.
- Функция импорта, которая разбирает тысячу строк и должна вернуть список плохих, — знает: она ловит `ValueError` для каждой строки и складывает в отчёт.
- Тест, как правило, не ловит исключения вообще: если что-то упало — тест должен упасть и показать причину.

:::mistake Голый except
```py tests/bad.py
try:
    qty = int(raw)
except:          # ловит всё, включая опечатки в коде
    qty = 0      # и прячет проблему
```
Такой код превращает любую ошибку в правдоподобное значение. Тест продолжит работу с `qty = 0`, и падение — если случится — будет далеко от причины. Ловите конкретный тип и не возвращайте «заглушку», если не уверены, что она правильная.
:::

## Исключения в тестах pytest

В pytest ожидаемое исключение проверяют контекстным менеджером `pytest.raises`. Тест падает, если исключения **не было**:

```py tests/test_parse.py
import pytest
from parse import parse_qty


def test_rejects_zero():
    with pytest.raises(ValueError, match="больше нуля"):
        parse_qty("0")
```

`match` — регулярное выражение, которому должно соответствовать сообщение. Это негативный тест: он проверяет, что некорректный ввод отвергается, а не принимается молча.

:::deep Цепочки исключений
Если внутри `except` выбросить новое исключение, Python покажет оба: «During handling of the above exception, another exception occurred». `raise NewError(...) from err` явно связывает их («The above exception was the direct cause…») — полезно, когда исходная причина важна для отладки. `from None` скрывает исходное исключение, когда новое сообщение полностью его заменяет.
:::

:::tech Свои исключения
Для доменных ошибок создают свои классы: `class ApiError(Exception): pass`, иногда с полями (`status_code`, `body`). Тогда вызывающий код ловит именно `ApiError`, а не любую ошибку. Иерархия важна: `except Exception` ловит почти всё, кроме `KeyboardInterrupt` и `SystemExit`, поэтому подходит только для верхнего уровня — записать в лог и пробросить дальше.
:::

:::interview
**Вопрос:** «Когда в тестовом коде уместен try/except?» **Ответ по сути:** когда код знает, как обработать конкретную ошибку: повторить запрос при временной сетевой ошибке, собрать отчёт о плохих строках, освободить ресурс в `finally`. Сам тест обычно исключения не ловит — падение должно быть видно. Для проверки ожидаемой ошибки — `pytest.raises`. Голый `except:` прячет дефекты.
:::
