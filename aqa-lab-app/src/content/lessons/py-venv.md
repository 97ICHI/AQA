:::why
У вас тесты проходят, а у коллеги и в CI — падают с `ModuleNotFoundError` или ведут себя иначе. Почти всегда причина в окружении: другие версии пакетов, пакет поставлен «глобально» только на вашей машине. Виртуальное окружение и файл зависимостей делают набор пакетов проекта явным и воспроизводимым.
:::

:::note Этот урок — про ваш компьютер
Команды ниже выполняются в терминале на вашей машине. Тренажёр в браузере уже содержит Python 3.14 и pytest и не устанавливает пакеты, поэтому здесь команды показаны как пример, а практическое задание — на разбор файла зависимостей.
:::

## Проблема общего Python

Если ставить пакеты в системный Python, все проекты делят одно пространство: проекту A нужен `pytest 8`, проекту B — `pytest 9`, и одновременно оба не установить. Кроме того, невозможно понять, какие пакеты действительно нужны проекту, а какие остались от экспериментов.

[[virtualenv|Виртуальное окружение]] (venv) — отдельная папка внутри проекта со своим интерпретатором и своими пакетами. Пакеты, поставленные в неё, видит только этот проект.

## Создать и активировать

```bash terminal
cd shop-tests
python -m venv .venv               # создать окружение в папке .venv

source .venv/bin/activate          # macOS / Linux
.venv\Scripts\activate             # Windows (PowerShell или cmd)

python --version                   # теперь это Python из .venv
which python                       # …/shop-tests/.venv/bin/python
deactivate                         # выйти из окружения
```

Активация лишь меняет `PATH` в текущем терминале, чтобы команды `python` и `pip` брались из `.venv`. Без активации можно вызывать интерпретатор напрямую: `.venv/bin/python -m pytest`.

Папку `.venv` не добавляют в git — её заносят в `.gitignore`. Окружение каждый создаёт у себя, а в репозитории хранится только список зависимостей.

## pip и requirements.txt

[[pip]] устанавливает пакеты из каталога PyPI в активное окружение:

```bash terminal
python -m pip install pytest requests       # установить
python -m pip list                          # что установлено
python -m pip freeze > requirements.txt     # зафиксировать точные версии
python -m pip install -r requirements.txt   # воспроизвести окружение
```

`python -m pip` вместо просто `pip` гарантирует, что пакет поставится именно для того Python, который вы запускаете.

[[requirements-txt|requirements.txt]] — обычный текстовый файл:

```text requirements.txt
pytest==9.1.1
requests==2.32.5
jsonschema>=4.23    # без точной версии — может поставиться любая новее
```

`==` закрепляет точную версию. `>=` или имя без версии означает «любая подходящая» — сегодня это одна версия, через месяц другая, и тесты, проходившие вчера, падают без единого изменения в коде. Для воспроизводимости в CI используют точные версии, а обновляют их осознанно, отдельным изменением.

## Как это выглядит в CI

```yaml .github/workflows/tests.yml
- uses: actions/setup-python@v5
  with:
    python-version: "3.14"
- run: python -m venv .venv
- run: .venv/bin/python -m pip install -r requirements.txt
- run: .venv/bin/python -m pytest -q
```

CI каждый раз создаёт окружение с нуля по `requirements.txt` — то есть проверяет, что файл зависимостей полный. Если пакет поставлен у вас вручную и забыт в файле, CI это обнаружит.

:::deep Альтернативы
`pip` + `requirements.txt` — минимальный стандарт. Современные проекты часто используют `pyproject.toml` для описания зависимостей и инструменты вроде `uv` или `poetry`, которые создают окружение и lock-файл (точные версии всех пакетов, включая транзитивные) одной командой. Принцип тот же: окружение отдельно для проекта, версии зафиксированы, файл зависимостей — в git.
:::

:::tech Транзитивные зависимости
`requests` сам зависит от `urllib3`, `idna`, `certifi`, `charset-normalizer`. Если в `requirements.txt` закреплён только `requests==2.32.5`, его зависимости всё равно могут обновиться. `pip freeze` записывает всё установленное, включая транзитивные пакеты, — так окружение воспроизводится полностью. Минус — файл длиннее и его труднее читать; поэтому иногда держат два файла: короткий «что нужно» и полный lock.
:::

:::interview
**Вопрос:** «Зачем нужен venv и как воспроизвести окружение тестов в CI?» **Ответ по сути:** venv изолирует пакеты проекта от системы и других проектов. Зависимости с точными версиями фиксируются в `requirements.txt` (или lock-файле), `.venv` в git не кладётся. CI создаёт окружение с нуля: `python -m venv .venv`, `pip install -r requirements.txt`, `pytest`.
:::
