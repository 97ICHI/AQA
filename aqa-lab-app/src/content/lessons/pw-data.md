:::why
Тест, который проходит только после другого теста, однажды упадёт: при запуске по одному, в другом порядке, при повторе или параллельно. Искать такую ошибку долго, потому что сам тест «правильный». В этом уроке вы научитесь делать тесты независимыми: каждый сам готовит свои данные и не мешает другим.
:::

## Что значит «независимый тест»

[[test-isolation|Изоляция тестов]] — это свойство набора тестов: любой тест можно запустить отдельно, в любом порядке, параллельно с другими и повторно, и результат будет тем же. Нарушают изоляцию две вещи:

- **зависимость от порядка** ([[order-dependency|order dependency]]) — тест рассчитывает, что предыдущий тест что-то оставил;
- **общие данные** ([[shared-state|shared state]]) — несколько тестов меняют одну и ту же запись: один аккаунт, одну корзину, один заказ.

## Тест, который рассчитывает на соседа

```ts tests/cart.spec.ts
test('добавить два блокнота', async ({ page }) => {
  // … два клика «В корзину» …
});

test('итог корзины — 780 ₽', async ({ page }) => {
  // рассчитывает, что корзину заполнил предыдущий тест
  await page.goto('/cart');
  await expect(page.getByTestId('cart-total')).toHaveText('780 ₽');
});
```

Автор второго теста рассуждал так: «первый тест уже положил два блокнота, мне остаётся проверить сумму». Запустим.

## Каждый тест готовит свои данные

Правильно — подготовить нужное состояние внутри теста или в его fixture. Через интерфейс это медленно, через API — быстро:

```ts tests/cart.spec.ts
test('итог корзины — 780 ₽', async ({ page }) => {
  await page.request.post('/api/cart', { data: { productId: 3, qty: 2 } });
  await page.goto('/cart');
  await expect(page.getByTestId('cart-total')).toHaveText('780 ₽');
});
```

`page.request` отправляет HTTP-запрос с cookies этой страницы, поэтому товар попадает в корзину той же сессии. Через интерфейс проверяется то, ради чего тест написан (страница корзины и сумма), а подготовка — короткий вызов API.

## Уникальные данные

Когда тест **создаёт** что-то на общем стенде — пользователя, заказ, промокод, — фиксированные значения приводят к конфликтам. Второй запуск упадёт на «такой email уже есть», а параллельный тест изменит «вашу» запись. Решение — уникальная часть в каждом значении:

```ts tests/data.ts
import { test } from '@playwright/test';

export function uniqueEmail(prefix = 'buyer') {
  const info = test.info();
  return `${prefix}-${Date.now()}-w${info.workerIndex}-r${info.retry}@example.test`;
}
```

`test.info()` возвращает сведения о текущем тесте: `workerIndex` — номер worker, `retry` — номер попытки. Метка времени плюс номер worker делают значение уникальным даже при параллельном запуске. По такому значению легко найти «свои» данные в базе и убрать их.

:::warn Учебный магазин
В учебном магазине нет регистрации: пользователи заданы заранее, а каждый запуск начинается с чистой базы. Уникальные данные понадобятся на настоящем стенде, где база живёт дольше одного прогона.
:::

## Уборка после теста

Данные, созданные тестом, нужно удалять — [[test-data-cleanup|очистка тестовых данных]]. Надёжное место — teardown fixture, который выполняется и после падения:

```ts tests/fixtures.ts
export const test = base.extend<{ order: { id: number } }>({
  order: async ({ request }, use) => {
    const res = await request.post('/api/orders');   // создаём
    const order = await res.json();
    await use(order);                                 // тест работает с заказом
    await request.delete(`/api/orders/${order.id}`);  // убираем, даже если тест упал
  },
});
```

`DELETE /api/orders/:id` — пример для настоящего API. В учебном магазине такого маршрута нет, ему уборка не нужна: база живёт только один прогон.

:::mistake «Почищу в начале»
Удалять «всё старое» перед тестом опасно: при параллельном запуске вы удалите данные соседнего теста, который выполняется прямо сейчас. Убирайте только то, что создали сами, — по уникальному значению.
:::

:::deep Почему describe.serial — не решение
`test.describe.serial` запускает тесты группы строго по порядку, и после первого падения остальные пропускаются. Это делает зависимость явной, но не устраняет её: группу нельзя распараллелить, отдельный тест нельзя перезапустить. Если нужен длинный сценарий «вход → корзина → заказ», пишут **один** тест с шагами `test.step`, а не цепочку зависимых тестов.
:::

:::tech Как проверить независимость
Запустите тесты в разных режимах и сравните результат: один тест по строке (`npx playwright test tests/cart.spec.ts:12`), несколько повторов (`--repeat-each=3`), параллельно (`--workers=4 --fully-parallel`). Тест, который проходит в одном режиме и падает в другом, зависит от чужих данных или от порядка. Подробнее о стратегиях работы с данными — [[test-data-management|управление тестовыми данными]].
:::

:::interview
**Вопрос:** «Второй тест использует заказ, созданный первым. Что не так?» **Ответ по сути:** зависимость от порядка. Второй тест нельзя запустить отдельно, повторить или выполнить параллельно, а падение первого роняет второй. Каждый тест должен сам создавать свой заказ (быстро — через API, в fixture) и убирать его в teardown; длинный сценарий оформляют одним тестом с `test.step`.
:::
