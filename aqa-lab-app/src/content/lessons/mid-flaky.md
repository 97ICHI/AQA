:::why
Нестабильный тест хуже отсутствующего: он приучает команду перезапускать красные прогоны и не верить отчёту. Middle-инженер должен уметь не просто «добавить ретрай», а найти причину по артефактам, воспроизвести её и исправить так, чтобы тест стал стабильным на любой машине.
:::

## Что такое нестабильный тест

[[flaky-test|Нестабильный (flaky) тест]] при неизменном коде продукта, теста и окружения то проходит, то падает. Цена выше, чем кажется. Если доля ложных падений одного теста p, то вероятность зелёного прогона из N тестов — (1 − p)^N. При p = 0,5 % и 300 тестах это 0,995^300 ≈ 0,22: почти четыре прогона из пяти будут красными без единого дефекта.

Основные причины:

| Причина | Как проявляется |
|---|---|
| Гонка в тесте: проверка до обновления страницы | старое значение, «клик не сработал» |
| Ожидание временем (`waitForTimeout`), однократное чтение | падает на медленном агенте CI |
| Зависимость от порядка и общих данных | падает при параллельном запуске или отдельно |
| Время и дата | падает в полночь, в конце месяца, в другом часовом поясе |
| Окружение и внешние сервисы | много тестов падают сразу с 502/503/таймаутом |
| Дефект продукта (настоящая гонка) | воспроизводится и вручную при быстрых действиях |

Последняя строка важна: часть «флаков» — реальные дефекты, которые пользователи тоже встречают. Списывать всё на тест нельзя.

## Расследование по шагам

1. **Собрать артефакты** упавших попыток: trace, скриншот, лог, сообщение об ошибке. Без них расследование превращается в гадание.
2. **Сравнить** trace упавшей и успешной попытки: на каком шаге состояние страницы или ответы сети разошлись.
3. **Сформулировать гипотезу:** «проверка выполняется до ответа `/api/cart`», «кнопка ещё неактивна».
4. **Воспроизвести** — сделать условие постоянным, чтобы тест падал стабильно.
5. **Исправить причину**, а не симптом.
6. **Проверить** исправление в тех же условиях, что воспроизводили падение.

Инструменты воспроизведения:

```bash
npx playwright test tests/cart.spec.ts --repeat-each=30 --retries=0        # много повторов без маскировки
npx playwright test tests/cart.spec.ts --repeat-each=10 --workers=4        # параллельное давление
npx playwright test --project=chromium --grep @cart --retries=0
```

[[repeat-each|`--repeat-each`]] запускает каждый тест N раз; `--retries=0` гарантирует, что падение не спрячется за повтором. Медленную сеть или сервер имитируют задержкой через `page.route`, медленный интерфейс — вариантом стенда.

## Разбор на учебном магазине

Тест ниже писали на быстром ноутбуке, и там он всегда проходит. Запустите его на «медленном магазине», где кнопки становятся активными через 1,5 с, — так ведёт себя загруженный стенд.


:::happened
Тест не нажал кнопку: через 300 мс она ещё неактивна, `isEnabled()` вернул `false`, и условие пропустило клик. Затем `textContent()` один раз прочитал `0`. Ни один шаг не упал с ошибкой — тест «прошёл» до последней строки и сообщил о несуществующем дефекте. Это типичная картина гонки: сообщение говорит о результате, а причина на два шага раньше. В trace такой прогон видно сразу — на шаге клика нет действия.
:::

Исправление — убрать все предположения о времени. `click()` сам ждёт, пока кнопка станет видимой и активной ([[actionability|actionability]]), а [[web-first-assertion|веб-первая проверка]] `toHaveText` повторяет чтение до таймаута:

```ts tests/cart.spec.ts
await card.getByRole('button', { name: 'В корзину' }).click();
await expect(page.getByTestId('cart-count')).toHaveText('1');
```

## Карантин и метрика

Пока причина не найдена, тест не должен блокировать команду, но и пропадать не должен. [[test-quarantine|Карантин]] — временный перенос в неблокирующий набор с задачей, владельцем и сроком:

```ts tests/export.spec.ts
test('экспорт заказов', { tag: '@quarantine', annotation: { type: 'issue', description: 'QA-512: гонка при генерации файла' } }, async ({ page }) => {
  // ...
});
```

```bash
npx playwright test --grep-invert @quarantine   # блокирующий набор
npx playwright test --grep @quarantine          # отдельная задача: видно, исправился ли тест
```

Чтобы карантин не превратился в кладбище, нестабильность измеряют. [[flaky-rate|Доля нестабильности]] — доля прогонов теста, в которых результат менялся без изменения кода.

:::deep Почему ретраи — не решение
`retries: 2` в CI делает прогон зелёным, если тест прошёл хотя бы раз из трёх. Это полезно как временная мера и как источник данных (Playwright помечает такие тесты как `flaky`), но опасно как политика: настоящая гонка в продукте, проявляющаяся в 30 % случаев, будет проходить почти всегда. Разумный компромисс: ретраи в CI включены, `flaky` попадает в отчёт и метрику, порог нестабильности — часть quality gate, а для критичного набора — `failOnFlakyTests`.
:::

:::tech Trace для нестабильных тестов
`trace: 'on-first-retry'` записывает trace только при первом повторе — дёшево и как раз для флаков. `retain-on-failure` сохраняет trace любой упавшей попытки. В trace сравнивайте вкладки Actions (был ли клик и в каком состоянии элемент), Network (успел ли ответ) и Console. Для гонок с данными полезно приложить `correlation id` запросов и найти их в логах сервера.
:::

:::interview
**Вопрос:** «Как вы работаете с flaky-тестами?» **Ответ по сути:** собираю артефакты падений, сравниваю trace упавшей и успешной попытки, формулирую гипотезу и воспроизвожу её (`--repeat-each`, задержка ответа, параллельный запуск). Исправляю причину — ожидание состояния вместо паузы, изоляцию данных, контроль времени. Пока причина не найдена — карантин с задачей и сроком. Слежу за flaky rate; ретраи — временная мера, а не решение.
:::
