:::why
На собеседовании проверяют не память на термины, а то, как вы рассуждаете в рабочей ситуации. Большинство вопросов к AQA Middle сводятся к десятку сценариев. Если для каждого есть короткий структурированный ответ с примером из своей практики, интервью превращается в разговор коллег.
:::

## Как отвечать на сценарий

Хороший ответ укладывается в 30–60 секунд и строится по схеме, похожей на [[star-method|STAR]]:

1. **Ситуация** — одна фраза контекста: «в проекте магазина ночная регрессия падала через раз».
2. **Действия** — что сделали вы, по шагам и с инструментами: «собрал trace, сравнил попытки, воспроизвёл через `--repeat-each`».
3. **Результат** — измеримо: «доля нестабильных прогонов упала с 30 % до 2 %».
4. **Вывод** — что вы делаете теперь иначе.

Чего избегать: общих слов без примера («я всегда пишу качественные тесты»), перечисления инструментов без объяснения выбора, ответа «никогда так не делаю» на вопрос о компромиссе. Если чего-то не знаете — скажите, как бы выясняли: это тоже ответ.

Ниже десять сценариев. Сначала ответьте вслух сами, засеките время, потом откройте образец. Под каждым — урок, где тема разобрана подробно.

## Десять сценариев

:::interview 1. Тест упал в CI, а локально проходит
Сначала артефакты прогона: trace, скриншот, лог, сообщение. Затем сравниваю окружения — версии Node.js и браузера, переменные, данные стенда, ресурсы агента, параллельность. Проверяю доступность сервиса. Исключив окружение и тест, воспроизвожу падение в условиях CI (тот же образ Docker, `--workers` как в CI) и только тогда завожу дефект. Уроки: [окружение](#/l/proj-env), [отчёты](#/l/proj-reports).
:::

:::interview 2. Тест нестабилен: падает раз в десять прогонов
Не добавляю ретрай как решение. Собираю trace упавшей и успешной попыток, ищу шаг, где они расходятся; формулирую гипотезу и делаю её воспроизводимой (`--repeat-each=30 --retries=0`, задержка ответа, медленный стенд). Исправляю причину: ожидание состояния вместо паузы, изоляцию данных. Пока ищу — карантин с задачей и сроком; слежу за flaky rate. Урок: [расследование нестабильного теста](#/l/mid-flaky).
:::

:::interview 3. Тесты проходят по одному и падают параллельно
Почти всегда общее состояние: один аккаунт, общая запись, неубранные данные, зависимость от порядка. Воспроизвожу через `--workers=4 --repeat-each=5` и запуск отдельно, по trace нахожу общий ресурс. Лечу изоляцией: уникальные данные на тест или аккаунт на worker, подготовка и очистка в фикстурах. `workers: 1` — маскировка, а не исправление. Урок: [общие данные и параллельные тесты](#/l/mid-isolation).
:::

:::interview 4. Регрессия идёт слишком долго
Сначала измеряю: самые медленные тесты, этапы CI, что внутри теста занимает время. Затем — подготовка через API вместо UI, вход через storageState, удаление пауз, перенос проверок правил на API-уровень, шардирование при изолированных данных, кэш зависимостей. Проверки не удаляю и таймауты вслепую не уменьшаю; после изменений убеждаюсь, что набор ловит те же дефекты. Урок: [ускорение без потери проверок](#/l/mid-speed).
:::

:::interview 5. Как устроен ваш тестовый проект
Тесты описывают сценарий и проверки; фикстуры готовят и чистят состояние; Page Object и компоненты скрывают локаторы; API-клиенты отвечают за запросы и коды ответа; данные — через фабрики; адреса и секреты — из переменных окружения. Проверка бизнес-результата — только в тесте. Изменение вёрстки или API правится в одном месте. Урок: [структура тестового проекта](#/l/proj-structure).
:::

:::interview 6. Как тесты встроены в CI
На каждый merge request — lint, типы, smoke и API-набор; полная регрессия — по расписанию. Окружение — Docker Compose с healthcheck, код возврата берётся из сервиса тестов и не подавляется; отчёт и trace загружаются всегда (`if: always()`). Quality gate: нет упавших, есть выполненные тесты, flaky не выше порога, merge закрыт без зелёного pipeline. Уроки: [Docker](#/l/proj-docker), [CI/CD](#/l/proj-ci).
:::

:::interview 7. API поменял формат ответа, и сломался фронтенд
Ответ API в тестах считаю `unknown` и проверяю форму во время выполнения: коды, обязательные поля, типы. Проверяю «терпимо» — используемые поля, без запрета новых, чтобы совместимые изменения не ломали тесты. Несовместимые изменения (удаление поля, смена типа) ловятся контрактной проверкой в pipeline провайдера; для нескольких потребителей — consumer-driven contracts. Урок: [схемы и контракты API](#/l/mid-contracts).
:::

:::interview 8. Вы первый AQA на проекте
Разберусь в рисках: критичные сценарии, история дефектов, архитектура, процесс релизов. Подниму каркас с CI и отчётами и один smoke-тест критичного пути, затем API-тесты критичных функций, затем немного UI-тестов с подготовкой через API. Оцениваю результат по найденным дефектам, стабильности и времени обратной связи, а не по числу тестов. Урок: [стратегия автоматизации](#/l/mid-design).
:::

:::interview 9. Как вы понимаете, что тест упал из-за дефекта, а не из-за теста
Порядок: окружение → тест → продукт. Окружение — сервис доступен, адрес и данные верные. Тест — ожидание соответствует требованию, локатор находит нужный элемент, нет гонки. Продукт — расхождение воспроизводится, в том числе вручную или через API, есть шаги и данные. Только после этого — баг-репорт с trace, запросом и ожидаемым/фактическим результатом. Урок: [окружение: терминал, сеть, DevTools](#/l/proj-env).
:::

:::interview 10. Расскажите о сложной проблеме, которую вы решили
Выберите реальную историю и расскажите по STAR. Пример: «Тест заказа падал раз в 20 прогонов. В trace упавшей попытки запрос `GET /api/orders/:id` возвращал 403. Гипотеза — заказ записывается не тому пользователю при параллельных запросах. Воспроизвёл через API двумя сессиями одновременно, приложил запросы и correlation id. Оказался дефект в продукте; после исправления добавил API-тест на доступ к своему и чужому заказу». Урок: [итоговая работа](#/l/iv-final).
:::

## Live coding

Часть интервью — небольшая задача на код за 10–15 минут. Оценивают не только результат, но и процесс: уточняющие вопросы («какой разделитель тысяч?», «что вернуть при ошибке?»), граничные случаи, проверку своего кода. Проговаривайте мысли вслух.

:::try Задача с интервью
Сообщение «Заказ №105 оформлен на сумму 780 ₽» показывает учебный магазин после оформления заказа. Разберите его на номер и сумму — пригодится в итоговой работе.
:::

```widget
{"type":"exercise","id":"m11-parse-status"}
```

:::happened
Регулярное выражение сразу проверяет формат и извлекает данные, поэтому для чужой строки функция возвращает `null`, а не объект с `NaN`. На интервью после такого решения обычно спрашивают: «как это протестировать?» — назовите граничные случаи из проверки: неразрывный пробел, дробная часть, сообщение об ошибке, пустая строка.
:::

:::deep Вопросы, которые стоит задать работодателю
Интервью двустороннее. Полезно спросить: сколько тестов и как часто они нестабильны; кто чинит упавшие тесты и сколько времени на это есть; запускаются ли тесты на каждый merge request; есть ли тестовый стенд и способ создавать данные; кто решает, что автоматизировать. Ответы многое говорят о том, будет ли у вас возможность делать работу хорошо.
:::
