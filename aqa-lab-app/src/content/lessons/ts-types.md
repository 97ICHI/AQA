:::why
До сих пор TypeScript в основном сам догадывался о типах. Но когда данные описаны явно — «товар — это id, название, цена и остаток» — компилятор ловит опечатки в полях, лишние и пропущенные свойства, строку вместо числа. В тестах это значит: ошибка в тестовых данных видна в редакторе, а не через минуту прогона.
:::

## Вывод типов и аннотации

TypeScript многое понимает сам. Это называется *выводом типов*:

```ts tests/data/catalog.ts
const price = 390;              // тип выведен: number
const titles = ['Блокнот A5'];  // string[] — массив строк
```

[[type-annotation|Аннотация]] нужна там, где выводить не из чего — прежде всего в **параметрах функций** — и там, где вы хотите зафиксировать договорённость:

```ts tests/helpers/money.ts
function lineTotal(price: number, qty: number): number {
  return price * qty;
}
```

Основные записи типов: `string`, `number`, `boolean`, массив — `number[]` (или `Array<number>`), функция «принимает число, возвращает строку» — `(n: number) => string`.

## Описать форму объекта: type и interface

Чтобы не повторять `{ id: number; title: string; price: number }` в каждой функции, форме объекта дают имя. Есть два способа:

```ts tests/types/shop.ts
// псевдоним типа
export type Product = {
  id: number;
  title: string;
  price: number;
  stock: number;
};

// интерфейс — то же самое для объектов
export interface CartLine {
  product: Product;
  qty: number;
}
```

[[type-alias|type]] даёт имя любому типу, [[interface-ts|interface]] описывает только объекты. Для формы объекта они почти взаимозаменяемы; в одном проекте лучше придерживаться одного стиля. Имена типов принято писать с заглавной буквы.

Теперь тип можно использовать везде:

```ts tests/helpers/cart.ts
import type { Product, CartLine } from '../types/shop';

export function cartTotal(lines: CartLine[]): number {
  return lines.reduce((sum, l) => sum + l.product.price * l.qty, 0);
}

const notebook: Product = { id: 1, title: 'Блокнот A5', price: 390, stock: 12 };
```

## Что проверяет компилятор

С описанным типом TypeScript сообщает об ошибке, если:

- не хватает поля: `{ id: 1, title: 'Ручка', price: 120 }` — нет `stock`;
- тип поля не тот: `price: '120'`;
- лишнее или опечатанное поле в объекте-литерале: `prise: 120`;
- обращение к несуществующему полю: `notebook.cost`;
- вызов функции с неверными аргументами: `cartTotal(notebook)` вместо массива.

Всё это — [[type-error|ошибки типа]], найденные до запуска. Для тестов, где данных много и они кочуют между файлами, это главная польза TypeScript.

:::mistake Тип any «чтобы не ругалось»
`any` отключает проверку: с ним можно присвоить что угодно и обратиться к любому полю. Одна переменная `any` может незаметно «заразить» всё, что из неё получено. Если тип неизвестен, честнее `unknown` — о нём через урок.
:::

:::deep Структурная типизация
TypeScript сравнивает типы по форме, а не по имени. Объект подходит под `Product`, если у него есть все нужные поля нужных типов, — неважно, как он был создан. Лишние поля запрещены только в объекте, записанном прямо на месте (литерале); объект из переменной с лишними полями пройдёт. Это удобно для тестовых данных: ответ API с дополнительными полями совместим с узким типом.
:::

:::tech type или interface
Интерфейсы можно расширять (`interface Admin extends User`) и дополнять повторным объявлением с тем же именем. `type` умеет больше: объединения (`'new' | 'paid'`), пересечения (`A & B`), типы функций и кортежи. Практическое правило: `interface` для форм объектов, `type` — для всего остального; главное — единообразие в проекте.
:::

:::interview
**Вопрос:** «Чем `type` отличается от `interface`?» **Ответ по сути:** оба описывают форму объекта; `interface` расширяется через `extends` и может дополняться повторным объявлением, `type` может описывать объединения, пересечения и любые другие типы. Проверяются они одинаково — по структуре.
:::
