:::why
Страница никогда не готова «сразу»: кнопка появляется после загрузки скрипта, становится активной после ответа сервера, сдвигается из-за анимации. Playwright многое из этого ждёт сам — поэтому в хорошем тесте почти нет ручных пауз. Но важно точно знать, *чего* он ждёт, а чего нет: иначе тест будет проходить у вас и падать в CI.
:::

## Что проверяется перед действием

Перед каждым действием Playwright находит элемент по локатору и проверяет, готов ли он. Эти условия называются [[actionability|проверками готовности]]:

| Условие | Что значит | Какие действия ждут |
|---|---|---|
| **Visible** — видим | есть размер, нет `visibility: hidden` | click, check, fill, hover… |
| **Stable** — стабилен | не двигается (анимация закончилась) | click, check, hover, dragTo |
| **Receives events** — получает события | не перекрыт другим элементом в точке клика | click, check, hover |
| **Enabled** — доступен | нет `disabled` | click, check, fill, selectOption |
| **Editable** — редактируем | доступен и не `readonly` | fill, clear |

Если условие не выполнено, Playwright не падает сразу: он повторяет проверку, пока элемент не станет готов или не истечёт таймаут действия. Это и есть [[auto-waiting|автоматическое ожидание]]. Перед ним элемент ещё нужно найти: если локатор пока ничего не находит, действие ждёт появления элемента.

## Медленный магазин

В варианте магазина «медленный» кнопки «В корзину» первые 1,5 секунды неактивны (`disabled`). Для пользователя это небольшая задержка, а для теста — проверка, правильно ли он ждёт.

```ts tests/slow.spec.ts
const add = card.getByRole('button', { name: 'В корзину' });
await add.click();   // ждёт, пока кнопка станет enabled, затем кликает
await expect(page.getByTestId('cart-count')).toHaveText('1');
```

Здесь ничего не нужно добавлять: `click` сам дождётся, пока кнопка станет доступной.

Ниже тест, написанный так, будто автоматического ожидания нет: он сам проверяет `isEnabled()`, делает паузу и читает счётчик. Запуск — на медленном магазине.
:::

:::happened
`isEnabled()` — это **разовый** вопрос «доступна ли кнопка прямо сейчас?». Он не ждёт. В медленном магазине ответ — «нет», клик пропускается, через 500 мс счётчик равен `0`, и тест падает. На исправном магазине этот же тест проходит — поэтому такие ошибки обнаруживаются только на медленном стенде или в CI. Если просто вызвать `click()`, Playwright сам подождёт доступности кнопки.
:::

## Чего автоожидание НЕ гарантирует

Это главная часть урока. `click()` завершается, когда клик **выполнен**, а не когда приложение закончило на него реагировать.

После клика по «В корзину» страница отправляет запрос на сервер и только по ответу обновляет счётчик. Действие этого не ждёт. Поэтому:

- после действия нужна [[web-first-assertion|ожидающая проверка]] результата (`toHaveText`, `toBeVisible`), а не разовое чтение;
- второе действие, зависящее от первого, начинайте после проверки, что первое завершилось.

```ts
await add.click();
await expect(page.getByTestId('cart-count')).toHaveText('1');  // ← синхронизация
await add.click();
await expect(page.getByTestId('cart-count')).toHaveText('2');
```

Ещё два случая, которые автоожидание не покрывает:

- **Методы-вопросы** `isVisible()`, `isEnabled()`, `isChecked()`, `textContent()`, `count()` отвечают про текущий момент и не ждут. Для проверок используйте `expect(локатор).toBeVisible()`, `toBeEnabled()`, `toHaveText()`, `toHaveCount()`.
- **Готовность данных.** Кнопка может быть доступна, пока список товаров ещё грузится. Действие кликнет по тому, что есть. Если важно дождаться данных — проверьте их появление явно.

:::mistake
**`waitForTimeout` «на всякий случай».** Пауза в 500 мс слишком коротка для медленного стенда и слишком длинна для быстрого: тест одновременно нестабилен и медлен. Документация Playwright предупреждает: тесты, которые ждут фиксированное время, нестабильны по своей природе; `waitForTimeout` годится для отладки. Вместо паузы — ожидание конкретного состояния: проверка `expect`, ожидание ответа сервера или URL.
:::

:::deep Почему проверяется «стабилен» и «получает события»
Если кликнуть по кнопке, которая ещё едет в анимации, курсор попадёт туда, где кнопка была мгновение назад, — в соседний элемент. Проверка stable ждёт, пока положение элемента не изменится в двух кадрах анимации подряд. Проверка receives events кликает только если в точке клика верхним оказывается сам элемент (или его потомок), а не, например, баннер cookie поверх него. Если элемент перекрыт, сообщение об ошибке говорит, *какой* элемент перехватывает клик — часто это реальный дефект вёрстки.
:::

:::tech Как ждёт сам Playwright
Действие выполняет цикл: найти элемент → проверить условия → выполнить. Если элемент пропал или перерисовался между шагами, цикл начинается заново — поэтому локаторы устойчивы к перерисовкам. Ограничивает цикл таймаут действия: `actionTimeout` в `use` конфигурации или опция `timeout` у конкретного действия; по умолчанию у действий отдельного предела нет, и их ограничивает таймаут теста. `locator.waitFor({ state })` ждёт состояния `attached`, `detached`, `visible` или `hidden` без действия — это редкий случай, обычно хватает `expect`.
:::

:::interview
**Вопрос:** «Если у Playwright есть auto-waiting, почему тесты всё равно бывают нестабильными?» **Ответ по сути:** автоожидание касается готовности элемента перед действием. Оно не ждёт, пока приложение обработает действие (запрос, перерисовка), и не действует на методы-вопросы вроде `isVisible()` или `textContent()`. Нестабильность появляется, когда после действия читают состояние один раз или ставят фиксированные паузы, а не ожидающие проверки.
:::
